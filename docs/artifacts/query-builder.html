Query Builder Визуальный конструктор дерева фильтров и грамматика, которую он пишет

Query Builder — это не плагин, а чистая UI-библиотека: у неё нет ни таблиц в базе, ни HTTP-маршрутов, ни слоя данных. Она делает ровно одно — превращает типизированную схему полей в экран, на котором редактор мышью собирает условие, и сериализует собранное в JSON-грамматику, которую на сервере разбирает parseFilterTree. Обратное преобразование — тоже её работа: ?filter= из адресной строки поднимается обратно в редактируемое дерево целиком, вместе с OR и вложенными группами.

01Бизнес-описание

Списки в CMS длинные. Реестр записей коллекции, журнал активности, список участников — всё это таблицы, в которых ответ на рабочий вопрос («какие статьи автора Иванова не обновлялись 90 дней и не имеют немецкого перевода?») лежит в трёх-четырёх пересечениях сразу. Поисковая строка отвечает на один вопрос из десяти; всё остальное упирается либо в «выгрузите мне CSV», либо в запрос к разработчику.

Какую задачу решает

  • Сложный вопрос без SQL. Пользователь набирает условие из готовых кубиков: поле, оператор, значение. Комбинация AND/OR и вложенные группы дают полноценную булеву логику, но ни одного символа синтаксиса вводить не нужно.
  • Один язык на весь продукт. Реестр записей, журнал, участники и правила алармов используют одну грамматику и один конструктор. Выучив фильтр в одном месте, редактор умеет фильтровать везде, а инженеру не приходится поддерживать второй язык запросов.
  • Фильтр как ссылка. Результат живёт в ?filter=. Отправив коллеге адрес, вы отправляете ему ровно тот срез, который видите сами — а не описание того, как его повторить.
  • Фильтр как правило. То же самое дерево, но сохранённое, становится правилом аларма («следи за записями, которые выглядят так») или сохранённым представлением. Правило аларма — это буквально дословно сохранённое дерево фильтра списка, вычисляемое тем же движком, поэтому у алармов нет собственного языка условий.
  • Невозможность собрать запрос, который сервер отвергнет. Список операторов сужается типом поля; значение проверяется по тем же правилам, что применяет серверная коррекция типов; кнопка «Применить» не срабатывает на недособранном правиле. Ошибка ловится в интерфейсе, а не приходит из API как «не удалось загрузить коллекцию».

Кому это видно

Редактор контента

Открывает панель под тулбаром реестра, набирает два-три условия, жмёт «Применить». Таблица под панелью пересобирается, условия оседают в виде удаляемых чипов. Из этого же состояния делается «Сохранить как аларм».

Администратор

Фильтрует журнал активности («кто и что делал с этой записью за последние сутки») и список участников («все отключённые контрибьюторы»). Обе страницы предлагают ту же панель с тем же поведением.

Инженер поддержки

Разворачивает блок «JSON preview», копирует полезную нагрузку и вставляет её в curl или в тикет. То, что показано в превью, — ровно то, что уйдёт на провод.

Ключевая идея

Пакет — управляемый компонент без слоя данных. Он ничего не запрашивает и никуда не ходит: схему полей и редактор значения для связи ему передают снаружи. Именно поэтому одну и ту же панель удалось повесить на четыре совершенно разных экрана, у каждого из которых свой источник полей — статический массив, ответ API или вклад плагина через слот.

Почему отрицания нет

И у локалей, и у аудиторий из списка операторов сознательно убрано is not. Отрицание в этих полях уходит внутрь подзапроса: hasLocale ne "de" означает «в группе переводов есть какая-то локаль, кроме немецкой» — чему удовлетворяет и полностью переведённая запись. Отсутствие выражается соседним полем missingLocale. То же с аудиториями: audienceAllowed ne "acme" читается как «не виден Acme», но означает не это.

03Грамматика дерева фильтров

Грамматика умышленно крошечная. В ней два вида узлов и больше ничего: группа и правило. Всё остальное — комбинации этих двух.

Узел-группа

Объект ровно с одним ключом — and либо or, — значение которого массив дочерних узлов. Дети могут быть и правилами, и другими группами, вперемешку и на любую разрешённую глубину.

{ "and": [ <узел>, <узел>, ... ] }
{ "or":  [ <узел>, <узел>, ... ] }

Сервер отвергает группу, где объявлены оба ключа сразу (FILTER_INVALID_NODE), и группу с пустым массивом (тоже FILTER_INVALID_NODE) — пустая группа не имеет смысла и, будучи переведённой в SQL, дала бы либо «ничего», либо «всё».

Узел-правило (лист)

Объект с тремя ключами: field, op, value.

{ "field": "author.name", "op": "ilike", "value": "%Иван%" }
КлючЧто этоПроверка на сервере
field Непустая строка. Может быть точечным путём по связям — author.company.name. Путь режется по точкам и проходится посегментно по FilterSchema: все сегменты кроме последнего должны быть объявленными связями, последний — объявленным полем FILTER_UNKNOWN_FIELD, FILTER_UNKNOWN_RELATION, FILTER_DEPTH_EXCEEDED, FILTER_EMPTY_PATH
op Непустая строка из словаря wire-операторов FILTER_UNKNOWN_OPERATOR — нет такого оператора вообще; FILTER_OPERATOR_NOT_ALLOWED — оператор есть, но тип колонки на него не отвечает
value Скаляр (строка/число/булево), массив для in/nin, булево для null, объект {n, unit} для within_last. Единственный объектный тип значения во всей грамматике — within_last FILTER_INVALID_VALUE, FILTER_EMPTY_IN_LIST, FILTER_MAX_IN_LIST_EXCEEDED
Почему value не приводится через String()

Сервер отвергает нескалярное значение вместо того, чтобы привести его к строке. Причина в том, что String(v) даёт правдоподобную строку, по которой потом идёт сравнение: null → "null", отсутствующий ключ → "undefined", {} → "[object Object]", [1,2] → "1,2". Каждый такой случай возвращал бы 200 с пустой выборкой, которую клиент прочитает как «совпадений нет», а не как «плохой запрос» — единственный молчаливый отказ в библиотеке, которая на всё остальное отвечает 400.

Корень

Корнем может быть и группа, и одиночное правило — сервер принимает оба. Клиент же всегда держит в состоянии группу: jsonFilterToTree, встретив в корне одиночное правило, оборачивает его в группу and. Пустой объект {}, отсутствующий и пустой параметр дают null — вызывающий просто не добавляет WHERE.

Примеры целиком

Плоское условие из двух правил

«Активные участники с почтой на @lilly» — то, что напишет ?filter= страницы участников:

{
  "and": [
    { "field": "status", "op": "eq",    "value": "active" },
    { "field": "email",  "op": "ilike", "value": "%@lilly%" }
  ]
}

OR внутри AND — вложенная группа

«Записи, автор которых Иванов или Петров, и при этом не обновлявшиеся с 1 января»:

{
  "and": [
    {
      "or": [
        { "field": "author.name", "op": "eq", "value": "Иванов" },
        { "field": "author.name", "op": "eq", "value": "Петров" }
      ]
    },
    { "field": "updatedAt", "op": "lt", "value": "2026-01-01T00:00:00.000Z" }
  ]
}

Внешняя группа — корень со своим переключателем AND/OR; внутренняя — то, что появляется по кнопке «Добавить группу» и рисуется пунктирной рамкой со своим переключателем и крестиком «Удалить группу».

Диапазон: одно правило в UI, три узла на проводе

Оператор between не имеет собственного wire-представления. Он раскрывается в маленькую группу and из gte и lte по тому же полю:

{
  "and": [
    { "field": "createdAt", "op": "gte", "value": "2026-01-01T00:00:00.000Z" },
    { "field": "createdAt", "op": "lte", "value": "2026-02-01T00:00:00.000Z" }
  ]
}
Обратное преобразование здесь с потерями

jsonFilterToTree сворачивает группу and ровно из двух правил gte+lte по одному полю обратно в одно правило between. Отличить это от честной группы, собранной вручную из двух правил, невозможно — сериализация у них побайтово одинаковая. Выбран вариант «between», как более частый и авторски-редакторский. Семантика при этом не теряется: WHERE получается идентичный, различается только то, какой редактор значения пользователь увидит после перезагрузки.

Относительное окно

Единственное объектное значение в грамматике. Хранится и вычисляется на стороне базы:

{ "field": "updatedAt", "op": "within_last", "value": { "n": 90, "unit": "days" } }

Единицы — только minutes, hours, days. В SQL это column >= now() - make_interval(days => 90): отсечка считается Postgres в момент выполнения запроса, а не в момент написания фильтра.

Пустота

Оператор null обслуживает два UI-оператора, различаясь только значением:

{ "field": "summary", "op": "null", "value": true  }   // is empty      → IS NULL
{ "field": "summary", "op": "null", "value": false }   // is not empty  → IS NOT NULL

Принимаются как булевы литералы, так и строки "true"/"false"; всё остальное — 400.

04Операторы: три словаря и как они соотносятся

Операторов не один список, а три, и путать их — главный источник недоразумений при чтении кода.

UI-операторы — OP

14 штук. То, что видит пользователь в выпадающем списке. Живут в filter-tree.type.ts, никогда не сериализуются в этом виде.

Wire-операторы — WIRE_OP

12 штук. То, что уходит в JSON. Живут в utils/wireOp.ts. Клиент никогда не пишет голую строку — только через таблицу соответствия.

Серверные — FilterOperator

13 штук: те же 12 плюс регистрозависимый like, который админка не порождает никогда.

Полная таблица

Колонка «типы» — для каких FieldType оператор вообще предлагается пикером (таблица OPS_FOR_TYPE); поле может сузить этот набор своим operators, но не расширить.

Почему у дат нет equals

Редактор даты — <input type="datetime-local">, то есть точность до минуты, а колонка — timestamptz с миллисекундами. eq сравнивал бы с мгновением на нулевой секунде и практически никогда не совпадал бы ни с одной реальной строкой — тупиковый фильтр. Диапазоны (between, gt/gte/lt/lte, within_last) ограничивают, а не пришпиливают мгновение, поэтому остаются.

На сервере eq по дате при этом разрешён: серверная таблица OPERATORS_BY_TYPE описывает, на что способна колонка, а не что предлагает конкретный редактор. Через API-токен или руками собранный URL легальный publishedAt eq <мгновение> пройдёт.

Единственное реальное ограничение сервера по операторам

Серверная таблица шире клиентской ровно в одном месте, и это семейство ~~: like/ilike/nilike Postgres определяет только для текста. Поэтому ilike по date, number, boolean или uuid отвергается кодом FILTER_OPERATOR_NOT_ALLOWED. До появления этой проверки такое правило доходило до драйвера и возвращалось как 500 по ссылке, которую можно переслать. Проверка идёт до коррекции значения, чтобы в ошибке был назван оператор, а не значение, которое этот оператор всё равно бы не принял.

Асимметрия таблиц соответствия

Таблица UI_TO_WIRE содержит девять записей, а не четырнадцать. Пять UI-операторов не имеют в ней строки и обрабатываются сериализатором напрямую, потому что либо разворачиваются в составную форму, либо требуют преобразования значения:

  • contains и not_contains — есть в таблице (ilike) или обрабатываются веткой (nilike), но в обоих случаях значение экранируется и оборачивается в проценты вручную;
  • is_one_of / not_one_of — значение должно остаться массивом;
  • is_empty / is_not_empty — делят один wire-оператор, различаясь значением;
  • between — группа из двух узлов;
  • within_last — две разные wire-формы в зависимости от того, куда фильтр едет.

Обратная таблица WIRE_TO_UI — наоборот, полная (11 записей): она должна уметь прочитать всё, что могло быть написано. Все три таблицы читаются через Object.hasOwn, а не голым индексом: op приходит с публичного, редактируемого руками URL, и WIRE_TO_UI['constructor'] вернул бы Object — истинное значение, из-за которого «неизвестный оператор» не отсеивался бы, а превращался в правило, чей op — функция.

Одно свойство group, два прочтения — и различает их id

На точечном id крошки называют связи, по которым идёт путь: author.company.name + ['Автор','Компания'] — сегменты и крошки выравниваются по индексу. На плоском id первая крошка называет обычную категорию — просто заголовок в пикере, за которым нет никакого обхода: так группируются виртуальные поля плагина (раздел «Segmentation» у сегментов). Это одно свойство, отвечающее на один вопрос — «под каким заголовком это лежит», — а не второе свойство category, означающее то же самое, которое хлебной крошке в поиске пришлось бы читать наравне с первым.

Категория одноуровневая: читается только первая крошка. Вкладываться здесь имеет право связь, у которой есть путь в доказательство.

Восстановление дерева — buildFieldTree

Единственная функция пакета, покрытая модульными тестами (браузер до неё дёшево не достаёт). Один проход по плоскому массиву раскладывает поля в три корзины:

  1. Поля коллекции (fields) — плоский id, group отсутствует. Всё, что сервер вывел из самого типа.В пикере — секция «Fields», первой
  2. Категории (categories) — плоский id, есть group. Ключ корзины — id сообщения-заголовка; порядок корзин — порядок первого появления, то есть порядок регистрации вклада, а не выдуманный сортировкой.В пикере — между «Fields» и «Relations»
  3. Связи (relations) — точечный id. Каждый ведущий сегмент даёт узел RelationNode с ключом-накопителем (author, затем author.company), подпись берётся из крошки с тем же индексом. Рекурсивно, до той глубины, которую сервер решил показать.В пикере — «Relations», свёрнутыми

Обход завершается всегда: циклы связей отсекает сервер — он не разворачивает путь обратно в тип-предок. Если подпись для сегмента не пришла, узел получает запасной дескриптор qb.field.relation.<путь> с именем сегмента в качестве текста.

Пикер поля

В покое триггер показывает выбранный путь чипами: сегменты-связи — нейтральными, лист — сплошным («Автор · Почта»), либо приглушённый плейсхолдер «Field». Открывается кликом или Enter.

В покое

Секции по порядку: Fields — собственные скаляры типа; именованные категории — виртуальные поля плагинов (это поля коллекции, поэтому выше связей, но не то, что ищет читатель, сканирующий колонки, поэтому ниже Fields); Relations — свёрнутые связи. Раскрытая связь показывает подзаголовок «<Связь> fields», свои поля и свои вложенные связи, рекурсивно. Отступ — 8px плюс 12px на уровень, задан padding'ом, чтобы подсветка строки шла на всю ширину.

При вводе в поиск

Секции исчезают, всё достижимое сплющивается в один список. Совпадение — токенное И: каждое слово запроса должно найтись в строке «крошки + подпись листа + сырой id». То есть «авт поч» найдёт «Автор · Почта», и по author.email тоже. У каждой строки — маленький тег типа, помеченный aria-hidden (он визуальная подсказка, а не часть имени).

Список — настоящий listbox. Каждая навигируемая строка это option, включая строку связи: она несёт aria-expanded вместо значения и никогда не бывает aria-selected — listbox не допускает других интерактивных детей. Заголовки секций помечены role="presentation", чтобы не оказаться невалидными узлами внутри listbox.

Почему у enum нельзя ввести значение руками. Чекбоксы и селект ограничивают выбор объявленными членами, поэтому массив на проводе всегда валиден. Свободный CSV остаётся только там, где множество значений принципиально открыто — у строк и uuid, — и именно поэтому его содержимое проверяется поэлементно.

Почему CSV хранит черновик. CsvValueInput держит сырую строку в локальном состоянии и никогда не читает её обратно из value.join(','): иначе висящая запятая, пауза посреди слова или перемещение курсора «схлопывались» бы прямо под руками. Разобранный массив уходит наверх на каждое нажатие (превью остаётся живым), а нормализация (a,,b → a,b) происходит по потере фокуса.

06Круговорот: состояние ⇄ провод

Два представления одного и того же условия. Слева — то, что держит React; справа — то, что едет в URL или в базу.

Состояние: FilterGroup

type FilterGroup = {
  id: string;              // ключ React
  combinator: 'and' | 'or';
  children: (FilterGroup | FilterRule)[];
}

type FilterRule = {
  id: string;              // ключ React
  fieldId: string;         // = FilterField.id
  op: OpId;                // UI-оператор
  value: RuleValue;
}

Поле id — клиентское, генерируется crypto.randomUUID() и никогда не сериализуется. Различает узлы isRule — по наличию fieldId.

Провод: JsonFilterNode

type JsonFilterNode =
  | { and: JsonFilterNode[] }
  | { or:  JsonFilterNode[] }
  | { field: string;
      op: WireOp;
      value: unknown }

Ни идентификаторов, ни подписей, ни типов — только то, что нужно, чтобы построить WHERE. Ровно эту форму принимает parseFilterTree.

Туда: treeToJsonFilter(tree, now?, options?)

  1. Пустое дерево отбрасывается. null или группа без детей → результат null, вызывающий просто не кладёт параметр в URL.treeToJsonFilter → null
  2. Незавершённые правила выпадают. isRuleComplete отсекает правило без значения (actorId equals с пустым инпутом), пустой массив у множественного оператора, диапазон без одной из границ, окно с нулевым счётчиком.чтобы сервер не отвечал FILTER_INVALID_VALUE на черновик
  3. Опустевшие группы выпадают тоже. Группа, все дети которой отпали, не отправляется как {or:[]} — сервер отверг бы её как FILTER_INVALID_NODE.симметрично пункту выше
  4. Каждое оставшееся правило переводится в wire-форму — по таблице UI_TO_WIRE или отдельной веткой для составных операторов.неизвестный op → throw, чтобы новый оператор без записи в таблице падал громко
  5. Результат — строка JSON, готовая к подстановке в ?filter=. Вариант treeToJsonNode возвращает объект — им пользуется превью.JSON.stringify

Инвариант этого прохода: полезная нагрузка всегда корректна по форме, даже пока в панели лежат черновики. Пользователю можно иметь недособранное правило на экране; на провод оно не попадёт.

Опция relativeDates — самый нагруженный аргумент в пакете

По умолчанию within_last резолвится: в момент сериализации считается конкретная ISO-отсечка и уходит обычный gte. Это правильно для ссылки — открывший присланный «за последние 7 дней» увидит те же строки, что отправитель.

И это молча неверно для сохранённого фильтра. Правило аларма «не обновлялось 90 дней», записанное с резолвленной отсечкой, навсегда означает «не обновлялось с того дня, когда правило написали», и выглядит при этом совершенно нормально. Поэтому: передавайте relativeDates всякий раз, когда фильтр сохраняется и переигрывается; не передавайте, когда он едет в URL.

Во всей админке флаг передаётся ровно в одном месте — AlarmRuleEditorPage. Это единственный экран, где фильтр хранится, а не линкуется.

Обратно: jsonFilterToTree(filter)

  • Не бросает исключений. Отсутствующая, пустая или битая строка даёт null: устаревший или отредактированный руками URL не должен ронять страницу.
  • Одиночное правило в корне заворачивается в группу and — в состоянии наверху всегда группа.
  • Неизвестный wire-оператор отбрасывает правило (проверка через Object.hasOwn).
  • null разводится по значению: true → is_empty, false → is_not_empty.
  • Проценты и экранирование снимаются: обёртка %…% срезается, \%/\_/\\ распаковываются обратно в буквальный текст — значение с процентом внутри переживает круг честно.
  • Пара gte+lte по одному полю сворачивается в between (описано выше).
  • Битое within_last не ломает контролы: нечисловой n становится 1, неизвестная единица — days.

QueryBuilderSummary — сводка в покое

Один удаляемый чип на каждое применённое условие («Автор · Почта contains @lilly ×») плюс «Clear all». Удаление чипа сразу переприменяет суженное дерево. Вложенность AND/OR здесь сплющивается — структура редактируется в панели, а это компактная читалка.

Значение enum-правила рисуется через объявленные члены поля, потому что на проводе там может лежать непрозрачный id, а чип — единственное место, где правило читают после схлопывания панели. Виртуальное поле плагина делает это очевидным: сегменты фильтруют по uuid аудитории, и неразрешённый чип читался бы как «Can be seen by is one of d19a552b-…». Неизвестный член откатывается к сырому значению, а не исчезает: сохранённое представление может пережить опцию, которую называет, а чип, показывающий пустоту, прочитался бы как «фильтр не применён».

08Сценарии по шагам

Сценарий А. Собрать фильтр в реестре записей

  1. Пользователь жмёт «Фильтры» в тулбаре. Потребитель переключает open; секция разворачивается анимацией grid-template-rows: 0fr → 1fr за ~150 мс, с уважением к prefers-reduced-motion.QueryBuilderPanel
  2. Панель синхронизирует черновик с применённым фильтром. На каждое открытие draft ← value, флаг showErrors сбрасывается: пользователь всегда правит текущее состояние, а не оставшееся от прошлого раза.useEffect по open
  3. Фокус переезжает в первую ячейку поля. Эффект ищет первый [role="combobox"]. Он перезапускается, когда поля догрузились, — до этого конструктора на экране нет вовсе.2.4.3
  4. «Add rule». Берётся fields[0], оператором ставится opsForField(first)[0] — не первый оператор типа, чтобы поле с суженным списком получило оператор, который оно реально предлагает. Значение сеется по форме оператора (defaultValueForOp). Живой регион произносит «Condition added. N conditions in total».addRuleTo → onChange
  5. Пользователь выбирает поле. Смена поля сбрасывает и оператор, и значение: правило не должно оставаться в состоянии «оператор был валиден для прошлого типа». Живой регион произносит «<путь> selected. Operator and value reset for the new field type» — два изменения контекста, происходившие раньше в тишине (3.2.2).RuleRow.onChange
  6. Пользователь выбирает оператор и вводит значение. Смена оператора снова пересевает значение по его форме. Превью JSON, если оно раскрыто, обновляется на каждое нажатие.defaultValueForOp
  7. «Apply». Сначала ворота: treeHasInvalidRules. Если чисто — onApply(draft) (или null, если детей нет), URL меняется, таблица пересобирается. Панель остаётся раскрытой: изменилась таблица под ней, и она на экране.applyFilter → updateParams({filter})
  8. Если грязно — showErrors включается, под каждым битым правилом появляется сообщение с именем поля, и фокус на следующем кадре уезжает на первый контрол первой ошибочной строки (не на само сообщение — оно нефокусируемо, а менять надо контрол).3.3.1
  9. Ошибки гаснут сами. Как только дерево становится валидным, showErrors сбрасывается — второго нажатия Apply не требуется.useEffect по draft
  10. Панель схлопывается. Условия оседают чипами QueryBuilderSummary под тулбаром.потребитель выключает open

Сценарий Б. Вложить группу и переключить AND/OR

Практически это упирается в терпение: набрать 50 узлов мышью тяжело. Но between стоит три узла (группа + два правила) при единице в бейдже «Фильтры (N)», поэтому бюджет расходуется быстрее, чем показывает счётчик, и восстановленный из сохранённого представления фильтр может оказаться уже за границей.

Ещё два числа, о которых стоит знать

MAX_WITHIN_LAST = 100 000 (клиент)

Инпут зажат в [1, 100000] на каждое нажатие, и сериализатор дополнительно ограничивает отсечку представимым мгновением. Причина сугубо практическая: превью сериализует живой черновик на каждую клавишу, и пользователь, набирающий длинное число, раньше получал new Date(NaN).toISOString() — RangeError, брошенный во время рендера, между которым и страницей нет никакой границы. Клемпинг делает сериализатор тотальным: бессмысленное окно вырождается в самое широкое представимое, а отказывает уже Apply.

MAX_WITHIN_LAST_N = 10 000 000 (сервер)

Здесь граница про Postgres: now() - make_interval(days => 1e9) переполняет диапазон timestamp и даёт 22008, который вызывающий увидит как 500. Клиент строже сервера по числу, но не по длительности: 100 000 дней — это около 274 лет, а 100 000 минут — всего 69 дней. Ограничение считает счётчик, а не окно.

Что делает сервер, чего клиент не отражает вовсе

  • Отрицания NULL-инклюзивны. ne, nin, nilike транслируются как предикат OR col IS NULL. В SQL трёхзначная логика дала бы NULL (то есть «не совпало») на пустой колонке, и «Заголовок не содержит foo» тихо прятало бы все черновики с пустым заголовком. Пустое значение — не то значение, которое исключают.
  • Отрицание на пути по связи переписывается. EXISTS(… NOT p …) превращается в NOT EXISTS(… p …). Это не одно и то же, как только связь может держать больше одной строки: «теги не содержат x» в первой форме означает «есть какой-то тег, отличный от x», чему запись с тегами [x, y] удовлетворяет.
  • Каждая связь несёт свой scope — границу воркспейса и защиту от мягко удалённых строк, приклеенную внутрь подзапроса EXISTS. Без него фильтр по связи ходил бы по строкам, которые сам корневой запрос исключает.
  • Пустой in отвергается (FILTER_EMPTY_IN_LIST): Drizzle выдаёт IN () как false, а NOT IN () как true — молчаливый ноль или молчаливая инверсия вместо намерения пользователя.
  • Виртуальные поля (extensionFields) уходят в хост-обработчик и становятся подзапросом, вшиваемым в позицию листа, — поэтому они спокойно живут внутри тех же групп AND/OR, что и обычные правила.

10Доступность и клавиатура

Доступность здесь — не отдельный слой поверх готового компонента, а причина, по которой некоторые части написаны именно так. Тикет ORT-157 прошёлся по конструктору целиком; ниже — что он изменил и почему.

Проблема, с которой всё началось: строки были неразличимы

Дерево доступности с тремя правилами на экране читалось буквально так:

combobox "Field"   combobox "Operator"   combobox "Value"   button "Remove rule"
combobox "Field"   combobox "Operator"   combobox "Value"   button "Remove rule"
combobox "Field"   combobox "Operator"   combobox "Value"   button "Remove rule"

Вторая строка ничем не отличалась от третьей, и после нажатия одной из пяти кнопок «Remove rule» узнать, какая именно исчезла, было неоткуда (4.1.2, 2.4.6). Решение — идентичность строки: функция fieldPath(intl, fields, fieldId) собирает локализованный путь «Автор · Почта», и он подставляется в имя каждого контрола строки и в её сообщение об ошибке. Ровно ту же композицию использовали чипы сводки — теперь реализация одна, и чип не может разойтись в названии с породившей его строкой. Для поля, которого больше нет в схеме, возвращается сырой fieldId: сломанное правило тоже обязано быть опознаваемым, а его id — единственная оставшаяся ручка.

Управление фокусом при удалении

Кнопка, по которой только что нажали, исчезает вместе со строкой — фокус падал на <body>, и следующий Tab начинал обход заново с начала документа. Удаление третьего условия из пяти стоило полного повторного прохода (2.4.3). Теперь:

  1. Элементы захватываются до удаления. Обработчик передаёт наверх сам нажатый элемент; список кнопок [data-qb-remove] снимается с живого DOM.onRemoveFocus(event.currentTarget)
  2. Цель выбирается по направлению списка: следующая кнопка удаления, затем предыдущая, затем «Add rule» этой группы. Удаляя три строки подряд, пользователь остаётся на одном месте, а не улетает наверх каждый раз.React ключует строки — все кроме удаляемой сохраняют свои узлы DOM
  3. Фокус ставится в requestAnimationFrame — после коммита, размонтирующего строку. Поставленный раньше, он был бы отменён браузером, размывающим исчезающий элемент.то же самое у чипов сводки

У чипов сводки логика та же (следующий чип, затем предыдущий), но с честной оговоркой: когда удаляют последний чип, вся сводка размонтируется и приземляться здесь не на что. Остаётся собственный контрол потребителя, и называть цель через эту границу значило бы привязать пакет к каждому хосту.

Живой регион

Один role="status" с именем «Filter builder status» на весь конструктор. Polite, а не assertive — пользователь сделал это намеренно и его не перебивают. Произносятся четыре события: добавлено условие (с итоговым числом), удалено (со сколькими осталось), добавлена группа, сменено поле. Правка оператора и значения не произносится — это пользователь смотрит, как его собственное нажатие попадает на экран. А вот смена поля произносится обязательно: она сбрасывает оператор и подменяет редактор значения, то есть меняет контекст дважды, и раньше делала это молча (3.2.2).

Строка поиска несёт aria-controls и живой aria-activedescendant. Подсветка стрелками без aria-activedescendant — чисто визуальное состояние, о котором вспомогательные технологии не узнают вовсе. А строки, достижимые только через Tab, объявляли бы позицию, с которой клавиатура ничего не может сделать. Нужны обе.

Ещё две детали клавиатуры, которые легко потерять при правках: подсветка сбрасывается на первую навигируемую строку при открытии и смене запроса, но не при разворачивании связи — иначе каждое раскрытие дёргало бы и подсветку, и прокрутку обратно наверх. И scrollIntoView({block:'nearest'}) следит за подсветкой, а не за перерисовкой списка, поэтому по той же причине не срабатывает на разворачивании.

Панель как область

  • Секция — role="region", подписанная кнопкой-переключателем через aria-labelledby.
  • В свёрнутом виде на неё ставится inert: содержимое не фокусируется и не читается, хотя и остаётся в DOM (высота анимируется гридом).
  • Esc возвращает фокус на переключатель — и делает это в requestAnimationFrame после коммита, ставящего inert. Панель намеренно уводит фокус внутрь при открытии, и до ORT-157 ничего не делала на выходе.
  • Esc пропускается, если event.defaultPrevented: открытый поповер пикера обязан съесть свой Escape первым.
  • aria-invalid вешается на сами чекбоксы EnumMultiSelect, а не на группу: это атрибут виджета-инпута, ARIA 1.2 не перечисляет его на role="group", так что на группе он не сообщал состояние вообще никому.
  • Анимация раскрытия уважает prefers-reduced-motion (motion-reduce:transition-none); список правил ограничен по высоте (22rem) и прокручивается внутри себя, чтобы таблица не уезжала за экран.

11Инварианты

То, что должно оставаться истинным после любой правки пакета. Нарушение каждого пункта — это конкретный дефект, уже случавшийся хотя бы раз.

  • И-01
    Полезная нагрузка на проводе всегда корректна по форме. Незавершённые правила и опустевшие группы выпадают при сериализации. Пользователь имеет право держать черновик на экране; сервер не имеет права его увидеть.
  • И-02
    Клиент никогда не пишет голую строку оператора. Каждый лист проходит через UI_TO_WIRE или через явную ветку сериализатора. Оператор, добавленный в OP без записи в таблице и без ветки, обязан бросить исключение, а не молча уехать.
  • И-03
    Правило всегда имеет поле. Модель не знает состояния «правило без поля», поэтому у ячейки поля нет разрушающего «очистить» — она просто открывается заново.
  • И-04
    Неизвестное поле не подменяется. RuleRow разрешает поле по id без отката к fields[0]. Подстановка чужого поля повела бы список операторов и валидацию по неверному типу, пока правило несёт старый путь: строка выглядела бы валидной, а ворота Apply (разрешающие тоже по id) молча отказывали бы в коммите.
  • И-05
    Смена поля сбрасывает и оператор, и значение. Иначе правило остаётся с оператором, легальным для прошлого типа, — и получает 400 на проводе. Смена оператора точно так же пересевает значение по его форме (defaultValueForOp), иначе составные операторы получают '' и ломают контролы переходом controlled → uncontrolled.
  • И-06
    Оператор по умолчанию берётся из opsForField, а не из OPS_FOR_TYPE. Порядок, объявленный полем, — это и есть его умолчание. Посев от типа разводил «Add rule» и пикер оператора по разным словарям.
  • И-07
    Объявленный список операторов сужает, но не расширяет. Он фильтруется тем, что допускает тип; сужение, не совпавшее ни с чем, откатывается к полному набору типа — пикер с нулём опций хуже, чем неверный порядок.
  • И-08
    Все словари читаются через Object.hasOwn. OPS_FOR_TYPE, UI_TO_WIRE, WIRE_TO_UI, MS_PER_UNIT, серверный OPERATORS_BY_TYPE. Это обычные объектные литералы, а ключ приходит с публичного URL или из построенной в рантайме схемы: WIRE_TO_UI['constructor'] вернул бы Object, и ?? null не сработал бы никогда.
  • И-09
    Сериализатор тотален. Ни одно значение, которое пользователь может ввести, не должно бросать исключение во время рендера: превью сериализует живой черновик на каждое нажатие. Отсюда клемпинг within_last в представимое мгновение и откат неизвестной единицы к дням.
  • И-10
    Деcериализатор не бросает. Битый JSON, неизвестный оператор, мусорное значение — всё даёт null или отброшенное правило. Пользователь способен отредактировать ?filter= руками, и страница обязана это пережить.
  • И-11
    Каждая группа владеет своим комбинатором. Глобального «режима AND/OR» нет; переключатель у корня и у каждой подгруппы независим, и все мутации адресуются по id узла, а не по позиции.
  • И-12
    Ключи React никогда не сериализуются. FilterGroup.id и FilterRule.id — клиентские; при разборе URL они генерируются заново.
  • И-13
    Пустое дерево — это null, а не пустая группа. treeToJsonFilter возвращает null, потребитель убирает параметр из URL. Отправка {and:[]} получила бы FILTER_INVALID_NODE.
  • И-14
    Черновик синхронизируется с применённым значением на каждое открытие. И у drawer'а, и у панели. Закрытие без Apply отбрасывает правки и сбрасывает состояние ошибок предыдущей попытки.
  • И-15
    Ворота Apply не пропускают ни одного невалидного правила, и в отсутствие определений полей отказывают все. Поэтому состояния загрузки и ошибки полей — часть контракта панели, а не полировка: пустой пикер читается как мёртвая кнопка.
  • И-16
    Сломанное правило сообщает о себе всегда, недописанное — после Apply. unknown_field и operator_not_allowed игнорируют showErrors: пользователь их не набирал и дописывать ему нечего.
  • И-17
    Фильтр, который конструктор отказывается нарисовать, он не отправляет. Легальность оператора проверяется до всех проверок значения.
  • И-18
    Фокус после удаления узла остаётся внутри конструктора. Цель захватывается до размонтирования и ставится в requestAnimationFrame после него.
  • И-19
    Список пикера — валидный listbox. Каждая навигируемая строка — option (строка связи тоже, с aria-expanded вместо значения), заголовки — presentation, фокус остаётся на поиске, aria-activedescendant живой.
  • И-20
    Внутри контейнера с блокировкой прокрутки поповеры порталятся в него. portalContainer публикуется через контекст и обязан читаться и пикером поля, и инжектированным редактором связи, иначе их списки не крутятся колесом.
  • И-21
    relativeDates передаётся тогда и только тогда, когда фильтр хранится. Ссылка получает замороженную отсечку, хранимое правило — скользящее окно. Ошибка в любую сторону тиха и выглядит нормально.

12Чек-лист тестирования

Модульные тесты в пакете покрывают только то, до чего браузер дёшево не достаёт: utils/fieldTree и utils/operators. Всё поведенческое живёт в apps/admin-e2e, где есть настоящий браузер. Ниже — что проверять руками или новым тестом.

Грамматика и круговорот

  • Плоское условие из двух правил — в URL {"and":[…, …]}, обратная загрузка даёт те же две строки
  • OR в корне — переключить комбинатор корня, применить, перезагрузить: комбинатор сохранился
  • Вложенная группа — добавить подгруппу с OR внутри AND, применить, перезагрузить: структура вернулась целиком, а не сплющилась
  • Две подгруппы рядом — обе восстанавливаются, нумерация в именах контролов не съезжает при добавлении правила между ними
  • contains со спецсимволами — значение 50%_off уезжает как %50\%\_off% и возвращается в инпут буквально
  • between туда-обратно — уезжает группой из двух правил, возвращается одним составным редактором, бейдж считает 1
  • Честная группа gte+lte — вернётся как between; убедиться, что результирующая выборка совпадает
  • is not empty — на проводе {"op":"null","value":false}, обратно поднимается как is_not_empty, а не как is_empty
  • within_last в ссылке — в URL резолвленный gte; после перезагрузки строка читается как абсолютное «greater than or equal to»
  • within_last в правиле аларма — в базе {"op":"within_last","value":{"n":…,"unit":…}}; повторное открытие правила даёт тот же составной редактор
  • Битый ?filter= — мусорная строка, оборванный JSON, {"op":"constructor"}: страница грузится, фильтр пуст, ничего не падает

Операторы и типы полей

  • Каждый из шести типов — пикер оператора предлагает ровно то, что в OPS_FOR_TYPE; у даты нет equals, у булева только equals
  • Поле с суженным operators — «Has locale» предлагает только equals и is one of; «Can be seen by» открывается на is one of, а не на equals
  • Сужение, не пересекающееся с типом — откат к полному набору типа, а не пустой список
  • Смена поля на другой тип — оператор и значение сброшены, редактор значения подменён, живой регион произнёс это
  • Смена оператора на составной — between даёт {from:'',to:''}, within_last даёт {n:7,unit:'days'}, множественный даёт []; ни один инпут не переходит из controlled в uncontrolled
  • enum + множественный оператор — чекбоксы по объявленным членам, ввести постороннее значение нельзя
  • Поле со связью и relationTarget — вместо ввода uuid пикер записей; при одиночном операторе выбор сводится к одному id

Валидация и ворота Apply

  • Каждый из 11 кодов — в частности uuid is one of с не-uuid элементом должен блокировать Apply (есть e2e на активности)
  • Ошибки гаснут сами — исправить значение: сообщения исчезают без повторного Apply
  • Фокус после неудачного Apply — на первом контроле первой ошибочной строки, не на кнопке и не на тексте ошибки
  • Неизвестное поле — переименовать поле в схеме и открыть старую ссылку: строка сообщает unknown_field сразу, ячейка поля осталась и позволяет перевыбрать
  • Нелегальный оператор из URL — ilike по дате: сообщение появляется немедленно, Apply не срабатывает
  • Поля грузятся — спиннер вместо конструктора, Apply заблокирован, Reset активен
  • Загрузка полей упала — Alert с «Try again», применённый фильтр продолжает действовать, таблица грузится
  • Превышение серверных границ — 51 узел, 6 уровней групп, 101 значение в CSV, строка длиннее 4096: клиент пропустит, проверяется корректность ответа 400 на экране

Клавиатура и доступность

  • axe на раскрытой панели с правилом — есть в e2e у участников и у активности
  • Обход пикера стрелками — заголовки пропускаются, обход цикличен, aria-activedescendant следует за подсветкой
  • Enter на строке связи — разворачивает её, а не выбирает; подсветка и прокрутка остаются на месте
  • Tab внутри поповера — выходит из него, а не обходит все поля схемы
  • Esc в панели — схлопывает и возвращает фокус на переключатель; при открытом поповере первым Esc закрывается поповер
  • Удаление третьего из пяти условий — фокус на кнопке удаления следующей строки, следующий Tab не начинает с начала документа
  • Удаление чипа сводки — фокус переходит на соседний чип; при удалении последнего сводка исчезает целиком
  • Живой регион — произносит добавление/удаление условия, добавление группы и смену поля; не произносит правку значения
  • Имена контролов в подгруппах — «Add rule to group 2» и т.д., корень остаётся без номера

Интеграция с потребителями

  • Прокрутка колесом внутри drawer'а и диалога — список пикера поля крутится колесом, а не только полосой (регресс portalContainer)
  • Бейдж «Фильтры (N)» — считает листья по всему дереву, включая вложенные группы
  • Чипы enum-значений — «Can be seen by is one of Acme», а не uuid; неизвестный член показывает сырое значение
  • Удаление чипа — немедленно переприменяет суженное дерево; удаление последнего даёт null, а не пустую группу
  • Слот-вклады — поля i18n и сегментов появляются под своими заголовками; в типе без i18n их нет
  • Save as alarm — кнопка отсутствует без фильтра в URL и без права alarms:manage
  • Apply в редакторе аларма — схлопывает панель, обновляет чипы, пересчитывает число совпадений, возвращает фокус на переключатель
  • Копирование JSON — по HTTP или при запрете доступа к буферу кнопка остаётся в исходном состоянии, в консоли нет необработанного отказа промиса

13Границы ответственности

Границы объясняют, почему в пакете нет вещей, которых от него ждут, — и почему добавлять их сюда было бы ошибкой.

Не слой данных

Ни одного запроса. Схема полей приходит пропом; пикер связанных записей инжектируется через renderRelationValue. Именно поэтому один компонент работает и там, где поля — статический массив из шести строк, и там, где они приходят из API вместе с рекурсивным графом связей.

Не владелец URL

Пакет не знает ни про роутер, ни про ?filter=. Он отдаёт строку и принимает строку. Класть её в адрес, в тело запроса или в поле формы — решает потребитель.

Не источник истины о том, что фильтруемо

Белый список путей, доходящих до SQL, держит серверная FilterSchema. У контента поверхность строится на сервере и отдаётся эндпоинтом /filter-fields — именно чтобы клиентское зеркало не разошлось с ней. Прежняя клиентская реконструкция filterFieldsFromSchema удалена: с графом связей такое расхождение становится видимыми пользователю 400.

Не валидатор дерева целиком

Ворота Apply зеркалят коррекцию листа. Количество узлов, глубина групп, длина строки, длина списка in — целиком серверные, и клиент их не знает. Дублировать их здесь означало бы завести пятое место, где числа могут разойтись.

Не переводчик в SQL

Превью показывает JSON, не SQL. Вкладка с SQL значится в «Deferred» и осознанно отложена: то, во что дерево превратится, зависит от вида связи, от scope воркспейса и от переписывания отрицаний — показать здесь можно было бы только правдоподобную выдумку.

Не хранилище фильтров

Сохранённые представления принадлежат контенту, правила алармов — алармам. Пакет умеет ровно две операции: сериализовать и разобрать. Что с результатом делать — не его вопрос.

Не про права

Ни одной проверки разрешений. Кнопку прячет потребитель (useHasPermission), доступность полей ограничивает сервер — поверхность фильтров у контента отсекает связи в типы, не выданные воркспейсу.

Не про сортировку и пагинацию

Конструктор отвечает только на «какие строки». Порядок, размер страницы и выбор колонок — другие контролы тулбара с собственными параметрами URL.

Что отложено сознательно

  • Откат на составную строку. Старая скобочная грамматика на клиенте больше не принимается вовсе: к моменту, когда URL доходит до jsonFilterToTree, он уже написан этим же пакетом.
  • Вкладка SQL-превью — см. выше.
  • Пикеры внешних ключей встроены — закрыто швом renderRelationValue.

FieldPicker — typeTagFor Тег типа «показывает тип поля» Тип uuid отображается тегом «relation» безусловно, даже когда relationTarget не задан. У журнала активности поле actorId — обычная колонка uuid, но в пикере помечено как связь. Тег помечен aria-hidden, поэтому дефект чисто визуальный, но вводящий в заблуждение
users-admin, MEMBERS_FILTER_FIELDS Комментарий: «the role.key dotted path resolves to the BE's role relation» Путь точечный, но group у поля не объявлен. buildFieldTree поэтому подписывает узел связи запасным дескриптором {id:'qb.field.relation.role', defaultMessage:'role'} — в пикере появляется непереводимый заголовок «role» со строчной буквы. Это единственный дотированный id в репозитории без выровненных крошек
Грамматика — оператор like Серверный словарь FilterOperator содержит 13 операторов Регистрозависимый like не имеет записи в WIRE_TO_UI, поэтому ?filter= с ним поднимается в дерево с молча выброшенным правилом: пользователь видит фильтр меньшей строгости, чем в ссылке, и никакого сообщения. Ни один потребитель админки like не порождает, но URL — публичная поверхность
Бейдж «Фильтры (N)» vs бюджет узлов countRules — «число условий, которое ожидает пользователь» Правило between считается за 1 в бейдже и стоит 3 узла на сервере (группа плюс два правила). При лимите в 50 узлов расхождение накапливается незаметно
Клиентский MAX_WITHIN_LAST «100,000 days reaches back about 274 years — far past any real content» Ограничение считает счётчик, а не длительность, и одинаково для всех трёх единиц: 100 000 минут — это 69 дней. Ссылка на 274 года верна ровно для одной единицы из трёх
Чего в этом артефакте нет

Разбор перевода дерева в SQL (tree-to-drizzle.ts, relation-exists.ts, пять видов связей и их scope) описан здесь ровно настолько, насколько нужно, чтобы понять смысл оператора. Это ответственность @orthacms/utils-server и тема отдельного паспорта. Также не разбираются сохранённые представления контента и движок алармов — они здесь только как потребители грамматики.

Паспорт компонента. Каркас тот же, что у паспорта плагина, но разделы адаптированы под то, что это UI-библиотека, а не плагин: вместо модели данных, HTTP API и конфигурации — грамматика, операторы, API компонента и круговорот состояние ⇄ провод. Разделов, которых у пакета нет (таблицы БД, маршруты, права, миграции), здесь просто нет.

Источник — исходный код packages/query-builder/admin целиком (12 компонентов, 12 модулей утилит, 2 модуля типов), серверный потребитель грамматики packages/utils/server/src/lib/filters, а также все пять точек монтирования и оба слот-вклада. Файлы AGENTS.md использованы как каркас, но каждое утверждение сверено с реализацией — расхождения вынесены в раздел 14.
