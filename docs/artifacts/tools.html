Пакет · packages/tools/server

Tools Единый каталог того, что агент может сделать с CMS — и единственное место, где вызов инструмента авторизуется

@orthacms/tools-server не умеет ничего сам. Он владеет контрактом инструмента, реестром и одной проверкой прав, через которую обязаны пройти оба потребителя: внешний MCP-эндпоинт и внутренний цикл прогона копайлота. Инструменты приносят прикладные плагины — контент, медиа, локали, журнал, тревоги, аудитории, участники. Пакет не владеет ни одной таблицей, не ходит в сеть и не знает слов «HTTP» и «JSON-RPC».

01Бизнес-описание

У OrthaCMS есть две принципиально разные аудитории машинных клиентов. Первая — внешний агент: Claude Desktop, Cursor, самописный клиент на SDK. Он приходит по HTTP с bearer-токеном и хочет спросить у сервера, что тот умеет. Вторая — собственный копайлот CMS: он живёт внутри процесса, работает от имени залогиненного человека и вызывает те же самые операции без всякого HTTP.

Раньше эти две аудитории обслуживались двумя разными наборами кода. В репозитории какое-то время лежало по два экземпляра каждого понятия: ToolSpec и ToolDefinition, permissions[] и requires[], CopilotToolRegistry и ToolRegistry, — и, что важнее всего, две независимые реализации проверки прав над одним и тем же контентом. Пакет tools/server — это решение схлопнуть их в одну (docs/adr/0007-one-tool-registry-two-surfaces.md).

Какую задачу решает

  • Одна проверка прав вместо двух. Изменение правил доступа физически не может примениться к MCP и промахнуться мимо копайлота: обе поверхности вызывают ToolRegistry.call, и проверка requires живёт внутри него.
  • Плагин регистрирует возможность один раз. media, i18n, activity, alarms, segments и users кладут инструменты в тот же реестр, что и content. Новая возможность не требует отдельной работы «а теперь то же самое для второй поверхности».
  • Осознанная адресация. Инструмент сам объявляет, кому он предназначен (surfaces). Это не фильтр где-то в стороне, который угадывает намерение автора, а поле рядом с определением, которое видно на код-ревью.
  • Прикладной плагин не выворачивается наизнанку. Инструмент лежит внутри своего плагина и дёргает его собственные внутренние сервисы (PublicEntriesQuery, EntryAccessService). Ничего не приходится реэкспортировать наружу ради чужого пакета — а именно так и появляется вторая, расходящаяся копия правил видимости.
  • Каталог как продукт. Для внешнего агента список инструментов — это и есть документация. Описание каждого написано для модели, а не для человека: в нём стоят правила рабочего процесса («создание даёт черновик», «публикация — отдельный вызов», «обновление сливает поля»).

Кому это видно

Внешний агент

Подключается к POST /api/v1/mcp с API-токеном. Видит ровно те инструменты, на которые у области токена хватает прав; отказ называет недостающее право прямым текстом, чтобы модель перестала пробовать.

Копайлот в админке

Работает от имени человека, который его открыл. Набор инструментов пересчитывается на каждый прогон: отобранное у роли право исчезает из следующего же ответа, а не через сутки.

Автор прикладного плагина

Пишет ToolProvider, регистрируется в onModuleInit через @Optional() и объявляет requires. Свою проверку прав он не пишет — и не имеет права написать.

Чем Tools не является

Границы здесь объясняют почти всю форму пакета:

  • Это не MCP. Ни строчки про JSON-RPC, Streamable HTTP, isError и structuredContent. Всё это — packages/mcp/server. Если бы контракт лежал там, развёртывание с копайлотом без MCP тащило бы за собой @modelcontextprotocol/sdk — зависимость на протокол, на котором оно не разговаривает.
  • Это не копайлот. Ни цикла прогона, ни SSE, ни модели, ни предложений (copilot_proposals). Поле effect здесь только объявляется; смысл ему придаёт движок прогона.
  • Это не инструменты. Пакет не содержит ни одного вызываемого инструмента — только контракт и реестр. Все 40 приходят из семи прикладных плагинов.
  • Это не модель данных. Нуль таблиц, нуль миграций, нет drizzle.config.ts. Реестр целиком живёт в памяти процесса и собирается заново при каждом старте.
  • Это не валидатор JSON Schema. validateToolInput — сознательно урезанное подмножество, и то, чего оно не умеет, перечислено в его же JSDoc.
Ключевая идея архитектуры

Фильтрация списка — удобство, проверка при вызове — граница. visibleTo() прячет то, что вызывающий всё равно не смог бы вызвать: клиент MCP волен назвать имя, которого ему не показывали, а языковая модель способна выдумать его целиком. Поэтому call() перепроверяет requires перед диспетчеризацией — это прямой аналог @RequirePermissions(...) на маршруте, с той разницей, что Nest охраняет маршруты, а здесь один маршрут несёт десятки операций.

Зависимости

package.json объявляет ровно две: @nestjs/common (декораторы @Injectable/@Global, классы исключений, Logger) и @orthacms/identity-server (PermissionKey и PERMISSION_KEYS). Ни Drizzle, ни HTTP-клиента, ни SDK какого-либо вендора.

Модель данных

Её нет. Пакет не владеет ни одной таблицей и не поставляет миграций — в отличие от identity (11 таблиц), copilot (разговоры, сообщения, предложения, вызовы инструментов) или alarms (правила и находки). След вызова пишет потребитель: копайлот кладёт строку в copilot_tool_calls, MCP не пишет ничего, кроме логов. Это осознанно: реестр не должен уметь писать, иначе он перестанет быть транспортно-нейтральным.

Почему это должен быть один экземпляр — и как это обеспечено

ToolsModule помечен @Global() и импортируется обоими потребителями:

// packages/mcp/server/src/lib/mcp.module.ts
imports: [ToolsModule],
exports: [MCP_CONFIG, ToolsModule]

// packages/copilot/server/src/lib/copilot.module.ts
imports: [ …, ToolsModule ]
  • Если бы реестр предоставлял McpModule, развёртывание с копайлотом без MCP осталось бы без реестра и без инструментов.
  • Если бы каждый предоставлял свой, инструменты прикладного плагина попадали бы в тот экземпляр, который выиграл у DI, а второй молча держал бы пустой каталог.
  • Прикладной плагин ToolsModule не импортирует. Он внедряет ToolRegistry как @Optional(), потому что развёртывание может не запускать ни одного потребителя — тогда его инструменты просто не регистрируются, и приложение обязано подняться.
Это проверяется, а не подразумевается

apps/server-e2e/src/server/tools/tool-registry.spec.ts поднимает приложение трижды: с обоими потребителями (и спрашивает у каждого один и тот же общий инструмент), без MCP (копайлот обязан сохранить полный каталог) и без копайлота (то же самое для MCP). Набор, который поднимает оба и спрашивает только одного, эту поломку не увидит вовсе.

Оба выключателя независимы

MCP_ENABLED=false→каталог цел, копайлот работает
COPILOT_ENABLED=false→каталог цел, MCP работает

Каждый выключатель снимает только свои маршруты, а не общую проводку: McpModule всё равно импортирует ToolsModule и регистрирует McpAuthService, просто не регистрирует контроллер. Ни один из них не уменьшает разделяемый каталог.

4.1 Публичный контент — content/server, поверхность mcp

Класс ContentToolProvider (src/lib/mcp/content-tools.provider.ts). Все шестнадцать штампуются surfaces: ['mcp'] одним местом в tools(), а не по одному: это единообразно набор публичного API — чтение через PublicEntriesQuery (по умолчанию только опубликованное), запись через PublicEntryWritesService с атрибуцией на токен (actor = null). Ресурсы, а не только инструменты

Тот же провайдер — единственный в репозитории, который реализует resources() и readResource(). Каждый выданный воркспейсу тип публикуется как ресурс ortha://content-type/<имя> с MIME application/json, чтобы клиент, умеющий ресурсы, втянул схему в контекст, не тратя вызов инструмента. Чтение проходит через тот же грант-гейт: невыданный тип даёт 404 и здесь. Поле requires у этих ресурсов не объявлено — они уже сужены до грантов воркспейса тем, кто их строит.

Ни одного инструмента над справочником аудиторий — ни создания, ни переименования, ни перетегирования, ни удаления. Это администрирование словаря, и оно остаётся на сессионном экране, где человек смотрит на последствие, которое диалог ему проговаривает. Поэтому segments:manage на токене со scope full достаёт ровно до записи и не дальше.

05Роли, права и видимость инструментов

Реестр не изобретает собственной модели прав. Он принимает готовое множество ключей resource:action и умеет ровно одну операцию — проверку принадлежности. Кто эти ключи вычислил, зависит от поверхности.

Одно право, два смысла — и здесь это кусается

Объявленное поле — это зафиксированное намерение, которое переживёт изменение соседней таблицы.

06Жизненный цикл вызова инструмента

У инструмента нет состояния и нет строки в БД, поэтому «жизненный цикл» здесь — это последовательность шлюзов, через которые проходит один вызов. Шлюзов пять, и порядок между ними выбран так, чтобы ошибка одного уровня не подсказывала ничего об уровне ниже.

известен на поверхности?→ права?→ аргументы?→ обработчик→ уплощение результата или ошибки

Почему неизвестный и запрещённый отвечают по-разному

Список инструментов не секрет: он выводится из собственной области или роли вызывающего, которую тот и так читает у себя в профиле. Назвать недостающее право — значит сэкономить модели ход, а не выдать чужую тайну. Правило обратное действует для данных: невыданный тип контента отвечает 404 неотличимо от несуществующего — на обеих поверхностях.

07Сценарии — как это работает по шагам

7.1 Сборка каталога при старте приложения

Каталог не описан нигде в конфигурации. Он собирается снизу вверх, из графа DI, и проверяется один раз.

  1. Хост поднимает плагины. createServer({ plugins }) импортирует динамический модуль каждого плагина. ToolsModule в списке плагинов не значится — он попадает в граф транзитивно, потому что его импортируют McpModule и CopilotModule.оба импортируют, ни один не предоставляет
  2. Nest отдаёт один ToolRegistry. Статический модуль кэшируется по классу, поэтому двойной импорт даёт один экземпляр. Это и есть тот инвариант, на котором держится весь шов; всё остальное — следствия.
  3. Каждый прикладной плагин регистрируется сам, из onModuleInit. this.toolRegistry?.register(this), где toolRegistry внедрён как @Optional(). Регистрация — вызов, а не DI-привязка, потому что у Nest нет multi-provider-токена: без него пришлось бы либо изобретать реестр провайдеров в самом Nest, либо заставить tools/server знать имена всех прикладных плагинов.@Optional() — потому что развёртывание может не запускать ни MCP, ни копайлот, и обязано подняться
  4. Повторная регистрация того же экземпляра — no-op. register() проверяет providers.includes(provider). Причина конкретная: onModuleInit, отработавший дважды (пересозданный тестовый модуль, провайдер, привязанный в двух модулях), положил бы один и тот же объект дважды, и тогда каждый его инструмент столкнулся бы сам с собой по имени и уронил весь каталог на обеих поверхностях — из-за ошибки, которая ничего не меняет.
  5. onApplicationBootstrap проходит по собранному каталогу один раз. Не в register(): tools() провайдера может зависеть от состояния (реестр типов контента), которое полно только после инициализации всех модулей.бросок отсюда прерывает app.init(), процесс не начинает обслуживать
  6. Все проблемы сообщаются разом. catalogueProblems() собирает список и склеивает его в одно сообщение — деплой, сломавший две вещи, должен узнать про обе, а не чинить их по очереди.
  7. Дальше каталог только читается. all() заново вызывает tools() у каждого провайдера на каждый запрос списка — поэтому инструменты, зависящие от типов контента, отражают текущий реестр типов. Дублирование имён после старта всё ещё бросает исключение из all(): это подстраховка на случай провайдера, который начал конфликтовать уже в рантайме.
Что именно ловит проверка на старте

Самая ценная из пяти проверок — requires, назвавший несуществующее право. can() — это точное совпадение по множеству, поэтому строковый литерал 'content:delete', устаревший после переименования, или ключ с лишним пробелом делают инструмент невызываемым вообще ни для кого — и молча: он просто не появится ни в одном списке. Сообщение об ошибке прямо требует использовать константу PERMISSIONS.*.

7.2 Внешний агент спрашивает, что сервер умеет (tools/list)

  1. Клиент шлёт POST /api/v1/mcp с Authorization: Bearer …. Контроллер помечен @Public() — глобальный AuthGuard сессии здесь не при чём — и @ApiExcludeController(), потому что JSON-RPC поверх одного маршрута не описывается как REST-операции.
  2. Аутентификация идёт до протокола. McpAuthService.authenticate вызывается раньше, чем создаётся транспорт: неаутентифицированный вызывающий не должен уметь двигать конечный автомат JSON-RPC вообще, даже до initialize. И 401 — правильный ответ по смыслу: JSON-RPC-ошибка читалась бы как «связь есть, операция не удалась».сессионная кука не принимается — ровно как на /api/v1
  3. Токен проверяется тем же ApiTokenService.verify, что и остальной публичный API. Неизвестный, отозванный и просроченный — один плоский 401: эндпоинт не должен служить пробником живых токенов.
  4. Разрешается воркспейс. Заголовок X-Workspace-Id или ?workspaceId= в URL (вторая форма существует потому, что клиенты MCP настраиваются ссылкой, а произвольные заголовки многим из них даются тяжело). Заголовок выигрывает; обе формы проходят одну и ту же проверку по «корзине» токена. Однословесный токен не требует ни того ни другого; многоворкспейсный без указания — 400, а не молчаливый выбор.
  5. Строится ToolContext. createToolContext({ kind: 'token', id: token.id, displayName: token.name, grantedPermissions: new Set(scopePermissions(token.scope)), userId: token.createdBy ?? null }, workspaceId). Заметьте id: это идентификатор токена, а не выпустившего пользователя, — токен действует от себя, поэтому отзыв токена отзывает доступ, кто бы его ни выписал. userId здесь только для атрибуции.
  6. Метод, отличный от POST, отвечает 405 — но уже после аутентификации, чтобы неаутентифицированный зонд узнал только 401. 405 отдаёт сам контроллер, а не транспорт: транспорт в stateless-режиме на GET открыл бы отдельный SSE-поток и держал бы его вечно, потому что здесь ничего никогда не пушится сервером.
  7. Собирается протокольный сервер — на один запрос. Не один долгоживущий: список инструментов есть функция от вызывающего, и вшивание контекста в замыкания обработчиков при конструировании — это то, что делает ошибку невозможной. Используется низкоуровневый Server, а не хелпер McpServer: последний принимает Zod-схемы, а здесь каждая схема — сгенерированная JSON Schema, и гонять её в Zod и обратно значит терять данные ради ничего.
  8. registry.visibleTo(context, 'mcp') — сужение по поверхности, затем фильтр по правам. Токен со scope read вообще не узнаёт, что существует content_create. Это лучше, чем узнать о нём через отказ, и бережёт ходы модели.
  9. Каждый инструмент переводится в форму MCP. inputSchema отдаётся как есть; readOnly становится annotations.readOnlyHint, destructive ?? false — destructiveHint. Это подсказки клиенту о том, что безопасно автоматически одобрять, и они не имеют отношения к effect.

7.3 Внешний агент вызывает инструмент (tools/call)

  1. Клиент присылает { name, arguments }. Всё, что было в 7.2 (шаги 1–7), повторяется заново: эндпоинт stateless, сессии нет, поэтому каждый запрос аутентифицируется с нуля. Плата за это — одна проверка токена; выигрыш — отсутствие хранилища сессий и липкой маршрутизации.
  2. Заводится дедлайн вызова. callWithinDeadline создаёт AbortController, вешает на него extra.signal транспорта (клиент отменил запрос или обмен закрылся) и таймер на callTimeoutMs (по умолчанию 30 000 мс). Флаг expired ставится до abort(), чтобы слушатель отличил дедлайн от разрыва.
  3. Реестр получает вызов: registry.call(name, args, { ...context, signal }, 'mcp').
  4. Сужение по поверхности. Инструмент ищется в forSurface('mcp'). Не найден — NotFoundException. Здесь же отсекаются все семнадцать копайлотовских: клиент, назвавший content_propose_update, получает «неизвестный инструмент».
  5. Проверка прав. tool.requires.every(k => context.can(k)). Отказ — 403 с текстом вида "content_delete" requires content:delete, which this token does not hold. Сообщение уходит к стороннему провайдеру модели дословно, и это осознанное решение: недиагностируемая проблема прав стоит дороже, чем название ключа.
  6. Аргументы по умолчанию. const args = input ?? {} — в реестре, а не на каждом краю. Оба потребителя раньше компенсировали отсутствующий объект аргументов у себя (args ?? {} в адаптере MCP, call.input ?? {} в движке прогона); для параметра, который сигнатура типизирует как объект, это защита, которую реестр им должен.
  7. Валидация против inputSchema. Провал — 422 с телом { message, issues: [{ field, message }] }. Разбор строки path: message на пару полей делается функцией toIssue, чтобы модель читала отказ реестра ровно так же, как 422 контентного плагина.
  8. Штамп и диспетчеризация. tool.handler(args, { ...context, surface: 'mcp' }).
  9. Обработчик делегирует, а не переписывает правила. Например, content_list вызывает assertDraftVisibility (единственное решение о доступе, которое обработчик принимает сам — потому что это правило об аргументе, а не об операции), затем resolveGrantedType, затем PublicEntriesQuery.list. Правила публичного API — только опубликованное, невидимость soft-deleted, неотличимость невыданного типа от неизвестного, связи, не пересекающие локали, валидация в момент публикации, нумерация ревизий под advisory-локом, outbox — здесь не повторяются и поэтому не могут разойтись с HTTP-поверхностью.
  10. Гонка с дедлайном. Promise.race([pending, rejectWhenAborted(...)]). У проигравшего всё равно навешен pending.catch(() => undefined): без этого обработчик, упавший после дедлайна, стал бы unhandled rejection и уронил процесс — ровно тот сбой, ради сдерживания которого таймаут и заведён.
  11. Дедлайн бросает, но не отменяет. Обработчику передан сигнал; проигнорировавший его инструмент доработает до конца, и ответ никто не прочитает. Ограничивается ожидание вызывающего — это гарантия, которую обмен «запрос-ответ» обязан дать; закончить саму работу этот слой не может.
  12. Размер результата меряется до отдачи. JSON.stringify(result, null, 2), затем Buffer.byteLength. Превышение maxResultBytes (4 МиБ) — isError с кодом result_too_large, называющий оба числа. Мерить надо до, потому что ответ стоит примерно втрое: текстовый блок, structuredContent и сериализация транспорта. И то, что не влезло в потолок, не влезет и в контекст модели, — поэтому отказ прямо просит спросить меньше.
  13. Успех отдаётся в двух написаниях сразу. content: [{ type: 'text', text }] для моделей, которые видят только content, и structuredContent для клиентов, которые его разбирают. Отдать что-то одно — значит сделать инструмент бесполезным для половины экосистемы. Не-объект боксируется под ключ value, потому что structuredContent по спецификации обязан быть объектом.
  14. Любой провал уезжает как isError-результат, а не как ошибка JSON-RPC. В этом весь смысл: ошибка протокола обрывает вызов клиента, а isError отдаётся модели, которая прочитает «title must be at most 200 characters» и исправит следующий вызов. Отказы по правам попадают сюда же — модель, узнавшая, что у неё нет content:publish, перестаёт пробовать вслепую.

7.4 Копайлот собирает набор инструментов на прогон

  1. Начинается прогон. CapabilityProfileService.resolve(user, workspaceId, signal) — на каждый прогон, без кэша. Права можно отобрать посреди переписки, и длинный разговор не должен нести устаревшие полномочия. Цена — одно индексированное чтение на прогон.
  2. Права берутся из роли: new Set(await permissions.forRole(user.roleId)).
  3. Строится актор kind: 'user'. id и userId — один и тот же идентификатор: у копайлота нет собственной личности, прогон действует от имени человека, который его открыл. Именно kind отличает прогон от вызова MCP в каждом обработчике, которому это важно.
  4. Контекст получает signal живого SSE-потока — чтобы инструмент, делающий реальный ввод-вывод, мог бросить работу, когда браузер отключился.
  5. Каталог сужается до поверхности: this.tools.forSurface('copilot') — не visibleTo, и это принципиально. Профилю нужен полный список поверхности, чтобы вернуть withheld с причинами; предварительно отфильтрованный список не смог бы сказать «вам не хватает content:update», а именно это показывает страница настроек.
  6. resolveCapabilityProfile решает, что предложить. Функция чистая и тотальная — без ввода-вывода и без часов, — поэтому утверждение «наблюдателю не предлагается ни одного пишущего инструмента» является юнит-тестом, а не обещанием. Она лежит в copilot/domain, который не импортирует ничего, и потому обобщена по структурному типу из трёх полей (name, requires, effect) вместо импорта ToolDefinition.
  7. Первое объявление имени выигрывает. Повтор попадает в withheld с причиной duplicate-name, а не затеняет предыдущий: имена инструментов пространственно разведены именно для того, чтобы один не мог выдать себя за другой, и «побеждает последний зарегистрированный» это бы отменило.
  8. Второго шлюза на effect нет. Пишущий инструмент предлагается на основании тех же объявленных прав, что и читающий. Раньше существовал per-workspace opt-in на автоприменение; ADR-0009 удалил и его, и таблицу copilot_workspace_policies, и причину apply-not-enabled. «Копайлот может то, что может ваша роль» иначе ничего не значит.
  9. Профиль уходит модели. Ровно эти определения превращаются в объявления инструментов запроса к провайдеру модели.

7.5 Копайлот вызывает инструмент внутри прогона

Самый длинный путь в системе: восемь проверок до обработчика, и каждая добавлена по конкретному поводу.

  1. Модель вернула блок tool_use. Движок ищет имя в authority.profile.tools. Не нашёл — Unknown tool "…", тем же текстом, что и реестр. Выдуманное имя и удержанное отвечают одинаково: список выводится из собственной роли вызывающего, и назвать его — значит сэкономить ход, а не выдать секрет.
  2. Пауза на подтверждение — только для пишущих. mayRun() вмешивается, если effect равен propose или apply. Читающие не спрашивают вообще: если бы спрашивали всё, все научились бы прокликивать не читая, а это хуже, чем не спрашивать, потому что обесценивает и тот запрос, который важен.разрешение «на весь чат» читается на каждый вызов, а не на прогон: список растёт, пока прогон стоит на паузе
  3. Прогон паркуется. Клиенту уходит кадр tool-permission-request с дедлайном; ToolPermissionBroker держит промис в памяти этого процесса. Бюджет — 5 минут на весь прогон, а не на вызов: ход, запросивший тридцать записей, иначе держал бы соединение, генератор и контекст модели два с половиной часа. Продление даёт полный свежий бюджет — человек, нажавший «нужно ещё время», говорит именно это.
  4. Отказ человека — обычная ошибка инструмента. Модель её прочитает и продолжит, прогон не умирает. И она попадает в аудит: «пользователь сказал нет» — ровно то, что ревьюер хочет видеть в copilot_tool_calls. Молчание отличается от отказа текстом сообщения.
  5. Права перепроверяются заново. this.profiles.resolve(...) вызывается ещё раз, уже внутри обработки вызова: предложение считалось в начале прогона, а роль может смениться, пока длинный ход в полёте. Пропавшее имя даёт You are not permitted to use "…" плюс запись в лог уровня warn.
  6. Аргументы валидируются до реестра. Движок сам зовёт validateToolInput(call.input, tool.inputSchema) — не дублирование, а точка принятия решения: провал должен стать сообщением модели, после которого прогон продолжается, а не исключением, которое придётся ловить. Реестр всё равно проверит ещё раз — за третьего потребителя, который забудет.
  7. Гвардия зацикливания. Подпись "<имя> <стабильный JSON аргументов>" кладётся в множество уже сделанных вызовов. Повтор отвечает текстом, который прямо говорит: результат выше, воспользуйся им или ответь. Без этого модель — особенно небольшая локальная — исчерпывает maxSteps на восьми одинаковых запросах. Проверяется после авторизации, чтобы повтор никогда не сообщал больше, чем первый вызов.
  8. Диспетчеризация через реестр, а не напрямую. this.tools.call(name, input ?? {}, fresh.context, 'copilot'). Предложение выше — фильтр удобства; здесь граница. Реестр ещё раз проверит requires, ещё раз провалидирует аргументы и поставит штамп surface: 'copilot'.
  9. Ветвление по effect. Это единственное место в системе, где effect вообще что-то значит:
    • propose → возвращённое значение и есть изменение. Оно проверяется isProposalDraft (иначе биндер, соврав про свой effect, записал бы кривую строку в append-only-таблицу; вместо этого получается обычная ошибка инструмента), пишется строкой copilot_proposals и затем применяется. Порядок «сначала строка, потом запись» — это всё, что несёт «отменяемо, но никогда не невидимо».
    • apply → инструмент записал сам, и квитанцию обязан написать движок, иначе получится «изменение без следа».
    • read (или поле отсутствует) → обычный результат.
  10. Результат заворачивается в «недоверенное». fenceUntrusted(call.name, output): тела записей написаны людьми и обязаны войти в модель как материал, а не как инструкции. Два свойства несут это: полезная нагрузка — JSON (ни одно поле не может внести строку, читающуюся как новый ход), и < экранируется (закрывающий разделитель не подделать изнутри).
  11. Аудит. Строка в copilot_tool_calls: имя, успех, длительность, сводка вывода. Плюс событие SSE tool-result для клиента.
  12. Бросок обработчика ловится и превращается в сообщение. Движок берёт error.message напрямую (userFacingMessage), а не через toToolError. Отсюда практическое следствие для автора общего инструмента, вынесенное в чек-лист: бросок new Error('No such asset') будет читаемым в панели и бесполезным по MCP, где toToolError сочтёт его багом и скроет за непрозрачным 500.

7.6 Чтение ресурса по MCP

  1. resources/list → registry.resources(context). Реестр опрашивает всех провайдеров (Promise.all по необязательному resources?.(context)), склеивает списки и фильтрует по requires ресурса.
  2. resources/read → registry.readResource(uri, context). Сперва полное перечисление объявленных ресурсов, чтобы найти объявление именно этого URI и проверить его requires — до того, как хоть у одного провайдера спросят байты.
  3. Почему перечисление, а не «спросить и надеяться». Правило то же, что у call: сокрытие ресурса в списке — это любезность, а клиент волен прочитать URI, которого ему не показывали. Лишний обход — цена шлюза; resources/read не горячий путь, а провайдер без ресурсов не стоит ничего.
  4. Провайдеры опрашиваются по порядку регистрации, побеждает первый, кто признал URI. Не признал никто — 404.
  5. Провал уезжает ошибкой JSON-RPC, а не isError. У чтения ресурса нет модели в цикле: клиент попросил байты по URI и либо получил их, либо нет. Уплощённый ToolError едет в поле data, так что клиент читает те же status/code/issues.
  6. 403 и 404 делят один код -32002. Для данных ответ намеренно единообразен; data.code всё ещё говорит forbidden тому клиенту, кому эта разница нужна.

08API: контракты и их сигнатуры

Пакет не выставляет ни одного HTTP-маршрута. Его «API» — это восемь экспортов из src/index.ts: четыре типа-контракта, класс реестра, модуль, конструктор контекста, уплощение ошибки и валидатор.

8.1 ToolDefinition — одна вызываемая единица

interface ToolDefinition {
    name: string;                          // snake_case, уникально по всем провайдерам
    title: string;                         // короткий заголовок для пикера MCP-клиента
    description: string;                   // документация ДЛЯ МОДЕЛИ
    inputSchema: JsonSchema;               // JSON Schema объекта аргументов
    requires: readonly PermissionKey[];    // ВСЕ ключи обязательны; проверяет реестр
    readOnly: boolean;                     // MCP-подсказка readOnlyHint
    effect?: ToolEffect;                   // 'read' | 'propose' | 'apply'; по умолчанию 'read'
    surfaces?: readonly ToolSurface[];     // 'mcp' | 'copilot'; ОТСУТСТВИЕ = ОБЕ
    destructive?: boolean;                 // MCP-подсказка destructiveHint
    handler(
        input: Record<string, unknown>,
        context: ToolContext
    ): Promise<ToolOutput>;                // бросает при неудаче; см. toToolError
}
ПолеОбязательноКомментарий, который стоит помнить
nameдаПространство имён — по субъекту (content_list, media_asset_read). Админские двойники несут префикс admin_, чтобы два набора читались врозь и на месте вызова, и в каждой строке аудита
descriptionдаЕдинственная документация, которую получает вызывающий. Сюда переносятся правила процесса, которые HTTP-API излагает прозой: «создание даёт черновик», «публикация — отдельный вызов», «обновление сливает»
requiresдаПоле, критичное для безопасности, которое не проверяет ни один тайп-чекер. Прямой аналог @RequirePermissions(...). Пустой массив — легальное значение, но он должен быть объявлен явно
readOnlyдаСловарь клиента: что безопасно автоматически одобрять
effectнетСловарь сервера: результат обработчика — это результат или это изменение. Из readOnly не выводится и не выводит его: propose не read-only в смысле MCP (это половина записи), а прямая запись не propose, как бы разрушительна ни была

8.2 ToolContext и ToolActor — «кто спрашивает»

type ToolActorKind = 'token' | 'user';

interface ToolActor {
    kind: ToolActorKind;
    id: string;                                  // id токена ИЛИ id пользователя
    displayName: string;
    grantedPermissions: ReadonlySet<string>;     // ЕДИНСТВЕННЫЙ вход решения о доступе
    userId: string | null;                       // подотчётный человек — ТОЛЬКО атрибуция
}

interface ToolContext {
    actor: ToolActor;
    workspaceId: string;                         // всегда разрешён до диспетчеризации
    signal?: AbortSignal;                        // есть только у копайлота
    surface?: ToolSurface;                       // штампует call(); только презентация
    can(permission: PermissionKey): boolean;
}
  • grantedPermissions — единственный вход решения. Инструмент никогда не выводит права заново из id или userId. Кто аутентифицировал вызывающего, тот и решил, что́ ему можно, — один раз, на краю.
  • id токена — это токен, а не выписавший его человек. Роль выписавшего не консультируется никогда, поэтому отзыва токена всегда достаточно.
  • can() — для решений тоньше собственного requires. Пример ровно один и он показателен: assertDraftVisibility расширяет видимость внутри одного инструмента для держателя content:update, вместо того чтобы плодить второй инструмент.
  • signal необязателен, потому что он есть только у одного потребителя. Прогон копайлота — живой SSE-поток, который кончается вместе с вкладкой; вызов MCP — запрос-ответ, который завершится так или иначе. Инструмент, игнорирующий сигнал, корректен: это любезность, а не граница корректности.
  • surface необязателен, чтобы обработчик можно было юнит-тестировать с контекстом, собранным руками. При отсутствии — трактовать как админский рендеринг копайлота.
Единственное правило про surface

Инструмент, которому захотелось if (surface === 'copilot') вокруг проверки, фильтра или скрываемого поля, — это два инструмента. Разделите его, и пусть requires и can() значат для всех одно и то же. Менять по поверхности разрешено только представление: например ссылку на скачивание, которую вызывающий действительно сможет достать своими учётными данными.

8.3 ToolProvider — как плагин приносит инструменты

interface ToolProvider {
    tools(): readonly ToolDefinition[];
    resources?(context: ToolContext): Promise<readonly ResourceDefinition[]>;
    readResource?(uri: string, context: ToolContext):
        Promise<ResourceContents | undefined>;   // undefined = «не мой URI»
}

tools() вызывается на каждый запрос списка, поэтому может зависеть от состояния рантайма (реестр типов контента) — но не должен быть дорогим и не должен делать ввод-вывод: фильтрация по правам идёт уже после его возврата. resources(), наоборот, асинхронный и принимает контекст, потому что видимость ресурса пер-воркспейсная.

Каноническая форма регистрации, одинаковая во всех четырнадцати провайдерах:

9.2 На вызове — validateToolInput

Сознательное подмножество JSON Schema, покрывающее ровно то, что используют генерируемые схемы инструментов:

Что проверяется

  • type: object, array, string, integer, number, boolean, null — с разделением integer и number
  • required — по именам ключей
  • properties — рекурсивно, с построением пути (filter.rules[0].field)
  • additionalProperties: false — лишний ключ становится ошибкой только если схема действительно закрыта
  • enum — членство
  • items, minItems, maxItems
  • minLength, maxLength
  • minimum, maximum — оба включительно

Что игнорируется молча

  • anyOf, oneOf, allOf
  • $ref — рекурсия по ссылке невозможна
  • format, pattern
  • любое незнакомое имя типа — принимается и пропускается: непонятая схема не повод обвинять значение

Правило, которое автор инструмента не имеет права прочитать неверно: ограничение, вложенное внутрь anyOf, не проверяется вовсе.

Это не граница безопасности

Границей является requires. Валидация аргументов — эшелонирование: она не даёт кривому вызову дойти до обработчика и вернуться непрозрачным 500 вместо validation_failed с названием поля. Обработчик по-прежнему владеет каждым правилом о собственных значениях. Контентный плагин, например, дополнительно прогоняет аргументы через настоящий class-validator-DTO своей HTTP-ручки, чтобы потолок вроде pageSize был написан один раз.

Ловушка имени

В репозитории две разные функции с именем validateToolInput: подмножество JSON Schema в @orthacms/tools-server и DTO-валидация в packages/content/server/src/lib/mcp/tool-input.ts, которая гоняет class-validator с опциями хостового ValidationPipe. Контентный MCP-провайдер импортирует вторую. Совпадение имён при чтении диффа сбивает.

  • tools/call по MCP → тело isError-результата, красиво отформатированным JSON.
  • resources/list и resources/read по MCP → поле data ошибки JSON-RPC, а код выбирается по статусу: 403 и 404 → -32002, 400 и 422 → InvalidParams, всё прочее → InternalError.

Следствие для автора общего инструмента

Инструмент, предложенный обеим поверхностям, обязан бросать подклассы HttpException, а не голые Error. new Error('No such asset') будет прекрасно читаться в панели копайлота и станет непрозрачным 500 по MCP. Асимметрия не в контракте, а в том, как две стороны уплощают бросок, — и учитывать её должен автор.

Два исключения, которые до toToolError не доходят

Класс CallAbandoned в build-mcp-server.ts заведён отдельно именно ради этого: дедлайн — собственное решение этого файла, а отключение клиента — рутина. Ни то, ни другое не баг инструмента, и логировать их со стеком как «необработанную ошибку» было бы шумом. Они превращаются в 504 timeout и 499 client_closed_request напрямую.

11Чек-лист автора нового инструмента

Формально это раздел «Adding a tool: decide surfaces deliberately» из packages/tools/server/AGENTS.md. По существу это единственная процедура в монорепозитории, которую обязан пройти автор инструмента в любом пакете, потому что пропущенное поле и осознанно пропущенное поле дают идентичный код и противоположные намерения.

11.1 Решить, кому инструмент предназначен

Вопросы отрабатываются по порядку; первое «да» решает. И они о самом инструменте, а не о том, кто его попросил: инструмент, написанный для копайлота и ответивший «нет» на все пять, принадлежит обеим поверхностям.

  1. Обработчик пишет — или возвращает изменение, чтобы его применил кто-то другой? → ['copilot'].почему: у MCP нет движка прогона. Обработчик propose ничего не пишет и отдаёт черновик наружу — по MCP вызов выглядел бы успехом и не менял бы ничего вообще. Прямой apply хуже: его квитанция — строка copilot_proposals, которую пишет движок, поэтому по MCP он писал бы без всякого следа
  2. Он показывает неопубликованный контент по одному content:read? Черновики, снимки ревизий, соседние переводы — всё, что выведено из админских сервисов, а не из public-api/. → ['copilot'].почему: content:read токена — это published-only область публичного API; content:read пользователя — наблюдатель, законно видящий черновики. Один ключ, два смысла
  3. Ему нужно право, которого не выдаёт ни одна область токена? scopePermissions даёт только content:*, media:read, media:create, segments:read и segments:manage. Всё, что требует activity:read, users:read, alarms:read, media:update, для токена не появится никогда. → ['copilot'].почему объявлять, а не полагаться на проверку прав: будущая область токена, случайно включившая такой ключ, молча откроет поверхность, которую никто не решал открывать
  4. Он читает или пишет то, что имеет смысл только для залогиненного человека? Атрибуция принявшему, текущий разговор, ожидающее предложение. → ['copilot'].
  5. Он построен на public-api/ и потому published-only? → ['mcp'].почему: предложить его копайлоту значит понизить наблюдателя до видимости внешнего токена

Иначе — не объявлять поле и разделить. Это путь наименьшего сопротивления по замыслу, а не лазейка.

Проработанные «нет» — чтобы вопрос не открывали заново

admin_content_revisions / admin_content_diff: выглядят как бесплатная возможность (у MCP аналога нет, гранты они перепроверяют сами), но проваливаются на (2) — таймлайн ревизий и есть история черновиков, по content:read. Ужесточить requires до content:update значило бы починить MCP и сломать копайлот: наблюдатель потерял бы историю версий, которую видит в админке сегодня.

i18n_translations_get: лежит в одном файле с общим i18n_locales_list. Проваливается на (2) менее заметно: LocaleGroupService.liveWhere сужает по воркспейсу и soft-delete, но не по состоянию публикации. То, что сосед общий, — не аргумент.

11.2 Написать определение

  • Имя snake_case, уникальное по всем провайдерам → пространство имён по субъекту; админский двойник публичного инструмента получает префикс admin_.
  • requires — только константы PERMISSIONS.* → сырой строковый литерал устаревает молча и оставляет инструмент невызываемым для всех; старт это поймает, но зачем.
  • requires объявлен даже когда он пуст → [] — легальное значение, отсутствие поля — нет.
  • surfaces либо объявлен с комментарием «в чём напряжение», либо пропущен с комментарием «напряжения нет» → записывается ответ, а не только код.
  • effect проставлен явно для всего, что пишет или готовит изменение → умолчание read означает «результат», и для propose-инструмента это молчаливая поломка записи предложения.
  • readOnly и destructive честны → это подсказки клиенту MCP о том, что можно автоодобрять; из effect они не выводятся.
  • inputSchema — объектная схема с additionalProperties: false → иначе лишний ключ не станет ошибкой; инструменту без аргументов положено { type: 'object', properties: {} }.
  • Схема не прячет ограничение внутрь anyOf / $ref → такое ограничение не проверяется вовсе.
  • description написан для модели → правила процесса — внутрь: что создание даёт черновик, что публикация отдельная, что обновление сливает, что пачка «успешна» даже с провалившимися элементами.
  • Обработчик делегирует сервисам собственного плагина → именно так вторая, расходящаяся копия правил видимости и не появляется.
  • Обработчик не проверяет собственный шлюз → это делает ToolRegistry.call; ctx.can() — только для решений тоньше requires.
  • Обработчик бросает подклассы HttpException → голый Error становится непрозрачным 500 по MCP.
  • Размер ответа под контролем → каждое поле — контекст, за который платит модель: разрежённый набор полей, маленькие страницы, узкая проекция.
  • ctx.surface — только презентация → если хочется ветвить проверку, фильтр или скрываемое поле, это два инструмента.

11.3 Подключить

  • Провайдер реализует ToolProvider и OnModuleInit → регистрация — вызов register(this), а не DI-привязка.
  • ToolRegistry внедрён как @Optional() → развёртывание может не запускать ни одного потребителя и обязано подняться.
  • Провайдер добавлен в providers модуля плагина → ToolsModule прикладной плагин не импортирует.
  • Приложение поднимается → это и есть прогон валидации каталога.

11.4 Покрыть тестами

  • Тест авторизации на requires → поле критично для безопасности и не проверяется ни одним тайп-чекером; surfaces его не заменяет.
  • Обновлены оба кросс-поверхностных e2e-набора → mcp.spec.ts утверждает, что́ токену показано и что́ нет; copilot-read-catalogue.spec.ts делает то же для прогона. Инструмент, отсутствующий в обоих списках, — это инструмент, который никто не проверяет.
  • Для общего инструмента — проверка обеих поверхностей → включая то, что разница в презентации осталась разницей в презентации.

13Безопасность и авторизация

13.1 Одна точка, и почему именно она

Nest охраняет маршруты. И MCP-эндпоинт, и цикл прогона копайлота — это один маршрут, несущий много операций, поэтому декоратор на маршруте здесь бесполезен по конструкции. Замена ему — объявленный requires плюс централизованная проверка в ToolRegistry.call.

13.2 Что защищает и от чего

  • Вызов имени, которое не показывали. Клиент MCP волен это сделать, а модель способна выдумать имя. Поэтому фильтрация списка — не защита, а call() — защита.
  • Вызов инструмента чужой поверхности. call применяет то же сужение, что и forSurface. Без этого клиент MCP смог бы дёрнуть propose-инструмент, которому нечем принять результат, а копайлот — публичный content_create, атрибутирующий запись на null.
  • Устаревшие полномочия в длинном разговоре. Профиль копайлота пересчитывается на каждый прогон, а внутри прогона права перепроверяются ещё раз перед каждым вызовом.
  • Инструмент, забывший свой шлюз. Он его физически не может забыть: обработчик не участвует в решении.
  • Инъекция инструкций через контент. Копайлот заворачивает результат в fenceUntrusted: JSON и экранированный <. Тело записи, написанное человеком, входит в модель как материал, а не как ход.
  • Перечисление воркспейсов и токенов. Неизвестный/отозванный/просроченный токен — один плоский 401; воркспейс вне «корзины» и несуществующий воркспейс — один 403.
  • CSRF. Сессионная кука на MCP не принимается вовсе. Кука ездит с запросом сама, а этот эндпоинт пишет контент.

13.3 Что сознательно раскрывается

Отказ называет недостающее право

"content_delete" requires content:delete, which this token does not hold. уходит к сторонней модели дословно. Обоснование: набор инструментов выводится из собственной области вызывающего и не сообщает ничего о ком-то ещё, а недиагностируемая проблема прав стоит дороже, чем название ключа. Цена — утекает форма модели прав. Отсюда требование: держать сообщение в границах requires и никогда не давать обработчику дописать туда собственную причину.

Правило, которое НЕ отменено для данных

Для списка инструментов «это существует, но вам нельзя» — не информация. Для данных — информация, и здесь ответ обязан быть единообразным: невыданный тип контента отвечает 404 неотличимо от несуществующего, на обеих поверхностях. Эти два правила легко перепутать между собой, и путаница в любую сторону — дефект.

13.4 Два поля, которые не проверяет тайп-чекер

requires

Тип у него правильный — PermissionKey[], — но правильность значения неверифицируема: инструмент, объявивший content:read вместо content:delete, скомпилируется. Отсюда правило «новый инструмент требует теста авторизации» и проверка на старте, ловящая хотя бы несуществующий ключ.

surfaces

Опущенное поле легально и означает «обеим». Забытое поле у propose-инструмента даёт вызываемый по MCP инструмент, которому нечем принять предложение. Тайп-чекер молчит; ловят кросс-поверхностные e2e-случаи, и новому инструменту нужен свой.

13.5 Известные ограничения

  • Проверка каталога — только на старте. Провайдер, зарегистрированный после app.init(), не проходит ни одной из пяти проверок. В продукте так никто не делает (все четырнадцать регистрируются из onModuleInit), но e2e-фикстуры делают — и их имена с точкой это демонстрируют.
  • validateToolInput — не граница. Правило внутри anyOf не проверяется вообще.
  • Дедлайн MCP не отменяет работу. Инструмент, игнорирующий signal, доработает до конца.
  • Брокер разрешений копайлота живёт в памяти процесса. Это реальное ограничение развёртывания: горизонтально масштабированной установке нужна липкая маршрутизация по runId.

14Инварианты

Утверждения, которые обязаны выполняться всегда. Одновременно список для ревью и заготовка утверждений для тестов.

  • И-01Вызов инструмента авторизуется ровно в одном месте — ToolRegistry.call, до диспетчеризации. Ни один обработчик не проверяет собственный requires.
  • И-02visibleTo() и forSurface() — фильтры удобства; убрать любой из них можно без потери безопасности, убрать проверку в call() — нельзя.
  • И-03Требуются все ключи из requires; проверка — точное совпадение по множеству grantedPermissions.
  • И-04Права никогда не выводятся заново внутри пакета: createToolContext получает готовое множество от того, кто аутентифицировал вызывающего.
  • И-05ToolActor.userId используется только для атрибуции и никогда для авторизации; для токена роль выпустившего пользователя не консультируется вовсе.
  • И-06Инструмент без поля surfaces предложен обеим поверхностям; surfaces: [] невозможно — приложение не стартует.
  • И-07call() применяет то же сужение по поверхности, что и forSurface(): вызов инструмента чужой поверхности отвечает «неизвестный инструмент».
  • И-08ToolContext.surface ставит call(), а не вызывающий; это всегда та поверхность, против которой вызов авторизовали.
  • И-09surface может менять только представление ответа и никогда — набор проверок, фильтр или состав раскрываемых полей.
  • И-10Неизвестное имя (404) и запрещённое имя (403) — разные ответы; отказ называет недостающие ключи.
  • И-11Для данных ответ единообразен: невыданный тип контента отвечает так же, как несуществующий, на обеих поверхностях.
  • И-12Авторизация выполняется до валидации аргументов: неавторизованный вызывающий получает один и тот же ответ, что бы он ни прислал.
  • И-13Отсутствующий объект аргументов трактуется как {} реестром, а не каждым потребителем по отдельности.
  • И-14Ресурс проходит тот же шлюз: объявленный requires и прячет ресурс из списка, и отклоняет чтение по прямо названному URI.
  • И-15Приложение не стартует при дубликате имени, имени не в snake_case, пустом surfaces, неизвестном праве в requires или необъектном inputSchema. Все проблемы сообщаются разом.
  • И-16register() идемпотентен по экземпляру провайдера; два разных провайдера, claim'ящих одно имя, остаются ошибкой проводки.
  • И-17ToolsModule глобален, импортируется обоими потребителями и не предоставляется ни одним; в одном приложении существует ровно один ToolRegistry.
  • И-18Прикладной плагин внедряет ToolRegistry как @Optional(); развёртывание без обоих потребителей поднимается, просто без каталога.
  • И-19Выключение MCP или копайлота снимает только соответствующие маршруты и не уменьшает разделяемый каталог.
  • И-20Не-HttpException уходит наружу непрозрачным 500 с сокрытым сообщением; стек попадает только в лог сервера.
  • И-21Пер-полевые issues из 422 переносятся в ToolError дословно, под тем же ключом.
  • И-22Профиль возможностей копайлота не кэшируется между прогонами, и права перепроверяются ещё раз перед каждым вызовом внутри прогона.
  • И-23Первое объявление имени выигрывает; повтор попадает в withheld, а не затеняет предыдущее.
  • И-24Пакет не владеет ни одной таблицей, не поставляет миграций и не импортирует ни Drizzle, ни SDK какого-либо вендора, ни @modelcontextprotocol/sdk.
  • И-25Ни один тип и ни одна функция пакета не упоминают HTTP, JSON-RPC или MCP.

15Чек-лист тестирования

Формулировки — «действие → ожидаемый результат». Существующие наборы: юниты packages/tools/server/src/lib/*.spec.ts (реестр — 27 случаев, ошибки — 5, валидатор — 20), кросс-поверхностный e2e apps/server-e2e/src/server/tools/tool-registry.spec.ts, проводные наборы …/server/mcp/mcp.spec.ts и …/server/copilot/copilot-read-catalogue.spec.ts.

Авторизация

  • Актор без объявленного права вызывает инструмент → 403; обработчик не вызывался.
  • Актор, которому инструмент скрыт из списка, называет его по имени → 403, а не выполнение: фильтрация списка ничего не гарантирует.
  • Инструмент с двумя правами, актор держит одно → 403; требуются все.
  • Инструмент с requires: [] → выполняется у любого, кто дошёл до эндпоинта.
  • Токен read просит tools/list → в ответе нет ни одного пишущего инструмента.
  • Токен read вызывает content_create → isError, 403, названо content:create.
  • Права роли отозваны между началом прогона и вызовом → вызов отклонён с You are not permitted to use "…", прогон продолжается.

Поверхности

  • Инструмент без поля surfaces → присутствует в forSurface('mcp') и в forSurface('copilot').
  • Инструмент с surfaces: ['copilot'], запрошенный у поверхности mcp → отсутствует в списке И невызываем (404, а не 403).
  • tools/list по MCP → нет ни одного имени с префиксом admin_ и ни одного *_propose_*.
  • Каталог прогона копайлота → нет ни одного публичного content_* (кроме общих content_access_get).
  • Обработчик читает ctx.surface → видит именно ту поверхность, через которую вызвали; подделать её вызывающий не может.
  • Общий media_asset_read по MCP и в копайлоте → одинаковый набор ассетов, разные downloadPath (/api/v1/… против /api/…).

Один экземпляр реестра

  • Приложение с обоими потребителями, общий инструмент спрошен у каждого → виден обоим — это и есть доказательство единственности экземпляра.
  • MCP_ENABLED=false → копайлот сохраняет полный каталог; маршрута /api/v1/mcp нет.
  • COPILOT_ENABLED=false → MCP сохраняет полный каталог; ни одного маршрута копайлота нет.
  • Оба выключены → приложение поднимается; инструменты просто не зарегистрированы.

Валидация каталога на старте

  • Два провайдера объявили одно имя → app.init() бросает, называя имя.
  • requires содержит право, которого нет в PERMISSION_KEYS → бросок, требующий использовать константу PERMISSIONS.*.
  • Имя Content_List / content__list / _content → бросок с указанием паттерна.
  • surfaces: [] → бросок: «предложен ни одному потребителю».
  • inputSchema: { type: 'string' } или не объект → бросок.
  • Каталог сломан в двух местах → сообщение перечисляет обе проблемы.
  • Корректный каталог → старт проходит.
  • Один и тот же экземпляр провайдера зарегистрирован дважды → старт проходит, инструменты не задвоены.

Валидация аргументов

  • Отсутствует обязательное поле → 422, issues: [{ field: '<имя>', message: 'required' }].
  • Неверный тип → 422 с expected <тип>; вложенные ветки не проверяются дальше.
  • 1.5 против type: 'integer' → 422; против type: 'number' — принято.
  • Значение вне enum → 422 с перечислением допустимых.
  • Лишний ключ при additionalProperties: false → 422; при открытой схеме — принято.
  • Границы minimum/maximum/minLength/maxLength ровно на значении → принято: все границы включительные.
  • Нарушены три правила сразу → сообщены все три, а не первое.
  • Ограничение спрятано внутрь anyOf или за $ref → не проверяется — это задокументированное поведение, а не баг.
  • Аргументы не присланы вовсе → трактуются как {}; схема без обязательных полей проходит.
  • Актор без прав присылает заведомо кривые аргументы → 403, а не 422: авторизация раньше.

Ошибки

  • Обработчик бросил NotFoundException → { status: 404, code: 'not_found' }.
  • Обработчик бросил 422 с issues → issues дошли до вызывающего дословно.
  • Nest отдал message массивом → склеен через ; в одну строку.
  • Обработчик бросил голый Error('таблица users не существует') → 500 internal_error, текст сокрыт, стек в логе.
  • Инструмент по MCP не уложился в callTimeoutMs → isError 504 timeout; процесс жив даже если обработчик упал позже дедлайна.
  • Результат больше maxResultBytes → 413 result_too_large с обоими числами.
  • Клиент отключился в середине вызова → никакого лога «unhandled error», никакого стека.

Ресурсы

  • URI, который не признал ни один провайдер → 404.
  • Два провайдера признают один URI → побеждает зарегистрированный первым.
  • Ресурс с requires, актору не хватает права → скрыт из списка И отклонён при чтении по прямому URI.
  • Ресурс без requires → читается любым, кто дошёл до эндпоинта.
  • Схема невыданного воркспейсу типа по ortha://content-type/… → 404, неотличимо от несуществующего типа.
  • Провал resources/read → JSON-RPC-ошибка (не isError), уплощённый ToolError в поле data.

Паспорт пакета packages/tools/server. Сделан по каркасу пилотного артефакта identity: бизнес-описание → состав → поверхности → реестр → права → жизненный цикл → сценарии → API → валидация → ошибки → чек-лист автора → конфигурация → безопасность → инварианты → чек-лист тестирования → границы → расхождения. Разделы, которых у пакета нет (модель данных, миграции, экраны админки), выпали — и это само по себе характеристика: tools/server не владеет ни таблицей, ни маршрутом, ни экраном.

Источник — исходный код: packages/tools/server/src/** целиком, оба потребителя (packages/mcp/server, packages/copilot/server/src/lib/chat), четырнадцать классов-провайдеров в семи прикладных пакетах, docs/adr/0006 и docs/adr/0007, юниты пакета и кросс-поверхностный набор apps/server-e2e/src/server/tools/tool-registry.spec.ts. Файлы AGENTS.md использованы как каркас, но каждое утверждение сверено с реализацией — расхождения вынесены в раздел 17.
