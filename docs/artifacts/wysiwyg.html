WYSIWYG Не место в приложении, а поведение одного типа поля

WYSIWYG — это редактор форматированного текста для админки OrthaCMS. У него нет ни маршрута, ни пункта навигации, ни собственного экрана: весь его внешний контур — одна контрибьюция в слот ENTRY_FIELD_CONTROL_SLOT плагина content-admin. В форме записи поле типа richtext показывает содержимое так, как оно читается, а нажатие разворачивает редактор TipTap в рабочую область записи — не диалогом поверх формы, а подменой контента вкладок, так что шапка записи, кнопки Save/Publish и правая панель свойств остаются живыми.

01Бизнес-описание

Пакет @orthacms/wysiwyg-admin отвечает на один вопрос: как редактор пишет тело записи. Всё остальное в CMS — типы контента, права, публикация, публичный API — уже существует и без него; без него поле richtext просто рендерится обычной текстовой областью с HTML-разметкой внутри. Именно этот вариант плагин и заменяет.

Какую задачу решает

  • Текст вместо тегов. Тело статьи в <textarea> — это стена разметки, которую невозможно вычитать. Свёрнутое поле показывает содержимое: заголовки заголовками, списки списками, картинки картинками — а сама поверхность письма спрятана за осознанным нажатием.
  • Редактирование не выкидывает автора из записи. Развёрнутый редактор — это вид, а не модальное окно. Он занимает рабочую область вместо полосы вкладок, а вокруг всё остаётся на месте: боковое меню приложения, заголовок записи, кнопки сохранения и публикации, панель свойств справа, у которой индикатор готовности к публикации пересчитывается прямо по мере набора текста.
  • Доступность как часть авторского инструмента, а не как аудит после. Под документом живёт список структурных замечаний (пропущенный уровень заголовка, таблица без шапки, ссылка «подробнее», непарсибельный языковой тег). Правила берутся из общего ядра — те же самые, что откажут в сохранении на сервере, — поэтому список не «второе мнение», а ровно то, что произойдёт при Save.
  • Содержимое остаётся переносимым. Свои узлы сериализуются в семантический HTML с data--атрибутами (<aside data-callout data-tone="warning">, <div data-columns="3">), без единого имени класса из админки. Оформление на публичном сайте — дело сайта.
  • Ноль связанности с медиатекой. Редактор умеет держать картинку и видео, но ничего не знает про библиотеку файлов. Кто умеет — тот и заполняет объявленный слот.

Кому это видно

Автор / редактор

Видит поле с готовым текстом и чипом «Edit». Нажимает — попадает в редактор с курсором в конце документа. Пишет, форматирует, вставляет картинку из медиатеки, возвращается кнопкой «Back to fields» или «Done». Своего сохранения у редактора нет — Save у записи один.

Читатель без прав на изменение

Видит тот же чип, но «View» и с иконкой глаза. Разворачивание сохраняется — это единственное поле, которое свёрнутая строка формы физически не может показать целиком, — но открывается оно без тулбара, без каретки и без автофокуса.

Автор схемы контента

Не делает ничего: редактор берёт каждое поле richtext по умолчанию. Отказаться можно точечно — admin: { widget: 'textarea' } для тела, которое правят как разметку нарочно (шаблон письма, вручную поддерживаемый фрагмент).

Чем плагин не является

  • Это не страница. Ни routes, ни nav, ни layout в фабрике WysiwygPlugin() нет — только slots. Его нельзя «открыть», к нему нельзя дать ссылку.
  • Это не серверный плагин. В группе packages/wysiwyg ровно один пакет — admin. Ни таблиц, ни миграций, ни маршрутов API, ни изменений в проводном формате.
  • Это не тип поля. richtext существует в @orthacms/content-domain и @orthacms/content-server независимо; плагин меняет контрол, а не схему, не валидацию и не колонку.
  • Это не медиатека. Просмотр папок, фильтрация по типу и загрузка — целиком работа @orthacms/media-admin, которая приходит в объявленный слот снаружи.
  • Это не правила доступности. Правила (inspectRichText, isWellFormedLanguageTag, isEmptyRichText) живут в ядре content-domain; плагин их только показывает и им подчиняется.
Ключевая идея архитектуры

Значение поля — документ (дерево узлов ProseMirror/TipTap), а не строка HTML (ADR-0011). Из этого следует всё остальное: maxLength считает слова, а не теги; порядок заголовков и шапки таблиц становятся проверяемыми фактами; предпросмотр в админке безопасен, потому что его собирают заново из схемы редактора, а не вставляют чужую разметку в DOM.

2.1 Куда он подключается

В apps/admin/src/plugins.ts WysiwygPlugin() стоит после ContentPlugin(), чей слот он заполняет. Порядок здесь — выражение намерения, а не требование: слоты — модульные синглтоны, и createAdmin регистрирует контрибьюции всех плагинов до первого рендера. Что от позиции действительно зависит — порядок элементов внутри слота: ENTRY_FIELD_CONTROL_SLOT резолвится через find, то есть первый подошедший элемент выигрывает в порядке регистрации.

2.2 Какие поля он забирает

Предикат isWysiwygField буквально в две строки:

function isWysiwygField(field: ContentField): boolean {
    if (field.type !== CONTENT_FIELD_TYPE.RichText) return false;
    return field.admin['widget'] !== WYSIWYG_WIDGET.Textarea;
}

То есть каждое поле richtext — по умолчанию, без opt-in. Обоснование прямое: opt-in оставил бы сырой textarea на всех схемах, написанных до появления плагина. Отказ — по полю, в схеме контента: field.richtext({ admin: { widget: 'textarea' } }). Значение 'wysiwyg' тоже принимается — чтобы схема могла заявить намерение, а не полагаться на умолчание. widget в AdminProps типизирован как свободная строка, так что оба значения — конвенция этого плагина, а не enum на сервере.

Бандл: TipTap не должен попасть в entry-чанк

Фабрика плагина выполняется на старте — иначе её контрибьюция не успеет зарегистрироваться до первого рендера, — поэтому всё, что она импортирует статически, оказывается в стартовом чанке приложения. TipTap и ProseMirror — это ~460 кБ ради контрола, который живёт только внутри редактора записи. Отсюда два правила: обе половины берутся через React.lazy, а src/index.ts не реэкспортирует ни предпросмотр, ни редактор. Документация называет контрольную цифру: entry-чанк админки ~255 кБ (было ~254 кБ до плагина), TipTap отдельно в editorExtensions-*.js ~420 кБ, разворачивание поля докачивает ~39 кБ. Сдвинулось первое число — граница ленивости сломана.

03Формат документа: почему дерево, а не HTML

ADR-0011 («Rich text is a structured document, not an opaque string», статус Proposed, 19.08.2026) описывает решение, которое в коде уже реализовано целиком. До него значение richtext было строкой HTML в колонке text, а ядро валидировало его как typeof === 'string' плюс длина и pattern. Это делало семантику тела немоделируемой и потому непроверяемой: вот это проходило валидацию начисто —

validateFieldValue('body', { type: 'richtext', required: true },
  '<h4>Intro</h4><h1>Title</h1><table><tr><td>a</td></tr></table>')
// → []

Пропущенный уровень заголовка, перевёрнутая структура и таблица без шапки — три вещи, которые пользователь скринридера встречает как сломанный документ, и платформа не могла назвать ни одну из них ошибкой (WCAG 1.3.1, 2.4.6, Section 508 504.2). Плюс два следствия той же категориальной ошибки: maxLength считал разметку (выделение слова жирным тратило <strong></strong> из бюджета автора), и язык фрагмента (3.1.2) негде было выразить.

3.1 Что теперь считается значением

  • Документ — дерево { type: 'doc', content: [...] }, то самое, что отдаёт editor.getJSON(). Хранится в jsonb-колонке (table-builder.ts: case CONTENT_FIELD_TYPE.RichText: builder = jsonb(col)).
  • Строка HTML — тоже валидное значение. Миграция была USING to_jsonb(col), то есть старое тело стало JSON-строкой в той же колонке. Ничего не парсилось — значит, ничего не могло потеряться.
  • null — отсутствие тела. Именно в это схлопывается пустой документ на выходе из редактора (normalizeRichText).
Апгрейд по мере редактирования, а не пакетной миграцией

Старое HTML-тело превращается в документ ровно тогда, когда запись в следующий раз сохранят из редактора: asEditorContent отдаёт строку TipTap, тот парсит её своей собственной схемой, и первый же onUpdate кладёт в форму дерево. Пакетная миграция отвергнута сознательно: конвертация HTML требует решить, что означал каждый неизвестный тег, а единственный парсер, который знает, что эта инсталляция умеет представлять, — схема самого редактора.

3.2 Словарь: что редактор умеет записать

Словарь ядра (RICH_TEXT_NODE, RICH_TEXT_MARK) открыт: он называет то, о чём ядро рассуждает, а не то, что документу разрешено содержать. Расширение редактора (коллаут, колонки, встраивание) проезжает сквозь него нетронутым — закрытый словарь сделал бы ядро привратником каждого плагинного набора расширений. Набор, который производит именно этот редактор, складывается из StarterKit, TableKit и четырёх собственных расширений:

3.3 Что валидно и кто это решает

Валидатор ядра (validate-entry-values.ts) для richtext делает ровно четыре вещи:

  1. Пустота считается по документу, а не по JSON. isEmptyRichText, а не общий isEmpty: { doc: [paragraph] } — это то, что оставляет опустошённый редактор, и required обязано на этом упасть.пусто — значит: doc, paragraph, hardBreak, text (только пробелы), container. Всё прочее — содержимое
  2. Форма значения. Не строка и не документ → must be a rich-text document.
  3. Длина и pattern — по тексту. richTextPlainText(value): границы блоков дают перевод строки, разметка не даёт ничего. Длина считается в воспринимаемых человеком символах, а не в кодовых единицах UTF-16.
  4. Структурная проверка — inspectRichText, если поле не отключило её через validation: { structure: 'off' }. Валидацию валит только severity error.

3.4 Что из этого следует наружу

Публичный API и GraphQL

REST отдаёт дерево как есть; в OpenAPI поле описано как oneOf из RichTextDocument и строки. В GraphQL тип поля — JSON, а не String: ломающее изменение для потребителя, который рассчитывал на строку. Зато потребитель получает дерево, которое рендерит как хочет, вместо разметки, которую обязан санировать.

Фильтрация, сортировка, поиск

richtext не фильтруется и не сортируется (scalarTypeFor возвращает null): equals над документом сравнивал бы сериализации деревьев, а не прозу. Свободный ?search= до тела доходит — колонка кастуется ::text и ищется по сериализованному дереву; цена в том, что запрос со словом paragraph может попасть в тело, которое его не произносит. В списке записей richtext-колонка по умолчанию выключена (HEAVY_TYPES).

Перенос (export / import)

В JSON/NDJSON дерево едет как есть. В CSV ячейка — это richTextPlainText, то есть текст без разметки: то, с чем работает переводчик. Обратно каждая строка ячейки становится абзацем (htmlToRichTextDocument над <p>…</p>) — то есть CSV-круг лоссиный по форматированию и это осознанно.

Контрол-запасной вариант

Поле с widget: 'textarea' рендерится обычной областью, и content-admin сериализует документ в HTML на входе в неё (asRichTextSource → richTextToHtml), а обратно отдаёт строку — которая остаётся валидным значением. То есть переключение виджета не ломает данные, но обратный путь лоссиный: сохранение из textarea превращает документ в строку.

04Инвентарь возможностей редактора

Панель — это role="group" с именем «Formatting», а не role="toolbar". Паттерн ARIA toolbar обещает навигацию стрелками с одной точкой табуляции; пообещать и не реализовать — значит завести пользователя скринридера в пустоту. Как группа, каждый контрол — обычная точка табуляции.

Панель обязана помещаться в одну строку. Это ограничение, а не случайность: рабочая область уже, чем окно (примерно 620px при вьюпорте 1280px — слева меню приложения, справа панель свойств), а перенос на вторую строку сдвигает документ вниз и превращает всё, что уехало, в приписку. Отсюда состав: впереди остаётся то, до чего тянутся посреди фразы, остальное свёрнуто в меню, сгруппированные по роду действия. Бюджет — около 40px: добавить контрол на панель значит снять другой. flex-wrap оставлен запасным вариантом на действительно узкое окно — переносить плохо, обрезать хуже.

Автор, которому строка была нужна, в ней печатает — строка перестаёт быть пустой, и добавление снова взводится.

4.3 Две общие формы контролов

ToolbarButton

Иконка декоративна, имя несёт aria-label, он же текст тултипа — так кнопка не может читаться одним, а озвучиваться другим. Переключатель передаёт active, что даёт и aria-pressed, и заливку: состояние не должно передаваться одним лишь цветом. Простое действие (undo, вставить таблицу) active не передаёт вовсе — «нажато» было бы враньём.

ToolbarMenuTrigger

Иконка, необязательное текущее значение, шеврон. Рендерится через asChild из DropdownMenuTrigger/PopoverTrigger, поэтому пробрасывает ref и все пропсы Radix.

Правило, которое ломается тише всего

Обе формы кнопок обязаны делать preventDefault на mousedown. Иначе нажатие на контрол уносит фокус из редактора и схлопывает выделение, над которым команда собиралась работать, — та самая классика «выделил слово, нажал Bold, ничего не произошло». Клик при этом происходит; подавляется только перенос фокуса. То же самое делает чип alt-текста на картинке — без этого mousedown снимает выделение с узла и уносит сам чип раньше, чем долетит клик.

4.4 Как подписываются на состояние редактора

Каждое меню читает свой срез через useLiveEditorState, а не общий селектор панели, — иначе панель стала бы единственным местом, через которое перерисовывается всё. Обёртка существует из-за StrictMode: каждый useEditor монтируется, разрушается и монтируется снова, а подписка мёртвого экземпляра успевает выполнить селектор последний раз. can().undo() или storage.characterCount.words() на уничтоженном редакторе бросают исключение во время рендера, React разматывает всё поддерево — и тулбар, до которого автор тянулся, просто исчезает. Обёртка возвращает переданное значение whenGone ровно на этот кадр («ничего не активно, ничего невозможно» — правда про несуществующий редактор).

4.5 Вставка из буфера

transformPastedHTML вырезает из вставляемого HTML три свойства — color, font-size, background-color. Обоснование в самом файле: инлайновый цвет, выбранный из палитры тулбара, — это содержимое и остаётся. Вставка — не выбор: никто не открывал меню цвета и обычно даже не заметил. Измерено на живом стенде (ORT-164): Word отдаёт <span style="color: rgb(192,0,0); font-size: 14pt;">, Google Docs штампует color: rgb(0,0,0); font-size: 11pt практически на каждый прогон текста — то есть тело, вставленное из Docs, теряло собственную типографику сайта на всю запись. Обрабатывается только путь буфера обмена; команды тулбара идут мимо. Разбор через DOMParser, а не регуляркой по style="…": там бывают кавычки, запятые в url() и экранирование, и ошибка здесь портит авторский текст, а не просто промахивается. Элемент, у которого style опустел, теряет атрибут целиком.

05Сценарии по шагам

5.1 Как редактор открывается

Ключевой переход всего плагина: из строки формы — в вид, занимающий рабочую область. Ни одного сетевого запроса на этом пути нет.

  1. Форма рисует строку поля. EntryFieldInput до switch по типу поля спрашивает ENTRY_FIELD_CONTROL_SLOT: есть ли элемент, чей appliesTo берёт это поле. Метка, обязательность, значок «Changed», описание и сообщение об ошибке остаются за content-admin — контрибьютор рисует только саму поверхность ввода.первый подошедший элемент выигрывает, в порядке регистрации
  2. Грузится чанк контрола. LazyWysiwygFieldControl под Suspense; заглушка — Skeleton высотой h-24, специально соразмерная свёрнутому предпросмотру, чтобы форма не прыгнула вверх и обратно.
  3. Значение превращается в HTML предпросмотра. WysiwygPreview → renderRichText(value), мемо по сырому значению: перерисовка формы на каждое нажатие в любом другом поле не должна заново разбирать неизменившийся документ.
  4. Карточка собирается из трёх слоёв. Содержимое (min-h-40, при непустом теле — max-h-72 с градиентной затухающей полосой понизу, чтобы обрез читался как продолжение, а не как обрыв фразы); прозрачная кнопка absolute inset-0; чип «Edit» с карандашом в правом верхнем углу (aria-hidden, чисто визуальный).кольцо фокуса рисует не кнопка, а карточка — has-[button:focus-visible]:ring-2
  5. Автор нажимает — куда угодно по карточке. Единственное, что делает контрол: setExpanded(true). Своего состояния у него нет.
  6. EntryEditor подменяет содержимое рабочей области. Он держит expandedFieldName, находит поле среди generalFields, находит в слоте элемент с FullView — и рендерит его вместо полосы вкладок. Заголовок записи остаётся сверху, боковое меню, кнопки Save/Publish в верхней панели и панель свойств справа не трогаются вовсе: развёрнутый вид находится внутри той же формы записи. Одновременно развёрнутым может быть одно поле; разворачивание второго сворачивает первое.если после смены локали поле исчезло из схемы, имя сбрасывается, и вкладки возвращаются сами
  7. Собирается контекст развёрнутого вида. Тот же EntryFieldControlContext, но без describedBy: <FieldError>, на который он бы указывал, принадлежит строке формы, а её на экране нет. Зато передаётся contentLocale — строка формы наследовала lang от обёртки группы Translated, а развёрнутый вид рендерится вне неё.
  8. Монтируется панель редактора. useEditor с расширениями, засеянный asEditorContent(value) один раз: вид смонтирован только пока поле развёрнуто, поэтому редактор владеет своим состоянием и никакой синхронизации управляемого содержимого нет — а значит, нет и прыжков каретки, которые с ней приходят.
  9. Фокус ставится в конец документа (autofocus: 'end'). Автор нажал поле, чтобы продолжать писать; оставлять фокус на кнопке, которая только что исчезла, — потерять его.

5.2 Как правки попадают в запись

  1. Каждая транзакция вызывает onUpdate. Первым делом — if (readOnly) return: editable: false и так отвергает транзакции, но это единственная строка, которая пишет в запись.
  2. Берётся getJSON(), а не getHTML(). Хранимое значение — документ; именно это делает порядок заголовков, шапки таблиц и языковые маркеры проверяемыми, а не символами в непрозрачной строке.
  3. Нормализация. normalizeRichText: пустой документ схлопывается в null, содержательный отдаётся дословно — эта функция никогда не переписывает настоящий документ.
  4. Запись в форму через onChange слота — ровно так же, как набор в любом другом поле. Поле помечается «изменённым», индикатор публикации в панели свойств пересчитывается на лету.onChange держится в ref: форма отдаёт новый колбэк на каждый рендер, а TipTap захватывает опции при создании редактора
  5. Своего Save у редактора нет. Единственная граница коммита — Save самой записи, вместе со сторожем несохранённых изменений. Поэтому выход из вида любым способом не может потерять работу.

5.3 Как редактор закрывается

  1. Два явных выхода: «Back to fields» вверху вида и «Done» в футере панели. Оба зовут один и тот же collapse.
  2. Escape намеренно не назначен. Меню и попроверы тулбара отвечают на Escape сами; второй обработчик на виде гонялся бы с ними и закрывал бы весь редактор из-под открытого меню.
  3. setExpanded(false) — EntryEditor возвращает полосу вкладок.
  4. onBlur?.() — форме это значит «поле тронуто», то есть с этого момента обязательное поле имеет право пожаловаться.
  5. Фокус возвращается на кнопку поля. Фокус не следует за удалённым элементом — браузер роняет его на <body>, и автор, нажавший «Done» с клавиатуры, оказывается нигде. Поэтому requestAnimationFrame и getElementById(id)?.focus(): кнопка несёт id поля, а строка формы появится лишь кадром позже (WCAG 2.4.3).

5.4 Как вставляется изображение или видео

  1. Insert ▸ Media. Подменю перечисляет сначала контрибьюции слота (в порядке order), затем разделитель, затем два встроенных пункта — «Image from a URL…» и «Video from a URL…». Пункты меню только открывают; ничего не рисуют.
  2. Источник открывается там, где смонтирован. Все Source и оба диалога смонтированы тулбаром, а не пунктом меню: DropdownMenuContent размонтируется ровно в тот момент, когда пикер должен появиться, и диалог открылся бы в разбираемое дерево. Источник живёт всё время жизни редактора и получает open.
  3. Источник отдаёт WysiwygMediaEmbed[] — URL плюс метаданные показа (kind, src, необязательные alt и width), а не ассет библиотеки. Именно это позволяет одному типу узла обслуживать и выбор из библиотеки, и загрузку, и напечатанную вручную ссылку. Вызов onInsert не закрывает источник — сценарий «вставил и продолжил листать» остаётся возможным.
  4. Команда insertMedia фильтрует. Всё, чей src не проходит isSafeMediaSrc, пропускается, а не сохраняется сломанным узлом. Затем отсекается тип, которого нет в схеме этого редактора (иначе вставка упала бы на неизвестном имени узла). Пусто на выходе — команда возвращает false.
  5. Узел появляется у каретки с width, если источник знал натуральную ширину и она не меньше 64px, иначе width: null.
  6. Дальше правится на месте: ручка размера, чип alt-текста, меню Alignment (которое само переключилось на setMediaAlign, потому что выделен медиа-узел).
Почему «по URL» встроено, а библиотека — нет

Диалогу «from a URL» не нужно ничего: ни библиотеки, ни эндпоинта загрузки, ни плагина. Он — то, что позволяет инсталляции без медиа-плагина вообще положить картинку в тело, и честный ответ для ассета, который действительно живёт в другом месте (CDN, сайт партнёра). Его текст это и говорит: «The file stays where it is — nothing is copied into the Media Library». URL проверяется дважды: диалогом — чтобы объяснить, почему ничего не произошло, и узлом при вставке и при разборе — и вот это уже защита сохранённого содержимого.

5.5 Как вставляется таблица и колонки

  1. Insert ▸ Table ▸ Insert table — сразу 3×3 со строкой шапки. Это единственный способ создать таблицу в этом редакторе, и он всегда строит строку-шапку — потому scope="col" и корректен для каждой <th>, которую редактор способен произвести (шапка-столбец потребовала бы переключателя, которого нет, и scope="row" вместе с ним).
  2. Пока каретка вне таблицы, подменю показывает один живой пункт. Десять серых строк читать труднее, чем одну живую, поэтому пункты правки скрыты, а не заблокированы.
  3. Insert ▸ Columns ▸ 2/3/4. Вне раскладки — вставляется новый columnBlock, каждая колонка засеяна пустым абзацем (схема column{2,4} отвергает пустой блок).
  4. Внутри раскладки то же меню её перестраивает. Рост — добавляются пустые колонки; сжатие — блоки отбрасываемых колонок переезжают в последнюю оставшуюся. data-columns, прочитанный из чужой разметки, зажимается в диапазон 2..4: рукописное data-columns="wide" иначе стало бы NaN и утащило бы за собой grid-template-columns.
  5. «Merge back to one column» разворачивает раскладку, выкладывая блоки всех колонок в порядке чтения. Это не lift: тот снял бы один уровень, а здесь их два.
  6. Внутри колонки Backspace не сливает соседей — узел column объявлен isolating. Без этого Backspace в начале колонки утягивал бы её в последний абзац предыдущей, и раскладка тихо разваливалась.

5.6 Как открывается тело, написанное до перехода на документ

  1. В колонке лежит JSON-строка — старое HTML-тело, которое миграция перенесла как есть.
  2. Свёрнутое поле его уже показывает: renderRichText для строки идёт «строчным путём» — DOMParser в инертный документ, разбор схемой ProseMirror, повторная сериализация.
  3. При разворачивании asEditorContent отдаёт строку TipTap, и тот парсит её собственной схемой — сохраняя всё, что этот редактор умеет представить, и ничего, чего не умеет.
  4. Первый же onUpdate кладёт в форму дерево. Конверсия фиксируется при следующем сохранении записи: контент апгрейдится по мере редактирования.
  5. Марка language при этом переживает круг: её parseHTML заявляет span[lang] — но только тот span, который действительно называет язык, иначе безусловное правило проглотило бы каждый textStyle-span и превратило цвета в пустые языковые марки.

06Стык с media и с content

6.1 Инверсия зависимости: media → wysiwyg

Редактор умеет держать картинку и видео и знает один способ их назвать — вставить URL. Про медиатеку он не знает ничего, и это решение: импорт media-admin сделал бы форматированный текст неработоспособным в инсталляции без медиа-плагина и навсегда прибил бы редактор к форме одной конкретной библиотеки. Включён multiple: положить три картинки подряд — нормальное дело. accept редактора передаётся пикеру как его собственное ограничение, так что аудиофайл или PDF отфильтровываются из сетки, а не оказываются выбираемыми и потом молча отброшенными.

Upload files… order 20

Файлы уходят в медиатеку, а потом ставятся в текст — не data-URI и не «вложение записи». Для изображения берётся previewUrl (производная ~1280px), а не оригинал: телу на странице 12-мегапиксельный JPEG не нужен, и производная именно для этого и сделана; запасной вариант — url, он покрывает SVG и мелкие картинки без производных. Видео всегда идёт по url — производных для видео нет. Собственный alt ассета едет вместе с ним, чтобы автор, написавший его один раз в библиотеке, не писал заново в каждом теле. Для чего у редактора нет узла (аудио, PDF, архив) — возвращается null: пикер такое и так отфильтровал, но это вторые ворота.

6.3 Проверка src: что вообще может попасть в тело

const ALLOWED_PROTOCOLS = new Set(['http:', 'https:']);

export function isSafeMediaSrc(src: unknown): src is string {
    if (typeof src !== 'string') return false;
    const value = src.trim();
    if (value === '' || value.startsWith('//')) return false;
    // Корневой или относительный путь — схемы нет, проверять нечего.
    if (!/^[a-z][a-z0-9+.-]*:/i.test(value)) return true;
    try {
        return ALLOWED_PROTOCOLS.has(new URL(value).protocol);
    } catch {
        return false;
    }
}
  • Свой путь разрешён и это не любезность, а основной случай: медиатека отдаёт ассеты с /api/media/assets/…, и сохранённый абсолютный URL прибил бы содержимое к тому хосту, на котором в тот момент был автор.
  • Протокол-относительный //host/… отвергается: он наследует схему потребителя, а за неё этот редактор поручиться не может.
  • Разбор при вставке в узел строже, чем при вводе: parseHTML у image и video отказывает узлу целиком, а не импортирует его с обнулённым src, — картинка без источника в теле выглядит как потеря данных.

6.4 Граница доверия предпросмотра

Значение richtext — это то, что напечатал, вставил или записал прямо через API какой-то другой пользователь CMS, а предпросмотр рендерит его как разметку. Отдать такую строку в dangerouslySetInnerHTML без проверки — сделать каждое поле форматированного текста вектором хранимого XSS против любого, кто откроет запись: <script> через innerHTML не выполняется, а <img src=x onerror=…> выполняется, и контрибьютор мог бы нацелить его на администратора.

  1. Документ пересобирается из JSON схемой самого редактора (ProseMirrorNode.fromJSON). Схема строится один раз и кэшируется — она зависит только от набора узлов и марок, но не от плейсхолдера поля.
  2. Легаси-строка разбирается из инертного документа DOMParser: он не грузит ресурсов и не выполняет скриптов — именно это делает безопасным само прикосновение к входным данным.
  3. Результат сериализуется заново из полученных узлов. Выживает только то, что объявлено схемой: обработчики событий отброшены, а расширение Link обнуляет любой href вне своего списка протоколов (javascript:). Список разрешённого — это то же самое определение, что «что этот редактор умеет написать», поэтому предпросмотр в точности равен тому, что автор увидит, развернув поле. Рукописный список тегов был бы вторым определением, свободным разъехаться.
  4. Документ с узлом, которого у этой инсталляции нет (написан через API или другим развёртыванием с лишним расширением), пересобрать нельзя. Тогда — откат на ядровый richTextToHtml и строчный путь: то, что редактор понимает, всё равно отрендерится, вместо пустой карточки.
  5. Ссылки уплощаются в <span data-link>. Единственное намеренное отличие от редактора — и условие, при котором кнопку вообще можно класть поверх: в предпросмотре не остаётся ни одного фокусируемого элемента.
Правило для любого нового места

Добавили узел или марку в editorExtensions — предпросмотр поддерживает их в тот же день. Понадобилось отрендерить форматированный текст где-то ещё — только через renderRichText, и никогда innerHTML по сырому значению. И не «чините» уплощение ссылок: живая <a> под кнопкой — это точка табуляции, в которую читатель провалится по дороге к ней, а нажатие уведёт его из записи.

6.5 Стиль: одна область видимости на редактор и предпросмотр

src/styles.css (429 строк) целиком висит на .ortha-wysiwyg, который несут и поверхность редактора, и каждый предпросмотр. Хост импортирует его один раз, после дизайн-системы. Почему таблица стилей, а не Tailwind-классы на компонентах — две причины. Большинство этих элементов производит ProseMirror из сохранённого содержимого, и JSX, на который можно повесить className, просто нет; альтернатива — вшить имена классов админки в renderHTML, то есть записать оформление этого приложения в содержимое, которое публикуется в другом месте. И редактор с предпросмотром обязаны рендериться одинаково — общая область видимости делает это структурным свойством, а не тем, что надо поддерживать в согласии.

Цвета берутся из --color-* темы приложения, поэтому редактор следует светлой и тёмной. Цвета, выбранные автором (цвет текста, подсветка), лежат инлайново на содержимом и остаются как есть — это содержимое, а не оформление. Тот же принцип в своих узлах: коллаут сериализуется в <aside data-callout data-tone>, раскладка — в <div data-columns>, а потребляющий сайт оформляет структуру как хочет. Две вещи в стилях есть только у редактируемой поверхности (обе через селектор [contenteditable]): минимальная высота пустой колонки и пунктирный контур вокруг раскладки — предпросмотр должен показывать раскладку, а не строительные леса вокруг неё.

6.6 Почему медиа не выравнивается через text-align

@tiptap/extension-text-align настроен на heading и paragraph — и добавить в этот список медиа-узлы не сработало бы: text-align позиционирует строчных детей блока, а изображение и есть блок. Свойство садится на <img> и не двигает ничего — так и выглядело «выравнивание по центру ничего не делает с выделенной картинкой». Поэтому медиа несёт собственный атрибут align, хранится как data-align и двигается отступами в таблице стилей. Именно data-, а не давно устаревший align="center" и не инлайновый style, — по той же причине, что и width: атрибут переживает санитайзер шаблона или почтового клиента. left не записывается никогда — это и так место, где блок стоит.

AlignMenu при этом остаётся одним контролом, потому что для автора это одно решение: он переключается на setMediaAlign, как только выделение стоит на медиа-узле, и на это время убирает из списка «Justify» (выключка растягивает слова строки, а у картинки слов нет). Фигура, которую рисует node view, имеет width: fit-content, пока автор не выбрал ширину (data-sized): иначе неразмеченная картинка растягивалась бы на всю меру в редакторе, а предпросмотр показывал бы её натуральный размер — и центрировать было бы нечего, блок и так занимает строку.

07Состояния

У плагина нет собственных сетевых запросов — ни хука данных, ни ключа кэша, ни клиента API. Поэтому и «загрузка» здесь означает только загрузку кода, а «ошибка» — валидацию формы, а не отказ сервера. Единственные сетевые операции на его территории принадлежат контрибьюциям медиа-плагина.

Почему read-only не «просто заблокировать поле»

Каждое другое поле записи в режиме чтения просто становится инертным на месте. Тело не может: свёрнутый предпросмотр обрезан по высоте, с затуханием на срезе, — и читатель, которому разрешено читать запись, оказался бы не в состоянии прочитать самую важную её часть. Поэтому контрол сохраняется и только переименовывается.

Счётчик слов в режиме чтения считается иначе

useEditorState обновляет снимок только по событиям transaction/update, а первый снимок берётся до того, как начальное содержимое устоялось. При редактировании это невидимо: autofocus: 'end' даёт транзакцию на монтировании, дальше их даёт каждое нажатие. У read-only редактора нет ни того, ни другого — editable: false отвергает все транзакции, — и подписка навсегда осталась бы на первом пустом снимке, а футер показывал бы «0 words · 0 characters» над полным документом. Поэтому в этом режиме счётчики читаются прямо с редактора, а не ждут события, которое не придёт.

08Доступность и клавиатура

Section 508, критерий 504.2, спрашивает не о том, доступен ли сам инструмент, а о том, позволяет ли авторский инструмент производить соответствующее требованиям содержимое. Это объясняет половину решений в этом пакете: список структурных замечаний под документом, чип «Add alt text» на картинке, диалог языка фрагмента, scope="col" на каждой <th>.

8.1 Свёрнутое поле

  • Кнопка стоит рядом с предпросмотром, а не оборачивает его. Обернуть форматированное содержимое в <button> — значит положить внутрь контрола заголовки, списки и таблицы (невалидно) и сплющить всё тело в доступное имя кнопки. Вместо этого предпросмотр рендерится обычным содержимым, а прозрачная кнопка кладётся поверх: вспомогательные технологии читают содержимое, потом получают одно ясно названное действие, а указателем по-прежнему можно нажать куда угодно по карточке.
  • Имя задаётся aria-label, а не скрытым текстом. Кнопка несёт id поля — на неё указывает <label for> из content-admin, — а нативная метка перебивает собственное содержимое кнопки, из-за чего та объявлялась просто «Body», без намёка, что нажатие что-то открывает. aria-label перебивает метку в свою очередь и содержит видимый текст метки, так что имя совпадает с тем, что произнесёт пользователь голосового ввода (2.5.3).
  • Нет aria-haspopup: нажатие переводит рабочую область на редактор, а не открывает всплывающее окно поверх неё.
  • В предпросмотре нет фокусируемых элементов — иначе они были бы точками табуляции, спрятанными под кнопкой.

8.2 Развёрнутый редактор

  • Секция названа заголовком поля (<section aria-labelledby> + <h2> с меткой и словом «Required», если поле обязательное).
  • Язык строки, если поле локализовано: lang={field.localized ? contentLocale : undefined}. Свёрнутый предпросмотр наследовал lang от обёртки группы Translated; развёрнутый вид рендерится вне неё, и цепочка обрывалась бы здесь — немецкое или арабское тело озвучивалось бы по английским правилам под захардкоженным <html lang="en"> (3.1.2). Для общего (нелокализованного) поля язык не заявляется вовсе: одно значение на все локали, и заявить локаль строки было бы худшим утверждением, чем не заявлять ничего.
  • dir="auto", а не направление локали — как и в форме: порядок берётся по первому сильному символу тела, что верно для RTL-локали и остаётся верным для RTL-цитаты внутри LTR-текста.
  • Поверхность документа — role="textbox", aria-multiline="true", aria-required, aria-label вида «{поле} content». Голый contenteditable-div не имеет роли вообще, и вспомогательным технологиям остаётся догадываться, что он редактируемый.
  • Замечания объявляются вежливо. aria-live="polite", aria-atomic="false" — и это не лог: находки меняются почти на каждое нажатие, пока заголовок перепечатывают, и читать каждое промежуточное состояние вслух значило бы говорить поверх автора непрерывно. Заголовок блока несёт число, поэтому изменение, которое действительно важно («проблем стало две, была одна»), объявляется первым.
  • Счётчик слов не объявляется: aria-live="off".
  • Список замечаний виден и в режиме чтения. Тело, которое читатель не может починить, — всё равно тело, о проблемах которого стоит знать, и это единственная поверхность, которая о них говорит.

Alt-попровер, попровер ссылки, диалог «from a URL» и диалог языка рендерят <form>, чтобы работал Enter. Все они портированы — перенесены в DOM, но не в дереве React, а React пузырит синтетические события именно по дереву. Поэтому submit каждого долетал до <form> редактора записи и сохранял-и-публиковал запись. Теперь каждый зовёт stopPropagation(), а форма content-admin дополнительно игнорирует submit, который подняла не она (if (event.target !== event.currentTarget) return). Закреплено e2e-случаем «never saves the record from an overlay's own form», который до исправления давал три сохранения — по одному на всплывающее окно. Любое новое всплывающее окно с формой в этом пакете обязано делать тот же вызов.

8.4 Alt-текст: почему «декоративное» — это галочка

alt="" — это то, как HTML говорит «изображение не несёт информации», но само по себе оно неотличимо от «никто ещё не написал», а этим двум нужно противоположное обращение: одно закончено, другое — дефект, на который редактор должен продолжать показывать. Поэтому ответ записывается атрибутом decorative (data-decorative в сохранённом HTML — инертный для любого потребителя, который его игнорирует), и приглашение опирается на него. Галочка также очищает alt: иначе скринридер озвучил бы текст, оставшийся за отмеченной галочкой. Поле ввода при этом отключается, а не прячется, — чтобы два выбора оставались видны как одно решение.

Одна намеренная асимметрия: внутри редактора картинка без alt всё равно получает запасное доступное имя («Embedded image»), иначе она читалась бы как безымянная графика собственному скринридеру автора, пока он работает. В сохранённый HTML уходит настоящее значение — пустое, если оно пустое: выдумывать alt для публикуемого содержимого хуже, чем не иметь его вовсе.

09Инварианты

Утверждения, которые обязаны выполняться всегда. Одновременно список для ревью и заготовка утверждений для тестов.

  • И-01Плагин не контрибьютит ни одного маршрута, пункта навигации и layout: в объекте, который возвращает WysiwygPlugin(), есть только name и slots.
  • И-02Редактор claim'ит каждое поле richtext, кроме тех, где admin.widget === 'textarea'. Никакого другого условия в isWysiwygField нет.
  • И-03src/index.ts не экспортирует ни предпросмотр, ни редактор, ни что-либо, что статически тянет TipTap; обе половины контрибьюции берутся через React.lazy.
  • И-04Предпросмотр никогда не рендерит сохранённую разметку как есть: значение всегда прогоняется через схему ProseMirror самого редактора (renderRichText), легаси-строка — через инертный DOMParser.
  • И-05В предпросмотре не остаётся ни одного фокусируемого элемента: ссылки уплощаются в <span data-link>. Это условие корректности кнопки, лежащей поверх.
  • И-06Кнопка свёрнутого поля несёт id поля и aria-describedby, но не aria-invalid и не aria-required.
  • И-07Разворачивание — это подмена содержимого рабочей области, а не диалог: боковое меню, заголовок записи, кнопки Save/Publish и панель свойств остаются смонтированы и работоспособны.
  • И-08Одновременно развёрнуто не более одного поля; состояние держит EntryEditor, контрол только просит.
  • И-09Панель редактора монтируется только пока поле развёрнуто, и засевается из значения один раз при монтировании; управляемой синхронизации содержимого нет.
  • И-10У редактора нет собственных Save и Cancel: каждая правка пишется в форму записи через onChange, и единственная граница коммита — Save записи.
  • И-11Пустой документ сохраняется как null, а не как документ с пустым абзацем; содержательный документ отдаётся форме дословно.
  • И-12Пустота определяется ядром (isEmptyRichText) как перечень того, чем пустота является (doc, paragraph, hardBreak, пробельный text, container), а не как отрицание списка «содержательных» узлов.
  • И-13Список замечаний под документом строится ядровым inspectRichText: error здесь — ровно то, что откажет в сохранении, warning — ровно то, что не откажет.
  • И-14Языковой тег проверяется ядровым isWellFormedLanguageTag, поэтому редактор не может принять тег, который потом отвергнет сохранение.
  • И-15Марка language — не textStyle: «Clear formatting» её не снимает.
  • И-16Каждая <th>, которую способен произвести этот редактор, несёт scope="col", и атрибут едет и в предпросмотр, и в опубликованное тело (задан через HTMLAttributes, а не переопределением renderHTML).
  • И-17Tab в последней ячейке таблицы добавляет строку однократно; повторное нажатие в оставшейся пустой строке проваливается дальше и выпускает фокус.
  • И-18Уменьшение числа колонок никогда не удаляет содержимое: блоки отброшенных колонок переносятся в последнюю оставшуюся.
  • И-19Число колонок всегда в диапазоне 2..4 — и при вставке, и при разборе чужой разметки (clampCount обрабатывает NaN).
  • И-20Второй выбор тона коллаута перекрашивает текущий, а не вкладывает коллаут в коллаут.
  • И-21src медиа-узла проверяется дважды — в диалоге (объяснить автору) и в узле, при вставке и при разборе (защитить сохранённое содержимое). Разрешены только http(s) и свои пути; протокол-относительный //host/… отвергается.
  • И-22Небезопасный embed пропускается, а не сохраняется сломанным узлом; <img> с недопустимым src не импортируется вовсе, а не импортируется с пустым src.
  • И-23Размер медиа хранится атрибутом width; высота не хранится никогда; ширина меньше 64px читается как «ширина не выбрана», а не зажимается вверх.
  • И-24Выравнивание медиа хранится в data-align и применяется отступами; значение left не записывается; в меню выравнивания для медиа нет пункта «Justify».
  • И-25Отметка «декоративное» очищает alt: одновременно непустой alt и data-decorative в сохранённом HTML невозможны.
  • И-26Внутри редактора картинка без alt получает запасное доступное имя; в сохранённый HTML уходит настоящее значение, в том числе пустое.
  • И-27Каждый <form> во всплывающем окне этого пакета вызывает stopPropagation() на своём submit; запись не сохраняется из всплывающего окна ни при каких условиях.
  • И-28Всякое всплывающее окно, которое открывается из выпадающего меню (источники медиа, диалог языка, диалоги «по URL»), монтируется тулбаром, а не пунктом меню.
  • И-29Каждый контрол тулбара делает preventDefault на mousedown, то есть нажатие никогда не схлопывает выделение, над которым команда работает.
  • И-30Ни один селектор состояния редактора не вызывается напрямую через useEditorState: все идут через useLiveEditorState, который на уничтоженном редакторе возвращает whenGone.
  • И-31В режиме readOnly тулбар не монтируется вовсе, onUpdate не пишет в форму, фокус не ставится, роль поверхности — region.
  • И-32Вставка из буфера теряет color, font-size и background-color; цвет, применённый командой тулбара, — не теряет.
  • И-33Слой domain/ не импортирует ни React, ни TipTap; node view медиа лежит рядом со своим расширением, чтобы infrastructure/ не импортировал вверх, в presentation/.
  • И-34Все правила стилей пакета висят на .ortha-wysiwyg: ни одно не может дотянуться до остальной админки, и поверхность редактора и предпросмотр рендерят одну и ту же разметку одинаково.
  • И-35В сохранённое содержимое не попадает ни одно имя класса админки: свои узлы сериализуются в data--атрибуты.
  • И-36Развёрнутый вид заявляет lang только для поля, помеченного localized, и никогда — для общего.
  • И-37Выход из развёрнутого вида возвращает фокус на кнопку поля (через requestAnimationFrame), а не роняет его на <body>.
  • И-38В editorExtensions нет второй копии расширения, которое уже принесено StarterKit (Link, Underline, TrailingNode): дубликат имени заставляет TipTap предупреждать и разрешать набор расширений непредсказуемо.

10Чек-лист тестирования

Формулировки — «действие → ожидаемый результат». Серверной части у пакета нет, поэтому проверка целиком браузерная; существующий набор — apps/admin-e2e/src/content/wysiwyg-fields.spec.ts (987 строк, 38 случаев в пяти группах, включая два скана axe). Отдельно важно: видимый редактор — только половина фичи, вторая половина — что именно уходит в тело запроса на сохранение, и это видно только по запросу. Запуск: npx nx e2e admin-e2e -- --project=chromium wysiwyg-fields.

Свёрнутое поле

  • Открыть запись с непустым телом → видно форматированное содержимое (заголовки заголовками, списки списками), а не текст с тегами.
  • Тело содержит ссылку → в предпросмотре нет ни одного элемента, на который можно встать табом; Tab с предыдущего поля попадает сразу на кнопку поля.
  • Тело пустое, у поля есть admin.placeholder → показан плейсхолдер, а не умолчание.
  • Тело пустое, плейсхолдера нет → «Nothing written yet — press Edit to start.»
  • Поле объявлено с widget: 'textarea' → рендерится обычная textarea content-admin, чипа Edit нет.
  • Тело длиннее клампа → карточка обрезана по max-h-72, снизу градиент; страница формы не растёт.
  • Тело содержит <img src=x onerror=alert(1)>, записанное через API → ничего не выполняется; в DOM предпросмотра нет ни onerror, ни любого другого обработчика.
  • Тело — документ с узлом неизвестного типа → карточка не пустая: понятные редактору части отрендерены.
  • Нажать в любое место карточки → открывается развёрнутый редактор.

Разворачивание и возврат

  • Развернуть поле → рабочую область занимает редактор, полосы вкладок нет, каретка уже в конце текста.
  • Осмотреть окружение развёрнутого редактора → боковое меню, заголовок записи, кнопки Save/Publish и панель свойств на месте и живые.
  • Измерить положения детей тулбара при вьюпорте 1280px → все контролы в одной строке; группировка по вертикальному центру, а не по top (панель items-center, и 32px-кнопка рядом с 20px-разделителем иначе читается как две строки).
  • Выйти кнопкой «Back to fields», затем повторить и выйти «Done» → оба возвращают форму; правки на месте в обоих случаях.
  • Нажать «Done» с клавиатуры → фокус на кнопке поля, а не на <body>.
  • Нажать Escape при открытом меню тулбара → закрывается меню; редактор остаётся развёрнутым.
  • Развернуть второе richtext-поле на той же записи → первое сворачивается.

Что уходит в сохранение

  • Набрать текст, применить bold/italic/цвет/размер, сохранить → в теле запроса — документ ({ type: 'doc', … }), марки с ожидаемыми атрибутами.
  • Вставить коллаут тона Warning, сохранить → узел callout с attrs.tone === 'warning'.
  • Вставить таблицу, сохранить → в документе есть строка с tableHeader-ячейками.
  • Выровнять абзац по центру, сохранить → textAlign на самом блоке, не на его детях.
  • Вставить раскладку из трёх колонок, сохранить → columnBlock count=3 с тремя вложенными column.
  • Вставить раскладку и НЕ печатать в неё, сохранить → раскладка сохранена, а не выброшена как «пусто».
  • Стереть всё содержимое, сохранить → в запросе null, а не документ с пустым абзацем.

  • Открыть запись с легаси-HTML-телом, тронуть, сохранить → в теле запроса — документ; открыть заново — содержимое то же на вид.

11.1 Чего в пакете нет — и это осознанно

  • Ни одного собственного HTTP-запроса и ни одного ключа TanStack Query. Всё, что он умеет, — синхронные операции над документом в памяти формы.
  • Никакой конфигурации. WysiwygPlugin() не принимает аргументов; тип WysiwygAdminPlugin — тонкий алиас AdminPlugin, названный отдельно, чтобы у будущей конфигурации (урезанный тулбар, своя палитра) было место.
  • Ни одной пользовательской настройки. Палитры, шаги размеров, тона коллаутов и число колонок зашиты в domain/constants.
  • Никакого автосохранения, черновиков и совместного редактирования. Единственная граница коммита — Save записи.
  • Ни загрузки картинок перетаскиванием в документ, ни вставки картинки из буфера. Медиа попадает в тело только через Insert ▸ Media.
  • Ни подписи к таблице (tableCaption), ни шапки-столбца. Ядро о подписи знает и принимает её как альтернативу шапке, но редактор её не производит.
  • Ни сносок, ни оглавления, ни якорей, ни встраивания записей CMS.

12.1 Наблюдения, не являющиеся расхождениями

  • Таблица без шапки — блокирующая ошибка, а обойти её можно только шапкой. Ядро принимает tableCaption как альтернативу, но редактор узла подписи не производит; значит, единственный доступный автору выход — «Toggle header row». Это работает, но объединяет два разных решения в одно.
  • widget — свободная строка. В AdminProps это widget?: string с комментарием «render hint, e.g. 'textarea', 'slug', 'color'». Ни сервер, ни ядро не знают о значениях 'wysiwyg'/'textarea' — это конвенция плагина, и опечатка в схеме тихо вернёт поле к WYSIWYG (потому что «не равно 'textarea'»).
  • Обратный путь через textarea лоссиный. Переключение поля на widget: 'textarea' не ломает данные (документ сериализуется в HTML для показа), но первое же сохранение из textarea запишет в колонку строку вместо дерева — то есть тело «разапгрейдится» обратно.
  • Ключ элемента списка замечаний — индекс. Осознанно и объяснено в коде: два одинаковых замечания различает только позиция, а список каждый раз выводится из документа заново и своего состояния не держит.

Артефакт по UI-плагину. Каркас серии адаптирован под пакет, у которого нет ни маршрутов, ни API, ни таблиц: бизнес-описание → состав и место → формат документа → инвентарь возможностей → сценарии → стыки → состояния → доступность → инварианты → чек-лист → границы → расхождения. Разделы «HTTP API», «Модель данных» и «Конфигурация» выпали за отсутствием предмета; их место занял главный здесь раздел — полный инвентарь того, что автор может написать, и того, что от этого окажется в сохранённом документе.

Источник — исходный код packages/wysiwyg/admin/** целиком, плюс docs/adr/0011-richtext-as-a-structured-document.md, модуль richtext/ и валидатор из packages/content/domain, контракт слота из packages/content/admin, контрибьюции из packages/media/admin и набор apps/admin-e2e/src/content/wysiwyg-fields.spec.ts. Файл AGENTS.md использован как каркас, но каждое утверждение сверено с реализацией — расхождения вынесены в раздел 12.
