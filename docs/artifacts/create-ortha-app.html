01Бизнес-описание

OrthaCMS поставляется как набор npm-пакетов, а не как готовое приложение. Само по себе это правильно — приложение собирается из плагинов, и состав решает владелец. Но у такой поставки есть цена: чтобы увидеть продукт, нужно сначала собрать его. Скаффолдер снимает эту цену полностью.

Какую задачу решает

  • Убирает нулевой день. Между «услышал про CMS» и «вижу админку у себя на ноутбуке» — одна команда, три коротких ответа и npm run dev. Никакого «сначала прочитайте, как устроен композиционный корень».
  • Даёт согласованный набор версий. Все @orthacms/* пакеты выпускаются в lockstep, и скаффолдер вписывает в манифест свою собственную версию в каждую зависимость. Приложение согласовано по построению, а не потому, что кто-то следил.
  • Показывает эталонную композицию. Сгенерированный plugins.ts — это не «пример», а рабочий композиционный корень с комментариями, объясняющими, почему порядок именно такой. Он же — учебник по добавлению своего плагина.
  • Делает выбор явным там, где он есть, и убирает его там, где его нет. Хранилище файлов, бэкенды копайлота, протоколы контент-API, вход через внешнего провайдера — четыре настоящих решения. Всё остальное — включая сам копайлот — ставится безусловно, потому что предлагать выбор там, где правильный ответ один, значит просить пользователя угадывать.
  • Ничего не включает молча. Оба «дорогих» решения — отправка контента внешней модели и открытие нового эндпоинта — по умолчанию выключены. Копайлот установлен, но COPILOT_ENABLED=false; MCP, если выбран, — MCP_ENABLED=false.

Первое впечатление, спроектированное намеренно

Оценивающий продукт

Хочет посмотреть, стоит ли смотреть дальше. Получает работающую админку с контент-библиотекой, медиа, пользователями и журналом — и ноль демонстрационных типов контента, то есть чистый лист, а не чужой блог, который придётся вычищать.

Разработчик, который будет это вести

Получает ту же раскладку из четырёх приложений, что и сам монорепозиторий OrthaCMS: server, admin, server-e2e, admin-e2e. Всё, что он прочитает в исходниках CMS, лежит у него на том же месте.

CI и автоматизация

Скаффолдер не блокируется на вопросе, которого некому услышать: нет TTY или передан --yes — берутся значения по умолчанию. Каждый вопрос дублирован флагом.

Чем скаффолдер не является

  • Это не установщик и не апгрейдер. Он пишет файлы один раз. Обновление версий — задача владельца приложения (и делается целиком, а не по частям).
  • Это не набор шаблонов «блог / магазин / лендинг». Шаблон ровно один. Типов контента в нём нет вообще — ContentPlugin({ types: [] }) валиден и не владеет ни одной таблицей, поэтому приложение мигрирует и стартует до того, как появится первый тип.
  • Это не конфигуратор всего. Он не спрашивает про роли, локали, лимиты и почту: это либо продуктовые константы в ortha.config.ts, либо решения, принимаемые уже внутри админки.
  • Это не рантайм. После генерации пакет из жизни приложения исчезает: он не попадает в зависимости сгенерированного проекта.
Ключевая идея

Скаффолдер не хранит список версий и не ходит в реестр за latest. Он читает свою версию из собственного package.json и подставляет её в каждую @orthacms/* зависимость точным значением, без каретки. Отсюда два следствия: релиз не требует правки шаблона, а npx create-ortha-app@0.3.0 воспроизводимо генерирует приложение 0.3.0, а не «то, что успело выйти с тех пор».

02Место в системе и почему пакет вне scope

В монорепозитории 56 публикуемых пакетов. Пятьдесят пять из них — @orthacms/*. Пятьдесят шестой — create-ortha-app, единственный вне scope.

Почему имя без scope

Это не стилистика, а требование двух точек входа npm. Обе формы работают только с таким именем:

npx create-ortha-app my-cms
npm create ortha-app my-cms

npm create <name> разворачивается в npx create-<name>, то есть имя пакета обязано начинаться с create- и лежать в корневом пространстве имён. Пакет @orthacms/create-app был бы доступен только как npm create @orthacms/app — форма, которую никто не набирает.

Цена этого решения одна и она видна в nx.json: список релизных проектов не может быть просто глобом.

"release": {
    "projects": [
        "@orthacms/*",
        "create-ortha-app",
        "!@orthacms/nx",
        "!@orthacms/copilot-provider-fake"
    ],
    "projectsRelationship": "fixed"
}

projectsRelationship: "fixed" — это и есть lockstep: у всех перечисленных проектов одна версия и один тег. @orthacms/nx (внутренний Nx-плагин) и @orthacms/copilot-provider-fake (приватная тестовая фикстура) исключены явно.

Единственный пакет без рантайм-зависимостей

В package.json поле dependencies пустое, и это осознанно: npx скачивает этот пакет раньше всего остального, и каждая зависимость — это секунды ожидания в самой первой команде, которую человек вводит. Поэтому терминальный интерфейс — рамки, цвет, стрелочные и чекбоксовые пикеры — написан вручную в src/lib/ui.ts, вместо prompts/clack/chalk.

03Мастер и его выборы

Мастер состоит из двух частей. Сначала три текстовых вопроса о проекте, затем — блок функциональных выборов, перед которым печатается строка, задающая тон: «Everything else is installed for you. These are the choices.» Всё остальное поставлено за вас; вот то, что действительно нужно решить.

Число выборов: код против документации

И корневой AGENTS.md, и AGENTS.md самого пакета говорят о трёх вопросах (хранилище, бэкенды копайлота, протоколы). В коде групп четыре: MEDIA_PROVIDERS, COPILOT_PROVIDERS, SSO_PROVIDERS, PROTOCOLS, и resolveAnswers() задаёт все четыре подряд; комментарий в ui.ts прямо говорит «мастер задаёт четыре таких подряд», а USAGE перечисляет флаг --sso. Ниже описаны все четыре — по коду. Расхождение вынесено в раздел 11.

Он генерируется: randomBytes(12).toString('base64url'). Пароль, набранный в приглашении, эхом уходит в терминал и оседает в истории шелла. Этот пишется только в .env (который в .gitignore) и один раз печатается в итоговой рамке.

Медиа-плагин работает всегда; вопрос только в том, какой адаптер за ним стоит. Ровно один — deployment держит одно хранилище, и это правило самого медиа-плагина, а не скаффолдера.

Что меняется в сгенерированном приложении

  1. Манифест. В dependencies появляется ровно один @orthacms/media-provider-*.остальные четыре не ставятся вовсе
  2. Импорт фабрики в apps/server/src/plugins.ts: один createLocalStorageProvider / createS3StorageProvider / …
  3. Одно выражение внутри MediaServerPlugin({ … }). В шаблоне это пять взаимоисключающих ortha:if-блоков вокруг поля provider; в сгенерированном файле остаётся одна строка. Комментарий рядом говорит прямо: сменить бэкенд — это изменить это выражение.
  4. Тип конфигурации. В ortha.config.ts поле plugins.media.storage типизируется типом выбранной фабрики (LocalStorageConfig / S3StorageConfig / …), то есть тип и фабрика двигаются вместе, и несовпадение ловится компилятором.
  5. Блок в .env — только ключи выбранного адаптера, с комментариями про их подводные камни (постоянный публичный URL у Vercel Blob; пустые ключи у S3, которые нельзя заполнять пустыми строками, иначе они затенят instance role).
Вопрос может не появиться

Мастер спрашивает только тогда, когда доступных ответов больше одного: MEDIA_PROVIDERS.filter(p => p.available).length > 1. Механизм существует, чтобы не задавать «вопрос» с единственным возможным ответом. Сегодня все пять адаптеров помечены available: true, и тест features.spec.ts отдельно проверяет, что S3 предлагается («now that it is implemented»), — значит вопрос задаётся. Недоступный адаптер не прячется, а рисуется серым с пометкой (unavailable) и пропускается курсором: пикер говорит правду о том, что готовится.

3.2 Выбор второй — бэкенды AI-копайлота

Группа COPILOT_PROVIDERS, множественный выбор. Флаг --copilot <ids|none>.

Это не вопрос «нужен ли копайлот»

Сам копайлот — ядро: copilot-server и copilot-admin лежат в CORE_PACKAGES, а CopilotPlugin регистрируется на обеих сторонах любого сгенерированного приложения. Причина техническая и неустранимая: пять ядровых плагинов (content, activity, i18n, media, users) зависят от copilot-server, чтобы отдать туда свои инструменты. Код всё равно окажется на диске — не объявив его, мы купили бы себе только пропавшую панель чата. Спрашивается какие модельные бэкенды добавить.

idЧто этоПакетЧто регистрирует бэкенд
copilot-anthropicClaude (Anthropic), родной протоколcopilot-provider-anthropicнепустой ANTHROPIC_API_KEY; модели — COPILOT_ANTHROPIC_MODELS, по умолчанию claude-sonnet-5
copilot-openaiЛюбая точка с OpenAI-совместимым протоколом: Ollama, vLLM, LiteLLM, Azure, OpenAIcopilot-provider-openaiнепустой COPILOT_OPENAI_BASE_URL; COPILOT_OPENAI_MODELS, COPILOT_OPENAI_API_KEY

По умолчанию не выбрано ничего, и это содержательный ответ. Включение хостируемого провайдера означает отправку контента воркспейса третьей стороне — решение, которое ADR-0005 §10 требует принимать явно, а не получать по умолчанию.

Что меняется в сгенерированном приложении

  1. Манифест получает выбранные пакеты провайдеров — ноль, один или два.
  2. Функция copilotProviders(config) в plugins.ts собирается из ortha:if-блоков: в ней остаются ветки только выбранных провайдеров. Каждая ветка добавляет провайдера только если его настройки присутствуют в конфигурации.порядок массива — это и есть настройка: первый зарегистрированный обслуживает запуск, не назвавший провайдера; поля defaultProvider нет
  3. Типы в ortha.config.ts: AppCopilotConfig.providers получает поля claude? и/или openai?, и чтение переменных окружения — тоже под условными блоками.
  4. Ключи в .env — только выбранных провайдеров.
  5. COPILOT_ENABLED=false пишется всегда, независимо от выбора. Флаг снимает регистрацию маршрутов /api/copilot, поэтому приложение выходит с отсутствующими поверхностями чата, а не с присутствующими и отказывающими.
Почему «ничего» — законный ответ

Приложение без бэкендов имеет плагин установленным и ни одного провайдера зарегистрированным. Оффлайн-заглушки, на которую можно было бы упасть, нет: copilot-provider-fake — приватная тестовая фикстура репозитория CMS, не публикуемая никуда. Раньше она регистрировалась последней в каждом сгенерированном приложении, и установка без ключей отвечала на любой вопрос заготовленной фразой вместо честного отказа. Теперь COPILOT_ENABLED=true с пустым списком провайдеров не даёт приложению стартовать.

3.3 Выбор третий — вход через внешнего провайдера (SSO)

Группа SSO_PROVIDERS, множественный выбор, по умолчанию пусто. Флаг --sso <ids|none>.

Приложение без SSO входит по email и паролю — это тот самый режим «только по приглашению», который у Ortha был всегда. SSO выключено по умолчанию не из осторожности, а потому что скаффолдер физически не может его угадать: нужны issuer, client id и callback URL, зарегистрированный на той стороне.

Что меняется в сгенерированном приложении

Здесь есть важная асимметрия между тем, что предлагается, и тем, что подключено в шаблоне.

  1. Выбран sso-oidc. В манифест добавляется пакет; в plugins.ts появляются импорт createOidcProvider, тип SsoRegistration и функция ssoProviders(config); IdentityPlugin вызывается с вторым аргументом { sso: { providers: ssoProviders(config) } } вместо одноаргументной формы; в ortha.config.ts появляются тип AppIdentityConfig.ssoProviders.oidc и чтение шести переменных; в .env — блок SSO_OIDC_*.провайдер регистрируется только когда заданы и SSO_OIDC_ISSUER, и SSO_OIDC_CLIENT_ID — кнопка входа, которая может только упасть, хуже отсутствия кнопки
  2. Выбраны sso-github или sso-saml. В манифест добавляется пакет — и больше ничего. Маркеров ortha:if sso-github и ortha:if sso-saml в шаблоне нет ни в одном файле: ни импорта, ни регистрации, ни переменных окружения. Подключать адаптер придётся руками.это подтверждается и текстом USAGE, где у флага в скобках назван только sso-oidc
  3. Не выбрано ничего. IdentityPlugin(config.plugins.identity) в одноаргументной форме. Общие настройки рукопожатия (SSO_PUBLIC_BASE_URL, SSO_REQUEST_TTL_SECONDS) пишутся в .env всё равно — они безусловны.

Почему REST показан, а не спрятан. «На каких протоколах говорит это приложение?» — более полезный вопрос, чем «нужны ли вам эти два дополнения», и ответ читается как полный набор только если то, что вы получаете всегда, находится в нём. --protocols none всё равно даёт REST: lockedOf() добавляет заблокированные id к любому ответу, флагом это не выключается. В пикере такая строка рисуется как [x] REST (always on) и не принимает пробел.

Ни одно из двух дополнений не приносит собственных учётных данных: GraphQL — протокольный адаптер над сервисами того же REST-API (ADR-0008), MCP переиспользует те же API-токены и scope. Они опциональны просто потому, что эндпоинт, о котором никто не просил, — всё равно эндпоинт.

Что меняется в сгенерированном приложении

GraphQL выбран

Пакет в манифесте; импорт ContentGraphqlPlugin; запись в массиве плагинов сразу после ContentViewsPlugin, получающая content по значению и playground: config.docs.enabled === true; раздел «GraphQL» в README. Передача плагина целиком, а не только типов, — то, что позволяет упасть на старте из-за двух типов контента, чьи имена столкнулись бы в GraphQL, а не на первом запросе от воркспейса, которому выданы оба.

MCP выбран

Пакет в манифесте; импорт McpPlugin; запись последней в массиве плагинов, потому что MCP отдаёт наружу то, что вложили плагины выше; тип McpPluginConfig и блок plugins.mcp в конфигурации (имя коннектора, callTimeoutMs, maxResultBytes); блок MCP_ENABLED=false в .env; раздел «MCP» в README.

Опционально значит «не зарегистрирован», а не «не установлен»

content-server зависит от mcp-server, поэтому пакет физически лежит в node_modules любого сгенерированного приложения, что бы ни выбрал пользователь. Разница в том, что плагина нет в plugins.ts, а его блока — в ortha.config.ts. Именно поэтому приложение по умолчанию отвечает на /api/v1/mcp честным 404, а не падает на неразрешённом импорте.

3.5 Как устроен сам пикер

  • Без единой зависимости. ui.ts — рамки, SGR-цвет, перерисовка на месте через CSI nA + CSI 2K.
  • Стрелки и j/k двигают курсор, пробел переключает чекбокс, Enter подтверждает, Escape и Ctrl-C отменяют. Отмена в мультиселекте означает «взять значения по умолчанию», а не «выбрано пусто».
  • Курсор пропускает строки disabled и locked — обойти их нельзя ни в одну сторону, включая заворот списка.
  • Мультиселект, в котором нечего трогать (все строки locked или unavailable), не рисуется вовсе: он сразу возвращает уже отмеченное.
  • Цвет отключается сам при NO_COLOR, TERM=dumb или отсутствии TTY.
  • Опасность одна, и она обработана: пикер переводит stdin в raw mode, а процесс, вышедший в raw mode, оставляет терминал без эха — пользователю приходится вслепую набирать reset. Восстановление лежит в finally.
  • Слушатели, а не for await. Итератор Node-потока уничтожает поток при досрочном выходе из цикла: первый пикер ответил бы нормально и увёл stdin за собой, а следующий отрисовал бы строки и упал с AbortError до первого нажатия. Вопросов подряд четыре, поэтому stdin обязан остаться читаемым.

3.6 Неинтерактивный режим

Мастер спрашивает, только если !--yes && process.stdin.isTTY && process.stdout.isTTY. Иначе берутся значения по умолчанию, а флаги переопределяют их по группам. Это не аварийный режим, а CI, конвейер и --yes: скаффолдер, зависший на приглашении, которое некому увидеть, вешает джобу до таймаута — отказ куда худший, чем взять умолчание.

npx create-ortha-app my-cms [опции]

Механизм, который заставляет принять решение

Правил ухода за шаблоном два, и оба держатся тестами, а не памятью.

Релиз правки шаблона не требует

Ни одной версии в features.ts нет. Каждая зависимость пишется как __ORTHA_VERSION__ и штампуется версией скаффолдера в момент рендера. Списка версий, который мог бы отстать, попросту не существует.

Добавление пакета — требует

features.spec.ts перечисляет каталог packages/ на диске и падает на любом непроклассифицированном имени. Новый пакет не может слиться в основную ветку, пока кто-то не решил, получает ли его новое приложение.

Ценность защиты — в том, чего не происходит без неё. Без неё шаблон просто отстаёт на релиз: пакет опубликован, на него ничто не ссылается, и никто этого не замечает, пока пользователь не спросит, почему у него нет функции, про которую он прочитал.

Как устроена сама проверка

  1. Перечисление реальности. publishedPackages() обходит packages/* и packages/*/*, читает каждый package.json и берёт имена, начинающиеся с @orthacms/ и не помеченные private. Это источник истины — диск, а не список.каталог без манифеста молча пропускается
  2. Перечисление намерения. Множество classified — объединение CORE_PACKAGES, CORE_DEV_PACKAGES, TRANSITIVE_PACKAGES и всех Feature.packages.
  3. Каждый пакет классифицирован. it.each(publishedPackages())('%s is classified') — по одному тесту на пакет, поэтому в отчёте видно какой именно пакет забыли. В комментарии прямо написано, что делать.
  4. Ничего лишнего. Обратная проверка: в классификации нет имён, которых нет на диске (исключение — @orthacms/cli, попадающий в приложение как dev-зависимость).
  5. Никакой пакет не в двух корзинах сразу. Длина конкатенации сравнивается с размером множества.
  6. Список «чего не получает приложение по умолчанию» зафиксирован целиком. Отдельный тест сравнивает разницу между опубликованным и установленным с явным списком — так «что мне стоит ничего не выбирать?» имеет письменный ответ, который нельзя изменить молча.
Всё достижимое — объявлено

Точки расширения (content-domain, copilot-domain, tools-server, query-builder-admin, identity-domain) и общий инструментарий (design-system, utils-admin, utils-server) лежат в ядре, хотя приходят транзитивно и без объявления. Объявление — это то, что делает разрешение импорта собственностью приложения, а не одолжением: необъявленный импорт работает ровно до первого конфликта версий, который вложит вторую копию, и не работает под pnpm никогда. Это и называется фантомной зависимостью.

Оба транзитивных пакета — инструменты для написания провайдера хранилища, а не для его эксплуатации. Положить пакет в эту корзину — решение, которое защита принимает; забыть его вовсе — нет.

Из чего складывается манифест

--yes  →  40 (ядро) + 1 (media-provider-local)  = 41 в dependencies

итого 42 пакета @orthacms — ровно это число печатает итоговая рамка мастера

Важно, что зависимости собираются в коде, а не условными блоками внутри package.json.tmpl. Выбрасывание строк из JSON — это способ получить висящую запятую и приложение, которое невозможно даже установить, причём ошибка обвинит шаблон, а не ту возможность, которую выключили.

Три отличия от apps/* монорепозитория

Каждое — следствие того, что приложение потребляет пакеты из npm, а не из исходников.

Никакого webpack

Только tsc, поэтому node_modules остаётся на диске и вызовы вида join(__dirname, '../../../migrations') внутри каждого плагина продолжают разрешаться.

@source для Tailwind

Tailwind исключает node_modules из автоопределения контента. Без строки @source "../../../node_modules/@orthacms"; вся админка рендерится без стилей, и ничто не падает.

staticDir

Один процесс отдаёт и API, и админку с одного origin. В монорепозитории их разносит Vite; у деплоя dev-прокси нет, а сессионной куке identity с SameSite=lax нужен тот же origin.

Почему @source обязан быть голым каталогом

@source с глобом внутри всё равно проходит через правила игнорирования, среди которых node_modules. Шаблон вида @orthacms/*/dist/**/*.js не совпадёт ни с чем, и на выходе получится таблица стилей из одного блока темы — около 15 КБ, без утилит компонентов. Только буквальный путь к каталогу регистрируется как явный корень контента, обходящий эти правила. Тест проверяет и точную строку, и отсутствие звёздочки.

Композиционный корень сервера

apps/server/src/plugins.ts — самый содержательный файл приложения. Его комментарий формулирует правило: порядок массива — это порядок миграций. Миграции применяются обходом массива, транзакция между плагинами не натягивается, поэтому плагин, чьи таблицы ссылаются на чужие, обязан идти позже. WorkspacesPlugin следует за IdentityPlugin, потому что его memberships ссылается на users: поставьте наоборот — и свежая миграция упадёт с relation "users" does not exist, а уже мигрированная база пройдёт как ни в чём не бывало. То есть ошибка уедет в релиз и укусит следующую чистую установку, а не автора.

Порядок при этом не решает вопросов внедрения зависимостей: модуль каждого плагина глобален, а все onPluginInit отрабатывают до создания приложения Nest.

database → identity → workspaces → activity → users
        → content → content-views [→ content-graphql]
        → i18n → alarms → media → copilot [→ mcp]

Первым идёт DatabasePlugin — единственный плагин, открывающий ресурс в onPluginInit. Последним, если выбран, — McpPlugin: он отдаёт наружу то, что вложили плагины выше.

Композиционный корень админки

В apps/admin/src/plugins.ts значимы ровно две позиции. IdentityPlugin первый — он приносит единственные публичные маршруты (вход и приём приглашения), которые обязаны рендериться вне закрытого layout. ShellPlugin второй — он единственный поставляет layout, а хост монтирует первый найденный; layout оболочки — это то, что композирует шлюз авторизации identity. Плагин, зарегистрировавший свой layout раньше, отрендерил бы все приватные маршруты без охраны, и баг авторизации выглядел бы как поломка вёрстки.

Остальное — порядок ради читаемости: слоты являются синглтонами уровня модуля и заполняются до первого рендера.

Конфигурация: единственный читатель process.env

apps/server/ortha.config.ts — единственное место, читающее окружение. Всё ниже по течению получает типизированные значения, поэтому у вопроса «откуда взялась эта настройка» ровно один ответ. Файл вводит три аккуратных считывателя:

  • requireEnv(name) — падает при загрузке, а не через несколько секунд после старта. Отсутствующий DATABASE_URL, разрешённый в '', дошёл бы до pg как «используй умолчания libpq», и первый запрос упал бы с сообщением, где не названа ни одна незаданная переменная.
  • readPositiveInt(name, fallback) — намеренно не Number(x) || fallback, который неверен сразу в трёх направлениях и молчалив во всех: 0 ложен и подменяется умолчанием, отрицательное истинно и принимается (отрицательный TTL сессии выдаёт сессии уже просроченными), а 1e9 парсится.
  • readTrustProxy() — число хопов (рекомендуемая форма, которую клиент не может подделать), булево или строка-пресет.

Отдельно проверяется NODE_ENV: одно это сравнение управляет двумя защитами сразу — публикуется ли справочник API и несёт ли сессионная кука флаг Secure, — поэтому опечатка молча выключила бы обе и была бы неотличима от корректной настройки. Значение вне списка development / test / production валит старт.

Тесты, которые едут вместе с приложением

Стартовый набор, который нельзя протестировать, учит людей не тестировать. Поэтому в приложении четыре набора и два раннера — честный ответ, а не компромисс: у каждой половины свой тулчейн, и ни одна трансформация не обслуживает обе.

База данных серверного e2e — четыре вещи, которые дались не с первого раза

Набор управляет своей базой: <database>_e2e создаётся и мигрируется на первом запуске через applyPluginMigrations — ту же функцию, которую вызывает ortha migrate, поэтому под тестом настоящая схема, а не её ручная копия.

  • Вывод имени идемпотентен. global-setup выполняется в главном процессе Jest и переставляет DATABASE_URL; воркеры форкаются от него и наследуют значение — наивное дописывание суффикса дало бы в воркере app_e2e_e2e, и все тесты упали бы против базы, которую никто не создавал.
  • global-setup импортирует конфигурацию динамически. Статический импорт всплывает выше любого оператора, то есть выполнился бы до загрузки .env и до переадресации URL — и набор упал бы на переменной, лежащей в файле двумя строками ниже.
  • transformIgnorePatterns разыгнорирует @scalar. createServer тянет рендерер справочника API, опубликованный только как ESM, а Jest — CommonJS: без этого запуск умирает на Unexpected token 'export' в файле, которого никто в приложении не писал.
  • assertDisposable отказывается от базы разработки. Набор делает TRUNCATE каждой таблицы, а E2E_DATABASE_URL можно выставить куда угодно. Проверка идёт до первого TRUNCATE.

Ещё три детали: jest.setup.js подставляет плейсхолдеры, потому что спеки импортируют ortha.config.ts, который намеренно отказывается загружаться без DATABASE_URL (ничего при этом не соединяется — список плагинов есть чистая функция конфигурации, так что npm test работает в CI без .env); apps/server/tsconfig.json исключает **/*.spec.ts, иначе ortha build компилирует тесты в dist/server и поставляет их; конфигурация Vite названа .mts, потому что приложение объявлено "type": "commonjs", и Vite ругается на ESM-синтаксис в CJS-конфигурации. И серверные e2e-спеки читают ALLOWED_ORIGIN из конфигурации, потому что вход защищён списком разрешённых origin, следующим за ADMIN_PORT: жёстко зашитый :4200 упал бы на любом приложении с другим портом админки — как невнятный 403, а не как «не тот origin».

06Сценарии — как это работает по шагам

6.1 Создать приложение

  1. Запуск. npx create-ortha-app my-cms. Целевой путь — первый позиционный аргумент, иначе текущий каталог. Печатается рамка с путём.длинный путь обрезается с начала: хвост — то, что его опознаёт
  2. Проверка каталога. isNonEmptyDirectory(target) — существующий непустой каталог означает отказ с текстом, что делать. Скаффолдер никогда не пишет поверх чужих файлов.
  3. Разрешение ответов. Есть TTY и нет --yes — задаются три текстовых вопроса и четыре пикера. Иначе берутся умолчания, переопределённые флагами. Заблокированные id (rest) добавляются к любому ответу.
  4. Генерация пароля администратора. randomBytes(12).toString('base64url'). В приглашении он не спрашивается никогда.
  5. Итоговая рамка. Имя, база, хранилище, протоколы, копайлот, вход, число пакетов @orthacms. Пустой мультивыбор печатается приглушённым none / no backend — то есть отсутствие выбора показано, а не скрыто.
  6. Рендер шаблона. renderTemplate(templates/default, target, values): обход всех файлов, применение ortha:if, подстановка __PLACEHOLDER__, переименования. Манифест идёт другим путём — через renderManifest.файлы вне списка текстовых расширений копируются побайтово: прогон фавикона через строковую замену испортил бы его так, что видно только в браузере
  7. git init --quiet, если каталог .git ещё не существует и не передан --no-git.
  8. npm install --no-audit --no-fund, если не передан --no-install. Провал установки не притворяется успехом: печатается ошибка и выставляется process.exitCode = 1, но файлы остаются на месте — доустановить можно руками.
  9. Рамка с учётной записью — email, пароль и напоминание, что он записан в .env.
  10. Следующие шаги: cd my-cms, docker compose up -d, npm run migrate, npm run dev.

Что именно делает рендер с каждым файлом

  1. Условные блоки. applyConditionals(raw, flags, file): строки-маркеры удаляются всегда, тело остаётся только если условие выполняется. Блоки вкладываются, и внутренний блок внутри выброшенного остаётся выброшенным.
  2. Схлопывание пустых строк. Снятый блок почти всегда оставляет за собой пустую строку рядом с той, что шла после. Без collapseBlankRuns каждый сгенерированный файл нёс бы шрам на месте выключенной возможности — а это первое, что человек открывает.
  3. Подстановка. Семь токенов: __APP_NAME__, __APP_TITLE__, __DATABASE_URL__, __DATABASE_NAME__, __ADMIN_EMAIL__, __ADMIN_PASSWORD__, __ORTHA_VERSION__. Заменяются все вхождения, не первое.
  4. Переименования. _gitignore → .gitignore, env.tmpl → .env, package.json.tmpl → package.json, README.md.tmpl → README.md.
Два переименования, за каждым — молчаливый провал

_gitignore. npm молча отказывается публиковать файл с именем .gitignore. Шаблон, несущий такой файл, уезжает в тарболл без него, и каждое сгенерированное приложение начинается с предложения закоммитить node_modules. При этом в тарболле ничто не выглядит неправильным. Тот же обходной приём применяют create-vite и create-next-app.

*.tmpl. Держит package.json вне глобов workspaces корневого манифеста, которые иначе прочли бы каталог шаблона как отдельный пакет.

6.2 Первый запуск

  1. Поднять Postgres. docker compose up -d — образ postgres:17-alpine, пользователь и пароль ortha, имя базы взято из введённого URL, healthcheck через pg_isready, том postgres-data.
  2. Применить миграции. npm run migrate → ortha migrate: обход массива плагинов, у каждого своя таблица учёта миграций. На этом шаге и проявился бы неправильный порядок плагинов.
  3. Запустить. npm run dev: watch-компиляция сервера, node --watch и dev-сервер Vite. Админка на :4200, API на :3000, /api проксируется на API — браузер видит один origin, и сессионная кука первосторонняя без CORS.ключ прокси — регулярное выражение ^/api/, а не строка: строковый префикс проглотил бы и SPA-маршрут /api-tokens
  4. Войти. Email и пароль из .env. Учётная запись поднимается на старте идемпотентно и недеструктивно — существующий аккаунт не трогается. README советует очистить обе переменные, как только вход получен.
  5. Что видно сразу. Дашборд, контент-библиотека с пустым реестром типов, медиатека, воркспейсы, участники, журнал действий, API-токены, алармы. Чата нет — COPILOT_ENABLED=false снимает регистрацию маршрутов, и поверхности отсутствуют, а не отказывают.
  6. Справочник API. http://localhost:3000/reference — включён вне production по умолчанию.

Добавить свои типы контента

  1. Описать типы и экспортировать массив contentTypes.
  2. Передать их в ContentPlugin({ types: contentTypes, migrations: … }) — точная форма дескриптора лежит комментарием в самом plugins.ts.
  3. Добавить drizzle.config.ts, указывающий schema на файл типов и out на каталог миграций.
  4. npm run generate -- --name=add_content_types && npm run migrate.

6.3 Добавить новый пакет в монорепозиторий и провести его через features.ts

Это тот сценарий, ради которого существует защита из раздела 4. Он всегда начинается с падающего теста.

  1. Пакет создан в packages/<группа>/<имя> с манифестом @orthacms/<группа>-<имя> и без "private": true.
  2. npx nx test create-ortha-app падает. Один именной кейс: @orthacms/<имя> is classified. В комментарии рядом написано, что делать.пакет с "private": true перечислением не подхватывается — приватность есть тоже решение, просто уже принятое
  3. Принять решение. Три возможных ответа, и правильный ровно один: получает ли каждое новое приложение этот пакет; ставится ли он вместе с какой-то возможностью; или это внутренняя деталь другого пакета, которую объявлять не нужно.
  4. Ядро. Добавить имя в CORE_PACKAGES, соблюдая алфавит. Если у пакета есть плагин, который надо зарегистрировать, — дописать его в templates/default/apps/server/src/plugins.ts или apps/admin/src/plugins.ts и в ожидаемый список в соответствующем plugins.spec.ts, иначе тесты сгенерированного приложения перестанут проходить.
  5. Возможность. Добавить объект Feature в нужную группу — id, label, hint, packages, enabledByDefault, available. Новая группа означает ещё и вопрос в resolveAnswers(), флаг в USAGE и строку в describeSelection().
  6. Обвязать шаблон. Импорт и регистрация — под ortha:if <id>; переменные окружения — под тем же маркером в env.tmpl; типы и чтение окружения — в ortha.config.ts; раздел в README.md.tmpl под HTML-комментарием <!-- ortha:if <id> -->.
  7. Транзитивный. Добавить в TRANSITIVE_PACKAGES и написать в докблоке, почему приложению незачем его импортировать. Забыть вовсе защита не позволит; положить сюда — позволит.
  8. Обновить зафиксированный список. Тест «leaves exactly the choosable packages out of a default app» перечисляет исключения дословно; новый опциональный пакет надо в него дописать. Это не формальность: список — письменный ответ на вопрос «что мне стоит ничего не выбирать».
  9. Прогнать тесты. npx nx test create-ortha-app — покрытие пакетов, процессор условных блоков и сгенерированный вывод для нескольких комбинаций.

6.4 Как устроены условные блоки

Один шаблон обслуживает все комбинации через три директивы — ortha:if, ortha:ifnot, ortha:end — в любом синтаксисе комментариев, поэтому одно и то же работает в TypeScript, YAML, .env, CSS, HTML и Markdown.

// ortha:if copilot-anthropic
import { createAnthropicProvider } from '@orthacms/copilot-provider-anthropic';
// ortha:end

# ortha:ifnot graphql
# (Только REST — GraphQL-эндпоинт не смонтирован.)
# ortha:end

<!-- ortha:if mcp -->
### MCP
<!-- ortha:end -->

Механизм намеренно построчный, а не выразительный язык: шаблоны читают куда чаще, чем пишут, и открывающий plugins.ts должен увидеть настоящий файл с несколькими комментариями, а не диалект шаблонизатора. Любое нужное здесь условие — это «включена ли эта возможность».

Незакрытый блок бросает исключение

И это единственно верное поведение. Пропущенный ortha:end в plugins.ts молча съел бы остаток файла — то есть все плагины ниже, — и приложение загрузилось бы без API вместо того, чтобы не собраться. Симметрично: ortha:end без открывающего блока тоже бросает.

07Lockstep-версионирование и релиз

Механизм в одном абзаце

Скаффолдер читает свою версию из собственного манифеста (ownVersion()) и подставляет её в каждую @orthacms/* зависимость сгенерированного приложения. Поскольку релиз lockstep, его версия и есть совместимый набор. Отсюда npx create-ortha-app@0.4.0 генерирует приложение 0.4.0.

Три свойства, которые из этого следуют

Точный пин, без каретки

"@orthacms/content-server": "0.4.2", а не "^0.4.2". Частичное обновление может оставить в node_modules две копии общего пакета: два экземпляра React-контекста, и сайдбар админки молча перестаёт разговаривать со своим провайдером.

Воспроизводимость

Чтение версии из манифеста, а не разрешение latest из реестра, — это то, что делает старую версию скаффолдера воспроизводимой. Иначе @0.3.0 генерировал бы приложение из сегодняшних пакетов.

Релиз не трогает шаблон

Списка версий нет ни в одном файле шаблона, поэтому отставать нечему. Единственное, что требует правки при релизе, — ничего.

Как манифест собирается на самом деле

renderManifest() пересобирает карту зависимостей, а не патчит её: шаблон везёт манифест с не-Ortha зависимостями и пустым набором @orthacms, выбранные пакеты вливаются и вся карта пересортировывается.

  1. Подстановка плейсхолдеров в текст, затем JSON.parse.
  2. dependencies = существующие + pin(resolvePackages(selection)), отсортированные.
  3. devDependencies = существующие + pin(resolveDevPackages()), отсортированные.
  4. JSON.stringify(manifest, null, 4) плюс перевод строки.

Что делает pack.mjs

Тарболл пакета — это не его закоммиченный манифест. Рабочая область резолвит пакеты из исходников, а потребитель так не может, поэтому build компилирует, а pack раскладывает в dist/pack/ переписанный манифест. Для скаффолдера здесь два специфических шага:

  • Каталог templates/ копируется дословно и добавляется в files — тем же способом, каким пакуются каталоги migrations/ у плагинов. Это данные, а не исходник, и компилировать там нечего.
  • bin перенаправляется с исходного ./src/cli.ts на скомпилированный файл. bin, указывающий на файл, которого сборка не выпустила, — худший вид поломки: он проявляется только у пользователя.

Релиз

npm run release из чистой копии main: версионирование по conventional commits, тег v{version}, публикация и GitHub Release. Публикации дросселируются и переповторяются — npm лимитирует запись в аккаунт, а за один прогон уезжает несколько десятков тарболлов, поэтому они сериализуются с паузой, и 429 отступает, а не валит релиз.

Для сгенерированного приложения обновление — это одновременный подъём всех @orthacms/* до одной версии. README говорит это прямо, и по той же причине: частичное обновление вкладывает вторую копию общего пакета.

08Инварианты

09Чек-лист тестирования

Скаффолдер тестируется в двух слоях: юнит-тесты пакета (пять спек-файлов — покрытие классификации, процессор условных блоков, рендер шаблона, терминальный интерфейс, валидаторы) и ручной сквозной прогон, который пока не автоматизирован.

9.1 Классификация и покрытие

  • Добавить в packages/ фиктивный публикуемый пакет → тест падает именным кейсом с именем этого пакета, а не общим «список не совпал».
  • Пометить его "private": true → тест зелёный: приватность есть уже принятое решение.
  • Положить пакет в две корзины сразу → падает проверка на дубликаты.
  • Вписать имя, которого нет на диске → падает проверка «classifies nothing that does not exist».
  • Добавить опциональный пакет, не обновив зафиксированный список исключений → падает «leaves exactly the choosable packages out of a default app».

9.2 Мастер и флаги

  • --protocols none → REST всё равно в наборе; ни content-graphql, ни mcp-server не установлены.
  • --copilot none → копайлот установлен и зарегистрирован, ни одного провайдера не установлено, COPILOT_ENABLED=false.
  • --copilot copilot-anthropic,copilot-openai → оба пакета в манифесте, обе ветки в copilotProviders(), оба блока ключей в .env.
  • --media media-s3 → установлен только S3-адаптер; в plugins.ts один createS3StorageProvider; в ortha.config.ts тип S3StorageConfig; в .env только MEDIA_S3_*.
  • Несуществующий id во флаге → поведение задокументировать: сегодня id просто не совпадает ни с одной возможностью и молча игнорируется.
  • Запуск без TTY (| cat) → ни одного приглашения, умолчания, нулевой код возврата.
  • Ctrl-C посреди пикера → терминал сохраняет эхо; повторный echo test печатается нормально.
  • Escape в мультиселекте → берутся значения по умолчанию группы, а не пустой выбор.
  • Пробел на строке REST и на недоступной строке → состояние не меняется; курсор на них не встаёт.
  • NO_COLOR=1 и TERM=dumb → ни одной ANSI-последовательности в выводе, рамки не разъезжаются.
  • Очень длинный целевой путь → обрезается с начала, рамка держит ширину.

9.3 Валидация ввода

  • Имя приложения My CMS, _x, .x, строка длиннее 214 символов → каждое отвергается со своим текстом, вопрос задаётся заново.
  • URL mysql://…, не-URL, postgresql://host:5432 без имени базы → три разных сообщения; ни одно не пропускается.
  • Имя базы из URL → попадает и в DATABASE_URL, и в POSTGRES_DB в docker-compose.yml — одно и то же значение.

9.4 Целостность сгенерированного приложения

  • Grep по __[A-Z_]+__ и по ortha: во всех файлах → ноль совпадений при любой комбинации возможностей.
  • .gitignore существует, _gitignore — нет, ни одного *.tmpl → и в первом строка node_modules.
  • JSON.parse сгенерированного package.json → валиден при любой комбинации; ключи зависимостей отсортированы; ни одной каретки в @orthacms/*.
  • Нет пробелов-шрамов → в файлах, где сняли блоки, нет тройных пустых строк.
  • npm install в сгенерированном каталоге → проходит; в node_modules одна копия @orthacms/design-system.
  • npm run typecheck → оба проекта чисты при каждой комбинации, включая обе крайние (ничего опционального / всё опциональное).
  • npm test → обе половины зелёные без .env; см. расхождение Р-07 в разделе 11.
  • npm run migrate на чистой базе → проходит; повторный запуск идемпотентен.
  • npm run build && npm start → один процесс отдаёт API и админку; dist/server не содержит скомпилированных *.spec.js.
  • Админка в браузере после npm start → стили на месте (проверка @source): размер CSS заметно больше ~15 КБ, у компонентов есть утилитарные классы.
  • GET /api/v1/graphql и POST /api/v1/mcp в приложении по умолчанию → честный 404, а не ошибка разрешения модуля.
  • Вход по учётным данным из .env → удаётся с первого раза; после очистки обеих переменных существующая учётка продолжает работать.

9.5 Упаковка и релиз

  • npm pack и распаковка тарболла → каталог templates/ внутри целиком, включая _gitignore; bin указывает на существующий скомпилированный файл.
  • Установка с локального реестра и генерация из неё → версия в зависимостях сгенерированного приложения совпадает с версией установленного скаффолдера.
  • Старая версия: npx create-ortha-app@<прошлая> → приложение той версии, а не сегодняшней.
  • npx nx graph после любых правок в templates/ → граф строится; если каталог случайно стал видимым для инференса, ломается вся команда nx.
Что пока не автоматизировано

Сквозной путь целиком — опубликовать в локальный реестр, сгенерировать, установить, мигрировать, собрать, поднять — не автоматизирован. Прогон описан вручную в PR, вводившем пакет. Пункты 9.4 (последние шесть) и 9.5 сегодня выполняются руками.
