01Бизнес-описание

Медиатека — это общий склад файлов организации внутри воркспейса: изображения, видео, аудио, документы, архивы. Всё, что редактор прикрепляет к записи, вставляет в текст или отдаёт наружу через публичный API, сначала становится активом — строкой в media_asset с указателем на байты.

Какую задачу решает

  • База не хранит байты. В строке лежат только метаданные и пара storage_key + storage_provider. Дамп базы остаётся дампом базы, а не терабайтом видео; резервные копии, реплики и миграции не растут вместе с медиатекой.
  • Один порт — шесть бэкендов. Локальный диск, любое S3-совместимое хранилище (R2, AWS, MinIO, Spaces, B2, Wasabi), Azure Blob, Google Cloud Storage, Vercel Blob и in-memory для тестов. Переезд между ними — одна строка в композиционном корне, а не переписывание плагина.
  • Медиатека приватна по умолчанию. Публичной ссылки на файл не существует: каждый байт проходит через маршрут приложения, который проверяет либо членство в воркспейсе, либо область bearer-токена. Отдельного «публичного бакета» нет и быть не должно.
  • Превью вместо оригиналов. Растровые изображения при загрузке получают два WebP-деривата — thumb (≤320px) и preview (≤1280px). Сетка медиатеки, плитки медиаполей и тела статей тянут дериват, а не 12-мегапиксельный исходник.
  • Доступность как часть модели. Альтернативный текст — колонка на активе, задаваемая прямо при загрузке (и по сессии, и по токену), а не только вторым PATCH, который никто не делает. Плюс дорожки таймированного текста (субтитры, титры, описания, главы) как отдельные ассеты-указатели.
  • Агенты работают с медиатекой так же, как люди. Пять инструментов в общем реестре: три чтения (поиск активов, список папок, чтение текстового файла) отдаются и копайлоту, и MCP; два «предложения» (альт-текст и создание файла) — только копайлоту.

Кому это видно

Редактор

Заходит в «Медиатеку» внутри воркспейса, раскладывает файлы по папкам, ищет, фильтрует по типу, прикрепляет к записи через вкладку «Медиа» или вставляет в текст. Загружает пачками — с прогрессом, отменой и повтором по каждому файлу.

Администратор / оператор

Выбирает бэкенд хранилища и его настройки в plugins.ts, ставит потолок загрузки, решает, идут ли байты через приложение или редиректом. Ошибка конфигурации — отказ старта с внятным сообщением, а не 500 на первой загрузке.

Интеграция / внешний агент

По bearer-токену умеет ровно две вещи: загрузить файл и скачать его. Переименование, перемещение и удаление — только по сессии: прикрепить картинку к записи это авторство контента, а курировать библиотеку — администрирование.

Чем Media не является

  • Это не CDN и не публичный файловый хостинг. URL актива — это маршрут приложения /api/media/assets/:id/raw, он требует аутентификации при каждом запросе. Прямая раздача из бакета включается отдельно (directServe: 'signed-url') и только на бэкенде, умеющем подписывать URL с закреплённым типом и disposition.
  • Это не дедупликация. sha256 считается и сохраняется в checksum, но нигде не используется для поиска: загрузка одного и того же файла дважды даёт два актива и два блоба. Колонка заведена «на будущее» — так и написано в порту.
  • Это не транскодирование. Обрабатываются только растровые изображения (Sharp). Видео не режется, не перекодируется, длительность не измеряется — колонка duration есть, но её никто не заполняет.
  • Это не проверка содержимого. MIME-тип — это то, что заявил загружающий в multipart-части. Байты не нюхаются, антивируса нет, белого списка типов при загрузке нет. Отсюда вся политика выдачи: файл считается враждебным по умолчанию.
  • Это не связь с контентом. Media не знает, кто на неё ссылается. Проверку «такой актив существует и подходит по accept» делает content-server на сохранении записи, через порт MEDIA_ASSET_RESOLVER, который Media реализует.
  • Это не аудит. Плагин пишет доменные события media.* в транзакционный outbox; строки журнала складывает activity.
Ключевая идея архитектуры · ADR-0012

Одно развёртывание — один провайдер хранилища, переданный одним объектом. Никакого реестра, резолвера и defaultProvider: байты уходят в одно место, значит выбирать не из чего. Объект описывает себя сам — id (пишется в каждую строку актива) и capabilities. Плата за это названа открыто: смена бэкенда осиротит уже загруженные файлы, поэтому StorageProviderCheck отказывается стартовать, если в таблице есть строки чужого провайдера — и называет его имя и количество строк.

Зачем testkit опубликован

Инварианты порта раньше жили только в прозе, в provider-local/AGENTS.md. Каждый из них — утверждение, на которое ядро опирается и которое проверить само не может: оно освобождает блобы по ключу, отдаёт результат get прямо в HTTP-ответ и кладёт деривативы рядом с оригиналами. Провайдер, написанный вне этого репозитория, не имел никакого способа узнать, что нарушил один из них. Поэтому набор — публичный npm-пакет, а не внутренний файл: он адресован автору стороннего адаптера.

Что он проверяет: непустой id и полный capabilities; наличие directUrl() ровно тогда, когда так сказано в capabilities; честные размер и sha256; круговорот байтов через get; разные ключи для двух активов с одинаковым именем файла; невозможность деривату затереть оригинал с именем thumb.webp; отсутствие следов после оборвавшегося put; отказ get до открытия потока; идемпотентность remove; и то, что всё отклоняется промисом, а не синхронным броском (синхронный бросок улетает мимо try, который должен был освободить блобы).

Соседи, которых легко перепутать

@orthacms/content-server объявляет порт MEDIA_ASSET_RESOLVER, а Media его реализует — инверсия «открытого хоста»: контент не зависит от медиа, зависимость идёт в обратную сторону. @orthacms/wysiwyg-admin объявляет слот WYSIWYG_MEDIA_SLOT, а Media его заполняет — редактор обязан оставаться работоспособным без медиаплагина. @orthacms/insights-admin рисует страницу Insights, но карточки про хранилище принадлежат Media, потому что Media владеет таблицей. @orthacms/transfer-server переносит файлы при экспорте/импорте — через обычный путь загрузки Media, а не мимо него.

03Роли и права

Четыре ключа прав, все выданы ролям в identity-server. Модель плоская: право проверяется guard'ом по константе (@RequirePermissions(PERMISSIONS.MEDIA_*)), никаких прав на отдельную папку или отдельный актив нет.

Почему у токена нет update и delete

scopePermissions в identity-server намеренно не выдаёт bearer-токену ни media:update, ни media:delete — ни в области read, ни в full. Прикрепить картинку к записи — это авторство контента, и без загрузки токен вообще не смог бы заполнить медиаполе (писатель контента отвергает id актива, которым воркспейс не владеет). А переименовывать, двигать и удалять чужие файлы в библиотеке — это администрирование, и для него есть сессия администратора.

Три независимых контура проверки

  • Право. PermissionsGuard + константа. На каждом маршруте, без исключений — включая маршрут выдачи байтов.
  • Воркспейс. WorkspaceGuard читает заголовок X-Workspace-Id и кладёт его в @CurrentWorkspace(). Все запросы, кроме одного, ходят через него.
  • Origin. OriginGuard на каждом изменяющем состояние маршруте сессионной половины (POST/PATCH/DELETE). На токенных маршрутах его нет: у не-браузерного клиента нет Origin, и защищать нечего.
Единственное исключение из WorkspaceGuard — и почему оно безопасно

GET /media/assets/:id/raw не несёт WorkspaceGuard. Этот URL грузит сам браузер — <img src> в плитках и в панели деталей, ссылки на скачивание — а такие запросы отправляют куки, но не могут отправить произвольный заголовок, поэтому guard отвечал 400 на каждое превью. Область не отброшена, а выведена: DownloadAssetQuery.locate читает воркспейс-владельца из строки актива, контроллер требует членства вызывающего в этом воркспейсе (через экспортируемый MembershipCheckQuery), и только потом трогает хранилище. Не-участник получает тот же 404, что и несуществующий актив, — иначе id активов можно было бы перебирать. Любой новый маршрут, чей URL грузит браузер, нуждается в такой же обработке, а не в заголовочном guard'е.

Три jsonb-колонки, и что в них лежит

variants

Словарь имя → { key, width, height, size }. Сегодня в нём бывают thumb и preview. Каждый дериват — собственный блоб у того же провайдера, в зарезервированном пространстве ключей variants/. Добавлено миграцией 0001_asset_variants.

tracks

Список указателей { kind, srclang, label, assetId, default? }. kind — один из captions | subtitles | descriptions | chapters: титры и субтитры разведены намеренно, как в HTML и в WCAG. Сам файл WebVTT — обычный актив библиотеки со своими правами и своим ключом, поэтому его можно заменить, не трогая видео. Миграция 0002_asset_tracks.

tags

Плоский список строк, до 50 штук по 64 символа. Заменяется целиком при PATCH. Участвует в поиске: ?search= ищет и по имени, и по тегам через jsonb_array_elements_text.

Что здесь не хранится

  • Байты. Никогда. Ни в bytea, ни в large object.
  • Обратные ссылки на контент. Media не знает, какая запись на неё ссылается, — и не узнаёт при удалении (см. раздел 5).
  • Публичный URL. AssetView.url собирается на лету как /api/media/assets/<id>/raw, в колонке его нет. Ни один URL хранилища не попадает в базу и в ответы API.
  • Индекса по checksum. Дедупликации нет; см. раздел 1.
Доменные события — семь видов, все через транзакционный outbox

media.asset.uploaded, media.asset.updated, media.asset.moved, media.asset.deleted, media.folder.created, media.folder.renamed, media.folder.deleted. Каждое изменение состояния идёт внутри UnitOfWork.run над репозиториями и OutboxWriter, так что строка и событие фиксируются атомарно: журнал не может показать загрузку, которой не было, и не может пропустить ту, что была.

Исключение — очистка воркспейса. MediaWorkspacePurger работает множествами и без событий: один delete … where workspace_id = … на таблицу, без загрузки агрегатов и без media.asset.deleted на каждый файл. В воркспейсе могут быть десятки тысяч активов, и их поштучные удаления отдельно не значимы — событием, которое произошло, является workspace.deleted. returning отдаёт ровно колонки хранилища, что и нужно освобождению блобов; оно идёт после коммита.

05Жизненный цикл файла

выбран в браузере — multipart → актив + блоб(ы) ⇄ правки, перемещение, копия ⇄ используется — удаление → строки нет, блобы освобождены

У актива нет колонки статуса и нет черновиков: он либо есть, либо нет. Состояния, через которые он проходит, — это состояния его байтов и указателя на них.

Что происходит с записями, которые ссылались на удалённый файл

Ничего не мешает удалить актив, на который ссылается опубликованная запись. Обратных ссылок Media не хранит, счётчика использований нет, предупреждения при удалении нет, и content об удалении не уведомляется. Последствия расходятся по трём поверхностям:

  • В редакторе плитка медиаполя превращается в явную предупреждающую карточку с «мёртвым» id — чтобы её можно было найти и убрать. Это не ошибка сохранения, а маркер.
  • При следующем сохранении записи EntryWriterService.assertMediaTargets отвергнет её с 422 must reference an existing asset. То есть запись «застревает»: она уже опубликована со сломанной ссылкой, но отредактировать её нельзя, пока ссылку не уберут.
  • В публичном API резолвер просто опускает ненайденный id — ответ приходит без этого медиа, без ошибки и без указания, что чего-то не хватает. Пропущенный и чужой актив неразличимы намеренно: иначе это был бы оракул по id.

Каскад папки делает то же самое разом и без отката: удаляется всё поддерево, блобы освобождаются после коммита, отмены нет. Единственный предохранитель — подтверждение в интерфейсе, которое называет числа («…также удалит 3 файла и 1 подпапку»); сервер спорить не умеет и намеренно не умеет.

Привязка к воркспейсу

workspace_id — обычный uuid без внешнего ключа: таблица воркспейсов принадлежит другому плагину, и связывать плагины схемой здесь не принято. Из этого следуют две вещи.

  • Область проверяется в приложении, а не базой: каждый запрос несёт workspace_id в WHERE. Рекурсивный обход поддерева при каскаде фильтрует по воркспейсу в обеих ветвях CTE — каскад, сбежавший из своего тенанта, был бы худшей возможной ошибкой здесь, и это закреплено e2e-тестом.
  • Удаление воркспейса нужно было закрывать отдельно. Раньше строки переживали свой воркспейс и запирали свои блобы: оба пути удаления идут через живой воркспейс, так что после его исчезновения ни один запрос не мог добраться до байтов. Теперь MediaWorkspacePurger реализует порт WorkspacePurger и сам регистрируется в WorkspacePurgeRegistry из onModuleInit — плагин воркспейсов так и не узнаёт, что медиа существует. Инъекция @Optional(), поэтому медиа поднимается и без него.

06Сценарии — как это работает по шагам

6.1 Загрузка файла по сессии

Прямая multipart-загрузка на сервер приложения. Presigned-URL для загрузки не существует — байты всегда идут через Nest. Подписанный URL в этой системе бывает только на выдачу, и только если оператор его включил.

  1. Браузер отправляет POST /api/media/assets — multipart/form-data с частью file и текстовыми полями folderId и alt.OriginGuard + PermissionsGuard(media:create) + WorkspaceGuard
  2. Multer режет по потолку. FileInterceptor('file') вызывается без локальных опций — намеренно: так он наследует лимит из MulterModule.register, который MediaModule.forRoot собрал из config.plugins.media.maxUploadBytes. Раньше потолок читался из process.env на уровне модуля, и настройка хоста была мертва.регистрируется cap+1, потому что busboy срабатывает при fileSize === limit — так «максимум» становится включительным
  3. Превышение — 413 с человеческим текстом. MulterUploadFilter ловит две формы одной ошибки: сырой код LIMIT_FILE_SIZE и уже преобразованное Nest'ом PayloadTooLargeException('File too large'). Фильтр, смотревший только на код, не срабатывал никогда, и его дружелюбное сообщение было недостижимо.
  4. Имя проходит через value object. FileName.create отвергает пустое, длиннее 255, содержащее /, \ или управляющие символы. Имя — это лист, а не путь: иначе оно протащило бы обход каталогов в ключ хранилища.
  5. Тип классифицируется, но не проверяется. MediaKind.fromMime раскладывает по префиксу: image/, video/, audio/, известные архивные типы → archive, всё остальное → document. Белого списка типов нет: загрузить можно что угодно, включая .html и .svg. Вся защита перенесена на выдачу (см. 6.4).
  6. Изображение буферизуется один раз. Поток одноразовый, а прочитать его нужно и записи оригинала, и процессору. Оговорка в самом коде: сегодня любая загрузка и так целиком в памяти, потому что оба маршрута используют memoryStorage multer'а; сквозной стриминг требует ухода от него и является отдельной работой. Границей памяти служит maxUploadBytes.
  7. Оригинал уходит в хранилище — provider.put до открытия транзакции: строке нужен storage_key, а он существует только внутри возврата put. Каждый записанный ключ складывается в локальный список written.
  8. Деривативы — «по возможности». Sharp читает размеры (пишутся в width/height) и делает WebP thumb (≤320px) и preview (≤1280px), без апскейла. Каждый — свой put с isVariant: true, то есть в пространство variants/: иначе файл, буквально названный thumb.webp, затёр бы собственный дериват. Источник, который процессор не декодирует (SVG, битые байты), просто не даёт деривативов и никогда не валит загрузку.
  9. Транзакция. Если указана папка — FOR SHARE на ней: это сериализует загрузку против одновременного удаления папки, чтобы новый актив не осиротел в удаляемой папке. Затем Asset.create, save и событие media.asset.uploaded в outbox — строка и событие фиксируются вместе.
  10. Любой сбой освобождает всё. catch проходит по written и удаляет каждый блоб, а не только оригинал. Неудачная загрузка не оставляет за собой ничего.
  11. Ответ — полный AssetView, включая url, список имён деривативов, размеры, теги и имя загрузившего (резолвится из id).
Почему put обязан быть «всё или ничего»

Ключ существует только в возвращаемом значении put. Отклонившийся put никому имени не отдал — значит, всё, что он оставил, это мусор, который никакой вызывающий уже не назовёт и не уберёт. Отсюда контракт порта, и отсюда реализации: локальный пишет в .hex.part и делает один rename; S3 при сбое вызывает upload.abort(), иначе части multipart остаются оплачиваемыми, невидимыми для ListObjects и недостижимыми.

6.2 Загрузка по bearer-токену

POST /api/v1/media/assets — вторая половина API, рядом с публичным контент-API и под теми же двумя guard'ами (ApiTokenGuard + ApiTokenWorkspaceGuard, которые экспортирует content-server; зависимость на него уже есть ради порта резолвера, так что нового ребра между пакетами не появилось).

  1. Область — из токена, не из членства. Воркспейс определяется разрешённым воркспейсом токена. Заголовок X-Workspace-Id обязателен, когда токен покрывает больше одного воркспейса, и необязателен, когда ровно один; воркспейс вне «корзины» токена — 403.
  2. Параметры — в query, а не в теле. ?folderId= и ?alt=. Альт-текст здесь особенно важен: неприсмотренный импорт второго PATCH никогда не делает, и без этого поля он производил бы библиотеку навсегда неописанных изображений.
  3. Авторство приписывается человеку. uploaded_by — NOT NULL, а токен человеком не является, поэтому загрузка записывается на того, кто выпустил токен: это ответственное лицо, и это сохраняет осмысленность колонки «кто загрузил» в библиотеке. Токен без createdBy получает 400. Это не шаг авторизации: роль того пользователя не спрашивается вообще — решение уже принято областью токена.
  4. Дальше — тот же use-case. UploadAssetUseCase принимает EventActor ({ id, email }), а не PublicUser — это всё, что он когда-либо читал. Сессионный маршрут от этого не изменился, а токенный получил доступ, не выдумывая пользователя ради удовлетворения более широкого типа.

6.3 Просмотр библиотеки

  1. Дерево папок одним запросом. GET /media/folders отдаёт все папки воркспейса плоско, с parentId, и число активов в корне. Дерево собирает клиент.
  2. Страница активов. GET /media/assets?folderId=&search=&kind=&sort=&page=&pageSize=. По умолчанию 24 на странице, максимум 100. Сортировки — закрытый список: newest (по умолчанию), oldest, name-asc, name-desc, largest, smallest; тай-брейк всегда по id, чтобы страницы не «плавали».
  3. Фильтры валидируются до Postgres. folderId — колонка uuid, kind — enum, поэтому непарсящееся значение раньше доезжало до драйвера и возвращалось как 500 (invalid input syntax). Теперь ListAssetsQuery бросает InvalidAssetFilterError → 400. Проверка живёт в запросе, а не в контроллере, потому что у запроса есть второй вызывающий — агентский инструмент media_assets_search.
  4. Поиск экранирует метасимволы. % и _ в терме матчат сами себя, а сам обратный слэш экранируется первым. Без этого ?search=_ находил каждый файл с именем хотя бы в один символ, а ?search=% — всю библиотеку. Ищет и по name, и по элементам tags.
  5. Имена загрузивших резолвятся пакетно (uploader-names.ts), с запасным значением для удалённого пользователя — колонка «кто загрузил» не должна показывать uuid.

6.4 Выдача файла — самая нагруженная решениями часть

Скачивание считается враждебными байтами. media_asset.mime_type — это то, что заявил загружающий; ничего не нюхает тело. При этом /api/media/... — тот же origin, что и админка (за dev-прокси и в любом развёртывании, которое фронтит оба с одного хоста). Без обработки загруженный .html становился хранимой XSS на собственном origin приложения.

  1. Актив находится и авторизуется. Сессионный маршрут — по членству в воркспейсе-владельце; токенный — по совпадению с воркспейсом запроса. В обоих случаях любой отказ (нет такого id, не участник, чужой воркспейс) — один и тот же 404.и это верно даже для другого воркспейса ВНУТРИ корзины токена — иначе X-Workspace-Id был бы рекомендательным
  2. Выбирается дериват. ?variant=thumb|preview. Поиск через Object.hasOwn, а не голым индексом: variants — обычный JSON-объект, и ?variant=toString иначе резолвился бы в член прототипа, вошёл бы в ветку без ключа и уронил бы провайдера. Отсутствующий дериват — не ошибка, отдаётся оригинал.
  3. Решается способ доставки. Если directServe: 'signed-url' и провайдер умеет подписывать — 302 на короткоживущий URL. Это происходит после авторизации, никогда вместо неё; редирект лишь решает, как поедут уже разрешённые байты.Cache-Control: private, no-store — URL истекает, и общий кэш отдал бы мёртвую ссылку следующему зрителю
  4. Disposition закрепляется на самом URL. Редирект выбрасывает Content-Disposition, X-Content-Type-Options и CSP этого ответа, поэтому провайдер обязан вшить тип и disposition в подпись (у S3 — ResponseContentDisposition/ResponseContentType, у Azure — rscd/rsct). Провайдер, который не может, объявляет capabilities.directUrl: false — это и есть весь смысл этой возможности.
  5. Иначе — поток через приложение (StreamableFile), с тремя слоями защиты на каждом ответе обоих сырых маршрутов:
    • X-Content-Type-Options: nosniff — браузер не «дообнюхает» text/plain до text/html;
    • Content-Security-Policy: default-src 'none'; sandbox; base-uri 'none'; form-action 'none' — документ, который всё-таки отрисовался, сидит в непрозрачном origin, не выполняет скриптов и не грузит подресурсов;
    • Content-Disposition: inline только для белого списка: PDF, text/plain, растровые изображения (apng, avif, bmp, gif, jpeg, png, webp, x-icon) и всё с префиксом audio/ или video/. Остальное — attachment. Имя файла процентно кодируется, чтобы кавычка или управляющий символ в name не сломали заголовок.
SVG исключён из inline намеренно

MediaKind относит SVG к изображениям, но при прямой навигации это скриптуемый документ. Поэтому он приходит как attachment. На плитки библиотеки это не влияет: <img src> игнорирует Content-Disposition — disposition действует только на навигацию.

Три способа провалить скачивание, и только один из них 500

Нет такого id или вызывающий не участник → 404, намеренно один и тот же код, чтобы id нельзя было перебирать. Строка есть, а блоба нет (база восстановлена на пустой том, блоб освободили руками, миграция оборвалась) → тоже 404: раньше это был 500, что и неверно (со стороны вызывающего неотличимо от отсутствующего актива), и является сигналом (сообщает, что строка настоящая). Порт требует от get отклоняться с ObjectNotFoundError — его поднимают provider-local на ENOENT/ENOTDIR и provider-s3 на NoSuchKey, — а to-http.ts превращает его в голый 404 без тела: собственное сообщение утекло бы ключом хранилища. Ключ резолвится вне корня хранилища → 500, специально: это испорченная колонка storage_key, а не ошибка вызывающего, и назвать её «не найдено» значило бы похоронить проблему оператора под правдоподобным ответом. to-http перебрасывает всё нераспознанное именно ради этого. Только ENOENT/ENOTDIR становятся «не найдено»: отказ по правам или исчерпанная таблица дескрипторов — это авария, и рядить её в 404 нельзя.

6.5 Правки: переименование, перемещение, теги, альт, дорожки

  1. Один PATCH /media/assets/:id принимает любое подмножество полей. folderId: null двигает в корень, отсутствие поля оставляет как есть — разница между «null» и «не передано» здесь несущая.
  2. Перемещение берёт FOR SHARE на целевой папке — та же сериализация против каскадного удаления, что и при загрузке.
  3. Теги и дорожки заменяются целиком, а не патчатся поштучно: редактор показывает список и сохраняет список, а у дорожки нет естественного ключа, кроме пары (kind, srclang), к которому мог бы адресоваться частичный мутатор.
  4. Альт нормализуется одинаково на всех путях — обрезка пробелов, пустое → null. Иначе пробел маскировался бы под покрытие в отчёте доступности.
  5. Переименование папки — отдельный маршрут и умеет только имя. Сменить родителя папки нельзя ни одним маршрутом, поэтому цикла в дереве возникнуть не может — проверка на цикл не нужна и её нет.

6.6 Удаление: массовое и каскадное

  1. Массовое удаление активов — DELETE /media/assets с телом { ids }: непустой список, не длиннее 100. Строки и события уходят в одной транзакции, ответ — { deleted: N }, где N — сколько нашлось в этом воркспейсе.
  2. Блобы освобождаются после коммита, веером с ограничением в 16 одновременных вызовов: 100 id — это 300+ блобов, и открывать столько провайдерских вызовов в один тик ради работы, которую никто не ждёт, не нужно. Освобождение сверяет storageProvider и молча пропускает чужие.
  3. Удаление папки каскадное и безусловное. Раньше непустая папка отвечала 409, и населённое дерево нельзя было удалить, не разобрав его руками по уровням. Предохранитель принадлежит подтверждению в интерфейсе, которое называет, что исчезнет, а не серверу, с которым нельзя поспорить. FolderNotEmptyError удалён.
  4. Обход поддерева — рекурсивный CTE по parent_id с фильтром по воркспейсу в обеих ветвях, затем перечитывание строк FOR UPDATE и возврат самых глубоких первыми: ни один родитель не удаляется раньше своих детей, а параллельная загрузка/перемещение/создание подпапки сериализуется против удаления вместо того, чтобы осиротеть. (FOR UPDATE нельзя навесить на SELECT самого рекурсивного CTE — Postgres запрещает, — отсюда два оператора.)
  5. Обход повторяется в цикле, пока поддерево не перестанет меняться: CTE не берёт блокировок, поэтому подпапка, созданная под потомком между двумя операторами, иначе пережила бы собственного родителя. Когда все известные id заблокированы, повторный обход либо соглашается, либо показывает нового ребёнка — а дальнейшие вставки под ним уже блокируются на нас. Сходимость ограничена SUBTREE_WALK_ROUNDS.
  6. reclaimAssetBlobs общий с массовым удалением активов, чтобы ни один путь не мог забыть про деривативы.

6.7 Дублирование актива

  1. POST /media/assets/:id/duplicate — право media:create, потому что это создание нового актива, а не правка старого.
  2. Имя копии строится до обращения к хранилищу. « copy» вставляется перед расширением и может перевалить 255 символов; сказать об этом умеет только value object. Оставленное до транзакции, слишком длинное имя доезжало до провайдера и взрывалось немаппленным ENAMETOOLONG — 500 вместо 400.
  3. Источник у чужого провайдера отвергается, а не копируется наполовину: get получил бы ключ, который здесь ничего не значит. В здоровом развёртывании это недостижимо благодаря загрузочной проверке.
  4. Деривативы копируются тоже, и все записанные ключи учитываются, чтобы откат освободил их все.

  • Проекция сужена. Отдаются id, имя, вид, MIME, размер, альт, теги, папка, дата и downloadPath; variants и размеры в пикселях выброшены, как и полный url — это маршрут, который модель всё равно не выберет, он стоит токенов и ни на что не отвечает. Путь оставлен для другого читателя: человека, попросившего «перечисли файлы», интересуют ссылки, по которым можно кликнуть.
  • downloadPath — единственное поле каталога, зависящее от поверхности. Копайлот получает /media/assets/:id/raw (выводит область из членства, поэтому браузер загрузит его напрямую); MCP получает /api/v1/media/assets/:id/raw (гейт media:read, скачивается тем же bearer-токеном, которым сделан вызов). Сессионный маршрут ответил бы внешнему агенту 401, а ссылка, гарантированно неработающая, хуже её отсутствия. Это только представление: оба маршрута проверяют одну и ту же область и одно и то же право.
  • Чтение байтов — четыре ограничения. Белый список MIME-типов, никогда чёрный: MediaKind кладёт PDF, Word и Markdown в один document, так что грубый вид фильтром быть не может, а перечисление того, что мы умеем, отказывает новому бинарному формату по умолчанию. Потолок применяется на лету (256 КБ): буферизовать актив целиком и потом резать — значит держать 50 МБ в памяти ради 256 КБ, и это давление на память может вызвать любой, у кого есть право загрузки; поток уничтожается сразу за потолком. Ошибка декодирования фатальна: MIME — это заявление, а не факт, и ошибка, называющая проблему, лучше страницы замещающих символов, которую модель добросовестно перескажет. Исключение — усечённое чтение, где stream: true придерживает неполную хвостовую последовательность: потолок падает на произвольный байт, и разрезанный трёхбайтовый кодпойнт не должен ронять годный файл. И, наконец, DownloadAssetQuery.locate намеренно не привязан к воркспейсу (маршрут выводит его из строки), поэтому инструмент сверяет location.workspaceId сам — и о несовпадении сообщает тем же «нет такого актива», иначе это был бы оракул по id.
  • Создание файла: формат из закрытого перечисления, а не MIME. Пять форматов — md, csv, html, json, txt; получив свободный contentType, модель рано или поздно выдаст что-нибудь вроде application/x-msdownload, и MediaKind без возражений отнесёт это к документам. Расширение следует из формата, заменяя то, которым модуль владеет (summary.txt в формате md становится summary.md, а не summary.txt.md), и оставляя чужое (2026.q3 сохраняет .q3). Путь отвергается, а не сплющивается: модель охотно предложит reports/2026/q3.md, и тихо выбросить каталоги значило бы положить отчёт в корень, пока модель говорит пользователю другое; сообщение об ошибке называет folderId. Потолок MAX_AUTHORED_BYTES — 1 МБ, намного ниже maxUploadBytes: контент пришёл аргументом инструмента, сгенерированным токен за токеном, и мегабайт такого — сбой, а не отчёт. Применитель зовёт тот же UploadAssetUseCase, наследуя атомарность, блокировку папки, освобождение блобов и маршрутизацию в провайдер.
  • Удаления не предлагается — намеренно. Каскад папки уносит всё поддерево с необратимым освобождением блобов, и у запроса на подтверждение нет способа отрисовать «это удалит 4 папки и 213 файлов». Отдать такое недетерминированному подборщику инструментов нужно через отдельный ADR, а не через провайдер.
Чтение файла расширяет поверхность prompt-injection

До этого инструмента копайлот читал контент, написанный командой; теперь он читает файл, который в библиотеку положил кто угодно с правом media:create, а .md — прекрасный носитель для «забудь предыдущие инструкции». Защита — та, что получает результат любого инструмента: движок прогона оборачивает вывод в fenceUntrusted. По MCP этой защиты нет — там нет движка прогона, и от MCP-хоста ожидается, что он сам относится к результатам как к недоверенным данным. Что переносится через границу, так это потолок, и он-то и важен: область токена решает, что он может сделать с прочитанным, и токен read, проглотивший инструкцию, всё равно не имеет инструмента записи.

6.9 Отложенные загрузки на медиаполе записи

Самый неочевидный сценарий во всей группе — и он объясняет, почему медиаполе и тело статьи ведут себя по-разному.

  1. Пользователь выбирает файл на медиаполе. Ничего не отправляется. Файлу выдаётся настоящий uuid-плейсхолдер, и именно он ложится в значение формы — настоящий именно потому, что общее ядро валидирует значение медиаполя как uuid, и подготовленный файл проходит клиентскую валидацию, бейдж «изменено» и гейт публикации ровно как прикреплённый актив.
  2. Хук живёт выше вкладки. Вкладки редактора — это маршруты, и панель «Медиа» размонтируется, стоит переключить вкладку; поэтому usePendingMediaUploads монтирует ContentEntryView, а панель дотягивается до него обратно через непрозрачный EntryTabContext.presave[id].
  3. commit выполняется внутри сохранения, до записи и под индикатором занятости: загружает каждый подготовленный файл, на который значения всё ещё ссылаются (по три за раз, по одному запросу на файл), и возвращает значения с плейсхолдерами, заменёнными на настоящие id.
  4. Упавший файл отменяет сохранение с тостом, который его называет. Ничего не записано, форма сохраняет плейсхолдеры. Те файлы, что успели загрузиться, помнят свой id актива, поэтому повтор их прикрепляет, а не загружает второй раз.
  5. settle после успешной записи отзывает object URL и сбрасывает подготовку — переинициализированная форма уже держит настоящие id сохранённой записи.
  6. Тело статьи ведёт себя противоположно — и это осознанно. Поле держит id, а тело держит URL, и URL не существует, пока не существуют байты, — значит, загрузка обязана произойти в момент выбора файла. Размен односторонний: брошенная правка оставляет актив в библиотеке, где он виден и удаляем, вместо тела, указывающего в никуда.
  7. Выбор существующего актива не откладывается — он уже загружен; прикрепление id это обычная правка формы, едущая на «Сохранить», как всякая другая.

Зачем токену вообще нужен сырой маршрут

Сессионный raw выводит область из членства, которого у токена нет вовсе, поэтому bearer получал 404 ровно на тех URL, которые ему раздают публичные чтения контента. Этот маршрут выводит ту же область из разрешённого воркспейса токена — эквивалентная граница для учётных данных, не являющихся человеком. Причём актив в другом воркспейсе того же токена тоже 404: запрос назвал воркспейс, и чтение через эту черту сделало бы X-Workspace-Id рекомендательным.

Живой сервер отдаёт сгенерированный OpenAPI на /reference. Токенные маршруты объявлены схемой безопасности apiToken и снабжены описаниями; сессионные документируются через DTO с @ApiProperty.

Один маршрут, две панели без «острова»: обе рисуются прямо на фоне страницы (никакой приглушённой доски, рамок и теней), разделённые волосяной линией lg:border-r, и каждая скроллится независимо. Страница берёт размер через flex-1 от колонки оболочки воркспейса, а не собственным svh-расчётом — одно измерение вьюпорта в цепочке, чтобы на масштабе не 100% не появлялся фантомный скроллбар. В отличие от контентной, она не выводится из маршрута: навигация по папкам здесь — состояние компонента, а не сегмент URL, поэтому крошки берутся из стора и рисуются как <button> — элемент, меняющий вид без смены адреса, это кнопка, а не ссылка.
  • Левая панель — дерево папок под заголовком «Все медиа», создание папки и счётчик занятого места.
  • Правая панель — заголовок с числом, тулбар (поиск, фильтр типа, сортировка), сетка плиток и пейджер. Списочного вида нет: переключатель grid/list и таблица удалены, константы MEDIA_VIEW не существует, состояния view в сторе нет. Вместе с таблицей ушёл и «выбрать всё» — он жил в её шапке; выделение теперь по плитке плюс «Очистить» в панели выделения.
  • Выделение и массовые действия — MediaSelectionBar: скачать, дублировать, переместить, удалить, очистить.
  • Меню на активе — один AssetActionsMenu: скачать, скопировать ссылку, дублировать, переименовать, переместить, удалить. Пункта «Открыть» в нём нет: в панели деталей он открывал бы панель, уже стоящую на экране, а на плитке дублировал бы миниатюру и имя файла — оба уже кнопки, отправляющие то же действие. Само действие 'open' осталось, исчез только пункт меню.
  • Панель деталей — превью (дериват preview), действия, метаданные, редактируемый альт-текст, теги.

Пагинация — серверная

Стор гоняет на сервер search, kind, sort, page и pageSize (24 / 48 / 96) и рисует ровно то, что пришло. Раньше это был filter + sort поверх одной фиксированной страницы в 100 элементов — то есть поиск мог не найти файл, который заведомо есть. Четыре сопутствующих правила, каждое исправляет свой класс бага:

  • placeholderData удерживает предыдущую страницу — иначе сетка гасла между страницами.
  • Смена страницы сбрасывает выделение. Выделение, пережившее свою страницу, было бы невидимым: панель выделения выводит имена из загруженной страницы, поэтому id, оставленные на первой, исчезали бы из счётчика на второй и молча возвращались позже — а «Удалить» их бы захватил.
  • Сужение списка возвращает на первую страницу. Страница 4 при новом поиске бессмысленна, и пользователь оказывался бы на пустой сетке сразу после ввода запроса, который что-то находит.
  • Страница подтягивается в диапазон, когда результат сжался — удалили последние три файла на пятой странице, и пейджер иначе остался бы на странице, которую сервер отдаёт пустой.

Очередь загрузки

  • Один запрос на файл, не более трёх сразу. Прежний Promise.all терял всю пачку из-за одного отказа.
  • Тост об успехе загрузки не показывается вообще. Диалог закрывается на подтверждении, так что тост заявлял бы результат, которого ещё нет; поверхностью статуса служит баннер, а кэш инвалидируется один раз на осевшую пачку.
  • Все остальные действия дают тост — на успехе, а не на отправке. Каждое действие стора возвращает Promise<boolean>, и страница цепляет свою фразу за него. Раньше рядом появлялись «Переименовано в “a/b.png”» и «Request failed with status code 400».
  • Отказы говорят словами API. toApiError кладёт описание транспорта в message, а разобранное тело в details, поэтому всё пользовательское идёт через apiMessage, который читает тело и падает на локальную формулировку — иначе вместо «File exceeds the maximum upload size.» показывался бы код статуса.
  • Файлы и учёт бегунка живут в ref, а не в состоянии, чтобы тик прогресса перерисовывал только маленькую строку, а не весь экран.
  • Размер в подсказке не называется. Потолок живёт в конфигурации сервера и ни один маршрут его админке не сообщает, поэтому прежнее «до 250 МБ» было числом, которое ничто не проверяло: 52-мегабайтный файл спокойно готовился и получал 413, передавшись целиком. Пока потолок нечитаем, подсказка говорит о принимаемых типах и молчит о размере.

Доступность

  • Медиаполе названо как группа (aria-labelledby → его <h3>), а не через <label for> на кнопку: медиаполе — составной контрол (выбрать / загрузить / убрать / переставить), и label заместил бы собственное имя триггера — дерево доступности читало «Обложка, кнопка» вместо «Выбрать из библиотеки». Как группа оно читается «Обложка, группа», а затем каждое действие своим именем.
  • Подтверждённое удаление отдаёт фокус сетке. И меню ⋯, и диалог подтверждения возвращают фокус каждый на свой триггер, а оба сидят на плитке, которую удаление только что убрало, — фокус оказывался на <body>. Страница перехватывает onCloseAutoFocus и наводит на озаглавленную секцию «Активы» с tabIndex={-1}, отвоёвывая фокус ещё несколько кадров, если чужой слой восстановит его позже. Отмена не тронута — её триггер всё ещё существует.
  • Триггер действий папки назван по папке («Действия для Изображений»), иначе сетка папок была бы рядом одинаковых кнопок «Действия с папкой».
  • Подтверждение удаления папки называет содержимое. Числа считаются из уже загруженного дерева — лишнего запроса нет, свежесть та же, что у последнего чтения папок. Пустая папка получает простую формулировку: перечислять опись из ничего — шум.
  • Object URL отзываются при размонтировании. Подготовленное видео на 200 МБ иначе висело бы в памяти всю жизнь вкладки.

Кэш

Ключи строятся фабрикой mediaKeys и всегда включают workspaceId: ['media', ws] → ['media', ws, 'folders'] → ['media', ws, 'assets', folderId, {search, kind, sort, page, pageSize}]. Мутации инвалидируют корень mediaKeys.all(workspaceId) — грубо, но безопасно: после загрузки меняются и счётчики папок, и страница, и виджеты. Виджеты Insights ходят по собственным ключам с retry: 1. Загрузки из тела статьи инвалидируют медиа-кэш, как только что-то осело, даже если запись потом не сохранится — актив-то уже в библиотеке.

Пять проверок при сборке приложения

assertOptions валидирует шов рано, там же, где он собран. Измерено на реальном приложении до её появления: указание конфига на бэкенд, который никто не подключил, поднималось без единого предупреждения, а каждая загрузка отвечала голым 500 Internal server error — сообщением, не называющим ни провайдера, ни настройку, которая его выбрала.

  1. Провайдер вообще передан — иначе текст ошибки содержит пример строки, которую надо написать.
  2. id непустая строка — он пишется в каждую строку актива и является тем, с чем загрузочная проверка сравнивает существующие.
  3. capabilities объявлены — ядру нечем их определить, и угаданная возможность — это либо молча неиспользованная функция, либо ответ, отданный без защиты.
  4. directUrl: true подтверждён методом — объявить возможность без реализации нельзя.
  5. directServe: 'signed-url' согласован с провайдером, и maxUploadBytes положителен — неположительный потолок отверг бы каждую загрузку.

Шестая проверка — уже во время старта: StorageProviderCheck (OnApplicationBootstrap) зовёт provider.verify?.() и группирует media_asset по storage_provider. 10Безопасность и устойчивость

Скачивание — это враждебные байты

MIME — заявление загружающего, приложение с медиа на одном origin. Отсюда три слоя на каждом ответе обоих сырых маршрутов: nosniff, CSP без единой возможности, и inline только по белому списку. Без этого загруженный .html был хранимой XSS на собственном origin.

Нет перечисления активов

Несуществующий id, чужой воркспейс, не-участник и потерянный блоб — один и тот же 404. То же правило у резолвера копайлотских вложений: чужой актив приходит отсутствующим, неотличимо от удалённого, а движок сворачивает недостачу в одну ошибку с числом.

Redirect не отменяет авторизацию

directUrlFor вызывается после резолва актива и проверки членства (или воркспейса токена) — он решает только, как поедут уже разрешённые байты. Внутри есть и вторая страховка: если провайдер подменили под нами, функция возвращает null, и байты пойдут потоком, а не исключением.

Disposition вшивается в подпись

302 выбрасывает Content-Disposition, nosniff и CSP этого ответа, поэтому решение принимает та же isInlineSafe, а провайдер закрепляет его на URL. Не умеющий этого объявляет directUrl: false. Плюс Cache-Control: private, no-store: кэшированный редирект пережил бы URL, на который указывает.

Имя файла — лист, а не путь

FileName отвергает /, \ и управляющие символы, а провайдер дополнительно чистит сегмент. Локальный проверяет, что ключ резолвится внутри корня: без этого remove('../../x') удалял бы произвольный файл, доступный пользователю сервера. Ключи из storage_key заслуживают этой проверки, потому что колонку может записать миграция, импорт или будущий провайдер.

Никакая ошибка не сплющивается в 4xx

to-http маппит ровно семь доменных ошибок и перебрасывает всё остальное. Испорченный storage_key обязан остаться громким 500 со стеком в логе — именно это нужно оператору; «не найдено» похоронило бы его проблему под правдоподобным ответом.

Потолок загрузки — единственная граница памяти

Оба маршрута используют memoryStorage, то есть файл целиком в куче. maxUploadBytes — это то, что не даёт её исчерпать, и потому он обязан быть конфигурацией хоста, а не константой. Сквозной стриминг — отдельная работа.

Каскад не выходит за тенант

Рекурсивный CTE фильтрует по воркспейсу в обеих ветвях, а не только в якорной. Каскад, сбежавший из своего тенанта, — худшая возможная ошибка здесь, поэтому это закреплено e2e-тестом, а не только ревью.

Блоки блобов и транзакция не расходятся

Запись блобов — до транзакции (нужен ключ), освобождение при удалении — после коммита. Первое требует компенсации в catch, второе гарантирует, что откатившееся удаление не уничтожит байты, на которые указывает уцелевшая строка. Обе стороны одинаково несущие.

Фильтры не доезжают до драйвера

Значения, идущие в WHERE по типизированным колонкам, валидируются в самом запросе — потому что вызывающих у него двое, и контроллер прикрыл бы только одного. Метасимволы LIKE экранируются, иначе ?search=% отдаёт всю библиотеку.

Отложено сознательно

  • Дедупликации нет — sha256 считается и хранится, но не ищется.
  • Сборщика мусора для блобов нет. Подписчик на media.asset.deleted назван в планах, но не написан; освобождение остаётся встроенным в use-case и «по возможности». Осиротевший блоб (провайдер отказал в момент освобождения) сегодня никто не подберёт.
  • Зондирование длительности видео не сделано — колонка duration всегда пуста.
  • Проверки содержимого нет — ни sniffing, ни антивирус, ни белый список типов при загрузке.
  • Инструмента переноса блобов между бэкендами нет. Смена провайдера — отказ старта; перенос делается вне системы.
  • Rate limit на загрузку отдельно не настраивается — общий лимитер плагина identity покрывает публичные маршруты аутентификации, а не медиа.

11Инварианты

Утверждения, которые обязаны выполняться всегда. Одновременно список для ревью и заготовка утверждений для тестов.

  • И-01Байты никогда не лежат в базе: строка актива содержит только storage_key + storage_provider.
  • И-02В развёртывании работает ровно один провайдер хранилища, переданный одним объектом; реестра, резолвера и defaultProvider не существует.
  • И-03provider.id — факт самого адаптера, записанный в каждую строку; приложение сравнивает его при чтении, удалении и очистке, а не ищет бэкенд по имени.
  • И-04Старт прерывается, если в media_asset есть строки чужого провайдера; сообщение называет имя и количество. Отсутствие таблицы отказом не является.
  • И-05capabilities.directUrl: true невозможно объявить без реализации directUrl(), а directServe: 'signed-url' — на провайдере, который не подписывает. Обе проверки — при сборке приложения.
  • И-06put — «всё или ничего»: отклонившийся вызов не оставляет за собой блоба и не отдаёт ключа.
  • И-07get отклоняется до открытия потока и именно с ObjectNotFoundError, когда ключа нет; remove идемпотентен.
  • И-08Все методы порта отклоняются промисом, а не бросают синхронно — синхронный бросок минует try, освобождающий блобы.
  • И-09Дериват никогда не может затереть оригинал: он пишется в зарезервированное пространство ключей variants/ через PutObject.isVariant.
  • И-10Генерация деривативов «по возможности»: источник, который процессор не декодирует, даёт ноль деривативов и никогда не валит загрузку.
  • И-11Неудачная загрузка (сбой хранилища или отката транзакции) освобождает все записанные блобы, включая деривативы.
  • И-12Удаление освобождает блобы после коммита, по Asset.storageKeys — оригинал и все деривативы; откатившееся удаление байты не уничтожает.
  • И-13Загрузка, перемещение и создание подпапки берут FOR SHARE на целевой папке и потому сериализуются против её каскадного удаления.
  • И-14Каскад удаления папки фильтрует по воркспейсу в обеих ветвях рекурсивного CTE, блокирует поддерево FOR UPDATE, возвращает глубочайшие первыми и повторяет обход до стабилизации.
  • И-15Каждый маршрут гейтится правом по константе PERMISSIONS.MEDIA_*; изменяющие состояние сессионные маршруты дополнительно несут OriginGuard.
  • И-16Каждый маршрут, кроме GET /media/assets/:id/raw, несёт WorkspaceGuard; этот один выводит область из строки актива и требует членства в воркспейсе-владельце.
  • И-17Несуществующий актив, чужой воркспейс, отсутствие членства и отсутствующий в хранилище блоб дают один и тот же 404; ключ хранилища в тело ответа не попадает.
  • И-18Ключ, резолвящийся вне корня хранилища, остаётся 500: это испорченные данные, а не ошибка вызывающего.
  • И-19Оба сырых маршрута всегда ставят X-Content-Type-Options: nosniff и CSP без возможностей; inline выдаётся только типам из белого списка, SVG в него не входит.
  • И-20Редирект прямой раздачи выполняется после авторизации, несёт закреплённые тип и disposition и сопровождается Cache-Control: private, no-store.
  • И-21Потолок загрузки включительный: ровно maxUploadBytes принимается, на байт больше — 413. Локальных limits у FileInterceptor нет ни на одном маршруте.
  • И-22Имя файла — лист: /, \, управляющие символы, пустое и длиннее 255 отвергаются FileName, а не чистятся молча.
  • И-23?variant= резолвится через Object.hasOwn; отсутствующий дериват — не ошибка, а откат к оригиналу.
  • И-24Непарсящийся folderId и неизвестный kind дают 400 из самого запроса, а не 500 от драйвера; % и _ в поиске матчат сами себя.
  • И-25Альт-текст нормализуется одинаково на всех путях (обрезка, пустое → null), поэтому пробел никогда не считается покрытием.
  • И-26Токенная половина умеет только загрузку и чтение байтов; media:update и media:delete не выдаются ни одной области токена.
  • И-27Загрузка по токену приписывается пользователю, выпустившему токен; его роль при этом не проверяется — решение уже принято областью токена.
  • И-28Актив в другом воркспейсе внутри корзины токена — тоже 404, иначе X-Workspace-Id был бы рекомендательным.
  • И-29Регистрация в реестре инструментов и в реестре очистки воркспейсов — @Optional(): медиа поднимается без копайлота, без MCP и без плагина воркспейсов.
  • И-30Три инструмента чтения видны обеим поверхностям, два «предложения» — только копайлоту; downloadPath — единственное поле, зависящее от поверхности, и это только представление.
  • И-31media_asset_read ограничен белым списком MIME и потолком 256 КБ, применяемым во время чтения; ошибка декодирования фатальна, кроме усечённого хвоста.
  • И-32media_propose_file принимает формат из закрытого перечисления, отвергает путь в имени и ограничен 1 МБ; применитель зовёт тот же UploadAssetUseCase, что и HTTP-маршрут.
  • И-33Слой domain/ не импортирует ни @nestjs/*, ни drizzle-orm, ни class-validator, ни infrastructure/.
  • И-34Провайдер зависит только от типа порта (стирается при компиляции) и своего вендорского SDK; ни один адаптер не тянет NestJS.
  • И-35Удаление воркспейса удаляет строки медиа и освобождает их блобы — без поштучных доменных событий, одним delete на таблицу.
  • И-36В админке отсутствие media:read не запускает запросы вовсе; сбой чтения даёт собственное состояние ошибки с повтором, а не пустое состояние.
  • И-37Смена страницы, поиска, фильтра или сортировки сбрасывает выделение; страница подтягивается в диапазон, когда результат сжался.
  • И-38Файл, выбранный на медиаполе записи, не загружается до сохранения записи; упавшая загрузка отменяет сохранение целиком, а уже загруженные файлы при повторе не загружаются второй раз.
  • И-39Файл, вставленный в тело статьи, загружается сразу — тело держит URL, а URL не существует без байтов.
  • И-40Ключи кэша админки всегда содержат workspaceId.

12Чек-лист тестирования

Формулировки — «действие → ожидаемый результат», чтобы их можно было брать в тест-кейс без переписывания. Серверная часть проверяется curl + psql (плюс просмотр каталога хранилища), админская — браузером. Существующие наборы: apps/server-e2e/src/server/media/* (8 файлов: активы, папки, прямая раздача, харденинг, локальное хранилище, проверка провайдера, область токена, потолок загрузки), apps/server-e2e/src/server/insights/media-insights.spec.ts, apps/server-e2e/src/server/content/content-media-fields.spec.ts, apps/server-e2e/src/server/copilot/copilot-media-files.spec.ts, apps/admin-e2e/src/media/* (3 файла) и apps/admin-e2e/src/content/media-fields.spec.ts.

Загрузка

  • Загрузить PNG → 200 с AssetView; строка в media_asset; в хранилище три блоба — оригинал и два под variants/; width/height заполнены.
  • Загрузить SVG → 200; kind = image; деривативов нет, variants = {}; загрузка не упала.
  • Загрузить ZIP → kind = archive; блоб один.
  • Загрузить файл с неизвестным MIME → kind = document, отказа нет — белого списка типов не существует.
  • Файл ровно в maxUploadBytes → 200. На байт больше → 413 с текстом «File exceeds the maximum upload size.», а не «File too large».
  • Запрос без части file → 400 «file is required».
  • Имя a/b.png → 400, актив не создан, блоб не записан.
  • Имя из 300 символов → 400.
  • folderId несуществующей папки → 404; блобы, записанные до транзакции, освобождены — каталог хранилища чист.
  • Оборвать соединение в середине загрузки → в хранилище не остаётся ни .part-файла, ни частичного объекта.
  • Загрузить один и тот же файл дважды → два актива и два блоба — дедупликации нет; checksum у них совпадает.
  • Загрузить с alt из одних пробелов → в базе alt IS NULL; в отчёте покрытия файл считается непокрытым.
  • Лишнее поле в теле → 400 от глобального ValidationPipe.
  • Загрузка под ролью viewer → 403.

Выдача файла

  • Скачать PNG → 200; Content-Disposition: inline; X-Content-Type-Options: nosniff; CSP default-src 'none'; sandbox; ….
  • Скачать загруженный .html → attachment, не inline; те же nosniff и CSP.
  • Скачать SVG → attachment. При этом плитка в сетке рисуется — <img> игнорирует disposition.
  • Имя файла с кавычкой или управляющим символом → заголовок не ломается (имя процентно кодируется).
  • ?variant=thumb на изображении с деривативами → WebP, размер меньше оригинала.
  • ?variant=thumb на SVG → оригинал, 200, не ошибка.
  • ?variant=toString → оригинал; провайдер не получает undefined и не падает.
  • Актив чужого воркспейса (пользователь не участник) → 404, идентичный несуществующему id.
  • Удалить блоб из хранилища руками, оставив строку → 404 с пустым телом, не 500; ключ хранилища в ответе отсутствует.
  • Подменить в базе storage_key на ../../etc/passwd → 500 со стеком в логе, а не 404 и не отданный файл.
  • Подменить в базе storage_provider на чужое значение и перезапустить → приложение не стартует; сообщение называет чужое имя и количество строк.
  • То же без перезапуска, запросить байты → 500 с сообщением, называющим оба провайдера.
  • Не-uuid в пути → 400 от ParseUUIDPipe.

Прямая раздача (directServe: 'signed-url')

  • Старт с signed-url на локальном провайдере → приложение не стартует; сообщение называет провайдера и предлагает либо убрать настройку, либо сменить бэкенд.
  • Скачивание на подписывающем провайдере → 302; Cache-Control: private, no-store; в URL закреплены тип и disposition.
  • Не-участник на том же маршруте → 404, редиректа нет — авторизация идёт первой.
  • Загруженный .html при включённой прямой раздаче → в подписанном URL disposition = attachment.
  • directServeTtlSeconds = 0 → приложение не стартует.

Папки и удаление

  • Создать две папки с одинаковым именем под одним родителем → обе создаются — уникальности имён нет.
  • Создать папку с несуществующим parentId → 404.
  • Удалить папку с подпапками и файлами → 204; исчезает всё поддерево; блобы всех активов (включая деривативы) освобождены; 409 не бывает никогда.
  • Удалить папку чужого воркспейса → 404; ни одна строка чужого воркспейса не тронута.
  • Создать подпапку под удаляемым поддеревом параллельно с удалением → по завершении осиротевших строк нет: либо подпапка удалена вместе с деревом, либо её создание отвергнуто.
  • Массовое удаление 100 активов → { deleted: 100 }; все блобы и деривативы исчезли из хранилища.
  • Массовое удаление 101 id → 400.
  • Пустой список id → 400.
  • В списке id чужого воркспейса → он не считается в deleted и не удаляется.
  • Удалить актив, на который ссылается опубликованная запись → удаление проходит без предупреждения; следующее сохранение записи даёт 422 «must reference an existing asset»; публичное чтение просто опускает это медиа.
  • Удалить воркспейс целиком → строки media_asset/media_folder исчезли, каталог хранилища этого воркспейса пуст, поштучных событий media.asset.deleted в outbox нет.

Список, фильтры, правки

  • ?folderId=не-uuid → 400, не 500.
  • ?kind=picture → 400 с перечислением допустимых значений.
  • ?search=% → находит только активы, в имени или теге которых есть литеральный %.
  • ?search=_ → то же для символа подчёркивания, а не вся библиотека.
  • ?pageSize=1000 → отдаётся 100.
  • ?page=0 или ?page=abc → трактуется как 1.
  • Две страницы подряд при одинаковых значениях сортировки → дубликатов между страницами нет (тай-брейк по id).
  • PATCH только { tags: [] } → теги очищены, имя и папка не тронуты.
  • PATCH { folderId: null } → актив в корне.
  • PATCH { folderId } несуществующей папки → 404, актив не перемещён.
  • PATCH с 51 тегом или тегом в 65 символов → 400.
  • PATCH { tracks } с kind: 'lyrics' → 400 — kind ограничен четырьмя значениями.
  • PATCH под ролью viewer → 403.
  • Дублировать актив с именем в 254 символа → 400 (« copy» переполняет предел), блоб копии не записан.
  • Дублировать изображение с деривативами → у копии свои блобы деривативов, альт-текст перенесён.

Токенная половина

  • Загрузка токеном области read → 403 — media:create есть только у full.
  • Загрузка токеном full → 200; uploaded_by = пользователь, выпустивший токен; в библиотеке колонка «кто загрузил» показывает его имя.
  • Скачивание токеном read → 200 — media:read есть у обеих областей.
  • Скачивание актива другого воркспейса той же корзины токена → 404.
  • Токен на два воркспейса без X-Workspace-Id → отказ; с одним воркспейсом заголовок необязателен.
  • PATCH или DELETE по токену → маршрутов не существует; сессионные отвечают отказом аутентификации.
  • Загрузка сессионного пользователя по токенному маршруту → отказ — маршрут гейтится ApiTokenGuard.

Агентские инструменты

  • media_assets_search без folderId → ищет по всему воркспейсу, включая вложенные папки.
  • То же с folderId: null → только корень — два состояния различимы.
  • Результат поиска → содержит downloadPath и не содержит variants, размеров в пикселях и полного url.
  • Тот же инструмент через MCP и через копайлот → downloadPath различается (/api/v1/… против /media/…), всё остальное одинаково.
  • media_asset_read на PDF → отказ по белому списку MIME, а не мусорный текст.
  • media_asset_read на файле в 1 МБ → возвращается не более 256 КБ, с признаком усечения; полный файл в память не читается.
  • Файл, объявленный text/plain, но содержащий бинарь → ошибка декодирования, а не страница замещающих символов.
  • Усечение попало в середину многобайтового символа → файл читается, хвост отброшен, ошибки нет.
  • media_asset_read на активе чужого воркспейса → «нет такого актива» — то же, что для несуществующего.
  • media_propose_file с именем reports/q3.md → ошибка инструмента, называющая folderId; модель может исправиться и предложить снова.
  • media_propose_file с summary.txt и форматом md → файл называется summary.md, а не summary.txt.md.
  • media_propose_file на 2 МБ содержимого → отказ (потолок 1 МБ), несмотря на больший maxUploadBytes.
  • Инструмент удаления → в каталоге отсутствует — ни копайлоту, ни MCP.
  • Приложение без копайлота и без MCP → стартует; регистрация инструментов молча пропускается.

Контракт провайдера (testkit)

  • npx nx test любого пакета адаптера → набор describeStorageProvider проходит целиком.
  • Два актива с одинаковым именем файла → разные ключи.
  • Дериват с именем thumb.webp рядом с оригиналом того же имени → ключи не совпадают, оригинал цел.
  • Поток, падающий в середине put → промис отклонён и в хранилище ничего не осталось.
  • get по никогда не записанному ключу и по удалённому → ObjectNotFoundError в обоих случаях, до открытия потока.
  • remove дважды и по несуществующему ключу → успех, без исключения.
  • Провайдер с directUrl: false и реализованным методом (или наоборот) → набор падает.

Админка

  • Открыть медиатеку под viewer → библиотека видна; кнопки загрузки, создания папки, переименования и удаления отсутствуют.
  • Отозвать media:read и открыть страницу → карточка «нет доступа»; сетевых запросов к /media/* нет вовсе.
  • API отвечает 500 на список активов → состояние ошибки с role="alert" и кнопкой «Повторить», не «здесь пусто».
  • Пустая библиотека → пустое состояние с приглашением загрузить (и без приглашения, если нет media:create).
  • Фильтр, не давший совпадений → формулировка отличается от «библиотека пуста» и предлагает сбросить фильтры.
  • Перетащить пять файлов в диалог загрузки → все пять в списке подготовки; у изображений локальные миниатюры; одновременно летят не более трёх.
  • Один файл из пачки падает → остальные доезжают; у упавшего есть «Повторить»; вся пачка не теряется.
  • Отменить загрузку в полёте → строка помечается отменённой; запрос действительно прерван.
  • Подтвердить диалог загрузки → тоста об успехе нет; статус показывает баннер.
  • Переименование с ошибкой сервера → на экране только сообщение сервера, без параллельного «Переименовано в …».
  • Удалить непустую папку → подтверждение называет числа файлов и подпапок; у пустой — простая формулировка.
  • Подтвердить удаление актива → фокус уходит на секцию «Активы», а не на <body>.
  • Отменить удаление → фокус возвращается на триггер меню.
  • Выделить активы, перейти на вторую страницу → выделение сброшено; счётчик не «мигает» и не возвращает старые id позже.
  • Удалить последние активы на последней странице → пейджер подтягивается на существующую страницу, пустая сетка не показывается.
  • Ввести поиск, находясь на 4-й странице → переход на 1-ю.
  • Сетка с изображениями → запрашиваются ?variant=thumb, а не полные оригиналы; панель деталей — preview.
  • Разрыв дерева фокуса при закрытии диалога переноса → фокус остаётся внутри страницы.

Медиаполе записи и тело статьи

  • Выбрать файл на медиаполе и не сохранять запись → в библиотеке файла нет — ни одного запроса загрузки не отправлено.
  • Выбрать файл и сохранить → загрузка происходит внутри сохранения; в значении записи реальный id, плейсхолдера нет.
  • Файл падает при сохранении → запись не сохранена, тост называет файл, форма сохраняет плейсхолдеры.
  • Повторить сохранение после частичного успеха → уже загруженные файлы не загружаются второй раз.
  • Убрать подготовленный файл до сохранения → object URL отозван, файл не загружается.
  • Переключить вкладку редактора и вернуться → подготовленные файлы на месте — хук живёт выше вкладки.
  • Выбрать существующий актив библиотеки → никакой загрузки; обычная правка формы.
  • Файл, не проходящий по accept поля → отвергается в момент выбора, в значение не попадает; сервер перепроверяет при сохранении.
  • Запись без content:update → плитки видны, всё остальное (выбрать, загрузить, убрать, переставить, зона перетаскивания) отсутствует; диалог загрузки не смонтирован.
  • Пользователь с полным набором media:*, но без права на эту запись → то же самое — это контентное право, а не медийное.
  • Медиаполе ссылается на удалённый актив → предупреждающая плитка с «мёртвым» id, а не пустое место и не бесконечное ожидание.
  • Открыть редактор до прихода ссылок на медиа → плитка-заглушка «резолвится»; полноразмерные оригиналы не запрашиваются; после осевшего чтения без ссылки — откат на оригинал, а не вечное ожидание.
  • Вставить изображение в тело статьи из библиотеки → в узел уходит previewUrl и ширина; ничего не загружается.
  • Загрузить изображение прямо из тела статьи → загрузка происходит немедленно, файл появляется в корне библиотеки, кэш инвалидируется.
  • Выбрать в теле статьи PDF или аудио → вставка не происходит — у редактора нет такого узла.

Insights

  • Виджет «Что занимает хранилище» → длина полос — байты, и только байты; количество показано отдельно.
  • Воркспейс с несколькими крупными видео и тысячами картинок → по количеству лидируют изображения, по байтам — видео; обе цифры видны.
  • Изображение с alt = ' ' → считается непокрытым.
  • Виджет альт-текста → заголовок — число недостающих, а не процент покрытия; окна дат нет.
  • ?days=9999 → обрезается до 365; ?days=abc → 30.
  • Сумма байтов у большого воркспейса → приходит числом без потери точности (sum(size)::bigint).

Чего ещё нет

  • Presigned-загрузки. Файл всегда идёт через приложение; подписанный URL бывает только на выдачу.
  • Дедупликации, GC осиротевших блобов, зондирования длительности видео.
  • Проверки использования при удалении — Media не знает, кто на неё ссылается.
  • Списочного вида и «выбрать всё» в сетке — удалены вместе с таблицей.
  • Редактирования тегов и дорожек субтитров в админке. Сервер это принимает (PATCH с tags и tracks), но интерфейс теги только показывает, а дорожки не показывает вовсе — экрана для них нет.
  • Смены родителя папки — папку можно только переименовать.
  • Чтения потолка загрузки клиентом — ни один маршрут его не сообщает, поэтому подсказка не называет размер.
  • Клавиатурного набора e2e для поля и библиотеки.

Не расхождение, но заметная асимметрия

Сервер принимает tracks (дорожки субтитров) через PATCH /media/assets/:id, отдаёт их в AssetView и резолвит для контента с готовыми src. В админке нет ни одного экрана, который бы их редактировал — поиск по packages/media/admin/src не находит слова tracks вовсе. То есть возможность существует только для API-клиента и агентов; редактор, работающий через интерфейс, добраться до неё не может.

Второй артефакт серии.
