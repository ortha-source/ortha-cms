Nx Плагин для инструмента сборки: миграции и релиз без единой строчки ручной настройки

@orthacms/nx — единственный пакет монорепозитория, который обслуживает не приложение, а сборочный конвейер. Он выводит (infers) таргеты на проекты по признаку наличия файла: положил drizzle.config.ts — получил db:generate; положил пакет под packages/ — получил build, pack и публикацию в npm. Никакого пер-проектного конфигурирования нет и не должно быть.

01Бизнес-описание

Этот пакет не видит ни один пользователь CMS. Его аудитория — разработчик, который добавляет плагин, и релиз-инженер, который выкатывает версию. Ценность у него ровно одна и вполне измеримая: сократить количество ручных решений в двух самых опасных операциях проекта — изменении схемы базы данных и публикации в реестр, откуда ничего нельзя отозвать.

Какую задачу решает

  • Ноль настройки на проект. В монорепозитории 11 проектов со своей схемой БД и 56 публикуемых пакетов. Если бы каждый описывал свои таргеты сам, эти описания разъезжались бы — по одному опечатанному пути на каждый десяток пакетов. Вместо этого таргеты выводятся из наличия файла: новый плагин получает и генерацию миграций, и сборку, и публикацию просто потому, что существует.
  • Одна реализация миграций на монорепозиторий и на сгенерированное приложение. Исполнители БД — тонкие адаптеры над @orthacms/cli. Применение миграций — самая разрушительная операция в системе; иметь две её реализации, которые со временем разойдутся, дороже, чем терпеть один слой косвенности.
  • Релиз, который не разваливается на середине. npm ограничивает скорость записи одного аккаунта, а lockstep-релиз просит его принять несколько десятков тарболов подряд. Штатный исполнитель Nx этого не переживает: версия уже закоммичена, отмечена тегом и запушена, а в реестре — половина набора. Здесь публикация сериализована файловой блокировкой, разнесена паузой и ретраится с экспоненциальным откатом.
  • Отказ вместо тихой беды. Три места, где инструмент лучше остановится: миграция без DATABASE_URL, Studio на порту 0, публикация имени, которое npm отказался создавать. В каждом случае раньше был «зелёный» результат, за которым не стояло ничего полезного.

Кому это видно

Разработчик плагина

Правит Drizzle-схему и запускает nx run <plugin>:db:generate --name=…. База данных для этого не нужна: генерация только сравнивает схему со снимком.

Тот, кто поднимает стенд

Один nx run server:db:migrate применяет миграции всех плагинов в порядке, который задал хост. Каждый плагин ведёт свою таблицу журнала.

Релиз-инженер

Запускает npm run release с чистого main. Внутри — сборка, стейджинг переписанного манифеста и троттлинг публикаций, которого он не настраивает.

Чем этот пакет не является

  • Это не CLI. Реализации generate, migrate и studio живут в @orthacms/cli. Здесь — только обёртки, которые умеют получить путь от Nx и прочитать TypeScript-конфиг из исходников.
  • Это не генератор проектов. Ни одного Nx-генератора пакет не поставляет: в package.json объявлен только ключ executors. Скаффолдинг приложения — это create-ortha-app.
  • Это не часть продукта. Пакет помечен private: true и исключён из релиза явным !@orthacms/nx в nx.json. Он живёт только внутри этого репозитория.
  • Это не владелец схемы. Ни одной таблицы, ни одной миграции своей у него нет. Он знает как применить чужие миграции, но не какие.
Ключевая идея архитектуры

Тонкие исполнители над общим ядром, и половина этого ядра вынесена из пакета. db:generate, db:migrate и db:studio — адаптеры над runDrizzleKitGenerate, applyPluginMigrations и runDrizzleKitStudio из @orthacms/cli. Раньше эти функции лежали здесь, в src/lib/drizzle/, куда приложение, установленное из npm, дотянуться не могло вовсе — пакет приватный и не публикуется, а значит у сгенерированного приложения не было способа мигрировать собственную базу. Релизная логика (src/lib/release/) осталась здесь: её запускает только этот репозиторий.

02Состав и место в системе

Пакет плоский — packages/nx, npm-имя @orthacms/nx, версия 0.0.1, флаг private: true. Он зарегистрирован в корневом nx.json строкой "@orthacms/nx" в списке plugins, рядом с @nx/js/typescript, @nx/eslint/plugin, @nx/vite/plugin, @nx/vitest, @nx/playwright/plugin, @nx/webpack/plugin и @nx/jest/plugin. Как и остальные пакеты воркспейса, он потребляется из исходников: main и types указывают на ./src/index.ts, и Nx загружает его как TypeScript-плагин без шага сборки.

Почему db:generate не кэшируется — это решение, а не недосмотр

Кэш когда-то был, с inputs: ['{projectRoot}/src/lib/schema/**/*'] и outputs: ['{projectRoot}/migrations']. Обе половины были неверны, и вместе они теряли работу.

(1) Входы не могли быть правильными. Расположение схемы каждый проект задаёт в своём drizzle.config.ts: у хоста это ./src/content/index.ts, у media — ./src/lib/infrastructure/schema/index.ts, у copilot — глоб ./src/lib/*/infrastructure/schema/index.ts. Большинство конфигов указывает наружу из src/lib/schema/, то есть объявленный вход не матчил ничего: правка схемы не меняла хэш, и повторный запуск с тем же --name проигрывал закэшированное «No schema changes, nothing to migrate» — зелёная галка без миграции, ровно тот дрейф схемы и миграций, о котором предупреждает .cursor/BUGBOT.md.

(2) Выход — одновременно вход. drizzle-kit диффит схему против migrations/meta/*_snapshot.json, который лежит внутри объявленной выходной директории. Значит, результат не является функцией объявленных входов, как бы их ни записали, а восстановление из кэша заменяет всю папку migrations/ — стирая миграции, созданные после записи кэш-записи, вместе с журналом и снимком.

Вывод входов из каждого конфига чинит (1), но не (2), и означал бы импорт десятка TypeScript-конфигов при каждом вычислении графа. Генерация занимает около секунды, запускается руками несколько раз в неделю и не запускается в CI вовсе — кэш не покупал ничего и рисковал рабочим деревом.

04Механизм вывода таргетов

Весь вывод — это одна экспортируемая константа createNodesV2: пара из глоба и асинхронной функции. Nx находит все файлы, подходящие под глоб, и спрашивает функцию, какие таргеты повесить на проект, в чьём корне этот файл лежит. Это тот же механизм, которым @nx/js выводит typecheck из tsconfig.

export const createNodesV2: CreateNodesV2 = [
    '**/{drizzle.config.ts,ortha.config.ts,package.json}',
    async (configFiles, _, context) => { /* … */ }
];

Диспетчеризация внутри функции — по имени файла, ровно три ветки:

  1. package.json → packageTargets(projectRoot, file, workspaceRoot). Возвращает build, а для непубличного пакета ещё pack и nx-release-publish.если функция вернула undefined, отдаётся пустой объект — проект просто не получает ничего
  2. drizzle.config.ts → один таргет db:generate с cwd = корень проекта и config: 'drizzle.config.ts'.config задан относительно cwd, потому что drizzle-kit резолвит schema/out относительно рабочей директории, а не расположения конфига
  3. ortha.config.ts → два таргета, db:migrate и db:studio. Первому дополнительно передаётся plugins: <projectRoot>/src/plugins.ts.путь к фабрике плагинов зашит соглашением, а не читается из конфига

Четыре предохранителя в packageTargets

Функция возвращает undefined — то есть проект не получает ни одного таргета — в четырёх случаях. Каждый закрыт отдельным тестом:

УсловиеПочему отказ
Корень проекта не начинается с packages/Приложения (apps/admin, apps/server) собираются собственными бандлерами; корневой манифест воркспейса — не пакет
Манифест не парсится как JSONСломанный package.json не должен уронить вычисление всего графа — тогда перестанет работать каждая команда nx в репозитории

Пятый случай — private: true — не отказ, а сужение: пакет получает build, но не получает pack и публикацию. Именно так сам @orthacms/nx оказывается собираемым, но не публикуемым.

Почему build выводится здесь, а не плагином @nx/js

@nx/js/typescript выводит build только для проекта, чей манифест указывает на выход. Манифесты воркспейса указывают на ./src/index.ts, потому что пакеты потребляются из исходников (см. корневой AGENTS.md, «How packages resolve»). Для разработки это правильный размен и неправильный — для npm, поэтому шаг компиляции выводится здесь.

nx-release-publish объявлен дважды — и обязан быть

Nx добавляет собственный неявный nx-release-publish каждому непубличному пакету и применяет его после вывода. Если два определения расходятся в исполнителе, побеждает определение Nx — и уносит с собой выведенные options, включая packageRoot. Практический итог: релиз молча опубликует корень проекта, чей манифест указывает на исходники, вместо того, что застейджил pack. Поэтому исполнитель продублирован в nx.json → targetDefaults, а dependsOn: ['pack'] живёт только там — здесь Nx его всё равно перезапишет.

Шаблоны скаффолдера скрыты от вывода

packages/create-ortha-app/templates перечислен в корневом .nxignore. Внутри шаблона лежит настоящий ortha.config.ts, и вывод честно повесил бы на него db:migrate — на директорию, у которой нет имени проекта, после чего граф перестал бы строиться целиком. Файл-исключение написан не под этот плагин, а под все сразу: @nx/js/typescript вывел бы typecheck из шаблонных tsconfig ровно так же охотно.

05Чтение TypeScript из исходников

Два исполнителя — db:migrate и db:studio — обязаны прочитать ortha.config.ts хоста, а первый ещё и src/plugins.ts с фабрикой buildPlugins(config). Оба файла — TypeScript, и в этом монорепозитории они не скомпилированы: воркспейс резолвит всё из исходников. Отсюда src/lib/jiti.ts.

export function createTsJiti(referenceFile: string) {
    return createJiti(referenceFile, { transform: swcTransform });
}

Почему именно swc, а не встроенный babel

Загрузка конфига тянет за собой весь граф плагинов — модули NestJS и их DTO, — а он использует legacy-декораторы (experimentalDecorators). Встроенный в jiti babel игнорирует наш tsconfig и по умолчанию берёт семантику декораторов stage-3. В этой семантике декорированное поле с definite assignment (email!: string) получает инициализатор, и трансформация падает в transform-typescript. swc с legacyDecorator: true и decoratorMetadata: true совпадает с реальным TS-конфигом репозитория, поэтому тот же самый исходник, который компилирует приложение, загружается и здесь.

Почему в CLI ничего этого нет

Это проблема только этого воркспейса. Сгенерированное приложение имеет собственный шаг сборки, поэтому @orthacms/cli просто собирает первым и делает require готового JavaScript: dist/server/ortha.config.js и dist/server/src/plugins.js (константы LAYOUT.compiledConfig и LAYOUT.compiledPlugins). Вся проблема трансформации на стороне потребителя просто не возникает — CLI не нужен ни jiti, ни swc. Там же выбран require, а не await import(): приложение компилируется в CommonJS, и импорт CJS-модуля из ESM кладёт весь module.exports в default пространства имён, так что module.default оказывается { default: config }, а первое же обращение падает на свойстве undefined.

6.1 Сгенерировать миграцию для плагина

База данных не нужна. Секреты не нужны. Результат — новый SQL-файл, который коммитится вместе с изменением схемы.

npx nx run identity-server:db:generate --name=add_sso_identities
  1. Nx нашёл таргет по файлу. В packages/identity/server лежит drizzle.config.ts — значит, db:generate у проекта уже есть, ничего не объявляя.опции вывода: cwd = packages/identity/server, config = drizzle.config.ts
  2. Исполнитель собирает абсолютный путь. join(context.root, options.cwd) — и передаёт его дальше как рабочую директорию.
  3. Вызывается runDrizzleKitGenerate(cwd, config, name) из @orthacms/cli. Он резолвит бинарь: exports у drizzle-kit не даёт достать ./bin.cjs напрямую, поэтому резолвится главный вход пакета и берётся соседний файл.
  4. drizzle-kit запускается со stdio: 'inherit'. Его вывод идёт прямо в терминал: работа выполняется в cwd плагина, потому что schema и out резолвятся относительно рабочей директории, а не расположения конфига.
  5. Схема сравнивается со снимком. migrations/meta/*_snapshot.json — эталон; соединения с базой не открывается вовсе.
  6. При падении сообщение переписывается. execFileSync бросает ошибку, чей текст — весь argv (путь к node, путь к бинарю, все флаги), и Nx печатает это многокадровым стеком. Вместо этого бросается короткое «drizzle-kit generate failed in <cwd> (exit N) — его вывод выше», с указанием проверить пути schema и то, что схема компилируется.оригинальная ошибка сохраняется в cause
  7. Коммитится эмитированный SQL. Файл миграции и обновлённые journal/snapshot — часть того же изменения, что и правка схемы.

6.2 Применить миграции всех плагинов

Единственная команда, которую запускают на стенде и на проде. Порядок плагинов — несущий.

docker compose up -d          # Postgres
npx nx run server:db:migrate  # применить всё
  1. Создаётся jiti-загрузчик — createTsJiti(__filename), тот самый, с swc в режиме legacy-декораторов.
  2. Импортируется ortha.config.ts хоста по пути join(context.root, options.config); берётся default-экспорт.
  3. Импортируется модуль плагинов — apps/server/src/plugins.ts, экспортирующий buildPlugins(config).
  4. Проверяется URL базы — и это отказ, а не предупреждение. Если config.database?.url пуст, бросается ошибка с прямым текстом: «db:migrate needs to know which database to migrate, and will not fall back to the local defaults».проверка стоит ДО построения списка плагинов — отдельный тест это фиксирует

  6. Ядро отфильтровывает плагины без миграций. Если таких нет ни одного — печатается «No plugin migrations to apply.» и всё.

  9. Падение называет, где остановились. «Migrating plugin <name> failed — applied N of M before it», плюс явное «ничего не откатывается: N уже закоммичены», плюс главная подсказка — про порядок в plugins.ts.

Почему пустой DATABASE_URL — это отказ

new Pool({ connectionString: '' }) не падает: pg проваливается в переменные окружения libpq — PGHOST, PGUSER, PGDATABASE — или в localhost и OS-пользователя. Замерено в этом репозитории до появления проверки: с неустановленным DATABASE_URL и PGDATABASE, указывающим в другое место, db:migrate отрапортовал «Migrations complete.» после того, как создал всю схему в базе, которую никто не называл. db:studio отказывался всегда; здесь тот же самый отказ.

Порядок плагинов не объявлен нигде

memberships из workspaces ссылается по внешнему ключу на users из identity, и ничто в системе эту зависимость не декларирует. Цикл применяет плагины ровно в том порядке, в каком их вернул buildPlugins(), поэтому сообщение об ошибке прямо указывает на порядок как на обычную причину «relation does not exist».

6.3 Открыть Drizzle Studio

npx nx run server:db:studio
npx nx run server:db:studio --port=5000        # другой порт
npx nx run server:db:studio --host=0.0.0.0     # напечатает предупреждение
  1. URL резолвится из конфига хоста тем же jiti-загрузчиком — ortha.config.ts остаётся единственным местом, которое читает DATABASE_URL.
  2. Пустой URL — отказ. «Drizzle Studio needs a live database connection.»
  3. --port=0 — отказ. drizzle-kit действительно займёт эфемерный порт, но напечатает тот, который у него просили, и Studio окажется по адресу, о котором никто не сообщает. Отказ лучше и молчаливого игнорирования, которое здесь было раньше, и бесполезного успеха от drizzle-kit.
  4. Синтезируется эфемерный конфиг во временной директории. Закоммиченные drizzle-конфиги намеренно содержат только схему и не содержат секретов, поэтому конфиг создаётся на лету — и он ссылается на process.env.DATABASE_URL, а не инлайнит URL.
  5. URL передаётся через env дочернего процесса и никогда не пишется на диск. Эфемерный конфиг экспортирует простой объект без import, чтобы бандлеру drizzle-kit не понадобилась резолюция модулей из временной директории.
  6. Небезопасный bind предупреждает вслух. Любой --host, кроме localhost, 127.0.0.1, ::1, [::1], печатает предупреждение с адресом: у Studio нет аутентификации и есть полный доступ на чтение и запись, а drizzle-kit об этой разнице молчит.
  7. Ctrl+C — это успех. execFileSync бросает, когда ребёнка убили сигналом; SIGINT и SIGTERM распознаются и возвращают успех. Считать документированный способ остановки красным падением — значит приучать людей игнорировать красное.
  8. Временная директория удаляется в finally при любом исходе.

npm run release:dry-run     # репетиция: ничего не пишет, не пушит, не публикует
npm run release             # версия → changelog → тег → push → публикация → GitHub Release
npm run release:publish     # только публикация, чтобы дожать частично упавший релиз
npm run release -- 1.2.0    # принудительная версия вместо выведенной

Преполётные проверки. tools/release/release.mjs грузит .env и отказывается стартовать, если вы не на main (обходится --allow-branch), дерево грязное, ветка отстала от origin/main, у npm нет пригодных учётных данных или отсутствует GITHUB_TOKEN.nx release коммитит, тегирует и ПУШИТ до публикации — поздно найденная проблема оставляет тег и пустой реестр
  2. Версия. nx release выводит её из conventional commits (feat: → minor, fix: → patch, ! → major), режим fixed: все пакеты двигаются вместе.
  3. preVersionCommand собирает всё: npx nx run-many -t build --projects=@orthacms/*,create-ortha-app.
  4. pack стейджит каждый пакет в dist/pack/<projectRoot>/ с переписанным манифестом. Таргет зависит от build.
  5. Подтверждение. nx release спрашивает перед публикацией, и этот вопрос оставлен намеренно: публикацию нельзя отменить, а номер версии нельзя переиспользовать.
  6. Публикация по одной. Каждый пакет проходит через рабочий слот с файловой блокировкой, пробуется реестром через GET и публикуется npm publish <packageRoot> --json.

  8. Если что-то упало — npm run release:publish. Пакеты, уже лежащие в реестре, пропускаются пробой без единой записи.

07Релизный процесс детально

Все пакеты под packages/ публикуются в один заход, одной версией, одним тегом. В nx.json это описано так: projects: ["@orthacms/*", "create-ortha-app", "!@orthacms/nx", "!@orthacms/copilot-provider-fake"], projectsRelationship: "fixed", releaseTagPattern: "v{version}". Приложения (apps/admin, apps/server) приватны и не публикуются никогда: они — референсный хост, а не дистрибутив.

Почему тарбол — это не закоммиченный манифест

Воркспейс резолвит пакеты из исходников: exports указывает на ./src/index.ts, а tsconfig.base.json даёт условие @orthacms/source. У потребителя, ставящего пакет из npm, нет ни того, ни другого — и нет способа скомпилировать наш TypeScript. Поэтому релиз обязан отменить ровно ту вещь, которая удобна в разработке. Делают это три выводимых таргета, и все три приходят из этого пакета — то есть новый пакет получает их фактом своего существования.

ШагЧто происходитЧто попадает в результат
build tsc --build tsconfig.lib.json — JS и .d.ts в dist/ пакета, попутно собираются project references Серверные пакеты компилируются в CommonJS (следствие nodenext и отсутствия "type": "module"), админские — в ESM для бандлера
pack tools/release/pack.mjs собирает публикуемый корень в dist/pack/<projectRoot>/ package.json переписанный · dist/ (вывод tsc + не-TS ассеты вроде styles.css) · migrations/ дословно, если плагин их везёт · templates/ дословно, если пакет их везёт · README.md и LICENSE
nx-release-publish Публикует эту директорию, а не корень проекта, через packageRoot. Исполнитель — наш, а не @nx/js:release-publish Тарбол ровно из застейдженного содержимого

Что именно переписывает pack в манифесте

  • exports — каждая подпуть переводится с ./src/*.ts на ./dist/*.js, причём декларации предлагаются первыми (чтобы types выигрывал у tsc), а компилированный JS — как default.
  • bin — ремапится так же, как main, в обеих формах, которые принимает npm: голая строка и карта. Оставленный указывать на ./src/cli.ts, он публикует команду, которая устанавливается чисто и умирает на первом npx, на чужой машине, с ошибкой про несуществующую команду, а не про файл.
  • Зависимости на воркспейс — объявленные как "*", что в реестре означает «что угодно последнее», пинятся на версию релиза.
  • files — dist плюс migrations и templates, если они есть; иначе npm их просто не опубликует.
  • publishConfig.access: 'public' — проставляется всегда.
Две вещи, которые pack отказывается отгружать

Обе были настоящими багами и обе валят релиз, а не доезжают до реестра. (1) Точка входа, которую не собрали — каждый путь в сгенерированном exports обязан существовать в стейджинге. (2) Фантомная зависимость — пакет, импортирующий то, что объявлено только в корневом манифесте, резолвится здесь (npm поднимает зависимости) и просто отсутствует в дереве потребителя. Импорты только типов тоже считаются: они попадают в .d.ts.

Стейджинг лежит в корне воркспейса, а не рядом с пакетом, намеренно: корневые globs workspaces покрывают packages/*, и директория стейджинга внутри плоского пакета читается как второй воркспейс с тем же именем — после чего npm отказывается работать вообще.

Троттлинг: почему публикация не может быть просто npm publish

npm ограничивает, как быстро один аккаунт пишет. Опубликованные с той скоростью, с какой их планирует Nx, тарболы начинают получать 429 Too Many Requests где-то в середине списка — а к этому моменту версия уже закоммичена, отмечена тегом и запушена, то есть репозиторий утверждает, что релиз состоялся, а реестр имеет только его половину.

Nx запускает nx-release-publish как обычные задачи — параллельно, в форкнутых воркерах, — поэтому интервал невозможно выдержать внутри одного процесса. Отсюда файловая блокировка под dist/.release-publish: кто держит её, тот публикует, остальные ждут своей очереди.

МеханизмКак устроенЧто защищает

spacing Минимальный интервал между двумя публикациями. Может быть функцией — она вычисляется только после захвата слота, чтобы пакет, который уже узнал, что публиковаться не будет, не отсиживал паузу Скоростной лимит записи

Жизненный путь одной публикации

очередь — взял блокировку → пауза — проба GET → npm publish → опубликован либо отказ

Из состояния «проба» есть два выхода мимо публикации: version-published уводит сразу в успех без записи, а взведённый предохранитель — сразу в отказ, тоже без записи. Из «npm publish» ретраибельный ответ возвращает в паузу с удвоенным откатом, и так до исчерпания попыток.

Проба реестра: спросить, прежде чем говорить

PUT — метрируемая операция, GET — нет. Перед каждой публикацией делается один GET пакумента (lib/release/registry.ts), и его ответ решает сразу два вопроса.

Создание имени — другой лимит, и его не пересидеть

Всё вышеописанное — про скорость записи, и интервал это чинит. Создание нового имени пакета метрируется отдельно и куда жёстче. Измерено: релиз 0.1.0 создал 25 имён за 32 секунды, после чего npm отказал остальным 12 — и продолжал отказывать им и в 0.2.0, и в 0.2.1, пока бампы версий на уже существующих 25 именах в тех же прогонах проходили нетронутыми. Час полностью простаивающего аккаунта ничего не изменил.

Поэтому: 429 на создании — терминальный. Одна попытка, внятное сообщение, и взведённый флаг рядом с блокировкой. Пакеты, стоящие в очереди за ним, выходят из игры не потратив ни одного запроса: один заблокированный релиз стоит одной отклонённой записи, а не одной на пакет. Флаг спрашивается заново изнутри слота, а не только на входе — до первой попытки публикации ответ всегда был бы «нет».

Лечится это только обращением в поддержку npm — или предварительным засевом имён: npm run release:reserve создаёт недостающие имена батчами, публикуя настоящий застейдженный тарбол под версией 0.0.0-reserve.0 и dist-тегом reserve. latest при этом остаётся непроставленным, так что npm install ничего не найдёт до настоящего релиза, а не поставит пустышку. Первый отказ завершает прогон: каждая отклонённая попытка — сигнал для рейт-лимитера.

Репетируйте через npm run release:dry-run, никогда через nx run-many

nx run <project>:nx-release-publish --dryRun работает — флаг доходит до исполнителя. nx run-many -t nx-release-publish --dryRun не работает: run-many съедает --dryRun сам, опция не приходит, и таргет выполняет настоящий npm publish. На аутентифицированной машине это публикует по-настоящему, а для имени, которое аккаунт ещё не создавал, тратит одно из рационированных созданий. npm run release:dry-run идёт через nx release publish --dry-run, который выставляет ещё и NX_DRY_RUN, так что репетиция держится в обоих случаях.

Что исполнитель пропускает без записи

  • private: true в застейдженном манифесте — «Skipped <pkg>, because it is marked private».
  • Nx не разрешил новую версию (nxReleaseVersionData[project].newVersion === null) — публиковать нечего, а спрашивать npm значило бы заработать ещё один 403.
  • Проба сказала version-published — «that version is already on the registry».
  • Предохранитель взведён другим пакетом — статус blocked-by-peer: сообщение называет пакет, который упёрся в лимит первым, а этот не тратит запрос.

Сухой прогон не пробует реестр и не ждёт ничего: он ничего не пишет, значит и лимита, под который надо подстраиваться, у него нет.

  • И-18nx-release-publish всегда указывает packageRoot на dist/pack/<projectRoot>, а не на корень проекта; исполнитель объявлен и в выводе, и в targetDefaults, и оба объявления совпадают.

  • И-30Приоритет числовых настроек: окружение → опция таргета → умолчание; 0 из окружения принимается как значение.

10Чек-лист тестирования

Формулировки — «действие → ожидаемый результат», чтобы их можно было брать в тест-кейс без переписывания. Существующий набор — 79 jest-кейсов в восьми файлах рядом с кодом (npx nx test nx); они мокают на границе процесса — node:child_process, pg, fetch, jiti, — так что весь пакет покрывается без базы, реестра и графа Nx. Вывод таргетов гоняется против одноразового корня воркспейса на диске: именно это делает предохранители манифеста проверяемыми вообще.

Вывод таргетов

  • Проект с drizzle.config.ts → ровно один таргет db:generate, cache: false, cwd = корень проекта, config = drizzle.config.ts.
  • Проект с ortha.config.ts → два таргета, оба cache: false; у db:migrate в опциях есть plugins, у db:studio — нет.
  • Публикуемый пакет под packages/ → ровно три таргета: build, pack, nx-release-publish; packageRoot = dist/pack/<projectRoot>.
  • Пакет с private: true → ровно один таргет — build.
  • Манифест вне packages/ (apps, корень воркспейса) → пустой объект таргетов.
  • Манифест без name → пустой объект таргетов.
  • Пакет без tsconfig.lib.json → пустой объект таргетов.
  • Битый JSON в package.json → пустой объект таргетов; nx graph строится, ни одна команда nx не падает.
  • npx nx show project <plugin> --json для нового плагина → все положенные таргеты присутствуют без единой строчки конфигурации в проекте.

db:generate

  • Запуск при полностью остановленном Postgres → успех: соединения не открывается.
  • Запуск с --name=… после правки схемы → новый SQL-файл в migrations/, обновлённые journal и snapshot.
  • Повторный запуск с тем же --name без правок схемы → drizzle-kit сообщает об отсутствии изменений; результат не берётся из кэша Nx.
  • Правка схемы плагина, чей schema указывает вне src/lib/schema/ (media, alarms, copilot, content, workspaces) → миграция генерируется — старый баг с несовпадающим входом кэша не воспроизводится.
  • Сломать путь schema в конфиге → одна короткая ошибка «drizzle-kit generate failed in <cwd>», без многокадрового стека с argv.

db:migrate

  • DATABASE_URL не задан → отказ с текстом про «will not fall back to the local defaults»; ни одной таблицы не создано.
  • DATABASE_URL пуст, но заданы PGDATABASE/PGHOST → тот же отказ; посторонняя база не тронута.
  • Чистая база → в логе названы host:port/database без учётных данных и число плагинов; в конце «Migrations complete.».
  • Повторный запуск на уже мигрированной базе → идемпотентно, новых применений нет.
  • Переставить workspaces перед identity в plugins.ts → падение называет плагин, число закоммиченных до него и указывает на порядок.
  • Убить процесс Postgres в середине → пул закрывается, ошибка называет плагин; повторный запуск продолжает с него же.
  • Плагин с декорированным полем email!: string в DTO → загрузка конфига проходит; падения в transform-typescript нет.

db:studio

  • Запуск без DATABASE_URL → отказ до старта drizzle-kit.
  • --port=0 → отказ с объяснением, а не запуск на неизвестном порту.
  • --host=0.0.0.0 → предупреждение с адресом и портом печатается до старта.
  • --host=127.0.0.1 → предупреждения нет.
  • Проверить временную директорию во время работы → в эфемерном конфиге process.env.DATABASE_URL, а не сам URL.
  • Ctrl+C → таргет завершается успехом; временная директория удалена.

Публикация

  • npm run release:dry-run с чистого main → ни одной записи в реестр, ни одного push; в логе «Would publish …» для каждого пакета.
  • Запуск не с main / с грязным деревом / с отставшей веткой → преполёт отказывает до того, как что-либо закоммичено или отмечено тегом.
  • Отсутствует GITHUB_TOKEN (не dry-run) → отказ на преполёте.
  • Приватный пакет в списке → «Skipped …, because it is marked private»; запроса к реестру нет.
  • Nx не разрешил новую версию для проекта → «Skipped …, because no new version was resolved».
  • Версия уже в реестре → пропуск по ответу пробы, без npm publish.
  • Реестр отвечает EPUBLISHCONFLICT → успех, а не падение.
  • Реестр отвечает 429 на бампе версии → ретраи с откатом 30/60/120/240/300 с; в логе номер попытки из общего числа.
  • Реестр отвечает 429 на создании имени → ровно одна попытка, файл creation-blocked появляется в dist/.release-publish.
  • Второй новый пакет после сработавшего предохранителя → падает без запроса к реестру, сообщение называет пакет, упёршийся первым.
  • Существующее имя при взведённом предохранителе → публикуется нормально.
  • Реестр недоступен (сеть отключена) на этапе пробы → ответ unknown, публикация всё равно пытается.
  • Два одновременных nx-release-publish → второй ждёт и печатает «waiting for another package to finish publishing»; наложения нет.
  • Убить процесс-держатель блокировки → следующий забирает слот немедленно, без пятнадцатиминутного ожидания.
  • Держатель, работающий дольше staleAfter, но обновляющий lock → блокировку не крадут.
  • ORTHA_PUBLISH_DELAY=0 → пауза действительно нулевая, а не подменённая дефолтом 5000.
  • Стереть dist/ между прогонами → блокировка и предохранитель очищены — оба живут под dist/.release-publish.

Стейджинг тарбола

  • nx run <pkg>:pack, затем осмотр dist/pack/<projectRoot>/package.json → exports указывает на ./dist, зависимости на воркспейс запинены версией релиза, publishConfig.access: 'public'.
  • Пакет с bin → путь переписан на вывод сборки; обе формы (строка и карта) обработаны; несуществующий bin валит pack.
  • Плагин с migrations/ → папка перенесена дословно и перечислена в files.
  • create-ortha-app → templates/ перенесена и перечислена в files.
  • Пакет, импортирующий зависимость, объявленную только в корневом манифесте → pack отказывает: фантомная зависимость до реестра не доезжает.
  • Новый пакет добавлен в packages/, но не классифицирован в features.ts → падают тесты create-ortha-app — намеренно.

  • Проверки, что схема и миграции не разъехались. Кэш убран именно потому, что создавал такой дрейф, но активной проверки взамен не появилось.

Почему цифры в этом артефакте посчитаны, а не переписаны

Все количественные утверждения выше получены перечислением по рабочему дереву на момент составления: 11 файлов drizzle.config.ts вне node_modules; 1 файл ortha.config.ts вне игнорируемых шаблонов; 56 манифестов под packages/* и packages/*/* без private: true; 4 записи в executors.json; 6 таргетов в createNodesV2; 79 кейсов it(...) в восьми спек-файлах пакета. Там, где документ утверждал другое, расхождение вынесено в таблицу выше, а не подогнано под документ.

Паспорт плагина сборки. Составлен по группе packages/nx в общем каркасе серии: бизнес-описание → состав → каталог таргетов → механизм вывода → загрузка TypeScript → сценарии → релиз → конфигурация → инварианты → чек-лист → границы → расхождения. Разделы, которых у этого пакета нет по природе (модель данных, HTTP API, экраны админки, права), выпали: он не владеет ни одной таблицей, не отдаёт ни одного маршрута и не имеет пользовательского интерфейса.

Источник — исходный код: src/index.ts, четыре исполнителя со своими схемами опций, src/lib/jiti.ts, три модуля src/lib/release/ и восемь спек-файлов рядом с ними; плюс корневой nx.json, .nxignore, docs/releasing.md, tools/release/{release,pack}.mjs и публичный API @orthacms/cli. Файлы AGENTS.md использованы как каркас, но каждое утверждение сверено с реализацией — расхождения вынесены в раздел 12.
