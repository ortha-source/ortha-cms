Пакет · packages/shell/admin

Shell Обвязка аутентифицированного приложения — сайдбар, слоты, палитра и ворота доступа

Shell — единственный пакет, который знает, как выглядит вошедший в систему админ. Он даёт хосту один layout, и внутри этого layout лежат сразу две вещи: рамка интерфейса (левый сайдбар, область страницы, правая панель) и ворота авторизации — AuthProvider вокруг RequireAuth. Хост про авторизацию не знает вообще: он только монтирует layout как единственного родителя всех непубличных маршрутов. Собственного содержимого у shell почти нет — он объявляет пять слотов и рисует то, что в них положили другие плагины.

01Бизнес-описание

Всё, что пользователь видит после входа, нарисовано этим пакетом — или вставлено в дырку, которую этот пакет оставил. Сайдбар слева, полоса контекста сверху, правая панель, домашний дашборд, палитра команд по ⌘K: это shell. При этом сам по себе он почти пустой — вся продуктовая функциональность приходит извне.

Какую задачу решает

  • Одна рамка на всё приложение. Сайдбар, область контента и правая панель монтируются один раз и переживают любую навигацию. Смена маршрута перерисовывает только содержимое <Outlet/>: сайдбар не мигает, скролл-порт не сбрасывается, открытый чат не перезагружается.
  • Ворота авторизации там, где рамка. Приватность маршрута — это не флаг на маршруте, а факт вложенности в layout, который сам себя закрывает. Плагину не нужно помнить про RequireAuth: он просто не ставит public: true, и его страница оказывается за проверкой.
  • Расширяемость без правки shell. Появился новый раздел — плагин кладёт запись в SIDEBAR_NAV_SLOT, и строка в навигации появляется сама, в нужной группе и на нужной позиции. Shell не импортирует ни один feature-плагин и не знает их имён.
  • Единый набор клавиатурных договорённостей. ⌘K — палитра, ⌘B — сайдбар, Tab с самого начала — «пропустить навигацию». Их не изобретает каждая страница.
  • Место для того, что страница хочет вынести в чром. Кнопка «Опубликовать» принадлежит редактору записи, но рисоваться должна в верхней полосе; панель свойств принадлежит той же странице, но живёт отдельной колонкой. Shell даёт под это два портала.

Кому это видно

Редактор контента

Живёт в сайдбаре: воркспейсы, типы контента, переключатель CMS ⇄ Agents. Сворачивает панель на ⌘B, когда нужна ширина под таблицу, и возвращает её оттуда же.

Администратор

Видит на две строки навигации больше — «Участники», «API-токены», «Сегменты» появляются только с соответствующим правом. Домашний дашборд собирает ему статистику и последние действия.

Разработчик плагина

Не трогает shell вообще. Кладёт запись в слот, маршрут в routes, при необходимости открывает портал в верхнюю полосу — и его страница выглядит как часть продукта.

Чем Shell не является

  • Это не аутентификация. AuthProvider, RequireAuth, useHasPermission, экран входа — всё это identity-admin. Shell только ставит два из них в правильном порядке.
  • Это не роутер. Разделение маршрутов на публичные и приватные, порядок, коллизии путей, catch-all — это bootstrap-admin.
  • Это не дизайн-система. Sidebar, SidebarProvider, TopBar, CommandDialog, куки состояния сайдбара, ⌘B, брейкпоинт мобильного — примитивы @orthacms/design-system. Shell их композирует и переводит их подписи.
  • Это не воркспейс-шелл. Контекстную область сайдбара внутри /workspaces/:id/* целиком забирает workspaces-admin через useSidebarContent. Shell в этот момент рисует только футер.
  • Это не поиск. Палитра — оболочка: список «Перейти» строится из слота навигации, а всё остальное дают плагины.
Ключевая идея архитектуры

Layout и есть гейт. Хост берёт первый попавшийся layout из списка плагинов (plugins.map(p => p.layout).find(Boolean)) и монтирует его как единственного родителя всех приватных маршрутов. Shell возвращает не голую рамку, а <AuthProvider><RequireAuth><AppShell/></RequireAuth></AuthProvider>. Следствие с обратным знаком: плагин, зарегистрированный раньше shell и отдающий свой layout, молча отключает авторизацию всему приложению — вместе с сайдбаром, skip-link и лендмаркой <main>. Поэтому хост печатает предупреждение при двух контрибьюторах layout, а apps/admin/src/plugins.spec.ts утверждает, что контрибьютор ровно один и это shell.

Направление зависимости

Shell зависит от identity-admin, но не наоборот, и ни один feature-плагин не импортируется shell'ом. Обратное направление — плагины импортируют слоты из @orthacms/shell-admin — и есть весь механизм расширения. Циклов нет: слот это чистые данные, React в модуле слота отсутствует.

2.3 Порядок загрузки

  1. Хост считает маршруты и слоты. createAdmin разделяет routes по флагу public и один раз вызывает wireSlotContributions со всеми контрибьюциями всех плагинов.регистрация идёт «с нуля»: сначала _reset() по каждому затронутому слоту, потом _register — иначе горячая перезагрузка Vite удваивала бы каждую строку сайдбара
  2. Хост выбирает layout. Первый ненулевой среди плагинов; при двух и более — console.warn с именами победителя и проигравших.
  3. Рендер. Публичные маршруты — сиблинги верхнего уровня; все остальные — дети безпутевого <Route element={layout}>, плюс catch-all * → <Navigate to="/" replace/>, тоже внутри layout, то есть тоже за гейтом.
  4. Слоты читаются во время рендера. SIDEBAR_NAV_SLOT.getItems() вызывается в теле компонента, не в эффекте — к этому моменту регистрация уже завершена, поэтому порядок регистрации плагинов на видимость не влияет.

03Роли и права: что именно гейтится в навигации

Собственных прав shell не вводит и решений о доступе не принимает. Он делает ровно одно: прячет строку навигации, если у пользователя нет права, объявленного в самой строке. Это зеркало серверного гейта, а не замена ему — страница за ссылкой в любом случае проверяет себя сама, и API тоже.

3.1 Правило видимости

Правило описано дважды и обязано совпадать: один раз построчно в SidebarNavButton и SidebarCommandItem, второй раз — на уровне группы в GlobalSidebar.

  • Нет поля permission → строка видна любому вошедшему.
  • Есть permission → видна, только если ключ есть в auth.user.permissions.
  • Хук вызывается всегда. useHasPermission(item.permission ?? '') — пустой ключ не выдаётся никогда, зато порядок хуков остаётся стабильным при любом наборе полей.
  • useHasPermission fail-closed: false во всех состояниях, кроме Authenticated. Пока идёт проба «кто я», ничего гейтированного не мигает.
  • Группа целиком исчезает, если после фильтра в ней не осталось строк — иначе заголовок «Directory» висел бы над пустым телом. Для этого GlobalSidebar читает набор прав один раз, вместо вызова хука на каждый элемент.

3.3 Что не гейтится в самом shell

  • Секции сайдбара и футер. SIDEBAR_SECTION_SLOT и SIDEBAR_FOOTER_SLOT отдают компонент целиком, и решение «показывать ли себя» принимает он.   • Дашборд. HOME_SECTION_SLOT — те же правила: плитка сама решает.
  • Правая панель и область действий. Их наполняет страница, которая уже прошла свои проверки.
Палитра зеркалит сайдбар

SidebarCommandItem применяет ту же проверку, что и SidebarNavButton: в палитре нельзя «перейти» туда, куда нельзя кликнуть. Это не удобство, а требование к гейту — иначе ⌘K был бы дырой в обход навигационных проверок (пусть и упирающейся в серверный отказ).

04Карта слотов

Слот — именованная точка расширения, созданная createSlot<T>(name) из @orthacms/utils-admin. Это чистые данные: модуль слота не импортирует React и ничего не знает ни о том, кто в него пишет, ни о том, кто его читает. Плагин объявляет контрибьюции декларативно в поле slots, хост регистрирует их все разом до первого рендера.

4.1 Механика — что нужно знать до чтения таблиц

  • Слот — синглтон уровня модуля. Один массив на всё время жизни приложения. Поэтому порядок регистрации плагинов на видимость вклада не влияет: плагин может писать в слот, объявленный плагином, который зарегистрируется позже.
  • getItems() отдаёт копию. Потребитель, который отсортирует или отфильтрует список на месте, не испортит его следующему потребителю.
  • Регистрация идемпотентна. wireSlotContributions сначала _reset()-ит каждый затронутый слот отдельным проходом (иначе очистка внутри цикла стирала бы вклад плагина, зарегистрированного ранее в том же прогоне), и только потом регистрирует. Это лечит реальный симптом: горячее обновление Vite переисполняет модуль входа, и без сброса каждая строка сайдбара и каждый воркспейс дублировались с каждым сохранением.
  • Порядок — byOrder, сортировка стабильная. items.slice().sort((a,b) => a.order - b.order). При равных order побеждает порядок регистрации плагинов из apps/admin/src/plugins.ts.
  • Слот — не единственный механизм расширения shell. Есть ещё два, устроенных иначе: перехват контекстной области (useSidebarContent — ровно один узел) и порталы страницы (PageActionsPortal, RightPanelPortal). См. 4.4 и 4.5.

Слотов NAVBAR_START_SLOT / NAVBAR_END_SLOT и верхнего тулбара в репозитории нет: они заменены сайдбаром. Имена сохранились только в JSDoc-примере createSlot и в комментариях-«formerly» внутри типов.

4.5 Не слоты, но тоже точки расширения

Перехват контекстной области — useSidebarContent

Область держит ровно один узел, поэтому это не слот. Потребитель зовёт useSidebarContent(render, deps), и AppSidebar рисует override ?? <GlobalSidebar/>. Двое смонтированных одновременно — последний победил, это by design. А вот не by design было то, что уборка проигравшего гасила контент победителя и вся середина сайдбара оставалась пустой до следующей смены маршрута: теперь каждый вызывающий держит токен-Symbol, и clearContent — no-op, если он уже не тот, кто показан.

Хранится отрендеренный элемент, а не функция. Поэтому deps обязаны перечислять каждое поле, которое узел реально рисует: WorkspaceShell ключуется на id, name, color, status, members.length — ключ по одному id оставлял переключатель со старым именем и цветом (включая aria-label) до конца сессии.

Порталы страницы — PageActionsPortal, RightPanelPortal

Обе области shell рисует, но не наполняет. Наполнение идёт createPortal, а не передачей узла вверх, и это принципиально: React резолвит контекст по месту рендера, поэтому узел, отрисованный shell'ом, был бы отрезан от всего, что ниже — от открытого воркспейса, от слот-контекстов плагина, от обработчиков и busy-состояния формы. Портал переносит только DOM и сохраняет дерево React.

Цена альтернативы видна в ContentNavSection: он рендерится выше CurrentWorkspaceProvider и вынужден заново вычислять открытый воркспейс из маршрута руками.

Хосты порталов смонтированы всегда — порталу нужна существующая цель, а немонтируемый хост правой панели означает, что сворачивание не выбрасывает состояние наполнителя и не перезапрашивает его данные.

4.6 Как добавить новый раздел — чек-лист

  1. Решить область. Глобальный раздел → SIDEBAR_NAV_SLOT + routes плагина. Инструмент внутри воркспейса → WORKSPACE_NAV_SLOT + WORKSPACE_ROUTE_SLOT (и тогда ни глобального маршрута, ни строки в глобальном сайдбаре).
  2. Выбрать группу и order. overview — обзорные экраны, directory — справочники. Шаг между существующими значениями — 10.
  3. Объявить permission, если страница гейтится. Пропуск поля означает «видно всем вошедшим», и тогда строка обязана вести на страницу, которая что-то показывает всем.
  4. Дать иконку и, по желанию, iconColor. Утилиты text-nav-* подобраны под тёмную поверхность сайдбара; акцент применяется только в активном состоянии.
  5. Отрисовать PageTopBar на странице с той же иконкой, что в строке навигации. Иначе рамка и полоса контекста будут спорить, и заодно на странице появится плавающий тумблер, которого там быть не должно.
  6. Проверить палитру. Новая строка появляется в «Go to» автоматически — отдельная контрибьюция в COMMAND_SLOT нужна только для динамических результатов.

Без контрибьюций в HOME_SECTION_SLOT остаётся только приветствие — контейнеры пустых регионов не рисуются.

Сайдбар

Три региона: шапка (бренд «Ortha CMS», триггер «Hide navigation», поиск), контекстная область (глобальная навигация либо перехват), постоянный футер из слота. CommandDialog: поле ввода, статическая группа «Go to» из слота навигации, затем секции из COMMAND_SLOT, снизу — легенда клавиш ↑ ↓ / ↵ / esc. Открывается кликом по триггеру или ⌘K / Ctrl+K.

Верхняя полоса и правая панель

PageTopBar — плитка иконки + хлебные крошки + область действий. Полоса вытягивает себя порталом из скролл-порта в фиксированную полосу SidebarInset, поэтому контент скроллится под ней. AppRightPanel — колонка 22rem с шапкой h-12 в одну линию с полосой; без зарегистрированной панели ширина 0 и inert.

Почему плавающий тумблер виден только на Home

SidebarToggle прячет себя селектором [main:has([data-slot=top-bar])~&]:hidden — сиблинговый комбинатор относительно <main>. Любая страница с TopBar несёт собственный встроенный триггер раскрытия внутри полосы, и плавающая кнопка не нужна. Единственная страница без полосы — домашняя, там кнопка и появляется. Отсюда жёсткое требование: SidebarToggle должен быть прямым сиблингом <main>, обёртка вокруг него ломает селектор и возвращает кнопку на все страницы.

06Сценарии — как это работает по шагам

6.1 Первый вход в приложение

  1. Хост монтируется. createAdmin выставляет <html lang> и dir, предупреждает о коллизиях layout и путей, регистрирует все слоты с нуля и рендерит дерево провайдеров: тема → QueryClient → IntlProvider → подписи дизайн-системы → тултипы → error boundary → BrowserRouter.слоты регистрируются до первого рендера, поэтому сайдбар с первого кадра полон
  2. Маршрут матчится в приватную ветку. Например /. Элементом родителя оказывается layout от shell.
  3. AuthProvider запускает пробу «кто я». Пока она в полёте, useAuth() отдаёт Loading.
  4. RequireAuth ветвится по четырём состояниям. Loading → полноэкранный AppLoader. Unavailable (проба упала по причине, отличной от 401) → экран «недоступно» с повтором, не редирект. Unauthenticated → <Navigate to="/identity/login" replace state={{ from: location }}/>. Authenticated → дети.различие Unauthenticated и Unavailable — почему падение API не выглядит как разлогин
  5. AppShell монтирует провайдеры рамки. SidebarContentProvider (пустой перехват) → PageChromeProvider (читает localStorage под правую панель) → AppShellChrome.
  6. SidebarProvider читает куку sidebar_state. Нет куки или значение мусорное → открыт. Вешает слушатель ⌘B на window.
  7. Рисуется рамка. Skip-link (первый фокусируемый элемент документа) → AppSidebar → SidebarInset с id="main-content" и <Outlet/> → AppRightPanel (нулевая ширина, inert) → SidebarToggle.
  8. Сайдбар наполняется из слотов. GlobalSidebar фильтрует навигацию по правам, схлопывает пустые группы, рисует секции; AppSidebar добавляет футер.
  9. Страница ставит заголовок вкладки. HomePage зовёт useDocumentTitle('Home') → document.title = 'Home · Admin'.

6.2 Переход между разделами

  1. Клик по строке сайдбара. SidebarNavButton — это <Link> внутри SidebarMenuButton asChild, то есть обычная клиентская навигация.
  2. Активность пересчитывается. useMatch(item.end ? item.to : item.to + '/*'). Флаг end есть только у «Home» — иначе корневой путь считался бы активным на всех маршрутах сразу.
  3. Активная строка помечается дважды: визуально (isActive + акцентный цвет иконки) и семантически (aria-current="page").
  4. Рамка не перерисовывается. Меняется только содержимое <Outlet/>; сайдбар, скролл-порт, правая панель и всё, что в них смонтировано, остаются на месте.
  5. Хост объявляет новый экран. RouteAnnouncer опрашивает <h1> внутри <main> с шагом 100 мс до 5 с, пропускает заголовки внутри [aria-busy="true"] (скелетоны ленивых чанков) и пишет устоявшееся имя в polite-регион.это работает только потому, что shell дал единственный <main>, по которому announcer скоупится
  6. Страница ставит свой заголовок вкладки и снимает его на анмаунте, возвращая голое «Admin».

6.3 Сворачивание и раскрытие сайдбара

  1. Свернуть можно тремя способами: триггер в шапке сайдбара («Hide navigation»), ⌘B / Ctrl+B, или — на мобильном — закрытие Sheet.
  2. ⌘B уступает редактору. Слушатель на window проверяет ownsBoldShortcut(event.target): в текстовом поле, textarea, select и внутри contenteditable аккорд означает жирный, и там он не перехватывается. Иначе автор получал бы и свёрнутый сайдбар, и несработавшее форматирование.
  3. Состояние пишется в куку. sidebar_state=true|false; path=/; max-age=604800; SameSite=Lax. Запись обёрнута в try/catch — в песочнице iframe без allow-same-origin доступ к document.cookie бросает исключение, и потеря настройки переживаема, а потеря тумблера — нет.
  4. Панель уезжает, а не размонтируется. Режим offcanvas: контейнер сдвигается на left: -var(--sidebar-width) за 300 мс, соседний «gap»-элемент анимирует ширину до нуля. Свёрнутая панель получает inert + aria-hidden, поэтому её ссылки и поиск покидают tab-порядок и дерево доступности.
  5. Фокус передаётся выжившему. Кнопка, которой свернули, только что уехала в inert-поддерево. SidebarProvider ловит переход expanded → collapsed, проверяет, что фокус действительно потерян (null, <body> или элемент внутри [inert]), и переводит его на первый [data-sidebar="trigger"] вне inert и не с tabindex="-1" — то есть на встроенный триггер в TopBar или на плавающий тумблер.без этого клавиатурный пользователь оказывался на body и должен был табать с начала документа
  6. Раскрыть — тем же ⌘B, встроенным триггером в полосе или плавающей кнопкой. Первые два всегда доступны; третья видна только там, где полосы нет.

6.4 Палитра команд ⌘K

  1. Открытие. Клик по триггеру-«полю поиска» в шапке сайдбара, либо ⌘K / Ctrl+K. Перед открытием запоминается document.activeElement.
  2. Аккорд уступает каретке. Если палитра закрыта и isComposingText(event.target) — обработчик выходит, не вызывая preventDefault(). Это WCAG 3.2.2: смена контекста в ответ на ввод в другой элемент, да ещё и с уничтожением нажатия, которое пользователь имел в виду.половина «закрыть» на эту проверку намеренно не завязана — собственное поле палитры тоже текстовое
  3. Содержимое. Группа «Go to» — SIDEBAR_NAV_SLOT, отсортированный byOrder и отфильтрованный по правам построчно. Затем секции COMMAND_SLOT по order: воркспейсы, потом типы контента. Пусто → CommandEmpty «No results.».
  4. Выбор результата. go(to): запомненный элемент фокуса сбрасывается, палитра закрывается, идёт navigate. Возврат фокуса намеренно пропущен — тянуть его обратно на триггер сайдбара значит воевать с приходящей страницей.
  5. Закрытие без перехода. Esc или повторный ⌘K → closePalette(): setOpen(false), затем через setTimeout(…, 0) фокус возвращается запомненному элементу, если он ещё isConnected, иначе триггеру. Отложено на такт, чтобы приземлиться после размонтирования focus-scope диалога.Radix здесь свой restore не выполняет, хотя для дропдауна аккаунт-меню — той же библиотеки — выполняет
  6. Двойного бинда не возникает. SidebarSearch живёт только в GlobalSidebar. Внутри воркспейса вся контекстная область заменена на WorkspaceNav, глобальная палитра размонтирована, и ⌘K владеет ContentNavSection с палитрой по типам контента.

6.5 Вход в воркспейс: перехват контекстной области

  1. Навигация на /workspaces/:id/*. Маршрут принадлежит workspaces-admin, рендерится в <Outlet/> shell'а.
  2. WorkspaceShell резолвит :id по списку воркспейсов. Список серверно скоупится членством, поэтому нерезолвенный :id — это и есть «нет доступа», без различения «не существует» и «не ваш».
  3. Он зовёт useSidebarContent. Хук берёт Symbol-токен на весь срок жизни компонента и в эффекте кладёт <WorkspaceNav workspace={current}/> в контекст вместе с токеном.
  4. AppSidebar перерисовывается и рисует override вместо GlobalSidebar. Бренд, глобальная навигация, быстрый список воркспейсов и глобальный поиск исчезают.
  5. Футер остаётся. Он вне контекстной области: ThemeSync продолжает работать, док копайлота и меню аккаунта на месте. Именно поэтому ThemeSync положен в футер, а не в секции — при заходе по прямой ссылке в воркспейс секции просто не смонтировались бы.
  6. WorkspaceNav приносит свою лендмарку. <nav aria-label="Tools">. Перехватывающий узел обязан её нести: <nav aria-label="Primary"> принадлежал GlobalSidebar и уехал вместе с ним.
  7. Выход из воркспейса. WorkspaceShell размонтируется, clearContent(owner) сверяет токен и, если он всё ещё показан, сбрасывает область — сайдбар возвращается к глобальной навигации.
Почему нужен токен владения

Область держит один узел, значит два одновременно смонтированных вызывающих — «последний победил». Это by design. Не by design было следующее: уборка проигравшего при его размонтировании гасила контент победителя, и вся середина сайдбара оставалась пустой до следующей смены маршрута. Теперь clearContent — no-op, если владелец уже сменился.

6.6 Переключение CMS ⇄ Agents

Контрол принадлежит copilot-admin и рисуется в WORKSPACE_SECTION_SLOT с order: 5 — то есть под переключателем воркспейсов и над навигацией по контенту.

  1. Он есть в обоих режимах. Полная страница «Agents», на которую ушли по строке навигации, — это место, откуда люди не знают, как выйти. Сегментированный контрол, видимый и там и там, сообщает, что режимов два и в каком вы сейчас, и стоит один клик в любую сторону.
  2. Пока вы в CMS, путь запоминается. Эффект пишет pathname + search в sessionStorage под ключом ortha:agents:return:<workspaceId>. Именно sessionStorage: контрол размонтируется и монтируется заново при каждой перестройке контекстной области, а «где я был» не должно переживать до следующей недели.
  3. Переключение на Agents — navigate(agentsPath(workspaceId)).
  4. Возврат в CMS — на ту же страницу, откуда ушли: readCmsPath(workspaceId) ?? '/workspaces/:id'. Прервались посреди редактирования записи, чтобы спросить — возвращаетесь в неё, а не в раздел по умолчанию.
  5. Повторный клик по активной половине игнорируется. Radix при клике по выбранному элементу очищает значение; это снятие выбора, а не переключение, и третьего состояния нет.
  6. Контрол не рисуется вовсе вне воркспейса, без права copilot:use и на деплое, где копайлот выключен (проверяется тем же кэшированным запросом, что и док).

6.7 Правая панель: регистрация, сворачивание, возврат

  1. Страница открывает портал. <RightPanelPortal title="…"> в эффекте вызывает registerPanel(title). Единственный сегодняшний потребитель — панель свойств редактора записи в content-admin.
  2. Регистрация и есть существование панели. Счётчик регистраций (массив заголовков) ненулевой → present: true, колонка получает ширину, в шапке появляется кнопка. Ноль → ширина 0 и inert. Счётчик именно ref-counted, чтобы перекрытие при перемонтировании страницы не читалось как «панели больше нет»; заголовок берётся у последней регистрации.
  3. Сворачивание. Кнопка «Hide {title}» внутри панели вызывает toggle(): взводится animate, назначается focusTarget = 'bar', open становится false.
  4. Передача фокуса — обязательная часть. Половинки тумблера живут в разных компонентах, и одновременно достижима только одна: сворачивание уносит «Hide» в inert-<aside>, раскрытие размонтирует «Show» в полосе. То есть любое переключение уничтожает контрол, которым его сделали, и браузер роняет фокус на <body>. Выживший назван в focusTarget и забирает фокус через usePanelFocusHandoff в том же коммите, который его показывает.оба направления были сломаны; хендофф только на сворачивание выглядит готовым и таковым не является
  5. Невостребованная передача истекает. Если контрол не появился, таймер на 0 мс обнуляет focusTarget — иначе его забрал бы следующий смонтированный контрол, и страница, открытая через десять минут, украла бы фокус из ниоткуда. Эффекты детей выполняются раньше родительского, поэтому уже показанный контрол успевает очистить цель до взвода таймера.
  6. Анимация только по требованию. Переход шириной гейтится на animate, который взводит только toggle и снимает таймер на 330 мс. Панель не выезжает ни на первом кадре, ни каждый раз, когда страница её регистрирует: движение означает «вы только что это сделали», и ничего больше.
  7. Возврат. Кнопка «Show {title}» в области действий полосы. Она существует, только когда панель зарегистрирована и свёрнута, несёт aria-controls="app-right-panel" и aria-expanded={false}; парная кнопка внутри панели — те же aria-controls и aria-expanded.

6.8 Страница выносит действия в верхнюю полосу

  1. Полоса монтирует хост. PageActions отдаёт ref пустого <div> в setActionsHost. Хост стоит всегда, наполнена область или нет.
  2. Страница портирует управление. <PageActionsPortal> рисует детей в этот хост через createPortal. Пока хоста нет — null, то есть страница, смонтировавшаяся раньше своей полосы, просто появляется кадром позже.
  3. Контекст сохраняется. Дети остаются в дереве React своей страницы: обработчики, права, busy-состояние и открытый воркспейс резолвятся как ни в чём не бывало.
  4. PageActions должен быть последним ребёнком TopBar. Область ml-auto, и всё, что после неё, будет вытолкнуто за край полосы. PageTopBar уже делает это правильно; страница, которая композирует TopBar сама, обязана добавить <PageActions /> последним ребёнком.
Почему это компонент, а не часть TopBar

Дизайн-система не может дотянуться до контекста shell — она про него ничего не знает и не должна. Поэтому область действий вынесена в компонент shell'а, который вставляют в примитив полосы. Из всех страниц, композирующих TopBar напрямую, <PageActions /> сегодня рисует только ContentTopBar.

На узком экране панель — оверлей поверх страницы, и оверлей, накрывающий страницу при заходе, никто не просил. Поэтому readOpen() при совпадении (max-width: 767px) возвращает false, минуя хранилище. И — это вторая половина, без которой первая ломает продукт — эффект персиста при том же совпадении выходит, ничего не записав. Раньше записывал: одна загрузка страницы на телефоне навсегда перетирала десктопную настройку, и на следующем визите с широкого экрана панель была свёрнута без всякого объяснения.

Почему не Radix Sheet. Sheet размонтирует своё содержимое при закрытии, а тело панели — хост портала, который обязан оставаться смонтированным, иначе сворачивание выбрасывает состояние наполнителя и заново запрашивает его данные. Поэтому единственная штука, которая досталась бы от Sheet даром — Esc — дописана руками, а фокус в оверлее удерживается через inert на всём, что под ним.

Обработчик Esc уступает. Он выходит, если в документе есть [role="dialog"]:not(#app-right-panel), [role="alertdialog"], [role="menu"] или [role="listbox"]. Исключение самой панели обязательно: на этом брейкпоинте она сама является role="dialog", и без исключения обработчик находил её, решал, что сверху что-то стакнуто, и уступал сам себе — Esc переставал работать ровно в момент, когда атрибут был добавлен.

Скрим — декорация, а не контрол. Он был <button aria-hidden tabIndex={-1}>: роль, объявленная никому, и элемент, недостижимый с клавиатуры. Клавиатурные эквиваленты — Esc и кнопка «Hide {title}» внутри панели, поэтому <div aria-hidden onClick> честнее.

08Заголовок вкладки и реестр

Реестр живёт в @orthacms/utils-admin (src/lib/documentTitle), но именно shell — его первый и образцовый потребитель, и именно рамка shell делает заголовок вкладки единственным устойчивым ориентиром при переключении окон.

8.1 Устройство

  • Имя приложения читается один раз — из document.title самого хост-HTML (apps/admin/index.html, где стоит <title>Admin</title>), в момент загрузки модуля, до того как что-либо успело его декорировать. Продуктовое имя не захардкожено в утилите.
  • Композиция: page ? `${page} · ${APP_NAME}` : APP_NAME. Модульная переменная page — заголовок текущего маршрута или null.
  • useDocumentTitle(title) ставит заголовок на время монтирования маршрута и на анмаунте возвращает null, то есть голое имя приложения.
  • setTitleDecorator(fn) ставит трансформацию над скомпонованным заголовком.

8.2 Почему декоратор, а не запись

Декорация — это трансформация, а не запись

Значок непрочитанного у копайлота ((3) перед заголовком) и смена заголовка страницы — два независимых источника. Если бы значок писал прямо в document.title, он «запечатал» бы ту страницу, которая случайно была открыта в момент первого чата, а любая смена маршрута стёрла бы значок. С декоратором обе стороны двигаются свободно: кто сдвинулся последним, тот перерисовывает от той же скомпонованной базы, а не от того, что оказалось в document.title. Счётчики не накапливаются.

10Доступность и клавиатура

Рамка приложения — это ровно тот код, который либо даёт всем страницам корректную структуру бесплатно, либо ломает её всем сразу. Ниже — то, что shell обязан держать.

10.1 Skip-link

  • Первый фокусируемый элемент документа — <a href="#main-content"> внутри SidebarProvider, до сайдбара. WCAG 2.4.1 Bypass Blocks.
  • Визуально скрыт до фокуса: sr-only focus:not-sr-only + фиксированная позиция, фон, паддинги, кольцо фокуса. То есть его видно, когда он нужен.
  • Цель фокусируема. SidebarInset получает tabIndex={-1}, поэтому переход по фрагменту действительно приземляет фокус в <main>, а не оставляет его на ссылке — иначе следующий Tab вернул бы пользователя в сайдбар, то есть ровно в тот блок, который он попросил пропустить.
  • Пока поднят мобильный оверлей правой панели, ссылка получает tabIndex={-1} и aria-hidden: она первая в документе, то есть ровно то место, куда раньше приземлялся заворачивающийся Tab из оверлея.

10.4 Управление фокусом — три места, где он иначе теряется

  1. Сворачивание сайдбара. Кнопка уезжает в inert. SidebarProvider проверяет, что фокус реально потерян, и переводит его на первый живой [data-sidebar="trigger"].
  2. Переключение правой панели. Обе стороны: focusTarget + usePanelFocusHandoff, фокус переезжает в том же коммите, который делает выжившего фокусируемым. Невостребованная передача истекает на следующем такте.
  3. Закрытие палитры без перехода. Отложенный на такт возврат к запомненному элементу либо к триггеру. При выборе результата возврат намеренно пропускается.

10.5 Интернационализация

  • 27 ключей defineMessages, все с префиксом shell., ко-локейтед в файлах компонентов — общего messages.ts нет. Плюс shell.nav.home, объявленный как labelId прямо в фабрике плагина.
  • Подписи дизайн-системы переводит потребитель. Дизайн-система не тянет react-intl, поэтому имена приходят пропами: mobileTitle, mobileDescription, label у Sidebar, label у SidebarTrigger, scrollLabel у SidebarInset. Без этого мобильный сайдбар объявлял бы себя английским дефолтом «Sidebar» в любой локали.
  • Тумблеры названы по действию, а не по компоненту. Триггер в шапке достижим только пока сайдбар открыт → «Hide navigation». Плавающий рисуется только пока сайдбар скрыт → «Show navigation». Родовое «Toggle Sidebar» называло бы компонент, а не результат нажатия.
  • Параметризованные подписи панели: «Hide {title}» / «Show {title}» — обе половины тумблера называют, чем именно управляют.

11Инварианты

Утверждения, которые обязаны выполняться всегда. Это одновременно список для ревью и заготовка утверждений для тестов.

  • И-01Контрибьютор layout в приложении ровно один, и это shell. Второй, зарегистрированный раньше, отключает авторизацию всем приватным маршрутам.
  • И-02layout — это именно AuthProvider снаружи, RequireAuth внутри, AppShell в центре. Перестановка провайдера и гейта делает гейт слепым.
  • И-03Ни один маршрут shell'а не несёт public: true. Домашняя страница приватна, как и catch-all-редирект, который тоже монтируется внутри layout.
  • И-04Shell не импортирует ни один feature-плагин. Расширение идёт только через слоты, перехват области и порталы.
  • И-05Все контрибьюции регистрируются до первого рендера и с нуля (_reset отдельным проходом), поэтому горячая перезагрузка не удваивает содержимое сайдбара.
  • И-06getItems() отдаёт копию: потребитель, сортирующий или фильтрующий на месте, не портит список следующему.
  • И-07Порядок внутри слота — byOrder, стабильно; при равных order решает порядок регистрации плагинов.
  • И-08Строка навигации без permission видна каждому вошедшему; строка с permission — только держателю ключа. Правило одинаково в сайдбаре и в палитре.
  • И-09useHasPermission вызывается безусловно (с '' при отсутствии поля), чтобы порядок хуков не зависел от данных слота.
  • И-10Группа навигации не рисуется, если после фильтра по правам в ней не осталось строк — заголовок никогда не висит над пустотой.
  • И-11Контекстная область сайдбара держит ровно один узел; clearContent — no-op, если вызывающий уже не владелец.
  • И-12Перехватывающий узел приносит собственную именованную лендмарку: <nav aria-label="Primary"> принадлежит GlobalSidebar и уходит вместе с ним.
  • И-13Футер сайдбара живёт вне контекстной области и переживает любой перехват — это единственный регион, гарантированно смонтированный в обоих контекстах.
  • И-14useSidebarContent принимает фабрику + deps; сырой JSX пересоздавался бы каждый рендер и зацикливал бы эффект. deps обязаны перечислять каждое поле, которое узел рисует.
  • И-15Обе наполняемые области заполняются createPortal, а не передачей узла в shell — иначе содержимое теряет контекст своей страницы.
  • И-16Хосты обоих порталов смонтированы всегда, наполнены они или нет; свёрнутая правая панель не размонтирует наполнителя и не перезапрашивает его данные.
  • И-17Правая панель существует ровно тогда, когда есть хотя бы одна регистрация; при нуле колонка нулевой ширины и inert.
  • И-18Любое переключение панели передаёт фокус выжившей половине тумблера — в обе стороны. Хендофф только на сворачивание не считается.
  • И-19Невостребованная передача фокуса истекает на следующем такте и не может быть подобрана следующим смонтированным контролом.
  • И-20Анимация панели гейтится на animate, который взводит только toggle: ни первый кадр, ни регистрация панели страницей движения не вызывают.
  • И-21На узком вьюпорте (совпадение MOBILE_QUERY) панель стартует свёрнутой независимо от хранилища, и это состояние не записывается обратно.
  • И-22Обработчик Esc мобильного оверлея исключает саму панель из проверки «есть ли что-то сверху» — иначе он уступает сам себе.
  • И-23Скрим оверлея — aria-hidden-декорация, а не <button>: контрол, недостижимый с клавиатуры, хуже отсутствующего.
  • И-24SidebarToggle — прямой сиблинг <main>; обёртка ломает селектор [main:has([data-slot=top-bar])~&]:hidden и возвращает плавающую кнопку на страницы с полосой.
  • И-25Skip-link — первый фокусируемый элемент документа, а его цель фокусируема (tabIndex={-1}).
  • И-26Глобальные аккорды (⌘K, ⌘B, ⌘J) не срабатывают в поле ввода и в contenteditable; проверку выполняет одна общая функция.
  • И-27Палитра возвращает фокус при закрытии без перехода и намеренно не возвращает при переходе.
  • И-28Активная строка помечается и визуально, и через aria-current="page"; end: true есть только у корневого маршрута.
  • И-29Все подписи, которые дизайн-система отдаёт наружу пропами, действительно переданы и переведены — mobileTitle, mobileDescription, label, scrollLabel.
  • И-30Каждое чтение и запись в cookie / localStorage / sessionStorage обёрнуты в try/catch; отказ хранилища деградирует до состояния в памяти, а не до ошибки.
  • И-31Маршрут ставит заголовок вкладки через useDocumentTitle и снимает его на анмаунте; значок непрочитанного применяется декоратором, а не записью в document.title.
  • И-32В документе ровно один <main> — на нём держится и skip-link, и скоуп RouteAnnouncer.

Формулировки — «действие → ожидаемый результат», чтобы их можно было брать в тест-кейс без переписывания. Проверяется браузером: собственных unit-тестов у пакета нет ни одного. Гейт и монтирование

  • Открыть / без сессии → редирект на /identity/login, replace, с state.from; сайдбар не мелькает.
  • Проба «кто я» отвечает 500 → экран «недоступно» с повтором, не редирект на форму входа.
  • Проба в полёте → полноэкранный загрузчик; ни сайдбара, ни содержимого страницы.
  • Открыть несуществующий путь при живой сессии → редирект на /, рамка на месте.
  • Открыть несуществующий путь без сессии → форма входа: catch-all тоже внутри layout.
  • Убрать ShellPlugin() из plugins.ts → plugins.spec.ts красный; приватные маршруты рендерятся в голом <Outlet/> и без гейта.
  • Добавить второй плагин с layout → предупреждение хоста с именами победителя и проигравших + красный plugins.spec.ts.

Сайдбар и слоты

  • Войти администратором → Overview: Home, Activity. Directory: Workspaces, Members, API Tokens, Segments — именно в этом порядке.
  • Войти пользователем без users:read, tokens:read, segments:read, activity:read → группа Overview содержит только Home, группа Directory — только Workspaces; заголовков над пустыми телами нет.
  • Отобрать все права, дающие строки в Directory → заголовок «Directory» не рисуется вовсе.
  • Кликнуть «Members» → строка получает aria-current="page"; «Home» — не получает (у неё end: true).
  • Убрать все элементы из SIDEBAR_FOOTER_SLOT → футер вместе с верхней границей не рисуется.
  • Сохранить файл в dev-режиме (горячее обновление Vite) → строки навигации и воркспейсы не дублируются.
  • Поменять местами CopilotPlugin() и UsersPlugin() → порядок в футере меняется — ничья по order: 10 решается регистрацией (см. раздел 14).

Сворачивание сайдбара

  • Нажать ⌘B на домашней → панель уезжает за 300 мс, контент занимает всю ширину, появляется плавающая кнопка «Show navigation» слева сверху.
  • Нажать ⌘B на любой странице с полосой → плавающей кнопки нет; триггер раскрытия появляется первым элементом внутри TopBar.
  • Свернуть с клавиатуры триггером в шапке → фокус оказывается на встроенном триггере полосы (или на плавающей кнопке на Home), а не на <body>.
  • Свернуть, перезагрузить страницу → сайдбар остаётся свёрнутым (кука sidebar_state=false).
  • Tab по свёрнутому сайдбару → ни поиск, ни ссылки, ни футер не получают фокус — панель inert.
  • Нажать ⌘B с кареткой в поле поиска записей и в теле richtext → сайдбар не двигается; в richtext срабатывает «жирный».
  • Сузить окно до <768px → сайдбар становится оверлей-drawer, объявляется как диалог «Navigation», закрывается по Esc и по клику вне.
  • Обернуть <SidebarToggle> в <div> → регресс: плавающая кнопка появляется на всех страницах поверх полосы.

Палитра команд

  • Нажать ⌘K на домашней → палитра открывается, фокус в поле; в «Go to» — все доступные строки навигации, ниже группы воркспейсов и типов контента.
  • Нажать ⌘K с кареткой в поле поиска страницы → палитра не открывается, символ «k» попадает в поле.
  • Нажать ⌘K, когда палитра уже открыта → закрывается, несмотря на то что фокус в текстовом поле палитры.
  • Открыть палитру и нажать Esc → фокус возвращается тому элементу, который держал его до открытия (или триггеру, если элемент исчез).
  • Выбрать результат → переход состоялся, фокус не утащен обратно в сайдбар.
  • Стрелки ↑ ↓ → меняется объявляемый выбор, а не только подсветка.
  • Пользователь без users:read ищет «Members» → результата нет.
  • Открыть воркспейс и нажать ⌘K → открывается палитра по типам контента (content-admin), а не глобальная; двойного открытия нет.

Воркспейс и перехват области

  • Войти в воркспейс → середина сайдбара заменяется на нав воркспейса; футер (док, аккаунт) остаётся.
  • Выйти из воркспейса на / → глобальная навигация возвращается.
  • Быстро перейти из одного воркспейса в другой → середина сайдбара не остаётся пустой (проверка токена владения).
  • Переименовать воркспейс в его настройках → переключатель в сайдбаре показывает новое имя сразу, включая aria-label.
  • Зайти по прямой ссылке внутрь воркспейса новой вкладкой → сохранённая тема пользователя применяется (ThemeSync в футере смонтирован).
  • Перейти на Agents и обратно на CMS → возврат на ту же страницу, с которой ушли, включая query-строку.
  • Кликнуть по уже активной половине переключателя → ничего не происходит, третьего состояния нет.
  • Пользователь без copilot:use → переключателя CMS ⇄ Agents нет вовсе.

Правая панель

  • Открыть запись в редакторе → появляется колонка 22rem с заголовком, без анимации выезда.
  • Свернуть панель с клавиатуры → фокус на кнопке «Show {title}» в полосе.
  • Раскрыть с клавиатуры → фокус на кнопке «Hide {title}» внутри панели.
  • Свернуть панель, поработать в форме, раскрыть → содержимое панели в том же состоянии, запросы не повторялись.
  • Свернуть и перезагрузить страницу → панель остаётся свёрнутой (ortha:right-panel=collapsed).
  • Открыть ту же запись на телефоне → панель свёрнута независимо от сохранённого; localStorage не изменился.
  • После визита с телефона открыть на десктопе → панель открыта, как и была.
  • На узком экране раскрыть панель → оверлей поверх страницы, role="dialog" + aria-modal, всё под ним inert; Tab не выходит на страницу и не заворачивается на skip-link.
  • Нажать Esc в оверлее → панель закрывается, фокус приземляется куда-то полезно.
  • Открыть меню внутри оверлея и нажать Esc → закрывается меню, панель остаётся.
  • Кликнуть по затемнению → панель закрывается; при этом Tab на затемнение не попадает — это не контрол.
  • Уйти со страницы с панелью → колонка исчезает, ширина 0, inert; кнопки в полосе нет.

Заголовок вкладки и объявления

  • Открыть / → заголовок вкладки «Home · Admin».
  • Перейти на /users и вернуться → заголовок меняется на «Members · Admin» и обратно.
  • Получить непрочитанные в чате → «(2) Home · Admin» + точка на favicon; при смене страницы счётчик остаётся и база меняется.
  • Закрыть чат → заголовок возвращается без префикса, favicon восстановлен.
  • Клиентская навигация → имя нового экрана объявляется в polite-регионе после того, как скелетон сменился реальным заголовком.

Доступность

  • Первый Tab на любой приватной странице → видимая ссылка «Skip to main content».
  • Активировать её → фокус внутри <main>; следующий Tab не возвращает в сайдбар.
  • Обход по лендмаркам → complementary «Sidebar», navigation «Primary» (или «Tools» в воркспейсе), main; бренд «Ortha CMS» — внутри лендмарки сайдбара.
  • Дойти табом до скролл-порта → остановка называется «Page content»; стрелки прокручивают.
  • Загрузить приложение с locale: 'de' → мобильный сайдбар объявляется не английским «Sidebar»; недостающие переводы логируются один раз на ключ, а не на каждый рендер.
  • Прогнать axe на домашней, в воркспейсе и с открытой панелью → нет нарушений; в частности нет висящего aria-controls у сворачиваемого списка воркспейсов.
  • Ширина 320px → горизонтального скролла документа нет, skip-link фокусируется и попадает во вьюпорт.
  • prefers-reduced-motion → панель меняет состояние без выезда (motion-reduce:transition-none).

Чего ещё нет

  • Ни одного собственного теста. В packages/shell/admin нет ни *.spec.ts(x), ни цели test — всё покрытие лежит в apps/admin-e2e. Для рамки это защитимо, но useSidebarContent с его токенами владения и pageChrome с истечением передачи фокуса — чистая логика, которую дешевле проверять юнитами.
  • Фокус в мобильном оверлее правой панели не заперт. Он ограничен инертностью всего, что снаружи, и это закрывает практическую дыру; но Tab из последнего элемента панели по-прежнему не заворачивается на её первый, а уходит в хром браузера.
  • Глобального поиска по содержимому нет. Палитра ищет только по меткам назначений и по тому, что положили плагины.
  • Групп навигации ровно две и они захардкожены в GROUPS. Третья потребует правки shell — расширяемость слота на группы не распространяется.
  • Правая панель одна на приложение. Регистрации ref-counted, но показывается заголовок последней, а тело — общий хост; двух панелей одновременно не бывает.
  • Плавающий тумблер не настраивается. Его видимость целиком определяется CSS-селектором по наличию TopBar на странице.

  • Только ContentTopBar рисует <PageActions />. Три другие страницы композируют TopBar напрямую — MediaTopBar, InsightsPage, AgentsTopBar — и области действий не подключают. Сегодня это ни на что не влияет (порталами пользуется только редактор записи), но страница, которая захочет вынести кнопку в полосу на любой из этих трёх, получит молчаливое «ничего не отрисовалось».
  • Тип ShellAdminPlugin — пустой алиас AdminPlugin, сохранённый «под будущую конфигурацию». Конфигурации пока нет; это осознанный задел, а не забытый код.
  • Комментарий в AppShell о том, что мобильный сайдбар не нуждается в инертности, верен и полезен: на телефоне он либо закрыт и размонтирован, либо открыт с собственной фокус-ловушкой Radix.

Паспорт пакета packages/shell/admin. Структура та же, что у пилотного артефакта по identity, адаптированная под то, что это не серверный плагин: бизнес-описание → состав → права в навигации → карта слотов → маршруты и экраны → сценарии по шагам → состояния и поведение → заголовок вкладки → конфигурация → доступность → инварианты → чек-лист → границы → расхождения. Разделы, которых у admin-пакета нет — модель данных, HTTP API, миграции — просто выпали.

Источник — исходный код: packages/shell/admin/src/** целиком, плюс сверка со смежными пакетами — bootstrap-admin (createAdmin), identity-admin (RequireAuth, authContext), design-system (ui/sidebar.tsx, ui/top-bar.tsx, hooks/use-mobile), utils-admin (slot, byOrder, documentTitle, isComposingText), а также фабрики всех плагинов-контрибьюторов и наборы apps/admin-e2e/src/{shell,home,host}. Файл AGENTS.md использован как каркас, но каждое утверждение сверено с реализацией — расхождения вынесены в раздел 14.
