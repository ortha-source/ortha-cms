Component library · packages/design-system

Design System One interface vocabulary across the whole OrthaCMS admin UI

This is not a plugin. The package has no routes, no NestJS module, no tables and not one permission key. @orthacms/design-system is a React component library built on shadcn/ui: buttons, fields, dialogs, tables, the sidebar. Its job is to make eighteen independent admin plugins, written at different times by different people, look and behave like one application, and to hand a page's author accessibility, theming and keyboard navigation by default rather than as separate work.

01Business description

The OrthaCMS admin UI is assembled from plugins: content, media, workspaces, members, the copilot, audiences, checks, analytics — each lives in its own package and is developed separately. Without a shared library that is eighteen different ideas of what a “button”, an “empty state” and a “modal window” are. The Design System is the one vocabulary that makes them a single product.

The problem it solves

  • Visual coherence with no coordination. The author of a page in content/admin does not agree a corner radius or a border shade with the author of a page in media/admin — both take Card and Button. Every styling decision was made once and lives in one place.
  • Accessibility by default rather than from memory. This is the biggest saving. Associating a label with a field, role="alert" on an error, scope="col" on a table header, a dialog's focus trap, keyboard reachability of a scrollable region — all of it is already inside the primitive. A plugin that simply took InputField gets a correct form knowing nothing about WCAG.
  • Theming by one switch. The light and dark themes are two sets of CSS variables. The components do not know which theme is active: they are written against semantic classes (bg-card, text-muted-foreground) rather than specific colours. Switching the theme requires an edit in not one component.
  • One place to fix a defect. The pointer cursor on buttons, a visible focus ring in high-contrast mode, suppressing animation under prefers-reduced-motion — each of those fixes was made once in the shared layer and propagated instantly to every page. A fix “at each call site” would have been incomplete, guaranteed.
  • Cheap extension. Components are added by the shadcn CLI straight into the package's sources — that is a copy of the code, not a dependency on somebody else's version. So any component can be adapted to the product, and no upstream release will break it.

Who sees it

The admin-plugin author

Writes import { Button, Card, cn } from '@orthacms/design-system' and gets a finished page of the right shape. Introduces no styles of their own, does not pull in Radix directly, does not think about the dark theme.

The admin-UI user

Sees one product rather than a set of mismatched screens. Can choose a light or a dark theme, work by keyboard alone, turn on high contrast or turn off animation — the interface survives all of it.

The owner of a generated application

Gets the library in the CORE_PACKAGES set of the create-ortha-app template — it is installed unconditionally, because it is the first thing you reach for when writing a page of your own.

What the Design System is not

The boundaries explain why the package lacks things a “design system” is often expected to have:

  • It is not a plugin. Neither an AdminPlugin nor a ServerPlugin. The package registers nothing, adds no routes and takes no part in the application's lifecycle. It is simply imported.
  • It is not where the theme lives. The tokens (@theme, .dark, the avatar palette) are declared in apps/admin/src/styles.css — in the host application, not in the package. The package only consumes them through semantic Tailwind classes. The library's own CSS is one small file, for rules that cannot be expressed as utilities.
  • It is not an i18n layer. The package has no react-intl and no translation catalogue. Every visible string comes from the consumer; the exception is pure iconography (the close cross, the sidebar toggle), whose default English text the host overrides through one context.
  • It is not a form library. InputField is presentational and form-engine-agnostic: it takes native <input> props and a list of errors. Validation and form state belong to the consumer (in the admin UI, TanStack Form).
  • It is not a Storybook or a showcase. There is no component catalogue with examples in the repository; the documentation is the JSDoc above each export and the real call sites.
  • It is not a charting library. The --color-chart-* tokens are declared in the host and used by insights/admin's widgets; the visualisation components themselves do not live in the design system.
The architecture's key idea

shadcn/ui is not an npm dependency but a source generator. The CLI puts a component's code into src/lib/components/ui/, and from that moment it is ours: it can be rewritten, its role renamed, a prop added. That is why half the files in the inventory diverge from upstream — Alert stopped being a heading, Spinner stopped being a live region, Table learned to be a keyboard-reachable scroll region. The flip side: upstream updates do not arrive by themselves, and each has to be merged by hand.

How a component reaches the browser: there is no build

In the monorepo packages are consumed from source. For design-system, main, types and all three branches of exports["."] point at the same ./src/index.ts; the ./styles.css subpath is published separately. No build step is needed before consumption — the apps/admin application's Vite transpiles the design system's TSX directly, like its own code.

Two practical facts follow, and they are the ones that most often bite a newcomer:

  1. Vite does not typecheck. A type error in a library component will not stop the dev server. It is caught by a separate admin:dev:typecheck task (tsc --build --watch) — the fourth pane in npm run dev.the same is true of any admin plugin
  2. The @/ alias does not resolve inside the library. It is declared in tsconfig.lib.json ("@/*": ["./src/*"]) and works for tsc, but the consuming application's Vite dev server does not see it and fails with Failed to resolve import "@/lib/utils". Hence the first of the two mandatory rules (section 6).

The tarball published to npm is built differently: tools/release/pack.mjs compiles the package through tsconfig.lib.json and assembles, under the temporary root dist/pack/<projectRoot>/, a rewritten manifest whose exports already point at ./dist. tsc does not emit src/styles.css, so pack copies it separately (every non-TS asset next to the sources is carried to the same relative position).

03Design tokens and theming

Not one component in the library contains a specific colour. They are all written against semantic Tailwind utilities — bg-background, text-muted-foreground, border-input, bg-success-soft — which expand into CSS variables. The variables themselves are declared not in the package but in the host application: apps/admin/src/styles.css. How the theme is switched

  1. The initial state is read synchronously. useState(readStoredTheme) — the value from localStorage['ortha.theme'] is taken right in the initialiser, so the first paint is already right and there is no flash of the wrong theme.unavailable or corrupt storage quietly yields the system default
  2. system is resolved against the OS. The subscription to matchMedia('(prefers-color-scheme: dark)') lives for the provider's whole lifetime, so a change of system theme applies without a reload.
  3. The result is reflected on the document. applyToDocument sets or clears the dark class on <html> and sets style.colorScheme, so the browser repaints its own furniture — scrollbars, native controls.
  4. The choice is stored. The localStorage write is wrapped in a try/catch: a private window or an exhausted quota loses only the cross-session memory, not the theme change itself.
  5. The durable copy is on the server. The provider knows nothing about it: a plugin reading the user's profile simply calls setTheme. setTheme compares the value with the current one and does not touch state when it has not changed — and hydration from the server usually repeats the value already in force.
  6. The hook does not fail outside a provider. useAppearance without an AppearanceProvider returns { theme: 'system', resolvedTheme: 'light', setTheme: () => undefined } — a component in isolation (a test) still renders.

Toaster is the one component that reads the resolved theme explicitly: it passes resolvedTheme to sonner, because sonner has chrome of its own that would otherwise drift away from the application.

Forced-colors mode is not cosmetics

Under forced-colors: active (Windows High Contrast) the browser discards box-shadow entirely. And every focus indicator in this library is a Tailwind ring-* utility, that is, a box-shadow. The consequence: a keyboard user in high contrast could see focus nowhere in the whole admin UI — a 2.4.7 and 1.4.11 failure across every page at once, which no axe run sees (axe does not emulate that media feature). The cure is a real outline, which the mode preserves. The !important here is load-bearing rather than lazy: several components carry a focus-visible:outline-none next to their ring, and by specificity a class with a pseudo-class beats a bare :focus-visible — without !important the outline would be switched off by exactly the components that need it most. Separately: a selected state drawn as a plain fill ([role=option][aria-checked=true], an active panel item, [aria-current]) gets a Highlight border, and disabled controls get GrayText, because opacity is not part of the forced palette and a disabled control would read as a working one. forced-color-adjust: none is deliberately used nowhere — that is precisely the failure this block was written to prevent.

06Rules and conventions for authors

Two rules that apply to every component

1. Relative imports, not @/. The consuming application's Vite dev server does not resolve the library's @/* alias when the admin UI eats the design system's sources — it fails with Failed to resolve import "@/lib/utils". From a file in src/lib/components/ui/ that means import { cn } from '../../utils', a neighbouring component './<x>', a hook '../../hooks/<x>'. The shadcn CLI generates exactly @/ imports, so they have to be rewritten every time. Verified against the code: all 48 files use relative paths, and there is not one @/ import in src/.
2. Export from src/index.ts. That is the package's one public surface. A component that did not reach the barrel does not exist for consumers — package.json hands out no subpaths other than ./styles.css and ./package.json. The rule covers types too (ButtonProps, MultiSelectOption, StepperStep and so on).

Both rules apply identically to a component added by the CLI and to one written by hand.

File layout

  • UI components → src/lib/components/ui/, with the file name in kebab-case (input-field.tsx) and the exported symbols in PascalCase.
  • Utilities → src/lib/; hooks → src/lib/hooks/.
  • Theme tokens — in apps/admin/src/styles.css, not in the package.
  • Global rules that cannot be expressed as a Tailwind utility — in src/styles.css; the host imports it once, after @import 'tailwindcss'.
  • Tests — next to the component, <component>.spec.tsx.

TypeScript conventions

  • type rather than interface. (There are exceptions in the code — see section 13.)
  • A JSDoc on every exported symbol. That is the library's documentation: there is no showcase.
  • import type for type-only imports.
  • No .js extensions in imports.
  • Prettier: 4-space indent, single quotes (the whole repository's rule).

The style rules that govern working with components

They are held by the shadcn skill — and they apply both inside the library and in any plugin that consumes it:

Styling

className is for layout, not for recolouring. No space-x-*/space-y-* — only flex + gap-*. size-* when width equals height. truncate instead of three utilities. No hand-written dark: colour overrides — the semantic tokens are there for that. Conditional classes through cn(), not through template strings. No hand-set z-index on overlays — they manage their own stacking.

Forms

A form is a FieldGroup + Field, not a div with vertical spacing. Inside an InputGroup, only InputGroupInput/InputGroupTextarea. A set of 2–7 options is a ToggleGroup, not a loop over buttons with a hand-rolled active state. Related checkboxes/radios are a FieldSet + FieldLegend. Validity: data-invalid on the Field, aria-invalid on the control.

Composition

An item always sits inside its group (SelectItem → SelectGroup, CommandItem → CommandGroup). A custom trigger goes through asChild. Dialog, Sheet and Drawer always require a Title (it may be sr-only). A card is used with its full set of parts. Button has no isLoading — the state is assembled from Spinner + disabled. Avatar always comes with an AvatarFallback.

Component first, markup second

A callout is an Alert, not a styled div. An empty state is Empty. A notification is toast(). A divider is Separator, not an <hr>. A placeholder is Skeleton, not your own animate-pulse. A label is a Badge, not a coloured span.

The shadcn CLI is always run naming the workspace: npx shadcn@latest add <component> -c packages/design-system. From the repository root it fails with monorepo_root, because components.json lives in the package rather than at the root.

What the library cannot provide

  • A control's name that depends on the data. A kebab in a table row must be called “Actions for {name}” — the component does not know which row. Likewise Stepper requires stepAriaLabel, SidebarInset a scrollLabel, Table an aria-label/<caption>, and Progress an aria-label and, where needed, an aria-valuetext.
  • A heading's rank. The page decides, not the banner and not the card.
  • Moving focus after a destructive action. Hence ConfirmDialog's onCloseAutoFocus and SearchToolbar's inputRef: the library provides the hook, but the caller must do the aiming.
  • The “skip to main content” link. It is drawn by AppShell in shell/admin, and SidebarInset only supplies the target — <main id="main-content" tabIndex={-1}>. Adding it again in a plugin is not allowed.
  • <html lang> and <html dir>. They are set by createAdmin from its locale. A component must not do it.
  • Translating strings. Every visible text comes from outside; the library only supplies English defaults for pure iconography.
Two role="alert"s in one view is a conflict

FieldError and Alert both declare themselves alert. A form showing a general error banner and a field error at once creates two live regions competing for the right to speak. That is exactly the ailment Spinner was cured of. The rule is not to put two such regions on one screen.

English names that cannot be overridden

Not all the furniture has been routed through the labels context. Breadcrumb hard-codes aria-label="breadcrumb" and Pagination aria-label="pagination"; neither has a prop to override it. That is not a 4.1.2 failure (there is a name), but it is a 3.1.2 of the same class as the one already fixed for the dialog's close cross: in a German session a landmark is named in English. The pagination's back/forward buttons, unlike the <nav>, can be overridden — they have both a label and an aria-label.

Where this is checked

Not in this package. Accessibility is measured in apps/admin-e2e, where the interface really exists: 7 a11y.spec.ts suites (axe) and 4 keyboard.spec.ts suites. Plus three host-level suites:

  • host/host.spec.ts — “bypass blocks”: the first Tab lands on the skip link, it becomes visible on focus, and activating it moves focus to <main>.
  • host/reflow.spec.ts — the same at 320px: a skip link a narrow layout pushed off screen is not a skip link.
  • host/platform-preferences.spec.ts — the one place the dark palette is scanned (every other axe run is in the light theme) and where the focus indicator is checked to survive forced-colors: active. An important harness detail: test.use({ forcedColors }) and test.use({ reducedMotion }) in Playwright do not work — those properties are not in the fixed list of context options; page.emulateMedia() and a project-level setting are what do.

08Working scenarios — step by step

8.1 Adding a component from the shadcn registry

  1. Check that it is not already there. In src/index.ts first, then npx shadcn@latest search. “Use what exists first” is the skill's first rule for a reason: MultiSelect, SearchToolbar and ConfirmDialog already exist and are not in the registry.the task is often solved by composition rather than by a new file
  2. Run the CLI naming the workspace. npx shadcn@latest add <component> -c packages/design-system. Without -c the command fails with monorepo_root.
  3. Rewrite the @/ imports as relative ones. Mandatory step 1. Otherwise the admin dev server will not come up.
  4. Add the exports to src/index.ts. Mandatory step 2. Including the *Props types.
  5. Check the colours. A registry component arrives on the neutral base palette; if it uses a token that is not in apps/admin/src/styles.css, either add it there (checking contrast) or swap it for an existing semantic one.
  6. Write the JSDoc on every exported symbol — there is no showcase, and this is the only documentation.
  7. Check the build and the types. npx nx typecheck design-system, then npx nx lint design-system. Tailwind picks up a new directory itself — the @source glob in apps/admin/src/styles.css already covers src/**/*.{ts,tsx}.
  8. Decide whether a test is needed. By the criterion in section 9: a test here is justified only if this is a seam a page test cannot reach.

8.2 Changing an existing component

  1. Work out who will be affected. grep -rl "<ComponentName" packages apps. For Button that is 146 files — changing a default variant is visible across the whole admin UI.
  2. Check whether the task can be solved at the call site. cn is built so a caller's className beats the base classes. If the exception is a one-off, it should stay a one-off.
  3. If the change is shared, make it in the shared layer. The cursor on buttons, the focus ring in high contrast, the pulse suppression — all of them are “one file instead of thirty” edits. The sign is that the property belongs to “is this operable at all?” rather than to a particular component.
  4. Do not change a role without reason — and change it with an explanation. Every case in this library where a role or an attribute differs from upstream (Alert, Spinner, Table, SidebarInset) carries a comment with a ticket number. That is a convention: whoever comes next to “fix it back” must first read why.
  5. Do not hard-code a string you are adding. Either a prop at the call site, or a key in DesignSystemLabels (the type is a Partial, so a new key does not break a consumer).
  6. Check both themes. The tokens are declared twice; an edit tied to a particular lightness usually breaks in the dark theme.
  7. Run the package's tests and the e2e. npx nx test design-system, then npx nx e2e admin-e2e -- --project=chromium src/**/a11y.spec.ts src/**/keyboard.spec.ts.

8.3 Updating a component from upstream

The riskiest of the three scenarios: shadcn is a copy of the sources, so an “update” physically overwrites a file that may contain our edits.

  1. Commit the current state to git. The update should be its own commit, so the diff shows exactly what arrived.
  2. Check whether it is on the rewritten list. Section 5 lists the files where upstream has already diverged from us. For those, an update is a manual merge rather than an overwrite.
  3. Run the CLI. npx shadcn@latest add <component> -c packages/design-system — the command will overwrite the file (the CLI asks for confirmation).
  4. Read the whole diff. Look for: vanished aria-*, a returned <h5> on the title, a returned role="status" on the spinner, a vanished scope, a vanished prop (closeLabel, container, label).every such loss is an accessibility regression, not cosmetics
  5. Rewrite the @/ imports again. The CLI generates them every time.
  6. Reconcile the exports with src/index.ts. Upstream may have renamed or added a subcomponent.
  7. Check for dead animation classes. If animate-in/fade-in-0/zoom-in-95 arrived, they will generate no CSS: the corresponding Tailwind plugin is not installed in the repository. Either remove them or express the motion through .ds-dropdown-motion.
  8. Run the package's tests. The localizable-copy, table, sidebar and input-field suites were written precisely so that such a regression fails here rather than in production.

8.4 Adding or changing a theme token

  1. Open apps/admin/src/styles.css — not a file in the package.
  2. Declare it in @theme (light) and in .dark (dark). A missing half is not “inheritance” but a token that stays light in the dark theme.
  3. Check the contrast: 4.5:1 for ordinary text, 3:1 for large text, 3:1 for borders and graphics. The axe run in admin-e2e checks color-contrast, and a regression here fails CI.
  4. Remember the palette's two traps. White text on bg-brand does not pass AA — orange is meant for icons and accents. In the dark theme the solid status fills invert their own foreground to ink: a lightened fill no longer carries white text to AA.
  5. If the token is substituted inline (as the avatar palette is), declare it in :root rather than in @theme: Tailwind prunes from @theme any token no generated utility referenced.
  6. For the chart palette — do not touch the values by hand: they are in hex because they are a colour validator's output. Changing them requires re-running the validator against the card surface.

10Invariants

Statements that must always hold. This is at once a review list and a draft set of test assertions.

  • I-01No file in src/ imports through the @/ alias — only through relative paths.
  • I-02Everything meant for a consumer is exported from src/index.ts; the package hands out no public subpaths other than ./styles.css and ./package.json.
  • I-03No component contains a literal colour: only semantic Tailwind utilities expanding into var(--color-*).
  • I-04Every light-palette token is overridden in .dark, except three families that are the same colour in both themes on purpose: the panel’s chrome (--color-sidebar-*), the navigation accents (--color-nav-*) and the avatar palette (--color-avatar-*). Nothing else may inherit, and an inherited family that acquires a .dark override has left the list.
  • I-05A caller's className prop always beats the component's base classes: cn puts it last and tailwind-merge gives a conflict to the last one.
  • I-06The package contains neither react-intl nor a translation catalogue; every visible string either arrives as a prop or has an English default overridable through DesignSystemLabelsProvider.
  • I-07DesignSystemLabelsProvider takes a Partial: a missing key keeps its English default, so adding a key does not break an existing consumer.
  • I-08A prop at the call site (closeLabel, label) always beats the value from the labels context.
  • I-09Spinner and Skeleton are decorative and announce nothing themselves; busyness is announced only by a named role="status" (SkeletonRegion, AppLoader, WizardPageSkeleton).
  • I-10There is exactly one live region per loading surface; two mounted at once is a defect.
  • I-11FieldError returns null when there are no messages; an empty role="alert" is never opened.
  • I-12invalid in InputField governs only the control's marking and never suppresses the error message.
  • I-13A control's aria-describedby is assembled from the hint, the error and the value the caller passed — none of the three is lost.
  • I-14AlertTitle, CardTitle and EmptyTitle are not headings by default; the page sets the rank — through asChild on CardTitle and EmptyTitle, and by nesting a heading inside AlertTitle, which takes no asChild because it stays the element the banner’s aria-labelledby points at.
  • I-15Alert writes aria-labelledby only after AlertTitle has actually mounted.
  • I-16The Table wrapper takes a tab stop only on actual overflow; the group role and the name are set exclusively together.
  • I-17SidebarInset's scrollport is focusable and draws a visible ring when it receives focus; the ring is inset, because the parent clips overflow.
  • I-18No nameable container in the library adds a second landmark: group is used, not region. The only landmarks the library creates are the <main> of SidebarInset/AppLoader, the complementary of a named panel, and the <nav> of the breadcrumbs, the link tabs and the pagination.
  • I-19A collapsed offcanvas panel is marked inert: its controls are outside the tab order and outside the accessibility tree.
  • I-20Ctrl/⌘+B is not intercepted when focus is in a text input, a textarea, a select or inside a contenteditable.
  • I-21useIsMobile returns the right value on the first render frame, not after an effect.
  • I-22The library's single layout breakpoint is 768px; 768 inclusive counts as desktop.
  • I-23Every access to localStorage, document.cookie and matchMedia is wrapped in an environment check and a try/catch; a storage failure loses only the persistence of the preference.
  • I-24The theme is applied to the document in two ways at once: the dark class on <html> and style.colorScheme — so the browser repaints its own furniture too.
  • I-25useAppearance outside an AppearanceProvider does not throw: it returns the defaults and a no-op setter.
  • I-26useSidebar outside a SidebarProvider throws; for an optional dependency there is useOptionalSidebar.
  • I-27TopBar inside an inset renders only through a portal into the bar; while the bar's host is null the bar is not drawn at all, so it does not flash in the page flow.
  • I-28Clicking a toast's body dismisses that toast; clicks on the close button, the action/cancel buttons and links inside the toast are not intercepted.
  • I-29Toasts are positioned in the bottom right corner, and that is decided in Toaster rather than at the call site: copilot-admin relies on it when suppressing a toast while the dock is open.
  • I-30Every non-operable animation is suppressed under prefers-reduced-motion: reduce — with one deliberate exception, the loading spinner, which is stripped of movement rather than stopped: opacity only, no transform, a cycle no faster than 1 s. A stopped indeterminate loader is indistinguishable from a hung request, and WCAG 2.3.3 is about non-essential motion, not about withholding essential feedback.
  • I-31The wizard step's animation changes only the transform; opacity stays at 1, so the content is visible even with animation clocks stopped.
  • I-32Under forced-colors: active, every :focus-visible has a real outline; forced-color-adjust: none is used nowhere.
  • I-33No state is carried by colour alone: a selected segment and an active panel item additionally thicken the font, and status dots are always accompanied by text.
  • I-34White text is never placed on bg-brand; there is a separate brand-text token for link orange.
  • I-35A wizard step list item's key is its position, not its caption: the caption belongs to the consumer and may repeat.
  • I-36A row in MultiSelect is identified by its value, with the caption added as keywords — otherwise two options with the same caption merge into one.
  • I-37The package exports nothing server-side and has no routes, no module, no tables and no permission keys.
  • I-38The only peer dependencies are react and react-dom at ^19; everything else is an ordinary dependency, so a consumer has nothing extra to install.

11Testing checklist

Phrased as “action → expected result”, so they can go into a test case without rewriting. The library is checked two ways: by the package's unit tests (npx nx test design-system) and by eye and keyboard in a live admin UI (npm run dev). The package has no server side, so curl and psql have nothing to do with it.

Visual coherence

  • Walk every admin page in the light theme → identical card radii, identical button and field heights (9), the same input border everywhere — noticeably darker than the structural one.
  • Switch to the dark theme → every page repaints in full; not one patch stays light; cards read as a surface a step lighter than the canvas.
  • The system theme, with the OS theme changed while the tab is open → the interface repaints without a reload.
  • Reload the page with the dark theme chosen → the very first paint is dark, with no flash of light.
  • Open the admin UI in a private window with storage blocked → the application works, the theme is system, and the console has no errors.
  • The sidebar in both themes → it stays dark: its tokens are dark to begin with and are not overridden in .dark.
  • Check all nine Badge variants on a highlighted table row → the secondary chip does not blend into the hover background.
  • An orange link on white and on dark → readable; there is no white text on an orange fill anywhere.
  • A page header with three or more action buttons at 900px wide → the cluster wraps to a second line rather than running off the right edge.
  • The scrollbars in every region (the inset, the panel, a table, the right-hand panel) → thin, with the thumb in the border token's colour and a transparent track — that is, they change with the theme.

Forms and fields

  • Click a field's label → focus moves into the control.
  • Submit a form with an error → the field is marked aria-invalid, the border is red, and the message appeared and was announced (role="alert").
  • Pass invalid={false} together with an error → the message is rendered anyway; it cannot be hidden with that prop.
  • Pass errors={[]} or errors={[{}, undefined]} → nothing is rendered; there is no empty role="alert" in the DOM.
  • Focus a field with a hint and an error → the screen reader reads out both the hint and the error — both made it into aria-describedby.
  • A field with the caller's own aria-describedby → it is not lost but added to the generated ones.
  • A MultiSelect with two options sharing a caption → the rows are distinguishable, highlight separately, and the arrow keys move between them.
  • Search a MultiSelect by an option's value rather than its caption → the option is found.
  • A MultiSelect inside a Dialog without the container prop → the defect reproduces: the list does not scroll with the mouse wheel. With container passed, it does.
  • DateTimePicker: type a time with seconds, then change the day → the seconds are preserved.
  • DateTimePicker: pick a day, then change the time → the day is not reset.
  • A disabled control → a not-allowed cursor, a click does nothing; in high contrast the text is GrayText.

Keyboard and focus

  • The first Tab on any private page → the “skip to main content” link, visible while focused; activating it moves focus to <main>.
  • Tab through the whole page → a focus indicator is visible at every stop; there are no “dead” presses where nothing visibly happens.
  • Tab to the inset's scroll region → the focus ring is visible (inset), and the arrow keys scroll the content.
  • A wide table in a narrow window → the wrapper takes a tab stop and gets a ring; in a wide window there is no extra stop.
  • Collapse the sidebar and Tab through → not one control of the hidden panel receives focus.
  • Press Ctrl/⌘+B while in an input or in an article's body → the panel does not collapse; in the editor bold is applied.
  • Press Ctrl/⌘+B while not in a field → the panel toggles.
  • Open a dialog and press Tab many times → focus does not leave the dialog.
  • Close a dialog with Escape → focus returned to the element that opened it.
  • Confirm a deletion in a ConfirmDialog whose trigger button disappears → focus lands on an existing element rather than on <body> (this needs an onCloseAutoFocus from the caller).
  • Clear the filters with the button inside the empty state → focus returns to the search field (through inputRef) rather than being lost.
  • Open a dropdown menu and press an item's first letter → focus jumps to that item (Radix type-ahead).
  • Walk a SegmentedControl with the arrow keys → it switches; the whole group takes one tab stop.

Screen-reader announcements

  • Go to a page that is loading → announced exactly once, with the text from SkeletonRegion's label; the individual placeholders stay silent.
  • Mount two SkeletonRegions at once → a defect: two competing live regions.
  • Perform an action that raises a toast → the toast's text is announced.
  • The application's start screen → it is a <main>, it has an <h1> (hidden though it is), and the status is announced once.
  • An Alert banner with no AlertTitle → there is no aria-labelledby attribute in the DOM — there must be no reference to a nonexistent id.
  • An Alert banner with a title → the banner's name equals the title's text; the title is not an h* element.
  • Walk the page by headings → exactly one <h1>, the ranks in order, no skipped levels.
  • Walk the page by landmarks → one main; the named sidebar is complementary; not one unnamed region.
  • The kebab menu in a table row → the name is tied to the row rather than being “Actions”.

Localising the furniture

  • Open the admin UI in a non-English locale and open any dialog → the close cross is named in the session's language.
  • Mount a Dialog without a DesignSystemLabelsProvider → the cross is named Close — the default is preserved.
  • Pass a closeLabel at the call site → the prop wins, not the context.
  • Check the breadcrumbs' and the pagination's <nav> in a non-English locale → a known divergence: their aria-label stays English (see section 13).
  • The pagination's back/forward buttons with a label and an aria-label passed → both the visible caption and the name are in the session's language.

System settings

  • Turn on prefers-reduced-motion: reduce → placeholders do not pulse, a wizard step does not slide, dropdowns appear without animation; a spinner stops turning but keeps fading gently, so a pending request still looks pending; the content is visible throughout.
  • Turn on Windows high-contrast mode → an outline is visible on every focusable element; on scrollable regions it is inset; a selected panel item and a selected option get a border; disabled controls are grey.
  • Run axe in the dark theme → no contrast violations (checked only in platform-preferences.spec.ts).
  • A 320px window width → no horizontal document scroll; the skip link stays reachable; the panel becomes a sheet.
  • Narrow the window to 767px → the sidebar becomes a sheet immediately, with no frame of desktop layout.

Regressions after an upstream update

  • After a shadcn add, run npx nx test design-system → the suite stays green; a red localizable-copy means a lost localisation prop.
  • Look for @/ in the diff → not one should remain; otherwise the admin dev server will not come up.
  • Reconcile the exports with src/index.ts → no previously public symbol has vanished, and the new ones are added.
  • Look for animate-in / fade-in-0 / zoom-in-95 in the diff → if they arrived, they are dead classes: the plugin that generates them is not in the repository.
  • Look for role="status", <h5> and a vanished scope in the diff → every match is a rollback of a deliberate accessibility fix.

A separate boundary: what Radix does and what we do

Radix owns the behaviour — roles, focus traps, roving focus, Escape, portals, focus return, type-ahead. The library owns the styling, the product decisions (toast position, icon-tile size, the variant set) and the accessibility work Radix cannot do because it does not know the page's context: aria-haspopup="listbox" on the multi-select, aria-checked in place of the taken aria-selected, the table's conditional tab stop, inert on a collapsed panel, the group role instead of region. The reading rule: if an attribute is set explicitly in our file, there is a reason for it, and it is written in the comment beside it.
