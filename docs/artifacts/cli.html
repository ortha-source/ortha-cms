Ortha CLI Команда ortha — как установленное из npm приложение собирается, запускается и мигрирует

Всё, что нужно, чтобы эксплуатировать приложение OrthaCMS, раньше жило в @orthacms/nx — приватном пакете, который никогда не будет опубликован. Приложение, установленное из npm, физически не имело способа применить свои миграции. @orthacms/cli закрывает эту дыру и одновременно фиксирует правило: монорепозиторий и любое сгенерированное приложение мигрируют одной и той же реализацией. Две реализации «применить миграции в порядке плагинов» — это два шанса ошибиться в самой разрушительной операции системы.

01Бизнес-описание

OrthaCMS распространяется двумя способами. Внутри монорепозитория разработчик живёт в Nx: npx nx serve server, npx nx run server:db:migrate. Но конечный продукт — это приложение, которое человек создаёт командой npx create-ortha-app my-cms и которое состоит почти целиком из пакетов @orthacms/*, установленных из npm. У такого приложения нет Nx, нет исполнителей, нет графа проектов — и нужен способ его собрать, запустить и мигрировать.

Этот способ и есть ortha. Шесть команд, которые сгенерированное приложение оборачивает в свои npm run-скрипты, так что владелец приложения обычно даже не набирает слово ortha:

Зачем это отдельный пакет

  • Публикуемость. @orthacms/nx помечен private: true и не попадёт в npm никогда — он завязан на @nx/devkit, граф проектов и файл nx.json. Функция applyPluginMigrations была достижима только через исполнитель Nx, то есть только изнутри монорепозитория.
  • Одна реализация на два мира. Исполнители db-migrate, db-generate и db-studio в @orthacms/nx — тонкие адаптеры поверх функций, экспортируемых отсюда. Тот же цикл применения миграций, тот же отказ при пустом DATABASE_URL, то же предупреждение при небезопасной привязке Drizzle Studio.
  • Скучность как продуктовое качество. CLI не имеет собственного файла конфигурации и не принимает пути к папкам. Раскладка приложения (apps/server, apps/admin, dist/server) — это соглашение. Приложение, которое может положить сервер куда угодно, требует конфига, описывающего где, — а его CLI обязан прочитать раньше, чем сделает хоть что-то.

Кому это видно

Владелец сгенерированного приложения

Единственный настоящий пользователь. Видит команду через npm run-скрипты и README, сгенерированный вместе с приложением. Ошибки читает как предложения на человеческом языке, а не как стек-трейсы.

Разработчик OrthaCMS

Не вызывает ortha напрямую — у него Nx. Но исполняет ту же логику: три исполнителя Nx импортируют функции из этого пакета.

Развёртывание / CI

Прод — это ровно ortha build && ortha start, один процесс, отдающий и API, и админку с одного origin. Миграции — отдельный шаг ortha migrate перед стартом.

Чем CLI не является

  • Это не сборщик. Компиляция — это tsc самого приложения, сборка админки — его же vite. CLI только находит их и запускает с правильными аргументами.
  • Это не менеджер миграций. Генерацию делает drizzle-kit, применение — drizzle-orm. CLI владеет порядком и сообщениями об ошибках.
  • Это не сервер. ortha start запускает уже скомпилированный main.js обычным node и умирает вместе с ним.
  • Это не генератор проекта. Создание приложения — create-ortha-app. CLI появляется в приложении уже как devDependency.
  • Это не бандлер. Намеренно: см. инвариант И-11.
Ключевая идея

Сначала компилируем — потом читаем JavaScript. Чтобы применить миграции, надо знать список плагинов, а он объявлен в TypeScript-файле приложения. Монорепозиторий читает этот TypeScript «на лету» и платит за это jiti плюс трансформ-хуком swc, настроенным на legacy-декораторы. У сгенерированного приложения есть собственный шаг сборки — значит, оно может просто собраться и require-нуть JavaScript. Вся проблема трансформации перестаёт существовать на стороне потребителя.

Бинарь в манифесте указывает на TypeScript

В репозитории package.json объявляет "bin": { "ortha": "./src/cli.ts" } — потому что все пакеты рабочего пространства резолвятся из исходников. Публикуемый тарбол это исправляет: скрипт tools/release/pack.mjs переписывает манифест и ремапит bin ровно так же, как main (на ./dist/…js), а затем проверяет, что файл, названный в bin, действительно был собран. Следствие: внутри монорепозитория команда ortha как таковая неработоспособна — там её роль исполняет Nx.

Как пакет попадает к пользователю

Между тем, что лежит в репозитории, и тем, что человек ставит из npm, есть шаг, без которого ortha просто не запустился бы. Все пакеты рабочего пространства резолвятся из исходников: их exports указывают на ./src/index.ts, а tsconfig.base.json задаёт условие @orthacms/source. Потребитель так не умеет — у него нет ни этого условия, ни компилятора в рантайме.

  1. Сборка. Цель build компилирует пакет через tsconfig.lib.json, эмитируя JS и .d.ts.
  2. Стейджинг. Цель pack собирает публикуемый корень под dist/pack/packages/cli с переписанным манифестом: main, types, exports и bin переводятся с ./src/*.ts на ./dist/*.js, а зависимости на пакеты рабочего пространства ("*") пинятся выпускаемой версией.именно здесь bin.ortha перестаёт указывать на TypeScript
  3. Проверка. Стейджинг отказывается собирать тарбол, чей манифест называет файл, которого сборка не эмитировала, — и bin в этом списке самый важный: тарбол с несуществующим бинарём ставится успешно и падает при первом вызове команды.
  4. Публикация. Все пакеты выпускаются одним набором, в шаге. Публикации сериализованы с паузой и ретраями: npm ограничивает частоту записей, а один прогон выпускает десятки тарболов.

Отсюда практическое следствие для отладки: увидеть ortha «как у пользователя» можно только на собранном тарболе, а не в чекауте монорепозитория.

Кодов выхода ровно два

0 — успех, включая намеренное завершение по Ctrl+C для dev, start и studio. 1 — любой отказ: неизвестная команда (через process.exitCode = 1) или брошенное исключение, перехваченное в main().catch (через process.exit(1)). Код выхода дочернего процесса не пробрасывается наружу: tsc, упавший с кодом 2, превращается в Error("tsc exited with code 2") и наружу выходит единицей.

3.2 ortha dev

Три процесса, объединённые надзирателем superviseUntilExit. Порядок обязателен: сначала разовая сборка сервера, и только потом watch-процессы.

ortha dev
  1. buildCommand(root, { serverOnly: true })          # dist/ гарантированно существует
  2. node <tsc> -p apps/server/tsconfig.json --watch --preserveWatchOutput
  3. node --watch dist/server/src/main.js
  4. node <vite> --config apps/admin/vite.config.mts   # только если есть apps/admin/index.html
  • --preserveWatchOutput — иначе tsc очищает экран при каждой перекомпиляции и стирает логи Nest, живущие в том же терминале.
  • --watch передаётся как флаг node, а не как аргумент скрипта. Поэтому spawnNode принимает один массив argv целиком: разложенный на «скрипт + аргументы» флаг ушёл бы в скрипт, процесс запустился бы один раз и не следил бы ни за чем.
  • Завершение забирает всех. Без этого выход из dev оставляет осиротевший node --watch, всё ещё держащий порт API, — и следующий ortha dev падает на занятом порту, обвиняя процесс, которого пользователь не видит.
Почему разовая сборка обязательна

node --watch не умеет восстанавливаться из отсутствующей точки входа. Получив путь к ещё не существующему файлу, он остаётся живым, не следит ни за чем и никогда не загружается. Снаружи это выглядит не как «стартовали на секунду раньше времени», а как зависший сервер. Монорепозиторий решает ту же задачу отдельной целью dev:prebuild.

Vite вызывается с явным --config, потому что конфиг лежит внутри собираемого приложения: Vite ищет конфиг в рабочей директории и иначе собрал бы бандл с дефолтами из неверного корня — молча.

3.4 ortha start

Самая короткая команда в пакете: проверить, что dist/server/src/main.js существует, и запустить его. Никакой сборки — если файла нет, это отказ с текстом … does not exist — run `ortha build` first. Прод — это буквально ortha build && ortha start: один процесс, один origin, API и админка вместе.

3.5 ortha migrate

Единственная команда, чей вход — собственный TypeScript приложения: список плагинов и порядок, в котором он записан. Поэтому она собирает сервер сама, а не полагается на то, что кто-то собрал раньше.

Applying migrations: database → __drizzle_migrations_database
Applying migrations: identity → __drizzle_migrations_identity
Applying migrations: workspaces → __drizzle_migrations_workspaces

Migrations complete.
  • Плагины без дескриптора migrations отфильтровываются заранее. Если таких не осталось ни одного — печатается No plugin migrations to apply. и соединение не открывается вовсе.
  • Каждый плагин ведёт свою таблицу истории (migrations.table), поэтому плагины версионируются независимо. Плагин из исходников и плагин, установленный из npm, идут одним и тем же путём — каждый лишь объявляет свой migrations.dir().
  • Строка назначения не содержит учётных данных: describeTarget собирает host:port/database, а нераспарсенный URL честно называет себя (unparseable DATABASE_URL) вместо догадки.

3.6 ortha generate

Это только о схеме, которую определяет само приложение. Плагины везут свои миграции внутри тарболов, генерировать для них нечего. Отсюда и требование apps/server/drizzle.config.ts, которого у только что созданного приложения нет: первый запуск этой команды — это и есть момент, когда появляется папка migrations/.

ortha generate --name=add_content_types
  → node <drizzle-kit>/bin.cjs generate --config=apps/server/drizzle.config.ts --name=add_content_types
     cwd = <корень приложения>, stdio = inherit

Без --name флаг не добавляется вовсе — имя выбирает сам drizzle-kit. Имя передаётся одним литеральным элементом argv, без shell, поэтому --name="a b; rm -rf /" — это просто длинное имя миграции, а не команда.

3.7 ortha studio

Drizzle Studio читает подключение из dbCredentials конфига, но все закоммиченные drizzle-конфиги намеренно только про схему — секретов в них нет. Поэтому CLI синтезирует эфемерный конфиг во временной папке:

export default {
    dialect: 'postgresql',
    dbCredentials: { url: process.env.DATABASE_URL }
};

Конфиг ссылается на переменную, а не инлайнит URL; сам URL уходит в окружение дочернего процесса. Credential не оказывается на диске ни на мгновение, а временная папка удаляется в finally. Схема не нужна: Studio интроспектирует живую БД, связи выводятся из внешних ключей.

Опасность одного флага

Studio — это неаутентифицированный браузер с полным доступом на чтение и запись ко всему, на что смотрит DATABASE_URL. Привязанный к loopback, он локальный инструмент; привязанный к чему угодно ещё — консоль БД, выставленная в сеть, и drizzle-kit об этой разнице не говорит ничего. Поэтому --host, не входящий в {localhost, 127.0.0.1, ::1, [::1]}, печатает явное предупреждение с адресом до старта.

3.8 Разбор аргументов — что именно понимает CLI

Библиотеки разбора аргументов здесь нет. Есть две функции по пять строк, и их поведение стоит знать точно, потому что оно определяет все крайние случаи.

04Сценарии по шагам

4.1 Первый запуск установленного приложения

То, что человек делает сразу после npx create-ortha-app my-cms. Сгенерированный README сводит это к трём строкам; ниже — что происходит на самом деле.

  1. Поднимается Postgres. docker compose up -d — docker-compose.yml входит в шаблон приложения.CLI в этом не участвует
  2. npm run migrate → ortha migrate. Первым делом findProjectRoot() идёт вверх от текущей директории до ближайшего package.json. Затем loadEnv(root) читает .env — и это происходит до любой команды, чтобы и ortha.config.ts нашёл свои настройки, и дочерние процессы унаследовали переменные..env отсутствует — это нормально, а не предупреждение
  3. Собирается сервер. tsc -p apps/server/tsconfig.json → dist/server/. Компиляция инкрементальная и стоит около секунды.
  4. Читается скомпилированный хост. require('dist/server/ortha.config.js').default и require('dist/server/src/plugins.js').buildPlugins(config). Оба отсутствия и обе «неправильные формы» экспорта названы отдельными сообщениями.
  5. Проверяется URL базы. requireDatabaseUrl(config) отказывается работать с пустым значением — молчаливый переход на локальные дефолты запрещён.
  6. Применяются миграции всех плагинов в порядке, который вернул buildPlugins. Каждый — в свою таблицу истории.одно соединение pg.Pool на весь прогон, закрывается в finally
  7. npm run dev → ortha dev. API на :3000, админка на :4200.
  8. Первый вход. Учётка администратора провижинится при старте из ORTHA_ROOT_ADMIN_EMAIL / ORTHA_ROOT_ADMIN_PASSWORD — это делает плагин identity, а не CLI. Но переменные до него доносит именно loadEnv.

4.2 Применение миграций после обновления пакетов

  1. Версии @orthacms/* подняты в шаг. Пакеты выпускаются одним набором; частичное обновление способно оставить две копии общего пакета в node_modules.
  2. ortha migrate. Пересборка сервера здесь не формальность: устаревший dist/ молча мигрировал бы против предыдущей композиции — плагин, добавленный час назад, просто не получил бы своих таблиц, и никто бы об этом не сказал.
  3. Каждый плагин применяет только своё непримененное. Таблицы истории раздельные, поэтому новый плагин догоняет с нуля, а старые не трогаются.
  4. Если что-то падает — прогон останавливается. Плагины, уже прошедшие до сбойного, зафиксированы: отката нет, каждый плагин коммитит по ходу. Сообщение говорит, сколько из скольких успело.повторный запуск возобновляет прогон с упавшего плагина
Порядок плагинов — несущая конструкция

Таблицы одного плагина ссылаются внешними ключами на таблицы другого (memberships у workspaces ссылается на users у identity). Эту зависимость нигде не объявляют. Единственная гарантия — то, что цикл применяет плагины ровно в порядке списка хоста. Поэтому при ошибке «relation … does not exist» текст отказа прямо указывает на порядок в plugins.ts как на самую вероятную причину.

4.3 Генерация миграции для собственных типов контента

  1. Описать типы контента и собрать их в массив contentTypes.
  2. Передать их в ContentPlugin({ types, migrations }) в apps/server/src/plugins.ts. Дескриптор migrations — это и есть то, за что зацепится ortha migrate.
  3. Добавить apps/server/drizzle.config.ts с путями schema и out. Без него ortha generate отказывается работать и объясняет, чего не хватает.пути в конфиге резолвятся относительно cwd, а не относительно самого конфига — см. раздел 11
  4. ortha generate --name=add_content_types. drizzle-kit сравнивает схему со снапшотом в migrations/meta/ и пишет SQL. Базы данных не требуется — секретов в конфиге поэтому и нет.
  5. ortha migrate. Сгенерированный SQL применяется через тот же общий цикл, что и миграции всех плагинов.
  6. SQL коммитится в репозиторий приложения. Так же, как плагины коммитят свой.

4.4 Продакшн-сборка и старт

  1. ortha build. tsc компилирует сервер в dist/server, Vite собирает админку в dist/admin. Ничего не бандлится.
  2. ortha migrate в окне развёртывания. Отдельным шагом, до старта нового процесса, — миграции не привязаны к загрузке приложения.
  3. ortha start. Проверка наличия dist/server/src/main.js, затем node на нём. Процесс отдаёт API и, через staticDir конфига, собранную админку — один процесс, один origin.
  4. Переменные берутся из окружения, а не из файла. .env в образе не обязателен, а если он там оказался — уже экспортированные переменные он не перетрёт.это и есть нужный приоритет для развёртывания
  5. Остановка. SIGTERM/SIGINT для run() — успех, а не отказ: код выхода 0.
Почему сборка не бандлится

Каждый плагин Ortha находит свои миграции как join(__dirname, '../../../migrations') — путь, ведущий к корню его собственного пакета внутри node_modules. Бандлер, который сплющит эти файлы в один, ломает такой поиск. Монорепозиторий использует webpack только потому, что обязан заинлайнить пакеты, потребляемые из исходников; у установленного приложения такой проблемы нет, поэтому оно оставляет node_modules в покое.

05Устройство: компиляция → чтение конфига → действие

Три команды из шести (migrate, studio и косвенно dev) проходят один и тот же конвейер. Его стоит разобрать целиком, потому что именно он объясняет, почему этому пакету не нужна машинерия, без которой не обходится @orthacms/nx.

5.1 Шаг «найти корень»

findProjectRoot() идёт вверх от process.cwd() до ближайшего каталога с package.json. Не «доверять текущей директории», а именно подниматься: ortha migrate должен работать из подкаталога, потому что оттуда его и запускают. Всё остальное резолвится относительно найденного корня, поэтому относительные пути приложения (migrations/, dist/) означают одно и то же, где бы ни была набрана команда. Если package.json нет нигде вверх по дереву — отказ с текстом «run this inside an Ortha app».

5.2 Шаг «прочитать .env»

loadEnv(root) вызывается ровно один раз, в main(), до диспетчера команд. Реализация — три строки поверх process.loadEnvFile, но каждая нагружена решением:

  • Отсутствие файла — норма, а не повод предупреждать: развёртывание задаёт настоящие переменные окружения и такого файла не пишет вовсе.
  • Уже экспортированное не перетирается. Реальные окружения задают конфигурацию в окружении, и .env, случайно уехавший в образ, не должен её побеждать.
  • Нужен Node ≥ 20.12. Более старая версия получает отдельное сообщение с указанием своей process.version, а не TypeError: process.loadEnvFile is not a function.
  • Момент вызова важен. Значения должны попасть в process.env до того, как будут порождены node, vite и drizzle-kit, — они наследуют окружение родителя.

5.3 Шаг «скомпилировать»

Команда, которой нужен список плагинов, сначала собирает сервер и только потом читает результат. Это выглядит как лишний шаг, а на деле убирает целый класс проблем.

Аспект@orthacms/nx (монорепо)@orthacms/cli (установленное приложение)

Чем читаетсяjiti + трансформ-хук @swc/coreобычный createRequire()
Почему такNx работает против исходников; шага сборки перед целью нету приложения есть собственный шаг сборки, и он всё равно нужен
Цена2 дополнительные зависимости (jiti, @swc/core) и настройка декораторов~1 секунда инкрементальной компиляции

Почему монорепозиторию не хватает «просто jiti»: загрузка ortha.config.ts или buildPlugins втягивает весь граф плагинов — модули NestJS и их DTO, — а он использует legacy-декораторы (experimentalDecorators). Встроенный в jiti babel игнорирует tsconfig репозитория и по умолчанию берёт семантику декораторов stage-3: поле с definite assignment под декоратором (email!: string) получает инициализатор, и transform-typescript падает. Поэтому в @orthacms/nx живёт createTsJiti — jiti с трансформом на swc в режиме legacyDecorator + decoratorMetadata, чтобы тот же исходник читался так же, как его компилирует само приложение.

Что из этого следует

Три следствия, и все три — в пользу потребителя. Первое: jiti и @swc/core остаются зависимостями @orthacms/nx и никогда не попадают в дерево установленного приложения. Второе: исчезает целый класс расхождений «конфиг читается одним компилятором, а приложение собирается другим» — читается ровно тот JavaScript, который потом и запустится. Третье: устаревший dist/ перестаёт быть возможным источником тихой ошибки, потому что команда собирает его сама.

5.4 Шаг «прочитать конфиг» — почему require, а не await import()

Приложение компилируется в CommonJS. Импорт CommonJS-модуля из ESM кладёт весь module.exports в default пространства имён — то есть module.default оказывается { default: config }, а не самим конфигом. Первое же обращение к полю падает с Cannot read properties of undefined, и в сообщении нет ни слова про interop: пользователь видит ошибку, не называющую ничего. require возвращает module.exports как есть, и такой двусмысленности не возникает. createRequire строится от package.json приложения, чтобы резолвинг шёл из его дерева.

loadHost проверяет четыре вещи и на каждую даёт своё сообщение:

ПроверкаСообщение
Нет dist/server/ortha.config.js… does not exist — the app has not been built. Run `ortha build` first (`ortha migrate` does this for you).
Нет dist/server/src/plugins.jsто же сообщение с другим путём
У конфига нет default-экспорта… has no default export — ortha.config.ts must `export default` the app's config.
plugins.js не экспортирует функцию… does not export buildPlugins(config).

5.5 Шаг «действие» — где берутся бинари

resolveBin решает две задачи разом.

  • Резолвинг от приложения, а не от CLI. ortha установлен внутрь приложения, которое собирает, поэтому работать должны те typescript и vite, которые объявило приложение. Резолвинг из собственного дерева CLI означал бы компиляцию чужого приложения версией, которую npm случайно поднял рядом.
  • Через манифест, а не угадыванием пути. Глубокий спецификатор вида vite/bin/vite.js резолвится, только если пакет экспортирует этот подпуть, — а Vite его не экспортирует, и попытка падает с Package subpath './bin/vite.js' is not defined by "exports". package.json экспортируют оба, и его поле bin — авторитетный ответ: именно его линкует npm.

С drizzle-kit та же история решается иначе: его карта exports тоже блокирует прямой доступ к ./bin.cjs, поэтому CLI резолвит главный вход пакета и берёт соседний bin.cjs — join(dirname(require.resolve('drizzle-kit')), 'bin.cjs').

Раскладка приложения: девять путей, ноль настроек

LAYOUT в src/lib/project.ts — это весь «конфиг» CLI: apps/server/tsconfig.json, apps/admin/vite.config.mts, apps/admin/index.html, dist/server, dist/admin, dist/server/src/main.js, dist/server/ortha.config.js, dist/server/src/plugins.js, apps/server/drizzle.config.ts. Раскладка повторяет папку apps/ самого OrthaCMS (server, admin, server-e2e, admin-e2e), чтобы человек, читавший исходники Ortha, находил у себя ту же форму.

Скомпилированные пути следуют из того, что apps/server/tsconfig.json задаёт rootDir: "." и outDir: "../../dist/server": apps/server/ortha.config.ts → dist/server/ortha.config.js, apps/server/src/main.ts → dist/server/src/main.js. Изменить rootDir, не изменив LAYOUT, — и пути перестают резолвиться: ortha start тогда сообщит об отсутствующей точке входа, а не о неверной настройке.

5.6 Надзор за дочерними процессами

Три функции в src/lib/run.ts делят между собой всю работу с процессами, и разница между ними — это разница между «дождаться результата» и «жить, пока живут».

ФункцияКто используетСемантика
spawnNode(argv, root, env)всеПорождает node с унаследованным stdio и окружением. Принимает один массив argv целиком, включая флаги самого node

Две детали в superviseUntilExit несут вес. Флаг settling делает завершение однократным: без него выход трёх детей подряд запускал бы уборку трижды и пытался бы резолвить уже разрешённое обещание. Проверка exitCode === null && signalCode === null означает «сигнал шлём только тем, кто ещё жив» — тому, кто и вызвал уборку своим выходом, второй раз не достаётся.

Почему это вообще важно

Без уборки выход из ortha dev оставляет осиротевшие tsc --watch и node --watch, причём второй продолжает держать порт API. Следующий ortha dev падает на «порт занят», и виноват в этом процесс, которого пользователь не видит и не запускал в этой сессии. Отладка такого занимает несопоставимо больше времени, чем стоит сам обработчик.

07Диагностика и ошибки

Философия сообщений задана в одном месте — в перехватчике на дне src/cli.ts:

main().catch((error: unknown) => {
    // The message, not the stack. Every throw reaching here is a condition the
    // user can act on — an unbuilt app, a missing DATABASE_URL, a failed
    // migration naming the plugin — and a stack trace buries the sentence that
    // says which.
    console.error(error instanceof Error ? error.message : String(error));

});

Пустой DATABASE_URL — это не «ничего страшного»

new Pool({ connectionString: '' }) не падает: он проваливается в дефолты libpq — PGHOST/PGDATABASE, а при их отсутствии в localhost и пользователя ОС. Это измеряли в этом репозитории до появления проверки: при неустановленном DATABASE_URL миграция отрапортовала об успехе, создав всю схему в базе, которую никто не называл. Отсюда правило: отказ, а не догадка. Идентичная проверка стоит и в исполнителе db-migrate.

Ctrl+C — это успех

dev, start и studio задокументированно завершаются пользователем. run() распознаёт SIGINT/SIGTERM и резолвится, runDrizzleKitStudio распознаёт то же самое в исключении execFileSync. Причина в поведении людей, а не в аккуратности: сообщать о задокументированном выходе как о падении — значит приучать читать красное как шум.

7.2 Что осталось «сырым»

  • Ошибки соединения с БД приходят от pg без обработки. Строка о цели, напечатанная до подключения, компенсирует это лишь частично.
  • Вывод tsc и vite не фильтруется — stdio наследуется целиком. Это осознанно: их собственные сообщения полезнее любого пересказа.
  • cause у ошибки миграции не печатается. Верхнеуровневый перехватчик выводит только error.message, а исходное relation "users" does not exist лежит в cause и наружу не попадает — хотя текст отказа прямо предполагает, что читатель знает про missing relation.

08Инварианты

Утверждения, которые обязаны выполняться всегда. Это одновременно список для ревью и заготовка утверждений для тестов.

  • И-01Одна реализация на два мира. Монорепозиторий и любое сгенерированное приложение применяют миграции через одну и ту же applyPluginMigrations; исполнители Nx — тонкие адаптеры, а не вторая реализация.
  • И-02migrate и studio никогда не работают против устаревшего dist/: обе сначала собирают сервер, потом читают скомпилированный конфиг.
  • И-03Пустой или отсутствующий URL базы — отказ, а не переход на локальные дефолты libpq.
  • И-04Плагины мигрируют ровно в том порядке, в котором их вернул buildPlugins(). Порядок не переставляется, не сортируется и не выводится из зависимостей.
  • И-05Плагин без дескриптора migrations пропускается; если таких плагинов нет вовсе, соединение не открывается.
  • И-06Каждый плагин отслеживается в своей таблице истории (migrations.table), поэтому плагины версионируются независимо.
  • И-07Сбой миграции называет плагин, число уже зафиксированных, общее число и указывает на порядок как на вероятную причину; исходная ошибка сохраняется в cause; плагины после сбойного не пробуются.
  • И-08Пул соединений закрывается и при успехе, и при сбое (finally).
  • И-09Ни один лог не содержит учётных данных: цель описывается как host:port/database, а нераспарсенный URL — как (unparseable DATABASE_URL), а не как догадка.
  • И-10Credential для Drizzle Studio никогда не пишется на диск: эфемерный конфиг ссылается на process.env.DATABASE_URL, URL передаётся окружением дочернего процесса, временная папка удаляется в finally.
  • И-11Привязка Studio к чему-либо, кроме loopback, печатает предупреждение с адресом до старта.
  • И-12Сборка никогда не бандлится: миграции плагинов должны оставаться файлами внутри их пакетов в node_modules.
  • И-13tsc и vite резолвятся из node_modules приложения и только через поле bin его манифеста — не из дерева CLI и не угадыванием подпути.
  • И-14.env не перетирает уже экспортированные переменные окружения; отсутствие файла — не ошибка и не предупреждение.
  • И-15.env читается один раз, до диспетчера команд, чтобы значения унаследовали все порождённые процессы.
  • И-16dev заполняет dist/ разовой сборкой до запуска node --watch.
  • И-17Завершение dev — по выходу любого из детей или по сигналу — забирает с собой всех остальных, ровно один раз (флаг settling).
  • И-18Завершение по SIGINT/SIGTERM для dev, start и studio — успех, код выхода 0.
  • И-19Любое исключение, дошедшее до верха, печатается одной строкой сообщения без стек-трейса, и процесс выходит с кодом 1.
  • И-20generate никогда не подключается к базе: генерация только сравнивает схему со снапшотом, поэтому в drizzle-конфигах нет и не должно быть секретов.
  • И-21Имя миграции доходит до drizzle-kit одним литеральным элементом argv, без shell: враждебное имя — это просто странное имя.
  • И-22Раскладка приложения — соглашение (LAYOUT), а не конфигурация: CLI не читает никакого собственного файла настроек.
  • И-23Скомпилированный конфиг читается через require, а не await import(), — иначе module.default оказывается обёрткой, а не конфигом.
  • И-24findProjectRoot поднимается до ближайшего package.json, поэтому команда работает из любого подкаталога приложения.

09Чек-лист тестирования

Формулировки — «действие → ожидаемый результат», чтобы их можно было брать в тест-кейс без переписывания. Существующее автоматическое покрытие: 31 юнит-тест в трёх файлах рядом с кодом (migrate.spec.ts — 13, studio.spec.ts — 12, generate.spec.ts — 6), мокающих на границе процесса (node:child_process, pg), поэтому пакет тестируется без базы данных. Запуск: npx nx test @orthacms/cli. Не покрыто юнит-тестами вовсе: cli.ts, project.ts, env.ts, run.ts и все шесть команд — их проверяют вручную по пунктам ниже.

Разбор аргументов и справка

  • ortha build --help → печатает справку и не собирает ничего, код 0.

  • ortha buld → Unknown command "buld"., справка, код 1.

  • ortha generate --name --other → имя не подхватывается (значение начинается с -), drizzle-kit выбирает имя сам.

  • Плагин переставлен так, что его FK ссылается вперёд → отказ называет плагин, «applied N of M», говорит про отсутствие отката и указывает на порядок в plugins.ts.

Интеграция с монорепозиторием

  • npx nx run server:db:migrate и ortha migrate на одинаковом списке плагинов → одинаковый порядок, одинаковые таблицы истории, одинаковый текст отказа.
  • npx nx run <plugin>:db:generate и ortha generate → оба вызывают drizzle-kit одним и тем же способом, различаясь только cwd и путём к конфигу.
  • Собранный тарбол пакета → bin.ortha указывает на существующий файл в dist/, а не на src/cli.ts.
Как устроены существующие юнит-тесты пакета

Спецификации лежат рядом с кодом (src/lib/*.spec.ts) и мокают строго на границе процесса: node:child_process для generate и studio, pg плюс drizzle-orm для migrate. Поэтому npx nx test @orthacms/cli не требует ни базы данных, ни собранного приложения.

Что именно закреплено тестами. Для migrate: точный порядок применения плагинов (это и есть вся гарантия, потому что зависимость между таблицами нигде не объявлена), передача каждому плагину его собственной папки и таблицы истории, отсутствие соединения при пустом списке, текст отказа с именами и счётчиками, сохранение исходной ошибки в cause, непопытка применить плагины после сбойного, закрытие пула и при успехе, и при сбое, отсутствие пароля в описании цели. Для studio: эфемерный конфиг не содержит ни пароля, ни имени базы, URL уходит окружением, временная папка удаляется, дефолты host/port не подставляются искусственно. Для generate: вызов идёт через process.execPath из корня проекта, --name отсутствует, когда его не дали, враждебное имя остаётся одним элементом argv, а ненулевой код превращается в сообщение с проектом и кодом вместо копии argv.

Чего тесты не покрывают: разбор argv и диспетчер (cli.ts), поиск корня и загрузку скомпилированного хоста (project.ts), чтение .env (env.ts), резолвинг бинарей и надзор за процессами (run.ts), а также все шесть адаптеров-команд. Это ровно та часть, которую проверяет ручной чек-лист выше.

Паспорт пакета packages/cli. Каркас тот же, что в артефакте по identity: бизнес-описание → состав → каталог команд → сценарии → устройство → конфигурация → диагностика → инварианты → чек-лист → границы → расхождения. Разделы, которых у пакета нет (модель данных, HTTP API, экраны админки, права), выпали — у CLI нет ни таблиц, ни маршрутов, ни UI.

Источник — исходный код пакета: src/cli.ts, src/index.ts, шесть команд в src/lib/commands/, шесть модулей ядра в src/lib/ и три файла спецификаций. Сверено с исполнителями @orthacms/nx (db-migrate, db-generate, db-studio, lib/jiti.ts), с шаблоном create-ortha-app (package.json.tmpl, env.tmpl, README.md.tmpl, apps/server/{tsconfig.json,src/plugins.ts}) и с типом ServerPlugin из @orthacms/bootstrap-server. Файлы AGENTS.md использованы как каркас, но каждое утверждение сверено с реализацией — расхождения вынесены в раздел 11.
