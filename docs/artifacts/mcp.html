Пакет · packages/mcp/server

MCP Парадная дверь для внешнего ИИ-агента: один маршрут, один протокол, ноль собственных инструментов

MCP — это протокольный адаптер. Он не знает ничего про контент, медиа и локали: он принимает JSON-RPC на единственном маршруте POST /api/v1/mcp, проверяет bearer-токен, выбирает воркспейс и передаёт вызов в чужой реестр инструментов. Внешний агент — Claude Desktop, Cursor, самописный клиент на SDK — получает ровно тот же CRUD над контентом, что и публичный HTTP API, с той же аутентификацией и тем же решением о правах. Плагин не владеет ни одной таблицей и ни одним инструментом.

01Бизнес-описание

У CMS уже есть полноценный внешний API — /api/v1/* с bearer-токенами, которые выписываются на странице «API-токены». Всё, что скрипт может сделать с этой CMS снаружи, он может сделать там. Проблема не в возможностях, а в способе знакомства.

Какую задачу решает

  • Агент не читает OpenAPI. MCP-клиент узнаёт, что умеет сервер, спросив его — он вызывает tools/list и получает список инструментов с описаниями и JSON-схемами аргументов. Он не скачивает спецификацию и не синтезирует по ней REST-клиент. Поэтому реальный вопрос не «должен ли агент уметь править контент» (он уже умеет — с токеном и HTTP-библиотекой), а «получит ли он описанную, отфильтрованную по правам поверхность, или каждому оператору придётся писать свой мост».
  • Правила безопасности не в контроллерах. Только опубликованное по умолчанию, мягко удалённые строки невидимы, невыданный тип контента неотличим от несуществующего, связи не пересекают локали, валидация откладывается до публикации, нумерация ревизий под advisory-блокировкой, транзакционный outbox. Всё это живёт в PublicEntriesQuery, PublicEntryWritesService и EntryWriterService под ними. Вторая точка входа, переписавшая бы хоть что-то из этого, была бы не второй точкой входа, а второй, тихо расходящейся моделью безопасности. Поэтому каждый обработчик инструмента дёргает те же объекты, что и HTTP-контроллер.
  • Один каталог на два потребителя. Тот же реестр инструментов в процессе читает копайлот. Инструмент, добавленный для одного, автоматически доступен другому — если он сам не сказал обратного полем surfaces.
  • Отзыв в один клик. Никакого второго хранилища учётных данных: тот же ApiTokenService.verify, та же таблица токенов. Оператор отозвал токен — доступ по MCP умер в ту же секунду.

Кому это видно

Внешний агент

Подключается к POST /api/v1/mcp с Authorization: Bearer. Видит только те инструменты, которые область его токена позволяет вызвать, и получает ошибки в виде, который модель может прочитать и исправить.

Оператор развёртывания

Решает, включать ли дверь вообще (MCP_ENABLED), и выписывает узкие токены: read для агента-читателя, full для агента-автора, с явным списком воркспейсов.

Разработчик плагина

Добавляет инструмент у себя, не трогая этот пакет: ToolProvider в своём модуле плюс ответ на вопрос «для кого это?». MCP про его плагин не узнаёт ничего.

Чем MCP-плагин не является

Границы здесь важнее возможностей — почти всё, чего от него ждут, находится в соседних пакетах:

  • Это не реестр инструментов. ToolDefinition, ToolContext, ToolProvider, ToolRegistry, createToolContext и toToolError живут в @orthacms/tools-server. MCP импортирует ToolsModule, а не предоставляет его — иначе развёртывание, которому нужен только копайлот, тянуло бы через этот бочонок @modelcontextprotocol/sdk, то есть зависимость от протокола, на котором оно не говорит.
  • Это не инструменты. Контентные инструменты контрибьютит content/server, медийные — media/server, локали — i18n/server, аудитории — segments/server. Именно эта инверсия позволяет обработчику звать PublicEntriesQuery напрямую: этот объект внутренний для контента и наружу не экспортируется.
  • Это не MCP-клиент. Копайлот отдельно планирует ходить в MCP-серверы оператора (docs/design/copilot.md §4). Это противоположное направление и другая фича. Здесь CMS является MCP-сервером.
  • Это не второй API. Ни одного нового правила видимости, ни одного нового формата токена, ни одной новой таблицы. Только другой способ спросить то же самое.
Ключевая идея архитектуры

Nest охраняет маршруты, а MCP — это один маршрут, несущий десятки операций. Поэтому три охранника публичного API здесь переписаны как три не-Nest-механизма: ApiTokenGuard → бирная половина McpAuthService.authenticate, ApiTokenWorkspaceGuard → его же воркспейсная половина, @RequirePermissions(...) → поле requires у инструмента, которое центрально проверяет ToolRegistry.call до диспетчеризации. Ни одного нового правила — только другая точка приложения тех же правил.

Почему низкоуровневый Server, а не McpServer

Хелпер SDK McpServer принимает Zod-схемы, а здесь каждая схема — это сгенерированный на рантайме JSON Schema: типы контента заданы в коде и лежат в реестре, их форма вычисляется на старте. Превращать сгенерированный JSON Schema в Zod, чтобы SDK превратил его обратно, — это потеря информации ради ничего.

03Области токена и права

У MCP нет своей модели прав. Актор здесь всегда токен (kind: 'token'), его права — это результат scopePermissions(token.scope) из identity-server, а решение «можно ли» принимает ToolRegistry.call, сверяя ToolDefinition.requires с этим набором. Ролей RBAC здесь не бывает: роль минтившего человека никогда не спрашивают.

Права media:update, media:delete, activity:read, users:*, alarms:*, copilot:*, tokens:*, workspaces:* и views:share не выдаёт ни одна область токена. Инструмент, который их требует, физически не может быть виден агенту — но правильный способ это выразить всё равно surfaces: ['copilot'], чтобы причина была объявлена, а не следовала из случайного совпадения таблицы областей.

Как право доходит до вызова

  1. Область → набор прав. scopePermissions(scope) — чистая функция без Nest и Drizzle, единственный источник истины «что может эта область».packages/identity/server/src/lib/api-tokens/domain/api-token-scope.ts
  2. Набор прав → контекст. createToolContext(actor, workspaceId) даёт context.can(permission) — простую проверку членства в Set. Функция никогда не выводит права сама: их разрешает тот, кто аутентифицировал вызывающего.
  3. Контекст → фильтр списка. registry.visibleTo(context, 'mcp') прячет то, что актор всё равно не смог бы вызвать. Это удобство, а не граница.
  4. Контекст → граница. registry.call(name, args, context, 'mcp') перепроверяет requires перед диспетчеризацией. Клиент волен назвать инструмент, которого ему не показывали, — и получит отказ.это и есть граница безопасности; ADR-0006 §5
  5. Внутри обработчика — более тонкие решения. context.can(...) используется там, где правило касается аргумента, а не операции: assertDraftVisibility требует content:update, чтобы разрешить status: 'draft'|'any'.
Почему видимость черновиков пробуется правом content:update

content:read есть у обеих областей, поэтому оно ничего не различает. Различает content:update. Логика: токен, который может читать черновики, — это токен, который мог бы их и опубликовать. А расширение вообще существует потому, что иначе пишущий агент создал бы черновик и больше никогда его не увидел: чтение по умолчанию отдаёт только опубликованное, и записывающий API стал бы write-only.

Валидация каталога на старте

Реестр реализует OnApplicationBootstrap и проверяет собранный каталог один раз, на старте, выбрасывая все проблемы разом. Отказ здесь прерывает app.init(), то есть процесс вообще не начинает обслуживать. Проверяется:

  • Уникальность имени — два плагина, заявившие одно имя, сделали бы выбор реализации зависящим от порядка регистрации.
  • Формат имени — ^[a-z][a-z0-9]*(?:_[a-z0-9]+)*$. Имя с пробелом регистрируется и вызывается только присылкой того же пробела; Content_List рядом с content_list — два живых инструмента в одну букву разницы.
  • Непустой surfaces — пустой массив означает «не предложен никому», то есть мёртвый инструмент.
  • Существование прав — каждое значение requires должно быть в PERMISSION_KEYS. Строковый литерал, разошедшийся со списком, оставил бы инструмент невызываемым для всех и молча.
  • Форма inputSchema — обязан быть объектом типа object.

04Каталог инструментов, доступных по MCP

Двадцать три инструмента, ни одного из них этот пакет не писал. Шестнадцать даёт content/server, три — media/server, один — i18n/server, три — segments/server. Токен области read видит тринадцать из них, токен full — все двадцать три.

Инструменты обобщённые, с typeName в аргументах, а не сгенерированные под каждый тип контента. Причина в цене: MCP-клиент загружает схемы всех инструментов в контекст модели при подключении, поэтому article_create, author_create, tag_create… масштабировали бы стоимость каждого разговора числом коллекций — и не могли бы быть фиксированным набором, потому что видимые типы зависят от выданных воркспейсу грантов. Форму типа модель узнаёт по требованию через content_type_get.

4.5 Ресурсы MCP

Кроме инструментов эндпоинт отдаёт ресурсы — документы, которые клиент может втянуть в контекст, не тратя вызова инструмента. Сегодня их ровно один вид: схема типа контента по URI ortha://content-type/<имя>, mimeType: application/json.

  • Список обрезан грантами воркспейса — теми же, что content_types_list.
  • Чтение проходит через тот же грант-шлюз (resolveGrantedType), поэтому невыданный тип даёт 404 здесь ровно так же, как при вызове инструмента: чтение ресурса не должно быть обходом.
  • Права ресурса объявляются полем requires и проверяются до того, как у провайдера спросят байты. Ни один поставляемый сегодня ресурс его не объявляет: они уже сужены грантами воркспейса.
  • valuesSchema не перечисляет required у publishable-типов — на них поля обязательны к публикации, и объявление их обязательными сказало бы модели, что она не может сохранить неполный черновик, который сохранить как раз можно.

Поле actor.userId в контексте несёт минтившего человека, но только для атрибуции — на решение о правах оно не влияет никогда.

06Жизненный цикл вызова

Жизненного цикла «сессии» здесь нет — есть жизненный цикл одного обмена. Транспорт и протокольный сервер создаются на запрос и умирают вместе с ним.

HTTP-запрос → аутентификация → разрешение воркспейса → проверка глагола → транспорт + Server → JSON-RPC диспетчер → ответ → close: teardown

Почему именно такой порядок

  1. Сначала «включено ли». Контроллер регистрируется только при enabled, но внутри стоит ещё одна проверка с 503 — на случай будущего изменения проводки. Выключенный плагин отдаёт 404, потому что маршрут просто не смонтирован.e2e: «unmounts the endpoint when disabled»
  2. Аутентификация — до того, как что-то попадёт в протокольный слой. Неаутентифицированный вызывающий не должен уметь двигать конечный автомат JSON-RPC вообще — даже до initialize. И ответ здесь обычный HTTP-статус: 401 — это то, что говорит MCP-клиенту «твои учётные данные не те», тогда как JSON-RPC-ошибка читалась бы как «соединение работает и вернуло сбой».
  3. Разрешение воркспейса — в той же операции. Один вызов McpAuthService.authenticate(headers, workspaceQuery) делает обе половины и сразу собирает ToolContext: дальше по коду не остаётся места, где контекст ещё «недоделан».
  4. Проверка глагола — после аутентификации. Иначе GET без токена сообщал бы 405, то есть подтверждал бы существование эндпоинта. Неаутентифицированный GET — это 401, и ничего больше.e2e: «401s an unauthenticated GET, before the verb is considered»
  5. Транспорт создаётся без генератора идентификаторов сессии (sessionIdGenerator: undefined) и с enableJsonResponse: true. Второе означает «отвечай одним JSON-телом, а не открывай SSE-поток»: здесь ничего не стримит — вызов инструмента возвращается один раз, — а обычный JSON лучше всех переваривают и клиенты, и прокси.
  6. Протокольный сервер строится вокруг уже разрешённого контекста. Это и есть причина «на запрос, а не один долгоживущий»: tools/list обязан показать токену read не тот набор, что токену full, а ресурсы обрезаются грантами воркспейса. Вшивание контекста в замыкания обработчиков при построении делает это невозможным сломать — нет общего сервера, чьи обработчики должны помнить переспросить, кто спрашивает.
  7. Уборка вешается на response.on('close'). Без этой строки каждый запрос протекал бы протокольным сервером и его замыканиями. Закрывается и то, и другое, как бы обмен ни закончился.
  8. Тело не перечитывается. Хостовый express-мидлварь уже распарсил JSON, поэтому оно передаётся третьим аргументом в transport.handleRequest — иначе транспорт попытался бы прочитать уже потреблённый поток.
  9. Аварийный выход. Если что-то бросило: заголовки ещё не отправлены — пишется 500 с JSON-RPC-конвертом -32603; уже отправлены — соединение просто закрывается. Обрезанный ответ диагностируем, а зависание — нет.

Три потолка одного обмена

Ни один из них не может дать реестр инструментов: он транспортно-нейтрален, а у обмена «запрос-ответ» есть обязательства, которых нет у внутрипроцессного цикла копайлота.

ОграничениеЗначениеГде живётЧто происходит сверху
Тело запроса 1 МБ (MAX_REQUEST_BODY) хостовый bodyLimit в createServer 413 обычным Nest-телом. Это выше слоя JSON-RPC, поэтому и не JSON-RPC-кадр
Один tools/call 30 с (MCP_CALL_TIMEOUT_MS) build-mcp-server.ts, callWithinDeadline результат с isError: true, status: 504, code: timeout

Дедлайн бросает работу, а не отменяет её

Обработчику передаётся сигнал, который срывается и по истечении срока, и когда вызывающий отвалился (extra.signal от SDK). Но инструмент, который сигнал игнорирует, досчитает до конца — просто его ответ никто не прочитает. Гарантия здесь — ограничение ожидания вызывающего, а не прекращение работы: прекратить работу этот слой не может.

Отдельная тонкость: проигравший гонку промис всё равно доводится до состояния (pending.catch(() => undefined)). Без этого обработчик, упавший после дедлайна, стал бы необработанным reject-ом и уронил бы процесс — ровно тот отказ, ради сдерживания которого таймаут и введён.

Почему потолок результата — не паранойя

Результат сериализуется трижды: как красиво напечатанный текстовый блок, который читает модель; как structuredContent для клиентов, которые его парсят; и ещё раз — транспортом, когда он собирает весь ответ. Пиковая память, таким образом, кратна полезной нагрузке, причём на каждый параллельный запрос, а в каталоге инструментов ничто не ограничивает, сколько обработчик вправе вернуть. Отказ полезнее самих данных: результат, не влезший сюда, не влезет и в контекстное окно модели, а сообщение прямо говорит ей сузить запрос.

07Сценарии — как это работает по шагам

7.1 Подключение клиента и знакомство

MCP-клиент не читает документацию — он спрашивает сервер. Три первых обмена — это и есть всё «знакомство».

  1. Оператор минтит токен. Страница «API-токены» в админке: read — агенту-читателю, full — агенту-автору, плюс явный список воркспейсов. Секрет показывается один раз. Область токена — это то, что решит, какие инструменты агент вообще увидит.никакой отдельной «MCP-регистрации» не существует
  2. Клиент настраивается на URL. Конфиг MCP-клиента URL-образный, поэтому воркспейс можно назвать прямо в адресе: https://cms.example.com/api/v1/mcp?workspaceId=<uuid>. Клиенту, который умеет только stdio, мост даёт mcp-remote — одна строка в его конфиге и ничего, что нам пришлось бы поддерживать.
  3. initialize. Клиент присылает свою версию протокола, свои возможности и имя. Сервер отвечает serverInfo (name и version из конфигурации плагина — это то, что клиент показывает в списке коннекторов) и capabilities, где объявлены два раздела: tools и resources.строго после аутентификации: даже initialize неаутентифицированному недоступен
  4. notifications/initialized. Уведомление, у него нет id, отвечать нечему — эндпоинт возвращает 202 с пустым телом.
  5. tools/list. Здесь и происходит главное: registry.visibleTo(context, 'mcp') — сначала сужение по поверхности, потом по правам актора. Каждый инструмент отдаётся с name, title, description, inputSchema и annotations (title, readOnlyHint, destructiveHint). Токен read никогда не узнаёт, что существует content_create, — это лучше, чем узнать об этом через отказ, и экономит модели ходы.
  6. resources/list (необязательно). Схемы типов контента, обрезанные грантами воркспейса, чтобы модель могла втянуть форму типа в контекст, не тратя вызова.
Почему аннотации, а не «просто описания»

readOnlyHint и destructiveHint — это подсказки клиенту, по которым он решает, что можно автоодобрить, а на что спросить человека. Они не полномочия: полномочия — это requires. Поэтому в контракте инструмента живут два словаря: readOnly/destructive отвечают клиенту «что безопасно», а effect (read | propose | apply) отвечает серверу «возвращённое значение — это изменение или результат». propose-инструмент не «только для чтения» в смысле MCP, а прямо пишущий инструмент не propose, как бы он ни был разрушителен.

7.2 Аутентификация: как разбирается bearer

  1. Заголовок режется по пробелам. header.trim().split(/\s+/). Схема сравнивается без учёта регистра с bearer.
  2. После схемы должно остаться ровно одно значение. Обрамляющие и повторяющиеся пробелы вокруг схемы терпятся — RFC 9110 их допускает, и клиенты их шлют. Пробел внутри значения — нет: в учётных данных пробелов не бывает, и склеивание кусков обратно изобрело бы токен, которого вызывающий не присылал, а потом доложило бы об этом изобретении как «Invalid API token», что читается как «не тот секрет», а не «кривой заголовок».заметное расхождение с REST-охранником — см. раздел 15
  3. ApiTokenService.verify(secret). Неизвестный, отозванный и просроченный токен дают один плоский 401: эндпоинт не должен быть инструментом для перебора существующих токенов.
  4. Собирается актор. kind: 'token', id — идентификатор самого токена (не пользователя: токен действует от себя, поэтому его отзыв всегда достаточен), displayName — имя токена, grantedPermissions — new Set(scopePermissions(token.scope)), userId — минтивший человек только для атрибуции.
  5. Кука не рассматривается вообще. Кука едет с запросом сама — именно это делает записи под кукой уязвимыми к CSRF. Bearer так не ездит никогда. Принять здесь и то, и другое означало бы вернуть CSRF на эндпоинт, вся суть которого — дать агенту писать контент.

7.3 Разрешение воркспейса

Правило дословно совпадает с ApiTokenWorkspaceGuard, переписанным для не-Nest-точки вызова.

  1. Источник — X-Workspace-Id, иначе ?workspaceId=. Заголовок побеждает, если есть оба. Второе написание существует потому, что конфиги MCP-клиентов URL-образные и несколько клиентов делают собственные заголовки неудобными или невозможными, — а мультиворкспейсный токен обязан как-то назвать один.оба проходят через одну и ту же проверку принадлежности; query — это написание того же правила, а не обход
  2. Не назван, токен покрывает один воркспейс → он и берётся. Обычный случай не требует настройки вообще.
  3. Не назван, токен покрывает несколько → 400 с числом воркспейсов и подсказкой, чем назвать. Тихий выбор одного всплыл бы как «почему тут пусто?» — отказ куда лучше.
  4. Назван, но кривой формат → 400 «Malformed x-workspace-id».
  5. Назван, но не в корзине токена → 403. «Не в корзине» и «такого воркспейса нет» — один и тот же ответ, чтобы токеном нельзя было прощупать, какие идентификаторы воркспейсов существуют.
  6. Назван дважды → 400. Повторённый ?workspaceId=a&workspaceId=b (и написание ?workspaceId[]=) парсится express-ом в массив; трактовка массива как «не назван» приводила к тому, что одноворкспейсный токен тихо срабатывал против своего воркспейса, хотя вызывающий назвал два чужих. У запроса, называющего больше одного воркспейса, нет ответа, который не был бы догадкой. Повторённый X-Workspace-Id Node склеивает в одно значение через запятую — оно не проходит формат и даёт тот же 400.

Что произошло между этими двумя блоками, по шагам

  1. Контроллер уже собрал контекст (шаги 7.2–7.3) и построил протокольный сервер вокруг него.
  2. SDK нашёл обработчик CallToolRequestSchema и передал ему params плюс extra с сигналом отмены.
  3. callWithinDeadline заводит свой AbortController. К нему ретранслируется клиентский сигнал (это единственный сигнал отмены, который у этой поверхности есть) и вешается таймер. Флаг expired ставится до вызова abort(), чтобы слушатель, срабатывающий следом, мог отличить дедлайн от отвалившегося клиента.
  4. registry.call('content_create', args, {…context, signal}, 'mcp'). Внутри реестра, строго в этом порядке:
    a) сужение по поверхности — forSurface('mcp'). Инструмент не той поверхности даёт «Unknown tool», а не предложение, которое нечем принять;
    b) неизвестное имя → 404, и это намеренно другой ответ, чем отказ по правам: набор инструментов не секрет (он одинаков для любого актора данной области и задокументирован), так что смешивать их значило бы сделать законную проблему с правами недиагностируемой. Секретны данные — вот там невыданный тип 404-ит ровно как несуществующий;
    c) проверка requires — та самая граница;
    d) подстановка args ?? {} — в реестре, а не на каждом краю: оба поставляемых потребителя раньше компенсировали это у себя;
    e) валидация аргументов по собственному inputSchema инструмента. Авторизация раньше валидации: вызывающий, которому нельзя, не узнаёт ничего об аргументах, и ответ на неавторизованный вызов один и тот же, что бы он ни прислал;
    f) штамп поверхности — {...context, surface}, ставится здесь, а не на краю: так поверхность, которую видит обработчик, по построению та, против которой инструмент авторизовали. packages/tools/server/src/lib/tool-registry.ts
  5. Обработчик content_create делегирует. resolveGrantedType — грант-шлюз; validateToolInput(PublicSaveEntryDto, input) — настоящий HTTP-DTO с теми же опциями, что у глобального ValidationPipe хоста (whitelist + forbidNonWhitelisted); this.writes.create(...) — тот же PublicEntryWritesService, что зовёт контроллер. Ни одного правила видимости здесь не переписано.
  6. Результат измеряется до отдачи. JSON.stringify(result, null, 2), Buffer.byteLength, сравнение с maxResultBytes. Измерение до того, как хоть одна копия попадёт в транспорт, потому что на выходе ответ стоит примерно втрое дороже.
  7. Таймер снимается в finally, слушатель клиентского сигнала — тоже. Иначе долгий процесс копил бы слушателей на чужом сигнале.

7.5 Как уходит отказ — и почему двумя разными путями

Отказ tools/call уезжает результатом с isError. Отказ resources/* уезжает ошибкой JSON-RPC. Это асимметрия протокола, а не случайность, и её стоит знать до того, как «чинить» любую из половин.

Инструмент → isError

Отказ инструмента — это исход, который должна прочитать модель и на него отреагировать («title must be at most 200 characters»). Поэтому MCP моделирует его как успешный вызов, несущий isError. Ошибка протокола прервала бы вызов у клиента; результат отдаётся модели, и та чинит свой следующий вызов. Отказ по правам приходит сюда же — модель, узнавшая, что у неё нет content:publish, перестаёт пробовать, вместо того чтобы повторять вслепую.

Ресурс → ошибка JSON-RPC

У чтения ресурса нет модели в контуре: клиент попросил байты по URI и либо получил их, либо нет. Поэтому MCP моделирует отказ как ошибку протокола, а -32002 зарезервирован под «такого URI нет». Плоский ToolError едет в поле data, так что клиент читает те же status/code/issues, что и от инструмента.

Общее у обоих путей — toToolError. Он превращает брошенное в { status, code, message, issues }:

  • HttpException — это ошибка вызывающего. Статус, короткий машинный код (bad_request, unauthorized, forbidden, not_found, conflict, validation_failed, иначе error) и сообщение как есть. Поле issues из 422-го контента переносится дословно — именно это делает ошибку валидации самоисправляемой.
  • Всё остальное — баг, а не ошибка вызывающего. Логируется со стеком для оператора и отдаётся голым 500 / internal_error с текстом «см. логи сервера»: сообщение могло бы назвать таблицу, колонку или строку подключения, а результат инструмента читает сторонняя модель.
// tools/call, который не прошёл по правам — HTTP 200, JSON-RPC result
{

  "id": 12,
  "result": {
    "isError": true,
    "content": [{
      "type": "text",
      "text": "{\n  \"status\": 403,\n  \"code\": \"forbidden\",\n  \"message\": \"\\\"content_create\\\" requires content:create, which this token does not hold.\"\n}"

// resources/read по невыданному типу — HTTP 200, JSON-RPC error

Отказ и отсутствие делят -32002 намеренно. Для данных ответ единообразен: невыданный тип контента читается ровно как несуществующий. При этом data.code по-прежнему различает их для клиента, которому это важно.

7.6 Полный цикл авторской работы агента

Тот самый круг, который e2e прогоняет целиком — «creates a draft, reads it back, publishes, and deletes it». Он показывает, почему рабочий процесс должен быть написан в описаниях инструментов: модели больше неоткуда о нём узнать.

  1. content_types_list. Точка входа любого авторского разговора, а не любезность: модель не может напечатать values, которых не видела.
  2. content_type_get. Схема полей + valuesSchema. Именно поэтому пишущие инструменты могут принимать открытый объект и оставаться пригодными к использованию.
  3. content_create → запись ложится status: "draft". На publishable-типе всегда: у каждого создания есть просматриваемое состояние. Обязательные поля обязательны к публикации, а не к созданию, поэтому черновик может быть неполным.
  4. content_list без аргументов не находит его — total: 0. Это не баг, это заголовочное правило публичного API.описание content_create прямо предупреждает: читай обратно со status: "any"
  5. content_get со status: "any" находит. Расширение открыто правом content:update — иначе записывающий API был бы write-only.
  6. content_update сливает. Присланное { number: 7 } не стирает text; явный null очищает поле. На publishable-типе обновление возвращает опубликованную запись в черновик, пока её опубликованная версия остаётся в эфире.
  7. content_publish перепроверяет и выводит в эфир. Черновик, не прошедший правила типа, падает здесь — с поимённо названными полями в issues. Это самая полезная ошибка, какую может получить модель.
  8. content_unpublish снимает с эфира, content_delete удаляет. После удаления content_get со status: "any" отвечает code: "not_found" — той же формой, что и невыданный тип.

7.7 Пакетные вызовы и уведомления

  1. Батч. Клиент вправе прислать массив кадров; ответ — массив результатов, по одному на запрос, с сохранением id. Это и есть причина, по которой эндпоинт — один маршрут, а не маршрут на инструмент: одна проверка bearer, много операций.
  2. Уведомление (кадр без id) — 202 и пустое тело.
  3. Неизвестный метод — -32601 (Method not found) с HTTP 200, а не 500. Клиент, пробующий prompts/list, получает внятный ответ: этот сервер объявляет только tools и resources.
  4. Испорченный кадр — пустое тело, кадр без method, кадр, объявляющий JSON-RPC 1.0 — отвечается 400 с отрицательным JSON-RPC-кодом, а не 500.
  5. Заголовок Accept. Streamable HTTP требует, чтобы POST принимал оба типа — application/json и text/event-stream. Клиент, приславший только первый, получает 406, и в сообщении назван недостающий тип: это самая частая ошибка первого подключения.
  6. Mcp-Session-Id игнорируется. Клиент, считающий, что у него есть сессия, обслуживается нормально: сессий нет, валидировать нечего.

7.8 Что происходит, когда выключатель выключен

  1. MCP_ENABLED не равен true → config.enabled === false → McpModule.forRoot возвращает controllers: [].
  2. Маршрут не смонтирован → POST /api/v1/mcp отвечает 404, даже с валидным токеном.
  3. Но ToolsModule всё равно импортируется и реэкспортируется. Реестр связывается и наполняется, потому что внутрипроцессный цикл копайлота потребляет тот же реестр и не имеет никакого отношения к тому, выставлена ли внешняя дверь.
  4. И плагину-контрибьютору не приходится об этом думать. Он регистрирует свои инструменты безусловно, а решает, кто до них дотянется, композиционный корень.
  5. Зеркальное правило у копайлота. COPILOT_ENABLED применяется точно так же — каждый выключатель убирает свою поверхность, и ни один не уменьшает общий каталог. E2E-набор tools/tool-registry.spec.ts проверяет оба направления: при снятом MCP копайлот видит полный каталог, при снятом копайлоте полный каталог видит MCP.
Почему выключено по умолчанию

Включение отдаёт любому держателю токена области full возможность гнать CRUD над контентом из внешнего агента. Это решение, которое оператор принимает осознанно, а не наследует, обновив версию. Токены, области и корзины воркспейсов при этом не меняются — выключатель управляет только тем, смонтирована ли дверь.

Почему 405 отвечает контроллер, а не транспорт

GET в спецификации — это поток, инициируемый сервером, DELETE — снос сессии. Ни того, ни другого здесь нет, и это ровно тот случай, под который спецификация резервирует 405. Транспорт SDK нарочно не спрашивают: получив GET в stateless-режиме, он открывает отдельный SSE-поток и держит его вечно — на этом эндпоинте никто никогда не отправляет сообщение по инициативе сервера, — так что клиент, который пробует GET (а так делают несколько), висел бы на соединении, которое ничего не понесёт, удерживая сокет, транспорт и протокольный сервер на каждую попытку. @All() заводит эти глаголы в тот же контроллер, чтобы ответ пришёл из протокольного слоя, а не был родовым 404 Nest-а, который клиент интерпретировать не может.

Требуется положительное целое: ноль провалил бы каждый вызов, а Number(env) || default превратил бы опечатку в тихий дефолт

—MAX_REQUEST_BODY'1mb' Не поле MCP: хостовый bodyLimit, применяемый ко всему приложению. Загрузки им не затронуты — они multipart и ограничены отдельно через maxUploadBytes медиаплагина

Что проверяется при построении плагина

  • config.name непусто → иначе исключение с текстом «it is the server identity MCP clients display». Кривая идентичность всплыла бы как испорченный ответ initialize, где диагностировать её несравнимо дороже.
  • config.version непусто → то же.
  • callTimeoutMs — положительное целое → Number.isInteger(v) && v > 0. Потолок, равный 0, отрицательный или NaN, хуже отсутствия потолка.
  • maxResultBytes — положительное целое → то же.

Юнит-тест mcp-plugin.spec.ts отдельно фиксирует, что плагин строится и в выключенном состоянии: реестр всё равно связывается.

11Безопасность: что и почему сделано именно так

11.1 Те же учётные данные, те же правила

MCP — это вторая парадная дверь в тот же дом, а не вторая модель безопасности. Он берёт bearer-токены, которые страница «API-токены» уже минтит, проверяет их тем же ApiTokenService.verify и выводит права тем же scopePermissions. Следствия прагматичные: отзыв токена закрывает MCP в ту же секунду, и нет второго хранилища учётных данных, которое пришлось бы аудировать.

Охранник на /api/v1/*Его двойник здесьЧто доказывает эквивалентность
ApiTokenGuardMcpAuthService.authenticateТот же verify, тот же плоский 401, тот же scopePermissions
ApiTokenWorkspaceGuardresolveWorkspaceПравило переписано дословно: 400 на кривой формат, 403 на «не в корзине», авто-выбор при одноворкспейсном токене, 400 при мультиворкспейсном без имени
@RequirePermissions(...)ToolDefinition.requires + ToolRegistry.callПроверка до диспетчеризации; обработчик собственный шлюз не проверяет никогда
DraftVisibilityGuardassertDraftVisibilityТот же пробник content:update, то же поведение на нераспознанном значении (оставить DTO, чтобы 400 сообщил правильную проблему)

11.2 Кука не принимается

Ровно как на /api/v1. Кука едет с запросом сама — именно эта амбиентность делает записи под кукой уязвимыми к CSRF; bearer так не ездит никогда. Принять оба варианта на эндпоинте, чья цель — дать агенту писать контент, значило бы вернуть CSRF ни за что. E2E проверяет это отдельным случаем: «does not accept a session cookie in place of a token».

11.3 Никакого сигнала для перебора

Что унифицировано

  • Неизвестный / отозванный / просроченный токен → один 401.
  • Воркспейс вне корзины / несуществующий воркспейс → один 403.
  • Невыданный тип контента / несуществующий тип → один 404, и в инструментах, и в ресурсах.
  • Черновик / удалённая запись / чужой воркспейс / неизвестный id → одно «не найдено».

Что намеренно различено

  • Неизвестный инструмент (404) и отказ по правам (403) — разные ответы. Набор инструментов не секрет: он одинаков для любого актора данной области и задокументирован, а список выводится из собственной области вызывающего. Смешивание сделало бы законную проблему с правами недиагностируемой и заставило бы модель жечь ходы вслепую.
  • Правило «единый ответ» продолжает действовать для данных, и это ровно та граница, где оно проходит.

11.4 Два поля, которые критичны для безопасности

  • requires
    Аналог @RequirePermissions(...). Ошибиться в нём — это привилегированный баг, которого не поймает ни один тайпчекер. Обработчик не имеет права проверять собственный шлюз: тогда новый инструмент сможет забыть это сделать. Реестр валидирует на старте, что каждое значение действительно существует в PERMISSION_KEYS, — сырой литерал, разошедшийся со списком, оставил бы инструмент невызываемым молча.
  • surfaces
    Столь же критично. Propose-инструмент, забывший это поле, стал бы вызываемым MCP-клиентом, которому нечем принять получившееся предложение, — а media_propose_file ещё и пишет, и прав токена full на него хватило бы. Останавливает только surfaces. Защитой служат кросс-поверхностные e2e-случаи, и новый инструмент обязан обзавестись своим.

11.5 Инъекция промпта

Риск, который здесь нельзя устранить — только ограничить

Агент, читающий запись CMS, в которой лежат инструкции, может им последовать. Ничто в этом пакете этому помешать не может. Что он ограничивает — это радиус поражения: область токена, его корзина воркспейсов и гранты контента. Отсюда практические выводы: минтить узкие токены; помнить, что выключатель по умолчанию выключен именно для того, чтобы оператор согласился на этот риск явно; и не выдавать full там, где хватит read.

11.6 Что нельзя достать по MCP вообще

  • Справочник аудиторий. Переименование тегов одной аудитории меняет видимость каждой записи, её называющей, установочно-широко. Это администрирование словаря — оно остаётся на экране под сессией.
  • Журнал действий, участники, находки проверок. Требуют прав, которых не выдаёт ни одна область токена; вдобавок помечены surfaces: ['copilot'], чтобы причина была объявлена, а не следовала из совпадения.
  • Черновики токену без права записи. Расширение status открыто правом content:update.
  • Загрузка файла. Инструмента для этого нет; media:create у токена full ведёт на REST-маршрут POST /api/v1/media/assets, а не сюда.
  • Переименование и удаление чужих ассетов. media:update и media:delete не выдаёт ни одна область: прикрепить ассет к записи — это авторство контента, а переименовать чужой файл в библиотеке — администрирование медиа.

11.7 Устойчивость

  • Каждый запрос убирает за собой. response.on('close') закрывает и транспорт, и протокольный сервер, как бы обмен ни кончился. Без этой строки каждый запрос протекал бы сервером и замыканиями обработчиков.
  • Поздний reject не роняет процесс. pending.catch(() => undefined) у проигравшего гонку промиса — иначе обработчик, упавший после дедлайна, стал бы необработанным reject-ом.
  • Отвал клиента — не сбой инструмента. Класс CallAbandoned отделяет «дедлайн» и «клиент ушёл» от настоящих ошибок, чтобы ни то, ни другое не дошло до toToolError и не залоглось как непойманная ошибка со стеком. Отвал клиента — рутина, а дедлайн — собственное решение этого файла; ни то, ни другое не баг инструмента.
  • Ответ всегда завершается. Если транспорт уже начал писать, ставить статус негде — соединение просто закрывается: обрезанный ответ диагностируем, а зависание нет.
  • Кривая проводка не доживает до первого вызывающего. Валидация каталога на onApplicationBootstrap прерывает app.init(): раньше дубль имени клал обе поверхности во время работы, тогда как старт рапортовал успех.

12Инварианты

Утверждения, которые обязаны оставаться истинными. Нарушение любого — это либо дыра, либо расхождение двух поверхностей.

  • И-01
    Аутентификация предшествует протоколу. Неаутентифицированный вызывающий не может двинуть конечный автомат JSON-RPC вообще, включая initialize. Ответ — обычный HTTP 401, а не JSON-RPC-ошибка.
  • И-02
    Проверка глагола следует за аутентификацией. Неаутентифицированный GET — это 401, а не 405: ответ про глагол недостижим без учётных данных.
  • И-03
    Сессионная кука не является учётными данными этого эндпоинта — никогда, ни в каком режиме.
  • И-04
    Неизвестный, отозванный и просроченный токен неразличимы — один плоский 401 без подсказки, что именно из трёх.
  • И-05
    Значение bearer не содержит внутренних пробелов. Куски после схемы не склеиваются: изобретённый токен доложился бы как «неверный секрет» вместо «кривой заголовок».
  • И-06
    Воркспейс всегда разрешён до диспетчеризации и всегда принадлежит корзине токена. Заголовок побеждает query; обе записи проходят одну проверку. Более одного названного воркспейса — 400, а не тихий выбор.
  • И-07
    Права актора выводятся только из области токена. Роль минтившего человека не спрашивают никогда — отзыва токена всегда достаточно, кто бы его ни выписал.
  • И-08
    ToolRegistry.call — единственная граница авторизации. visibleTo только прячет; клиент волен назвать не показанное имя. Обработчик собственный шлюз не проверяет.
  • И-09
    Сужение по поверхности применяется и в списке, и при вызове. Инструмент ['copilot'] не виден и не вызываем здесь, каким бы широким ни был токен.
  • И-10
    Авторизация предшествует валидации аргументов. Тот, кому нельзя, не узнаёт ничего об аргументах, и ответ одинаков, что бы он ни прислал.
  • И-11
    Поверхность в контексте штампует реестр, а не вызывающий. Значит, обработчик по построению видит ту поверхность, против которой инструмент авторизовали. Использовать её можно только для подачи, никогда для полномочий.
  • И-12
    Отказ tools/call — это результат с isError, а не ошибка JSON-RPC. Отказ resources/* — наоборот. Обе половины проходят через toToolError, поэтому плоская форма ошибки одинакова.
  • И-13
    Неожиданное исключение непрозрачно на обоих путях — 500 / internal_error и текст «см. логи». Сырое сообщение драйвера на провод не попадает никогда.
  • И-14
    Результат отдаётся обоими написаниями — текстовым блоком и structuredContent. Не-объект заворачивается в { value }, а не выбрасывается.
  • И-15
    Каждый обмен ограничен тремя потолками: тело запроса, время одного вызова, размер одного результата. Превышение времени и размера возвращается в виде, который модель может прочитать (504/timeout, 413/result_too_large).
  • И-16
    Дедлайн ограничивает ожидание вызывающего, а не работу. Инструмент, игнорирующий сигнал, досчитывает до конца. Ответ вызывающему приходит в любом случае.
  • И-17
    Транспорт и протокольный сервер живут ровно один обмен и закрываются на close. Идентификаторов сессии не выдаётся и не проверяется; присланный Mcp-Session-Id игнорируется.
  • И-18
    Список инструментов — функция вызывающего. Токен read и токен full получают разные списки от одного и того же развёртывания.
  • И-19
    Ни одно правило контента здесь не переписано. Обработчики зовут те же resolveGrantedType, PublicEntriesQuery, PublicEntryWritesService, что и HTTP-контроллеры, и валидируют настоящими DTO с опциями хостового ValidationPipe.
  • И-20
    Выключатель убирает только контроллер. Реестр связывается и наполняется при MCP_ENABLED=false, потому что тот же реестр потребляет копайлот. Симметрично COPILOT_ENABLED.
  • И-21
    Плагин не владеет ни одной таблицей и ни одной миграцией. Дескриптор миграций не объявляется.
  • И-22
    Кривой каталог не доживает до первого вызывающего. Дубль имени, невалидное имя, пустой surfaces, несуществующее право, кривой inputSchema — всё это прерывает app.init(), а все проблемы сообщаются разом.
  • И-23
    Чтение ресурса не является обходом грант-шлюза. Невыданный тип 404-ит при resources/read ровно так же, как при вызове инструмента; requires ресурса проверяется до того, как у провайдера спросят байты.
  • И-24
    Чтение по умолчанию отдаёт только опубликованное. Расширить до черновиков может лишь актор с content:update.

13Чек-лист тестирования

Формат «действие → чего ждём». Большая часть уже закрыта автотестами: юнит-набор пакета (mcp-auth.service.spec.ts, build-mcp-server.spec.ts, mcp-plugin.spec.ts) и wire-level e2e (apps/server-e2e/src/server/mcp/mcp.spec.ts, apps/server-e2e/src/server/tools/tool-registry.spec.ts). E2E ходит сырым JSON-RPC через supertest, а не через клиентский SDK: формат на проводе — это и есть контракт внешних клиентов, поэтому проверять надо байты.

13.1 Аутентификация

  • POST без заголовка Authorization → 401. Ни одного JSON-RPC-кадра в ответе.
  • POST с неизвестным bearer → 401 «Invalid API token», без намёка, чем именно токен плох.
  • Отозвать токен, повторить тот же запрос → 401 немедленно, без перезапуска сервера и без ожидания истечения.
  • Просроченный токен → тот же 401, неотличимый от неизвестного и отозванного.
  • Прислать сессионную куку вместо токена → 401. Кука на этом эндпоинте не учётные данные ни при каких условиях.
  • Схема в другом регистре: bearer, BEARER → принимается: сравнение регистронезависимое.
  • Лишние пробелы вокруг схемы: " Bearer   <token> " → принимается — RFC 9110 это допускает, и клиенты так шлют.
  • Пробел внутри значения: "Bearer <token> extra" → 401. Куски не склеиваются: склейка изобрела бы токен, которого не присылали.
  • Схема не bearer (Basic, Token) → 401.
  • Права актора при токене, выписанном администратором → равны scopePermissions(scope), а не правам роли администратора. Проверять именно на токене read, выписанном админом.

13.2 Разрешение воркспейса

  • Одноворкспейсный токен без заголовка и без query → работает; воркспейс подставлен сам. Обычный случай не требует настройки.
  • Мультиворкспейсный токен без указания → 400 с числом воркспейсов и подсказкой про заголовок и query. Не тихий выбор первого.
  • X-Workspace-Id с воркспейсом из корзины → работает; данные именно этого воркспейса.
  • ?workspaceId= в URL эндпоинта → работает так же, как заголовок: это второе написание того же правила.
  • Заголовок и query названы оба и различаются → побеждает заголовок; query не влияет и не даёт ошибки.
  • Воркспейс вне корзины токена → 403, идентичный ответу на несуществующий воркспейс: перебрать идентификаторы токеном нельзя.
  • Кривой идентификатор в заголовке или query → 400 «Malformed x-workspace-id».
  • Повторённый ?workspaceId=a&workspaceId=b → 400 «more than one workspace». Регрессия, которую легко вернуть: раньше массив читался как «не назван», и одноворкспейсный токен тихо срабатывал против своего воркспейса, хотя названы были два чужих.
  • Повторённый заголовок X-Workspace-Id → 400: Node склеивает повторы через запятую, и склейка не проходит формат.
  • Запись в воркспейс вне корзины → отказ; проверять именно пишущим инструментом, а не только чтением.

13.3 Транспорт и протокол

  • GET /api/v1/mcp с валидным токеном → 405, заголовок Allow: POST, в сообщении слово «stateless». Ответ обязан прийти сразу — если запрос висит, значит транспорт всё-таки открыл вечный SSE-поток.
  • DELETE /api/v1/mcp → 405: сессии, которую можно закрыть, не существует.
  • GET без токена → 401, а не 405: ответ про глагол недостижим без учётных данных.
  • Accept: application/json без text/event-stream → 406, и в сообщении назван недостающий тип. Это самая частая ошибка первого подключения.
  • Заголовок Mcp-Session-Id от клиента, который считает, что у него есть сессия → 200, заголовок проигнорирован.
  • Уведомление (кадр без id), например notifications/initialized → 202 и пустое тело.
  • Батч из двух кадров (tools/list + resources/list) → массив из двух результатов, идентификаторы сохранены, у обоих есть result.
  • Неизвестный метод prompts/list → 200 с ошибкой -32601, а не 500.
  • Пустое тело / кадр без method / "jsonrpc": "1.0" → 400 с отрицательным JSON-RPC-кодом, а не 500.
  • Тело больше 1 МБ → 413 обычным Nest-телом — это выше слоя JSON-RPC, поэтому кадра здесь нет.
  • initialize → serverInfo ровно из конфигурации плагина; capabilities содержит tools и resources и не содержит prompts.
  • Сотня последовательных запросов → RSS не растёт линейно: транспорт и протокольный сервер закрываются на close. Регрессия здесь — утечка на каждый запрос.

13.4 Видимость и авторизация инструментов

  • tools/list токеном read → 13 инструментов; есть content_list и content_types_list, нет content_create, content_update, content_publish, content_delete.
  • tools/list токеном full → 23 инструмента, включая все шестнадцать контентных и content_access_set.
  • Аннотации → content_list.readOnlyHint === true; content_delete.readOnlyHint === false и destructiveHint === true.
  • У каждого инструмента в списке → inputSchema.type === 'object' и непустое description. Описание — единственная документация, которую получает модель.
  • Токен read вызывает content_create по имени → isError: true, 403/forbidden. Это и есть граница: список только прячет, а клиент волен назвать не показанное имя.
  • Токен read вызывает каждый пишущий инструмент по очереди → все до одного отказ. Проверять именно перебором, а не выборочно: requires задаётся у каждого инструмента отдельно.
  • Токен read просит status: "draft" или "any" → 403: расширение видимости открыто правом content:update.
  • Неизвестное имя инструмента → 404/not_found, а не тот же ответ, что при отказе по правам. Различие намеренное.
  • Отказ по правам при заведомо кривых аргументах → приходит 403, а не 422: авторизация раньше валидации.

13.5 Изоляция поверхностей

  • tools/list токеном full → в списке нет ни одного admin_*, ни одного *_propose_*, ни i18n_translations_get, ни activity_recent, ни workspace_members_list, ни admin_alarms_findings.
  • Вызвать admin_content_search по имени → isError: true. Сужение по поверхности применяется и при вызове, не только в списке.
  • Вызвать media_propose_file токеном full → isError: true. Самый острый случай: прав у токена хватает (media:create входит в full), останавливает только surfaces.
  • Общие инструменты видны токену read → в списке есть i18n_locales_list, media_assets_search, media_folders_list, media_asset_read.
  • Общий инструмент не только виден, но и вызываем → i18n_locales_list отрабатывает и возвращает locales. Инструмент, который вылистывается, но 404-ит при вызове, означал бы, что список и вызов разошлись.
  • media_assets_search с MCP → downloadPath имеет вид /api/v1/media/assets/<id>/raw, и этот путь реально тянется тем же bearer-ом (200). Админский путь здесь был бы гарантированным 401.
  • Добавили новый инструмент в любом плагине → в PR есть либо surfaces с комментарием, в чём напряжение, либо отсутствие поля с комментарием, что напряжения нет. Отсутствие обоих — незакрытый вопрос.

13.6 Ошибки и потолки

  • Аргумент, не проходящий inputSchema → isError, 422/validation_failed с поимённо названным полем в issues.
  • Пропущен обязательный аргумент → то же; вызов не доходит до обработчика.
  • Неизвестный аргумент вместо игнорирования → ошибка. Тихо выброшенный опечатанный аргумент даёт правдоподобно выглядящий неверный ответ — самый трудно замечаемый отказ.
  • Не-uuid в folderId / assetId → 400/bad_request, а не непрозрачный 500.
  • Инструмент бросил HttpException → isError со статусом, коротким кодом и сообщением как есть; issues перенесены дословно.
  • Инструмент бросил не-HttpException → голый 500/internal_error и текст «см. логи сервера». В ответе нет имени таблицы, колонки или строки подключения. В логе — стек.
  • MCP_CALL_TIMEOUT_MS=1, любой вызов → isError, 504/timeout, в сообщении названы имя инструмента и величина дедлайна. Вызывающий получает ответ всегда.
  • Обработчик, падающий уже после дедлайна → процесс жив. Регрессия здесь — необработанный reject, роняющий сервер, то есть ровно тот отказ, ради которого таймаут и введён.
  • Клиент разорвал соединение на середине вызова → в логах нет записи «unhandled error in a tool handler» со стеком: отвал клиента — рутина, а не баг инструмента.
  • MCP_MAX_RESULT_BYTES=200, content_types_list → isError, 413/result_too_large, оба размера названы, и structuredContent в ответе отсутствует.
  • Результат чуть ниже потолка → проходит без изменений; отсечка не «примерно».
  • Значение-не-объект от инструмента → попадает в structuredContent как { value: … }, а не теряется.

13.7 Контент: полный цикл и правила видимости

  • content_types_list → только типы, выданные этому воркспейсу. Невыданный тип в списке — утечка модели данных.
  • content_type_get невыданного типа → 404, идентичный ответу на несуществующий тип.
  • content_list без status → только опубликованное. Черновик, созданный секунду назад тем же токеном, не виден и не считается в total.
  • content_list в чужом воркспейсе → записи соседнего воркспейса не попадают в выдачу.
  • content_create на publishable-типе → status: "draft". Не «опубликовано», не «зависит от типа».
  • content_get со status: "any" токеном full → черновик читается — иначе записывающий API был бы write-only.
  • content_update с одним полем → остальные поля живы; явный null очищает поле, а пропущенное — нет.
  • content_publish невалидного черновика → isError с issues, где названы конкретные поля. Это самая полезная ошибка, какую может получить модель.
  • content_delete, затем content_get со status: "any" → not_found — той же формы, что и невыданный тип.
  • content_delete на локализованном типе → удалена ровно одна строка; остальные переводы живы.
  • content_bulk_save со смешанным пакетом → вызов успешен, у каждого элемента свой вердикт на своей позиции, отказ несёт ту причину, с которой упал бы одиночный вызов.
  • content_bulk_publish, где часть черновиков невалидна → валидные опубликованы, остальные в skipped с причиной already-published / blocked / not-found. Частично пропущенный пакет — нормальный исход.
  • content_relations → показываются и считаются только опубликованные цели.
  • Ограничение pageSize → совпадает с ограничением одноимённого HTTP-маршрута: правило написано один раз, в DTO.

13.8 Ресурсы и аудитории

  • resources/list → только схемы выданных воркспейсу типов.
  • resources/read выданного типа → JSON со схемой полей и valuesSchema.
  • resources/read невыданного типа → JSON-RPC-ошибка -32002, и в data лежит { code: "not_found" }. Не результат с isError: у ресурса другая асимметрия.
  • content_access_get сразу после content_access_set → читается то, что только что записали. Регрессия здесь — чтение через публичное чтение записи, при котором агент теряет из виду запись, которую сам же и ограничил.
  • Пустой allow → означает «видят ВСЕ», а не «никто». Проверять именно на пустом списке.
  • Токеном read вызвать content_access_set → 403: нужен segments:manage, а его несёт только full.
  • Попытаться создать/переименовать/удалить аудиторию по MCP → инструмента не существует. Справочник аудиторий не выставлен ни одной токен-аутентифицированной поверхностью.

13.9 Выключатель и старт

  • MCP_ENABLED=false, POST с валидным токеном → 404: маршрут не смонтирован.
  • MCP_ENABLED=false, копайлот включён → копайлот видит полный каталог инструментов. Выключатель убирает свою поверхность, а не общий каталог.
  • COPILOT_ENABLED=false, MCP включён → зеркально: MCP видит полный каталог, а маршрутов копайлота нет вовсе.
  • Пустое config.name или config.version → исключение при построении плагина, а не испорченный initialize через неделю.
  • callTimeoutMs или maxResultBytes = 0, отрицательное, NaN, дробное → исключение при построении. Нулевой таймаут провалил бы каждый вызов.
  • Два провайдера заявили одно имя инструмента → процесс не стартует: app.init() прерывается. Не «первый вызов падает».
  • requires с несуществующим ключом права → процесс не стартует. Регрессия здесь — инструмент, невидимый и невызываемый для всех и молча.
  • Имя инструмента не в snake_case → процесс не стартует. Проверять и на пробел по краям, и на CamelCase.
  • Пустой массив surfaces: [] → процесс не стартует: инструмент не предложен никому.
  • Две проблемы каталога сразу → в сообщении об ошибке названы обе, а не первая попавшаяся.
  • Развёртывание без MCP-плагина вообще → приложение стартует; плагины-контрибьюторы просто остаются незарегистрированными (@Optional()).

Чего ещё нет

  • Атрибуции записи человеку. Ревизия агентского авторства несёт null в поле пользователя. Пробел унаследован от публичного write-API и заслуживает собственной колонки — ADR-0006 отмечает это как то, что стоит починить до массового агентского авторства.
  • Раздела prompts. Сервер объявляет только tools и resources; предзаготовленных промптов MCP-клиенту здесь не предлагают.
  • Подписок на изменения ресурсов (resources/subscribe) и вообще любых сообщений по инициативе сервера — прямое следствие statelessness.
  • Загрузки файлов инструментом. Токен full держит media:create, но ведёт оно на REST-маршрут POST /api/v1/media/assets.
  • Своей телеметрии. Счётчиков вызовов, длительностей и частоты отказов этот пакет не ведёт; логируется только непойманное исключение обмена.
  • Отдельного ограничения частоты. ThrottlerGuard на этом маршруте не стоит: ограничителем служит область токена и три потолка обмена.
  • Экрана-выключателя. MCP_ENABLED — переменная окружения; это решение развёртывания, а не редакции.
